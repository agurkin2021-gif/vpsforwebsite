تعتمد طريقة استضافة موقع على VPS على التطبيق. يحتاج الموقع الثابت إلى خادم ويب وDNS، بينما يحتاج ووردبريس أو نظام PHP آخر أيضًا إلى PHP وقاعدة بيانات. يعمل تطبيق Node.js أو Python عادة خلف وكيل عكسي. يمكنك إعداد هذه المكونات يدويًا على VPS نظيف أو إدارتها من المتصفح باستخدام لوحة تحكم.

يشرح هذا الدليل مسار **الانتقال من VPS جديد إلى موقع يعمل فعليًا**. إذا كنت تنقل موقع إنتاج قائمًا ببيانات حية، فاستخدم [نقل موقع إلى VPS]({{< relref "website-migration-to-vps.md" >}}) لخطوات التحويل والتراجع.

لقرار الشراء الأوسع، راجع [استضافة VPS للمواقع]({{< relref "_index.md" >}}).

## خطوات النشر المختصرة {#quick-deployment-sequence}

يتبع النشر الأول الموثوق هذا الترتيب:

1. **اختر VPS وحدد موارده.**
2. **اختر الإدارة اليدوية أو بلوحة أو بخدمة إدارة.**
3. **جهّز نظامًا نظيفًا أو صورة جاهزة حالية بلوحة لدى المزود.**
4. **أمّن الوصول الأول وأنشئ مسار إدارة دون تسجيل الدخول كـ root.**
5. **حدّث نظام التشغيل.**
6. **ثبّت مكونات الويب التي يحتاجها التطبيق فقط.**
7. **أعد الموقع أو التطبيق قبل تحويل DNS العام كلما أمكن.**
8. **انشر الملفات والشيفرة واضبط الملكية والأسرار والوصول إلى قاعدة البيانات.**
9. **قيّد الجدار الناري مع إبقاء SSH ووصول HTTP/HTTPS المطلوب يعمل.**
10. **اختبر الخادم الجديد قبل تحويل DNS العام.**
11. **وجّه النطاق إلى VPS.**
12. **فعّل HTTPS بعد وصول اسم المضيف إلى الخادم.**
13. **تحقق من cron والعمليات الخلفية والسجلات والنسخ الاحتياطي والمراقبة الخارجية.**
14. **أعد التشغيل مرة وتأكد من عودة كل الخدمات المطلوبة تلقائيًا.**
15. **بعد ذلك فقط اعتبر النشر جاهزًا للإنتاج.**

لا تثبّت PHP أو MySQL أو البريد أو لوحة لمجرد ورودها في دليل عام. ثبّت المكونات التي يحتاجها موقعك فعلًا.

## اختر الإدارة اليدوية أو اللوحة أو الخدمة المُدارة {#choose-manual-panel-or-managed}

توجد ثلاثة مسارات تشغيل مستقلة.

### إدارة يدوية دون لوحة تحكم {#manual--no-control-panel}

اختر Linux VPS نظيفًا وأدر البيئة عبر SSH.

يناسبك ذلك عندما:

- تفهم البيئة البرمجية للتطبيق؛
- تريد أقل عدد من الخدمات؛
- تحتاج إلى إعدادات مخصصة لـ Nginx/Apache أو بيئة التشغيل؛
- تستخدم سكربتات أو Git أو البنية التحتية كتعليمات برمجية؛
- لا تحتاج إلى واجهة حسابات استضافة تقليدية.

هذه الصفحة تجمع موضوع **VPS دون لوحة تحكم** المقترح سابقًا. لا ننشئ عنوانًا آخر ينافسها على الغرض نفسه.

### لوحة تحكم {#control-panel}

استخدم لوحة عندما تخفف إدارة المواقع والنطاقات وPHP وقواعد البيانات والبريد والمستخدمين من المتصفح عملًا متكررًا فعليًا.

راجع [VPS مع لوحة تحكم]({{< relref "vps-with-control-panel.md" >}}). وإذا اخترت FASTPANEL بالفعل، فاستخدم [استضافة VPS مع FASTPANEL]({{< relref "fastpanel-vps-hosting.md" >}}).

### خدمة إدارة {#managed-administration}

اللوحة والإدارة مختلفتان. إذا لم يكن لديك مسؤول عن التحديثات والأمان والنسخ الاحتياطي والمراقبة والحوادث، فاحسم ذلك قبل الإطلاق.

راجع [VPS المدار مقابل غير المدار]({{< relref "managed-vs-unmanaged-vps.md" >}}).

## المتطلبات المسبقة {#prerequisites}

قبل العمل على الخادم، جهّز:

- VPS بموارد مناسبة للأحمال؛
- عنوان IP للخادم؛
- بيانات دخول SSH أو مفتاح الوصول؛
- مسارًا يعمل لوحدة تحكم المزود أو VNC أو الاستعادة؛
- نطاقًا مسجلًا وصلاحية إدارة DNS؛
- ملفات الموقع أو مستودع التطبيق؛
- إصدارات بيئات التشغيل المطلوبة؛
- متطلبات قاعدة البيانات؛

## اختر نظام التشغيل {#choose-the-operating-system}

لخادم مواقع بإدارة يدوية، اختر نظامًا:

- يدعمه التطبيق وبيئة التشغيل؛
- ما زال يتلقى الصيانة؛
- يفهمه مسؤول الأنظمة؛
- تتوافر له حزم ووثائق حديثة لبيئة الويب؛
- يوافق متطلبات اللوحة إذا استخدمتها لاحقًا.

لا تختر النظام لمجرد أنه الأحدث. توافق التطبيق وخبرة المسؤول أهم.

لأمثلة Linux حديثة وبسيطة، يعد Ubuntu 24.04 LTS أو Debian 12 أساسًا مناسبًا للوثائق. إذا حدد مطور تطبيقك توزيعة مدعومة أخرى، فاتبع متطلباته.

## أمّن أول وصول عبر SSH {#secure-first-ssh-access}

يمنحك VPS الجديد صلاحيات إدارية، لكن العمل في الإنتاج لا ينبغي أن يستمر دائمًا بحساب root.

ترتيب آمن للوصول الأول:

1. اتصل ببيانات الدخول أو المفتاح المقدم من المزود؛
2. تأكد أن الخادم وعنوان IP هما اللذان أردت إنشاءهما؛
3. حافظ على عمل وحدة تحكم المزود أو VNC أو مسار الاستعادة؛
4. أنشئ مستخدمًا إداريًا باسم محدد؛
5. امنحه صلاحيات sudo أو الإدارة اللازمة فقط؛
6. أضف المصادقة بمفتاح SSH حيثما أمكن؛
7. تحقق من الدخول الجديد في جلسة ثانية **قبل** تعطيل وسيلة الدخول الأصلية أو تقييدها.

مثال على Ubuntu/Debian:

```bash
ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy
```

لا تغلق مسار الإدارة الوحيد الذي يعمل أثناء «تقوية» حماية الخادم.

يشرح [قائمة التحقق من أمان VPS]({{< relref "vps-security-checklist.md" >}}) حماية SSH والجدار الناري بالتفصيل؛ نكتفي هنا بما يلزم للنشر.

## حدّث الخادم قبل تثبيت البيئة {#update-the-server-before-installing-the-stack}

على Ubuntu/Debian:

```bash
sudo apt update
sudo apt upgrade -y
```

أعد التشغيل إذا تطلب التحديث ذلك، ثم تحقق من إمكان الاتصال مجددًا.

لا تؤجل تحديثات الأمان إلى ما بعد إتاحة الموقع للعامة.

## المسار اليدوي دون لوحة تحكم {#manual--no-control-panel-path}

ينبغي ألا يحتوي VPS اليدوي إلا على الخدمات التي يحتاجها التطبيق.

الخيارات المعتادة:

### موقع ثابت {#static-website}

المطلوب:

- Nginx أو Apache؛
- ملفات الموقع؛
- DNS;
- HTTPS.

ليس مطلوبًا تلقائيًا:

- PHP;
- MySQL/MariaDB/PostgreSQL؛
- خادم بريد محلي.

### موقع PHP أو ووردبريس {#php--wordpress-website}

المطلوب عادة:

- Nginx أو Apache؛
- PHP-FPM ووحدات PHP؛
- قاعدة البيانات؛
- ملفات الموقع والملفات المرفوعة؛
- DNS;
- HTTPS.

لأحمال ووردبريس، استخدم [VPS لووردبريس]({{< relref "vps-for-wordpress.md" >}}).

### Node.js أو Python أو تطبيق مخصص {#nodejs--python--custom-application}

عادة:

- بيئة تشغيل التطبيق؛
- مستخدم مخصص للتطبيق دون root؛
- مدير عمليات أو خدمة systemd؛
- ربط التطبيق بـ localhost أو مقبس خاص حيثما أمكن؛
- وكيلًا عكسيًا Nginx/Apache؛
- قاعدة بيانات عند الحاجة فقط؛
- DNS;
- HTTPS.

لا تجعل خادم التطوير مكشوفًا مباشرة للإنترنت كبنية إنتاج.

## ثبّت خادم الويب {#install-the-web-server}

تدعم وثائق خادم Ubuntu الحالية Nginx وApache. لا يوجد منهما خيار «أفضل» لكل الحالات.

في مثال Nginx:

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx
```

ينبغي الآن أن يعرض عنوان IP صفحة Nginx الافتراضية إذا سمحت قواعد الشبكة والجدار الناري بـ HTTP.

استخدم Apache إذا كان أنسب للتطبيق أو الفريق أو الإعداد الحالي.

## اضبط اسم مضيف الموقع {#configure-the-website-hostname}

DNS وإعداد خادم الويب جزءان من المهمة نفسها.

يجب أن يوجه مزود DNS اسم المضيف إلى VPS، **وأن** يعرف خادم الويب أي موقع يجيب عن ذلك الاسم.

في Nginx، أنشئ كتلة خادم للنطاق. الفكرة العامة:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

توجد إعدادات المواقع في Ubuntu/Debian عادة ضمن:

- `/etc/nginx/sites-available/`
- `/etc/nginx/sites-enabled/`

بعد التغييرات:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

اختبر صحة صياغة الإعدادات دائمًا قبل إعادة تحميلها.

للتطبيق خلف وكيل عكسي، توجه كتلة الخادم الطلبات إلى منفذ التطبيق المحلي أو مقبسه.

## انشر الملفات أو شيفرة التطبيق {#deploy-files-or-application-code}

اختر طريقة نشر يمكن تكرارها بثبات.

### SFTP/SCP {#sftpscp}

يناسب:

- المواقع الصغيرة؛
- النشر اليدوي غير المتكرر؛
- المشاريع البسيطة الأولى.

الخطر: قد تختلف ملفات مجلد الإنتاج بسهولة عن المستودع المصدر.

### rsync عبر SSH {#rsync-over-ssh}

يفيد مزامنة الملفات القابلة للتكرار والتحديثات التزايدية الفعالة.

### النشر باستخدام Git {#git-based-deployment}

يفيد عندما ينبغي أن تقابل إصدارات الإنتاج التزامات محددة في المستودع.

### CI/CD {#cicd}

يفيد عندما يتكرر النشر بما يبرر أتمتة البناء والاختبار والإصدار.

أيًا كانت الطريقة:

- لا تنشر بحساب root إلا إذا تطلبت المهمة صلاحياته فعلًا؛
- اجعل ملفات التطبيق مملوكة لمستخدم نشر أو تطبيق مناسب؛
- امنح خادم الويب الوصول اللازم فقط؛
- احفظ الأسرار خارج المجلدات العامة للمواقع؛
- لا تختصر الطريق بمنح الجميع صلاحية الكتابة.

## مسار PHP وووردبريس {#php--wordpress-path}

لموقع PHP على Ubuntu/Debian، ثبّت حزم PHP-FPM المدعومة الحالية والإضافات التي يحتاجها التطبيق.

بنية معتادة:

**المتصفح ← Nginx/Apache ← PHP-FPM ← قاعدة البيانات**

لا تنسخ قائمة إضافات عشوائية من نظام إدارة محتوى آخر. ثبّت ما يحتاجه التطبيق فعلًا.

لووردبريس:

- أنشئ قاعدة بيانات ومستخدمًا مخصصًا لها؛
- اضبط حدود رفع الملفات والذاكرة والتنفيذ في PHP وفق الحاجة المقاسة؛
- احمِ الأسرار في `wp-config.php`؛
- اضبط اسم مضيف الموقع؛
- فعّل HTTPS؛
- تحقق من wp-cron والمهام الخلفية؛
- أضف التخزين المؤقت بحسب الأحمال.

استخدم [VPS لووردبريس]({{< relref "vps-for-wordpress.md" >}}) لتحديد الموارد والأداء بدلًا من تكرارها هنا.

## مسار Node.js وPython والتطبيقات المخصصة {#nodejs--python--custom-app-path}

لا تشغّل أمر التطوير يدويًا في نافذة طرفية ثم تعتبره إنتاجًا.

استخدم المعادلة التالية:

- مستخدمًا مخصصًا للتطبيق؛
- ملف بيئة أو إعداد بصلاحيات مقيدة؛
- systemd أو مدير عمليات مناسبًا للإنتاج؛
- إعادة تشغيل تلقائية عند الفشل أو إعادة تشغيل الخادم؛
- استماع التطبيق على عنوان محلي أو خاص؛
- وكيلًا عكسيًا Nginx/Apache؛
- سجلات التطبيق؛
- فحوص سلامة الخدمة.

مسار معتاد:

**المتصفح ← HTTPS/Nginx ← التطبيق على 127.0.0.1:PORT ← قاعدة البيانات والخدمات الخارجية**

تحقق من إرشادات إطار العمل نفسه للنشر في الإنتاج.

## ثبّت قاعدة البيانات عند الحاجة فقط {#database-install-only-when-required}

لا يحتاج الموقع الثابت إلى قاعدة بيانات.

لتطبيق ديناميكي يحتاج إليها:

- ثبّت محرك قاعدة البيانات المدعوم؛
- أنشئ قاعدة مخصصة؛
- أنشئ مستخدمًا خاصًا بالتطبيق؛
- امنحه الصلاحيات المطلوبة فقط؛
- احفظ بيانات الدخول خارج مجلد الويب العام؛
- لا تفتح منفذ قاعدة البيانات للعامة إلا إذا تطلبت ذلك بنية محددة ومؤمنة؛
- أدرج قاعدة البيانات في خطط النسخ الاحتياطي والمراقبة.

قد تصبح قاعدة البيانات قيد الأداء الحقيقي لـ VPS حتى لو كان خادم الويب شبه خامل.

## ملكية الملفات والصلاحيات والأسرار {#file-ownership-permissions-and-secrets}

تجنب خطأين شائعين:

1. تشغيل الموقع كـ root؛
2. إتاحة الكتابة للجميع في مجلدات التطبيق «لإصلاح» أخطاء الصلاحيات.

بدلًا من ذلك:

- استخدم مستخدم نشر أو تطبيق؛
- افهم أي عملية تحتاج إلى قراءة وأيها تحتاج إلى كتابة؛
- امنح مجلدات الرفع والتخزين المؤقت صلاحيات الكتابة اللازمة فقط؛
- احمِ ملفات البيئة وبيانات الدخول؛
- لا تحفظ أسرار الإنتاج في التزامات Git؛
- احفظ المفاتيح الخاصة خارج المجلدات العامة.

تعتمد الملكية الدقيقة على التطبيق ونموذج خادم الويب؛ اتبع وثائق التطبيق بدلًا من نسخ وصفة عامة مثل `chmod 777`.

## اختبر قبل تحويل DNS العام {#test-before-public-dns}

لا تجعل تحويل DNS أول اختبار فعلي للتطبيق.

قبل التحويل العام، تحقق من الخادم الجديد بإحدى الطرق التالية حيثما أمكن:

- افتح عنوان IP لفحص افتراضي أو ثابت بسيط؛
- عدّل ملف hosts محليًا ليشير `example.com` إلى VPS الجديد على جهازك فقط؛
- استخدم اسمًا خاصًا أو تجريبيًا مع منع فهرسته كنسخة مكررة بالخطأ؛
- اختبر التطبيق بإعداد اسم المضيف نفسه في Nginx/Apache الذي سيستخدمه الإنتاج.

اختبر أكثر من الصفحة الرئيسية:

- الصفحات الداخلية المهمة؛
- الدخول والإدارة؛
- النماذج؛
- رفع الملفات؛
- الملفات الثابتة؛
- القراءة والكتابة في قاعدة البيانات؛
- نقاط وصول التطبيق وAPI؛
- إعادة التوجيه؛
- السجلات.

يفيد اختبار ملف hosts خصوصًا لأن تطبيقات كثيرة تتصرف بصورة مختلفة مع اسم المضيف الفعلي مقارنة بعنوان IP المباشر.

إذا كان الموقع قائمًا ويعمل، فاتبع التحويل الأكثر ضبطًا في [نقل موقع إلى VPS]({{< relref "website-migration-to-vps.md" >}}).

## وجّه النطاق إلى VPS {#point-the-domain-to-the-vps}

اضبط لدى مزود DNS السجلات التي ينبغي أن تصل إلى هذا الخادم.

إعداد IPv4 معتاد:

| الاسم | النوع | القيمة |
|---|---|---|
| `@` | A | عنوان IPv4 لخادم VPS |
| `www` | CNAME | النطاق الجذري |

يمكن أيضًا استخدام سجل A لـ `www`.

أضف سجل AAAA فقط إذا أعددت IPv6 فعلًا وكان الوصول إليه يعمل. قد يمنع سجل AAAA معطوب بعض الزوار من الوصول حتى لو عمل IPv4.

DNS وحده لا يشغّل الموقع؛ يجب أن يتضمن إعداد Nginx/Apache اسم المضيف المطابق أيضًا.

لنقل موقع قائم، يشرح [نقل موقع إلى VPS]({{< relref "website-migration-to-vps.md" >}}) تحويل DNS والتعامل مع الكتابات الأخيرة.

## أضف HTTPS بعد عمل DNS {#add-https-after-dns-resolves}

اطلب شهادة موثوقة بعد أن يشير اسم المضيف العام إلى الخادم الذي سيجيب عن طلب التحقق. تأكد مسبقًا من سماح الجدار الناري وقواعد شبكة المزود بمسار تحقق HTTP/HTTPS الذي ستستخدمه.

يمكن لعميل ACME مثل Certbot طلب شهادات Let's Encrypt وتجديدها مع Nginx/Apache. اتبع تعليمات Certbot ونظام التشغيل الحالية بدلًا من نسخ أمر حزم قديم دون تحقق.

تحقق من:

- تغطية الشهادة للنطاق الجذري ونسخ `www` المستخدمة؛
- إعادة توجيه HTTP إلى HTTPS كما تريد؛
- أتمتة تجديد الشهادة؛
- سماح إعدادات الجدار الناري وCDN بالتجديد؛
- توليد التطبيق عناوين HTTPS الصحيحة.

لا تفعّل التحويل إلى HTTPS قبل التأكد من عمل الشهادة.

## اضبط الجدار الناري {#configure-the-firewall}

حافظ على عمل الوصول الإداري أثناء تغيير القواعد.

يحتاج موقع عام بسيط عادة إلى:

- SSH من مصدر الإدارة أو مسارها المطلوب؛
- TCP 80 لـ HTTP والتحقق عبر ACME وإعادة التوجيه؛
- TCP 443 لـ HTTPS.

لا تكشف MySQL/PostgreSQL أو Redis أو منافذ التطبيق الداخلية للعامة لمجرد أنها تستمع محليًا بصورة افتراضية.

عند استخدام UFW، اسمح بمسار SSH المطلوب **قبل** تفعيل القواعد المقيدة.

تفاصيل الجدار الناري وتقوية الحماية في [قائمة التحقق من أمان VPS]({{< relref "vps-security-checklist.md" >}}).

## مهام cron والطوابير والعمليات الخلفية {#cron-jobs-queues-and-workers}

كثيرًا ما تفشل مواقع ديناميكية بعد النشر لأن إعدادها اقتصر على مسار طلبات الويب.

احصر ما يلي:

- مهام cron؛
- عمليات معالجة الطوابير؛
- الإجراءات المجدولة؛
- الاستيراد والتصدير؛
- مهام البريد؛
- تهيئة التخزين المؤقت مسبقًا؛
- المعالجات الخلفية.

اجعلها:

- تعمل بالمستخدم الصحيح دون root؛
- تبدأ تلقائيًا عند الحاجة؛
- تكتب في سجلات معروفة؛
- تتجنب تداخلًا يستنفد المعالج والذاكرة؛
- تعود بعد إعادة تشغيل الخادم.

## السجلات ومراقبة التشغيل الأساسية {#logs-and-basic-observability}

قبل استقبال زيارات الإنتاج، اعرف أين تبحث إذا تعطل الموقع.

حدد على الأقل:

- سجل الوصول في Nginx/Apache؛
- سجل الأخطاء في Nginx/Apache؛
- سجل التطبيق؛
- سجل PHP-FPM أو بيئة التشغيل؛
- سجل قاعدة البيانات وحالتها؛
- سجل النظام؛
- استخدام القرص؛
- ضغط الذاكرة والمعالج.

أضف فحص HTTP(S) خارجيًا لتوافر الموقع، كي يظهر عطل الخادم حتى دون وجود شخص مسجل الدخول إلى VPS.

تصميم الحدود والتنبيهات بالتفصيل في [مراقبة VPS]({{< relref "vps-monitoring.md" >}}).

## التحقق بعد إعادة التشغيل {#reboot-validation}

تعمل كثير من عمليات النشر الأولى على VPS حتى أول إعادة تشغيل فقط.

قبل اعتبار الخادم جاهزًا:

```bash
sudo reboot
```

بعد عودته، تحقق من:

- الوصول عبر SSH؛
- Nginx/Apache;
- PHP-FPM أو خدمة التطبيق؛
- قاعدة البيانات؛
- cron وعمليات الطوابير؛
- HTTPS;
- صفحات الموقع ونماذجه؛
- المراقبة؛
- جدول النسخ الاحتياطي.

إذا لم يعد التطبيق إلا بعد تشغيل أمر يدويًا، فالنشر غير مكتمل.

## متى لا تناسبك الاستضافة اليدوية دون لوحة؟ {#when-manual--no-panel-hosting-is-the-wrong-fit}

استخدم لوحة أو خدمة إدارة عندما:

- لا يجيد أحد SSH والاستعادة من سطر الأوامر؛
- لا يوجد مسؤول عن تحديثات النظام والأمان؛
- لا يستطيع أحد تشخيص أعطال خادم الويب وبيئة التشغيل وقاعدة البيانات؛
- تُنشأ النسخ الاحتياطية لكن لا يستطيع أحد استعادتها؛
- لا يوجد مسؤول عن الانقطاعات الحاسمة للأعمال؛
- يريد الفريق إدارة البريد والمستخدمين والنطاقات من واجهة استضافة بدلًا من إعداد الخادم؛
- تناسب التطبيقَ منصةٌ مُدارة أكثر.

قد يقلل VPS اليدوي استهلاك اللوحة ويزيد التحكم، لكنه لا يقلل حجم المسؤولية التشغيلية.

استخدم [VPS مع لوحة تحكم]({{< relref "vps-with-control-panel.md" >}}) لاختيار اللوحة، أو [VPS المدار مقابل غير المدار]({{< relref "managed-vs-unmanaged-vps.md" >}}) إذا كانت المشكلة غياب مسؤول تشغيل.

## قائمة التحقق من جاهزية الإنتاج {#production-acceptance-checklist}

| الفحص | شرط الاجتياز |
|---|---|
| الوصول إلى الخادم | يستطيع مسؤول بحساب محدد الدخول، وتظل وحدة الاستعادة متاحة |
| التحديثات | تطبيق تحديثات الأمان والنظام الحالية |
| خادم الويب | يبدأ تلقائيًا وينجح اختبار الإعدادات |
| اسم مضيف الموقع | سلوك مقصود للنطاق الجذري و`www` |
| DNS | تشير A/AAAA/CNAME إلى الخادم أو المسار المقصود |
| HTTPS | شهادة موثوقة وأسماء صحيحة ومسار تجديد واضح |
| التطبيق | عمل صفحات ممثلة للاستخدام والدخول والنماذج ورفع الملفات |
| قاعدة البيانات | عمل مستخدم التطبيق وعدم كشف المنفذ للعامة بالخطأ |
| الملفات | ملكية صحيحة دون التحايل بصلاحيات `777` |
| المهام | بدء cron والعمليات الخلفية وتسجيلها بصورة صحيحة |
| إعادة التشغيل | عودة الخدمات المطلوبة تلقائيًا |
| السجلات | يعرف المسؤول أين تظهر أعطال الويب والتطبيق والنظام |
| النسخ الاحتياطي | شمول الملفات وقاعدة البيانات المطلوبة وتحديد مسار الاستعادة |
| المراقبة | فحص خارجي للموقع مع رؤية أساسية للموارد |
| السعة | فحص المعالج والذاكرة والقرص تحت حمل فعلي |

عودة الصفحة الرئيسية بالحالة HTTP 200 وحدها لا تجعل الموقع جاهزًا للإنتاج.

- راقب توافر الموقع؛

- تابع ضغط المعالج والذاكرة وقاعدة البيانات؛
- تابع تجديد الشهادات.

## الأسئلة الشائعة {#faq}

### هل يمكنني استضافة موقع على VPS دون لوحة تحكم؟ {#can-i-host-a-website-on-a-vps-without-a-control-panel}

نعم. يمكن لخادم Linux نظيف استضافة الموقع باستخدام SSH ومكونات خادم الويب وبيئة التشغيل وقاعدة البيانات اللازمة. يشمل هذا الدليل مسار العمل دون لوحة، بدلًا من صفحة أخرى تنافسه.

### هل أحتاج إلى Nginx لاستضافة موقع على VPS؟ {#do-i-need-nginx-to-host-a-website-on-vps}

لا. Nginx وApache خياران شائعان. اختر ما يناسب التطبيق والإعداد وخبرة المسؤول.

### هل يحتاج كل موقع على VPS إلى قاعدة بيانات؟ {#does-every-vps-website-need-a-database}

لا. المواقع الثابتة لا تحتاج إليها. ثبّت MySQL/MariaDB/PostgreSQL فقط عندما يحتاج التطبيق إلى قاعدة بيانات.

### هل أستخدم root لاستضافة الموقع؟ {#should-i-use-root-to-host-the-website}

لا. root مخصص للإدارة. شغّل الموقع وانشره بمستخدمين وخدمات مناسبين دون root وبالصلاحيات اللازمة فقط.

### متى أستخدم لوحة تحكم؟ {#when-should-i-use-a-control-panel}

عندما توفر إدارة المواقع والنطاقات وPHP وقواعد البيانات والمستخدمين والبريد والنسخ الاحتياطي من المتصفح قدرًا من العمل المتكرر يبرر الاستهلاك الإضافي والقيود.

### هل يمكن استضافة ووردبريس على VPS دون cPanel؟ {#can-i-host-wordpress-on-a-vps-without-cpanel}

نعم. يحتاج ووردبريس إلى خادم ويب متوافق وPHP وقاعدة بيانات وملفات ووردبريس وصلاحيات صحيحة وDNS وHTTPS. اللوحة اختيارية.

### متى أوجه DNS إلى VPS؟ {#when-should-i-point-dns-to-the-vps}

للموقع الجديد، عندما يكون الخادم جاهزًا للاستجابة لاسم المضيف الفعلي. وللموقع القائم، اختبر أولًا واتبع خطة نقل وتحويل مضبوطة.

### لماذا يشير النطاق إلى VPS لكنه يعرض موقعًا آخر؟ {#why-does-my-domain-point-to-the-vps-but-show-the-wrong-site}

يوجه DNS اسم المضيف إلى عنوان IP فقط. يجب أن توجد أيضًا كتلة خادم أو مضيف افتراضي مطابق للاسم في Nginx/Apache.

### متى أفعّل HTTPS؟ {#when-should-i-enable-https}

بعد وصول اسم المضيف العام إلى الخادم وعمل مسار التحقق. أصدر الشهادة ثم تحقق من تغطية النطاق الجذري و`www` واضبط التحويل المطلوب من HTTP إلى HTTPS.

### ما الذي أتحقق منه بعد إعادة تشغيل VPS؟ {#what-should-i-check-after-rebooting-the-vps}

تأكد من عودة خادم الويب وخدمة التطبيق أو PHP-FPM وقاعدة البيانات والعمليات الخلفية وHTTPS والمراقبة والموقع دون تدخل يدوي.
