VPS 보안 점검표는 인터넷에 연결된 자체 관리 서버의 보안을 우선순위에 따라 강화하기 위한 절차입니다. 목표는 VPS를 “100% 안전하게” 만드는 것이 아닙니다. 불필요한 공격 표면을 줄이고, 관리자 권한을 보호하며, 소프트웨어를 유지 관리하고, 복구 가능성을 확보하며, 실제로 보안 업무를 책임지는 사람이 있는지 확인하는 것입니다.

안전한 작업 순서가 중요합니다. **먼저 복구 경로를 확보하고, 두 번째 관리자 로그인을 확인한 다음, 공개된 서비스를 파악하고 나서 SSH와 방화벽 규칙을 강화하세요**.

패치, 방화벽 정책, 백업 검증, 모니터링과 사고 대응을 책임지는 사람이 없다면 먼저 운영 방식을 정하세요. [관리형 VPS와 비관리형 VPS]({{< relref "managed-vs-unmanaged-vps.md" >}})를 참고하세요.

서버 선택의 전반적인 판단 기준은 [웹사이트용 VPS 호스팅]({{< relref "_index.md" >}})을 참고하세요.

## 기본 보안 적용 순서

일반적인 공개 Linux VPS에서는 다음 순서로 진행합니다.

1. **제공업체 콘솔과 복구 접속을 계속 사용할 수 있게 유지합니다.**
2. **이름이 있는 비root 관리 사용자를 생성하고 접속을 테스트합니다.**
3. **SSH 키 인증을 설정하고 두 번째 로그인 세션을 확인합니다.**
4. **수신 중인 모든 서비스와 공개 포트를 목록으로 정리합니다.**
5. **키 기반 접속이 작동한 뒤에만 SSH, root 및 비밀번호 정책을 제한합니다.**
6. **기본 차단 방화벽 정책을 적용하고 필요한 포트만 엽니다.**
7. **데이터베이스, Redis와 애플리케이션 내부 포트는 기본적으로 비공개로 유지합니다.**
8. **OS와 패키지 보안 업데이트를 적용하고 재부팅 및 서비스 재시작 담당자를 정합니다.**
9. **컨트롤 패널, CMS, 플러그인, 런타임과 의존성에도 패치를 적용합니다.**
10. **비밀 정보를 보호하고 사용자와 DB 계정에 최소 권한을 부여합니다.**
11. **다층 방어 수단으로 무차별 대입 방어와 요청 속도 제한을 추가합니다.**
12. **공개 웹사이트에 HTTPS를 적용하고 관리 인터페이스를 보호합니다.**
13. **독립적인 백업을 보관하고 복원을 테스트합니다.**
14. **보안과 복구 실패를 드러낼 수 있는 로그와 알림을 활성화합니다.**
15. **침해가 의심될 때의 대응 절차를 정합니다.**
16. **정기적으로 감사를 반복합니다.**

명령을 무작정 붙여 넣어 원격 접속을 강화하지 마세요. 정상적인 관리자의 접속을 막는 보안 변경은 서비스 장애입니다.

## 접속 설정 변경 전 복구 경로 확보

SSH를 제한하거나 엄격한 방화벽을 활성화하기 전에 잘못된 규칙을 적용해도 복구할 수 있는지 확인하세요.

제공업체의 브라우저 콘솔, VNC 또는 복구 인터페이스처럼 일반 접속 경로와 독립된 수단을 하나 이상 유지하세요.

그다음 다음 순서로 진행합니다.

1. 별도의 관리 사용자를 생성합니다;
2. SSH 공개 키를 추가합니다;
3. **두 번째** 터미널 세션을 엽니다;
4. 로그인과 sudo 또는 관리자 권한을 확인합니다;
5. 새 정책을 테스트하는 동안 정상 작동하는 세션을 열어 둡니다;
6. 그런 다음에만 기존 접속 방법을 제한합니다.

중요한 보안 조치는 “가능한 한 빨리 root를 비활성화하는 것”이 아닙니다. **접속 차단을 일으키지 않으면서 위험한 접속 방법을 검증된 더 안전한 경로로 교체하는 것**입니다.

첫 배포 절차는 [VPS에 웹사이트를 호스팅하는 방법]({{< relref "how-to-host-a-website-on-vps.md" >}})에서 다룹니다.

## 차단하기 전에 공개 서비스 파악

어떤 포트가 열려 있는지 추측하지 마세요.

Linux에서는 다음과 같은 도구로 수신 소켓을 확인합니다.

```bash
sudo ss -lntup
```

각 수신 서비스에 대해 다음을 판단하세요.

- 이 서비스가 필요한가요?
- 모든 인터페이스에서 수신해야 하나요?
- 공개되어야 하나요?
- localhost나 사설 네트워크에서만 수신하도록 설정할 수 있나요?
- 어떤 출발지 네트워크에서 접근할 수 있어야 하나요?
- 업데이트와 로그는 누가 책임지나요?

일반적인 공개 웹사이트 포트에는 다음이 포함될 수 있습니다.

- SSH와 관리자 접속;
- HTTP 80;
- HTTPS 443.

그렇다고 모든 서버가 이 세 가지를 인터넷 전체에 공개해야 한다는 뜻은 **아닙니다**.

방화벽으로 숨기는 데만 의존하지 말고 사용하지 않는 서비스를 제거하세요.

## 관리자 접속 보안 강화

Ubuntu의 OpenSSH 문서는 공개 키 인증을 지원하며 Ed25519와 같은 최신 키 알고리즘을 권장합니다.

기본적인 관리자 접속 모델은 다음과 같습니다.

- 이름이 있는 별도의 관리 계정;
- SSH 키 인증;
- 가능한 경우 암호문으로 보호한 개인 키;
- 필요한 사용자에게만 sudo 권한 부여;
- root로 실행하는 애플리케이션 없음;
- 더 안전한 접속을 확인한 뒤 직접 root 로그인과 비밀번호 SSH 접속 제한.

더 높은 수준의 보증이 필요한 환경에서는 OpenSSH가 FIDO/U2F 또는 TOTP 기반 2단계 인증을 포함한 더 강력한 인증 방식도 지원합니다.

### Root 로그인과 비밀번호 인증

키 기반 접속과 콘솔 복구를 확인하기 전에 이러한 옵션을 무작정 설정하지 마세요.

더 안전한 경로가 작동하면 다음을 검토하세요.

- `PermitRootLogin`;
- `PasswordAuthentication`;
- `AllowUsers` / `AllowGroups`;
- 필요한 경우 유휴 시간과 세션 정책.

구체적인 정책은 환경에 따라 달라집니다.

SSH 포트를 22에서 다른 번호로 변경하면 스캐너가 만드는 불필요한 시도는 줄일 수 있지만, 키 인증, 최소 권한, 방화벽 정책과 소프트웨어 유지 관리를 대신할 수는 **없습니다**.

## 방화벽: 필요한 서비스만 허용

Ubuntu의 기본 호스트 방화벽 프런트엔드는 UFW입니다.

안전한 기본 구성의 개념은 다음과 같습니다.

- 요청하지 않은 인바운드 트래픽은 기본 차단합니다;
- 실제로 사용하는 관리자 접속 경로를 허용합니다;
- 공개 웹 서버에는 HTTP/HTTPS를 허용합니다;
- 데이터베이스와 내부 서비스는 비공개로 유지합니다;
- IPv4와 IPv6 동작을 검토합니다.

제한적인 규칙을 활성화하기 전에 SSH 접속이 유지되도록 하세요.

상태 확인 예제:

```bash
sudo ufw status verbose
```

구성이 다르다면 일반적인 “22/80/443 허용” 목록을 그대로 복사하지 마세요.

### 제공업체 방화벽과 호스트 방화벽

제공업체 또는 네트워크 방화벽은 트래픽이 VM에 도달하기 전에 차단할 수 있습니다.

호스트 방화벽은 게스트 OS가 어떤 트래픽을 받아들일지 제어합니다.

두 가지를 함께 사용하면 유용한 다층 방어가 될 수 있지만, 규칙이 문서화되어 있고 서로 충돌하지 않아야 합니다.

## 데이터베이스와 내부 서비스는 기본적으로 비공개 유지

서비스가 수신 중이라는 이유만으로 MySQL/MariaDB/PostgreSQL, Redis, 내부 Node/Python 애플리케이션 포트나 제어 소켓을 인터넷에 공개하지 마세요.

다음 방식을 우선하세요.

- 같은 서버의 서비스에는 localhost 사용;
- 여러 서버로 구성된 환경에는 사설 네트워크 인터페이스 사용;
- 원격 관리가 필요할 때 출발지 IP 제한;
- 관리 작업에는 SSH/VPN/배스천 접속 사용.

구조상 꼭 필요하고 접근을 강력하게 제한한 경우에만 데이터베이스 포트를 공개하세요.

## 패치와 자동 보안 업데이트

지원되는 OS라도 패치 담당자가 없으면 점차 오래된 상태가 됩니다.

Ubuntu Server는 지원되는 설치 환경에서 기본적으로 `unattended-upgrades`를 사용해 보안 업데이트를 자동 적용합니다.

도움이 되는 기능이지만, 보안 운영 과정에서는 다음 질문에도 답해야 합니다.

- 어떤 저장소가 업데이트 대상인가요?
- 타사 패키지와 앱도 업데이트되나요?
- 서비스 재시작이 필요한가요?
- 재부팅이 필요한가요?
- 실패한 업데이트는 누가 확인하나요?
- 운영 서비스를 언제 안전하게 재시작할 수 있나요?

Ubuntu 문서에 따르면 업데이트된 코드가 실제로 적용되려면 서비스 재시작과 경우에 따라 재부팅이 필요할 수 있습니다.

“자동 업데이트를 활성화했다”는 사실을 패치 관리 전체로 여기지 마세요.

## Fail2ban, CrowdSec 및 요청 속도 제한

무차별 대입 방어 도구는 반복되는 악의적인 시도를 줄일 수 있습니다.

이러한 도구는 기본 인증 모델이 아니라 **다층 방어 수단**입니다.

다음 조건을 갖춘 뒤 사용하세요.

- 관리자 접근이 보호되어 있습니다;
- 강력한 인증이 적용되어 있습니다;
- 노출된 서비스가 의도적으로 공개되어 있습니다;
- 로그를 확인할 수 있습니다.

차단 도구가 약한 비밀번호, 패치하지 않은 패널 또는 공개된 데이터베이스를 안전하게 만들어 주지는 않습니다.

## 애플리케이션과 데이터베이스의 최소 권한

최소 권한 원칙은 전체 스택에 적용됩니다.

다음 구성을 우선하세요.

- 배포 사용자와 관리자 분리;
- 애플리케이션 사용자 분리;
- 애플리케이션별 DB 사용자 분리;
- 필요한 DB 권한만 부여;
- 서로 무관한 고객 사이트의 사용자 분리;
- 앱에 필요한 디렉터리만 쓰기 허용.

다음은 피하세요.

- 웹 앱을 root로 실행;
- 애플리케이션에서 DB root 또는 관리자 계정 공유;
- 권한 문제를 해결하기 위한 `chmod 777` 사용;
- 더 강한 격리가 가능한데도 서로 무관한 고객 사이트에 하나의 Unix 사용자 사용.

여러 사이트의 격리는 [여러 웹사이트용 VPS]({{< relref "vps-for-multiple-websites.md" >}})를 참고하세요.

## HTTPS는 전송을 보호할 뿐 서버 전체를 보호하지 않음

로그인이나 민감한 데이터를 처리하는 운영 웹사이트에는 HTTPS가 필요하며, 공개 사이트에서도 일반적인 기본 요건입니다.

HTTPS는 클라이언트와 서버 사이에서 전송되는 데이터를 보호합니다.

다음 문제를 해결하지는 못합니다.

- 취약한 플러그인;
- 취약한 SSH 설정;
- 공개된 데이터베이스;
- 유출된 API 키;
- 오래된 패키지;
- 안전하지 않은 파일 권한;
- 백업 부재.

인증서 갱신을 확인하고 만료와 갱신 실패를 감시하세요.

## 백업도 보안 조치임

보안에는 침해, 랜섬웨어, 잘못된 업데이트와 실수로 인한 삭제 후 복구할 수 있는 능력도 포함됩니다.

- 하나의 스냅샷이나 이미지에만 의존하지 않습니다;

- 백업 작업 실패를 감시합니다;
- 복원을 테스트합니다;
- 복구 지점 사이에 손실될 수 있는 데이터 양을 파악합니다.

## 침해가 의심될 때

관리자 또는 root 권한 침해가 의심된다면 임시방편의 “정리”만으로 서버가 안전하다고 바로 판단하지 마세요.

더 안전한 대응은 다음과 같습니다.

1. 영향을 받은 VPS와 네트워크 경로를 **격리**합니다;
2. 가능한 경우 관련 로그와 증거를 보존합니다;
3. 어떤 자격 증명과 비밀 정보가 노출되었을 수 있는지 확인합니다;
4. 깨끗하고 신뢰할 수 있는 시스템에서 해당 자격 증명을 교체합니다;
5. 정상임이 확인된 애플리케이션과 데이터의 복구 지점을 정합니다;
6. 적절한 경우 정상임이 확인된 OS와 설정 소스를 사용해 서버를 다시 구축합니다;
7. 침해된 실행 파일과 설정을 무작정 되돌리지 말고 검증된 데이터를 복원합니다;
8. 실제 트래픽을 다시 연결하기 전에 최초 침입 원인을 검토합니다.

CISA의 사고 대응 지침은 격리, 증거와 로그 검토, 검증된 백업을 통한 복구를 강조합니다.

비즈니스에 중요한 시스템이라면 자격을 갖춘 사고 대응 또는 보안 전문가를 참여시키세요.

## FAQ

### 새 VPS에서 무엇부터 보호해야 하나요?

콘솔과 복구 접속을 유지하고, 별도의 비root 관리 계정에서 SSH 키 로그인을 설정하고 테스트한 뒤, 수신 서비스를 파악하고 나서 SSH와 방화벽 정책을 강화하세요. 접속을 확인하기 전에 관리자를 차단할 수 있는 변경을 여러 개 한꺼번에 적용하지 마세요.

### SSH 비밀번호 로그인을 비활성화해야 하나요?

일반적인 VPS 관리에서는 키 기반 관리자 인증이 더 강력하지만, 먼저 키 로그인과 복구 콘솔을 확인하세요. 유일하게 작동하는 접속 경로를 비활성화하지 마세요.

### SSH 포트를 변경해야 하나요?

스캐너와 로그의 불필요한 기록을 줄일 수는 있지만 핵심 보안 조치는 아닙니다. 강력한 인증, 최소 권한, 방화벽 정책과 패치가 더 중요합니다.

### Fail2ban이 필요한가요?

항상 필요한 것은 아니지만 반복되는 로그인 악용에 대한 다층 방어 수단으로 유용할 수 있습니다. SSH 키, 패치 또는 올바른 서비스 공개 범위를 대신하지는 않습니다.

### VPS에서 어떤 포트를 열어야 하나요?

구조상 필요한 포트만 열어야 합니다. 공개 웹 서버에는 일반적으로 HTTP/HTTPS와 통제된 관리자 접속 경로가 필요합니다. 데이터베이스와 내부 애플리케이션 서비스는 보통 비공개로 유지해야 합니다.

### 방화벽이 취약한 애플리케이션을 보호하나요?

아니요. 방화벽은 네트워크 노출 범위를 제한합니다. 외부에서 접근할 수 있는 웹 애플리케이션에는 여전히 안전한 코드, 지원되는 의존성, 업데이트와 애플리케이션 수준의 보안 조치가 필요합니다.

### 자동 보안 업데이트만으로 충분한가요?

아니요. 지원되는 OS 패키지에는 도움이 되지만 타사 애플리케이션과 의존성은 별도의 업데이트가 필요할 수 있으며, 서비스 재시작이나 재부팅도 운영 과정에서 처리해야 할 수 있습니다.

### HTTPS만으로 VPS를 보호할 수 있나요?

아니요. HTTPS는 전송을 보호합니다. 취약한 SSH, 공개된 데이터베이스, 취약한 플러그인, 오래된 패키지, 유출된 비밀 정보나 백업 부재를 해결하지는 못합니다.

### VDSina의 DDoS 보호만으로 웹사이트를 보호할 수 있나요?

아니요. VDSina는 현재 무료 DDoS 보호를 안내하고 있으며, 공개 QA에서는 무료 보호가 SLA 없는 L3-L4 범위라고 설명합니다. 게스트 OS, 접속, 애플리케이션과 복구에 대한 보안 조치는 여전히 필요합니다.

### VPS 침해가 의심되면 어떻게 해야 하나요?

서버를 격리하고 관련 증거와 로그를 보존하며, 깨끗한 시스템에서 노출된 자격 증명을 교체하세요. 관리자 권한 침해가 의심되면 정상임이 확인된 소스와 검증된 백업으로 다시 구축하는 방식을 우선하세요. 중요한 시스템이라면 사고 대응 전문가를 참여시키세요.
