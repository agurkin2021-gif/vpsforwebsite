نحوه میزبانی سایت روی سرور مجازی به برنامه‌ای بستگی دارد که مستقر می‌کنید. سایت ایستا وب‌سرور و DNS می‌خواهد. وردپرس یا CMS دیگر PHP، به PHP و پایگاه داده هم نیاز دارد. برنامه Node.js یا Python معمولاً پشت پراکسی معکوس اجرا می‌شود. این اجزا را می‌توانید دستی روی VPS تمیز بسازید یا با کنترل پنل از مرورگر مدیریت کنید.

این راهنما روند **از VPS تازه تا سایت فعال** را پوشش می‌دهد. اگر سایت عملیاتی با داده زنده منتقل می‌کنید، برای انتقال نهایی و بازگشت از [انتقال سایت به سرور مجازی]({{< relref "website-migration-to-vps.md" >}}) استفاده کنید.

برای تصمیم کلی خرید، [سرور مجازی برای سایت]({{< relref "_index.md" >}}) را ببینید.

## ترتیب سریع استقرار {#quick-deployment-sequence}

استقرار اولیه قابل اتکا این ترتیب را دارد:

1. **VPS را انتخاب و منابعش را تعیین کنید.**
2. **مدیریت دستی، پنل یا خدمات مدیریت‌شده را انتخاب کنید.**
3. **سیستم‌عامل تمیز یا ایمیج فعلی پنل ارائه‌دهنده را ایجاد کنید.**
4. **دسترسی اول را امن و مسیر مدیریت غیر root ایجاد کنید.**
5. **سیستم‌عامل را به‌روز کنید.**
6. **فقط پشته وب موردنیاز برنامه را نصب کنید.**
7. **تا جای ممکن پیش از تغییر DNS عمومی سایت و برنامه را تنظیم کنید.**
8. **فایل و کد را مستقر و مالکیت، اطلاعات محرمانه و دسترسی DB را تنظیم کنید.**
9. **فایروال را محدود کنید و SSH و دسترسی لازم HTTP/HTTPS را باز نگه دارید.**
10. **پیش از DNS عمومی مقصد را بیازمایید.**
11. **دامنه را به VPS اشاره دهید.**
12. **پس از رسیدن نام میزبان به سرور، HTTPS را فعال کنید.**
13. **کران، پردازشگر، لاگ، پشتیبان و پایش بیرونی را بررسی کنید.**
14. **یک‌بار ریبوت و بازگشت خودکار همه سرویس‌های لازم را تأیید کنید.**
15. **فقط پس از آن استقرار را آماده محیط عملیاتی بدانید.**

PHP، MySQL، ایمیل یا پنل را صرفاً چون راهنمای عمومی VPS آورده نصب نکنید. اجزایی را نصب کنید که سایت واقعاً نیاز دارد.

## انتخاب مدیریت دستی، پنل یا خدمات مدیریت‌شده {#choose-manual-panel-or-managed}

سه مسیر بهره‌برداری مجزا وجود دارد.

### مدیریت دستی / بدون کنترل پنل {#manual--no-control-panel}

VPS لینوکس تمیز انتخاب و پشته را از SSH اداره کنید.

مناسب است وقتی:

- پشته برنامه را می‌شناسید؛
- حداقل سرویس را می‌خواهید؛
- پیکربندی اختصاصی Nginx/Apache یا محیط اجرا لازم دارید؛
- اسکریپت، Git یا زیرساخت به‌صورت کد به کار می‌برید؛
- رابط سنتی حساب هاست لازم ندارید.

ایده قبلی **VPS بدون کنترل پنل** در همین صفحه ادغام شده است. برای همان قصد جست‌وجو URL رقیب دیگری ایجاد نمی‌کنیم.

### کنترل پنل {#control-panel}

وقتی مدیریت سایت، دامنه، PHP، پایگاه داده، ایمیل یا کاربر از مرورگر مقدار قابل‌توجهی کار تکراری را کم می‌کند، پنل هاست به کار ببرید.

[سرور مجازی با کنترل پنل]({{< relref "vps-with-control-panel.md" >}}) را ببینید. اگر FASTPANEL را انتخاب کرده‌اید، از [میزبانی سرور مجازی با FASTPANEL]({{< relref "fastpanel-vps-hosting.md" >}}) استفاده کنید.

### خدمات مدیریت {#managed-administration}

پنل و مدیریت متفاوت‌اند. اگر وصله، امنیت، پشتیبان، پایش و رخداد در تیم شما مسئول ندارند، پیش از راه‌اندازی تصمیم بگیرید.

[سرور مجازی مدیریت شده یا مدیریت نشده]({{< relref "managed-vs-unmanaged-vps.md" >}}) را ببینید.

## پیش‌نیازها {#prerequisites}

پیش از دست‌زدن به سرور این‌ها را داشته باشید:

- VPS با منابع متناسب بار؛
- نشانی IP سرور؛
- اطلاعات ورود یا کلید SSH؛
- کنسول، VNC یا مسیر بازیابی سالم ارائه‌دهنده؛
- دامنه ثبت‌شده و دسترسی DNS؛
- فایل سایت یا مخزن برنامه؛
- نسخه محیط اجرای لازم؛
- نیازمندی پایگاه داده؛
- برنامه اطلاعات محرمانه و متغیر محیطی؛
- محل پشتیبان؛
- روش بیرونی بررسی دسترس‌پذیری سایت.

اگر نیاز منابع هنوز روشن نیست، پیش از استقرار از [تعیین منابع سرور مجازی برای سایت]({{< relref "vps-sizing-for-website.md" >}}) استفاده کنید.

## انتخاب سیستم‌عامل {#choose-the-operating-system}

برای سرور سایت با مدیریت دستی، سیستم‌عاملی انتخاب کنید که:

- برنامه و محیط اجرا پشتیبانی کنند؛
- هنوز نگهداری شود؛
- مدیر شما بشناسد؛
- بسته و مستندات فعلی پشته وب داشته باشد؛
- اگر بعداً پنل می‌گیرید با نیاز آن سازگار باشد.

سیستم‌عامل را فقط به‌دلیل جدیدترین‌بودن انتخاب نکنید. سازگاری برنامه و آشنایی مدیر مهم‌تر است.

برای مثال ساده فعلی لینوکس، Ubuntu 24.04 LTS یا Debian 12 گزینه‌های معقول مستندسازی‌اند. اگر سازنده برنامه توزیع پشتیبانی‌شده دیگری مشخص کرده، همان را دنبال کنید.

## ایمن‌سازی اولین دسترسی SSH {#secure-first-ssh-access}

VPS تازه دسترسی مدیریتی می‌دهد، اما کار عملیاتی نباید همیشه با root انجام شود.

ترتیب امن دسترسی اول:

1. با اطلاعات ورود یا کلید ارائه‌دهنده وصل شوید؛
2. تأیید کنید سرور و IP همان موردی است که می‌خواستید بسازید؛
3. کنسول، VNC یا مسیر بازیابی ارائه‌دهنده را سالم نگه دارید؛
4. کاربر مدیریتی نام‌دار بسازید؛
5. فقط حقوق sudo یا مدیر لازم را بدهید؛
6. هرجا عملی است احراز هویت کلید SSH اضافه کنید؛
7. ورود جدید را در نشست دوم **پیش از** غیرفعال یا محدودکردن روش دسترسی اولیه بررسی کنید.

مثال روی Ubuntu/Debian:

```bash
ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy
```

هنگام «ایمن‌سازی» تنها مسیر مدیریتی سالم را نبندید.

ایمن‌سازی عمیق SSH و فایروال در [چک لیست امنیت سرور مجازی]({{< relref "vps-security-checklist.md" >}}) آمده است؛ این راهنما فقط حداقل لازم استقرار را نگه می‌دارد.

## پیش از نصب پشته سرور را به‌روز کنید {#update-the-server-before-installing-the-stack}

روی Ubuntu/Debian:

```bash
sudo apt update
sudo apt upgrade -y
```

اگر به‌روزرسانی ریبوت می‌خواهد، انجام دهید و سپس اتصال دوباره را بررسی کنید.

به‌روزرسانی امنیتی را تا عمومی‌شدن سایت عقب نیندازید.

## مسیر دستی / بدون کنترل پنل {#manual--no-control-panel-path}

VPS دستی فقط باید سرویس‌های موردنیاز برنامه را داشته باشد.

انتخاب‌های رایج:

### سایت ایستا {#static-website}

لازم است:

- Nginx یا Apache؛
- فایل سایت؛
- DNS؛
- HTTPS.

به‌خودی‌خود لازم نیست:

- PHP؛
- MySQL/MariaDB/PostgreSQL؛
- سرور ایمیل محلی.

### سایت PHP یا وردپرس {#php--wordpress-website}

معمولاً لازم است:

- Nginx یا Apache؛
- PHP-FPM و ماژول‌های PHP؛
- پایگاه داده؛
- فایل سایت و بارگذاری‌ها؛
- DNS؛
- HTTPS.

برای رفتار منابع وردپرس، [سرور مجازی برای وردپرس]({{< relref "vps-for-wordpress.md" >}}) را ببینید.

### Node.js، Python یا برنامه اختصاصی {#nodejs--python--custom-application}

معمولاً:

- محیط اجرای برنامه؛
- کاربر اختصاصی غیر root برنامه؛
- مدیر فرایند یا سرویس systemd؛
- اتصال برنامه به localhost یا سوکت خصوصی، هرجا عملی است؛
- پراکسی معکوس Nginx/Apache؛
- پایگاه داده فقط در صورت نیاز؛
- DNS؛
- HTTPS.

سرور توسعه را به‌عنوان معماری عملیاتی مستقیم در اینترنت عمومی قرار ندهید.

## نصب وب‌سرور {#install-the-web-server}

مستندات فعلی سرور Ubuntu هر دو Nginx و Apache را پشتیبانی می‌کند. هیچ‌کدام همیشه «بهتر» نیست.

برای مثال Nginx:

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx
```

در این مرحله اگر قواعد شبکه و فایروال HTTP را مجاز بدانند، IP سرور باید صفحه پیش‌فرض Nginx را برگرداند.

اگر برنامه، تیم یا پیکربندی موجود با Apache سازگارتر است، از آن استفاده کنید.

## تنظیم نام میزبان سایت {#configure-the-website-hostname}

DNS و پیکربندی وب‌سرور دو نیمه یک کارند.

ارائه‌دهنده DNS باید نام میزبان را به VPS اشاره دهد **و** وب‌سرور بداند کدام سایت باید پاسخ آن نام را بدهد.

برای Nginx یک بلوک سرور دامنه بسازید. ساختار مفهومی:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

در Ubuntu/Debian تنظیمات خاص سایت معمولاً اینجا قرار می‌گیرند:

- `/etc/nginx/sites-available/`
- `/etc/nginx/sites-enabled/`

پس از تغییر:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

همیشه پیش از بارگذاری مجدد، نحو پیکربندی را آزمایش کنید.

برای برنامه پشت پراکسی، بلوک سرور درخواست را به پورت یا سوکت محلی برنامه هدایت می‌کند.

## استقرار فایل یا کد برنامه {#deploy-files-or-application-code}

روش استقرار تکرارپذیر انتخاب کنید.

### SFTP/SCP {#sftpscp}

مناسب برای:

- سایت کوچک؛
- استقرار دستی کم‌تکرار؛
- پروژه ساده اولیه.

ریسک: پوشه عملیاتی به‌آسانی می‌تواند از مخزن منبع فاصله بگیرد.

### rsync از طریق SSH {#rsync-over-ssh}

برای همگام‌سازی تکرارپذیر فایل و به‌روزرسانی افزایشی کارآمد مفید است.

### استقرار مبتنی بر Git {#git-based-deployment}

وقتی انتشار عملیاتی باید با commit مخزن منطبق باشد مفید است.

### CI/CD {#cicd}

وقتی تکرار استقرار، ساخت، آزمون و انتشار خودکار را توجیه می‌کند مفید است.

هر روشی به کار می‌برید:

- با root مستقر نکنید مگر کار واقعاً نیاز داشته باشد؛
- فایل برنامه را در مالکیت کاربر مناسب استقرار یا برنامه نگه دارید؛
- فقط دسترسی لازم را به وب‌سرور بدهید؛
- اطلاعات محرمانه را خارج از ریشه عمومی اسناد نگه دارید؛
- مجوز نوشتن همگانی را میان‌بُر قرار ندهید.

## مسیر PHP یا وردپرس {#php--wordpress-path}

برای سایت PHP روی Ubuntu/Debian، بسته فعلی پشتیبانی‌شده PHP-FPM و افزونه لازم برنامه را نصب کنید.

معماری معمول:

**مرورگر -> Nginx/Apache -> PHP-FPM -> پایگاه داده**

فهرست تصادفی افزونه CMS دیگر را کپی نکنید. آنچه برنامه واقعاً نیاز دارد نصب کنید.

برای وردپرس:

- پایگاه داده و کاربر اختصاصی DB بسازید؛
- سقف بارگذاری، حافظه و زمان اجرای PHP را از نیاز اندازه‌گیری‌شده تنظیم کنید؛
- اطلاعات محرمانه `wp-config.php` را محافظت کنید؛
- نام میزبان سایت را تنظیم کنید؛
- HTTPS را فعال کنید؛
- wp-cron و کار پس‌زمینه را اعتبارسنجی کنید؛
- کش را بر پایه بار اضافه کنید.

برای منابع و کارایی به‌جای تکرار در اینجا، از [سرور مجازی برای وردپرس]({{< relref "vps-for-wordpress.md" >}}) استفاده کنید.

## مسیر Node.js، Python یا برنامه اختصاصی {#nodejs--python--custom-app-path}

فرمان توسعه را دستی در ترمینال اجرا نکنید و نام محیط عملیاتی روی آن نگذارید.

استفاده کنید از:

- کاربر اختصاصی برنامه؛
- فایل محیطی یا پیکربندی با مجوز محدود؛
- systemd یا مدیر فرایند مناسب محیط عملیاتی؛
- شروع مجدد خودکار پس از خرابی یا ریبوت؛
- شنونده محلی یا خصوصی برنامه؛
- پراکسی معکوس Nginx/Apache؛
- لاگ برنامه؛
- بررسی سلامت.

جریان معمول:

**مرورگر -> HTTPS/Nginx -> برنامه روی 127.0.0.1:PORT -> پایگاه داده یا سرویس بیرونی**

راهنمای استقرار عملیاتی خود چارچوب را بررسی کنید.

## پایگاه داده: فقط در صورت نیاز نصب کنید {#database-install-only-when-required}

سایت ایستا پایگاه داده نمی‌خواهد.

برای برنامه پویای نیازمند پایگاه داده:

- موتور پشتیبانی‌شده را نصب کنید؛
- پایگاه داده اختصاصی بسازید؛
- کاربر خاص برنامه بسازید؛
- فقط مجوز لازم بدهید؛
- اطلاعات ورود را بیرون از ریشه وب نگه دارید؛
- پورت DB را عمومی باز نکنید مگر معماری امن مشخصی نیاز داشته باشد؛
- DB را در برنامه پشتیبان و پایش بگنجانید.

کار پایگاه داده حتی با وب‌سرور تقریباً بیکار می‌تواند گلوگاه واقعی VPS باشد.

## مالکیت فایل، مجوز و اطلاعات محرمانه {#file-ownership-permissions-and-secrets}

از دو اشتباه رایج پرهیز کنید:

1. اجرای سایت با root؛
2. نوشتنی‌کردن پوشه برنامه برای همه جهت «حل» خطای مجوز.

در عوض:

- کاربر استقرار یا برنامه به کار ببرید؛
- بدانید کدام فرایند خواندن و کدام نوشتن لازم دارد؛
- به پوشه بارگذاری و کش فقط دسترسی نوشتن لازم بدهید؛
- فایل محیطی و اطلاعات ورود را محافظت کنید؛
- اطلاعات محرمانه عملیاتی را در Git ثبت نکنید؛
- کلید خصوصی را بیرون از ریشه عمومی اسناد نگه دارید.

مالکیت دقیق به برنامه و مدل وب‌سرور بستگی دارد؛ به‌جای نسخه همگانی `chmod 777` از مستندات برنامه استفاده کنید.

## آزمون پیش از DNS عمومی {#test-before-public-dns}

DNS را اولین آزمون واقعی برنامه نکنید.

پیش از انتقال عمومی، هرجا عملی است سرور جدید را با یکی از این روش‌ها بررسی کنید:

- برای بررسی ساده پیش‌فرض یا ایستا به IP سرور بروید؛
- hosts محلی را بازنویسی کنید تا `example.com` فقط روی رایانه شما به VPS جدید اشاره کند؛
- نام میزبان خصوصی یا آزمایشی به کار ببرید که اجازه ایندکس‌شدن ناخواسته به‌عنوان نسخه تکراری نداشته باشد؛
- برنامه را از همان پیکربندی نام میزبان Nginx/Apache مورد استفاده محیط عملیاتی آزمایش کنید.

بیش از صفحه اصلی را بررسی کنید:

- صفحات داخلی مهم؛
- ورود و مدیریت؛
- فرم‌ها؛
- بارگذاری‌ها؛
- فایل‌های ایستا؛
- خواندن و نوشتن پایگاه داده؛
- مسیرهای برنامه و API؛
- ریدایرکت‌ها؛
- لاگ‌ها.

آزمون hosts بسیار مفید است، چون بسیاری از برنامه‌ها با نام میزبان واقعی متفاوت از IP خام رفتار می‌کنند.

اگر سایت زنده موجود است، روند سخت‌گیرانه‌تر انتقال در [انتقال سایت به سرور مجازی]({{< relref "website-migration-to-vps.md" >}}) را به کار ببرید.

## اشاره دامنه به VPS {#point-the-domain-to-the-vps}

نزد ارائه‌دهنده DNS رکوردهایی را تنظیم کنید که باید به این سرور برسند.

تنظیم معمول IPv4:

| نام | نوع | مقدار |
|---|---|---|
| `@` | A | نشانی IPv4 سرور مجازی |
| `www` | CNAME | دامنه اصلی |

رکورد A برای `www` هم ممکن است.

فقط وقتی IPv6 روی VPS واقعاً تنظیم و قابل دسترسی است AAAA اضافه کنید. AAAA خراب می‌تواند برخی بازدیدکنندگان را دچار خطا کند، حتی وقتی IPv4 کار می‌کند.

DNS به‌تنهایی سایت را فعال نمی‌کند؛ تنظیم سایت Nginx/Apache هم باید نام میزبان منطبق داشته باشد.

اگر سایت زنده موجود را منتقل می‌کنید، تغییر DNS و رسیدگی به آخرین نوشتن‌ها در [انتقال سایت به سرور مجازی]({{< relref "website-migration-to-vps.md" >}}) آمده است.

## افزودن HTTPS پس از حل‌شدن DNS {#add-https-after-dns-resolves}

فقط پس از آنکه نام میزبان عمومی به سرور پاسخ‌گوی درخواست اعتبارسنجی اشاره کرد، گواهی معتبر بگیرید. مطمئن شوید فایروال و قواعد شبکه ارائه‌دهنده مسیر اعتبارسنجی HTTP/HTTPS موردنظر را از قبل مجاز می‌دانند.

برای Nginx/Apache، کلاینت ACME مانند Certbot می‌تواند گواهی Let's Encrypt درخواست و تمدید کند. به‌جای کپی کورکورانه فرمان بسته قدیمی، دستور فعلی Certbot و سیستم‌عامل را دنبال کنید.

تأیید کنید:

- گواهی دامنه اصلی و گونه `www` مورد استفاده را پوشش می‌دهد؛
- HTTP طبق هدف به HTTPS ریدایرکت می‌شود؛
- تمدید گواهی خودکار است؛
- تمدید می‌تواند از پیکربندی فایروال و CDN عبور کند؛
- برنامه URL درست HTTPS تولید می‌کند.

پیش از اطمینان از کارکرد مسیر گواهی، ریدایرکت HTTPS را فعال نکنید.

## تنظیم فایروال {#configure-the-firewall}

هنگام تغییر قواعد فایروال دسترسی مدیریتی را سالم نگه دارید.

سایت عمومی پایه معمولاً این‌ها را لازم دارد:

- SSH از مبدأ یا مسیر مدیریتی لازم؛
- TCP 80 برای HTTP، ACME و ریدایرکت؛
- TCP 443 برای HTTPS.

MySQL/PostgreSQL، Redis یا پورت داخلی برنامه را صرفاً چون محلی گوش می‌دهند عمومی باز نکنید.

روی سرور UFW، مسیر SSH لازم را **پیش از** فعال‌کردن قواعد محدودکننده مجاز کنید.

جزئیات عمیق فایروال و ایمن‌سازی در [چک لیست امنیت سرور مجازی]({{< relref "vps-security-checklist.md" >}}) است.

## کران، صف و پردازشگر {#cron-jobs-queues-and-workers}

سایت پویا اغلب پس از استقرار دچار مشکل می‌شود چون فقط مسیر درخواست وب تنظیم شده است.

فهرست کنید:

- کران‌ها؛
- پردازشگرهای صف؛
- اقدامات زمان‌بندی‌شده؛
- ورود و خروج داده؛
- کارهای ایمیل؛
- گرم‌کننده کش؛
- پردازشگرهای پس‌زمینه.

طوری تنظیم کنید که:

- با کاربر درست غیر root اجرا شوند؛
- در صورت نیاز خودکار شروع شوند؛
- در لاگ شناخته‌شده بنویسند؛
- هم‌پوشانی‌شان CPU و رم را تمام نکند؛
- پس از ریبوت سرور دوباره کار کنند.

## لاگ و مشاهده‌پذیری پایه {#logs-and-basic-observability}

پیش از ترافیک عملیاتی بدانید هنگام خرابی سایت کجا را باید ببینید.

دست‌کم این‌ها را مشخص کنید:

- لاگ دسترسی Nginx/Apache؛
- لاگ خطای Nginx/Apache؛
- لاگ برنامه؛
- لاگ PHP-FPM یا محیط اجرا؛
- لاگ و وضعیت پایگاه داده؛
- ژورنال سیستم؛
- مصرف دیسک؛
- فشار حافظه و CPU.

بررسی بیرونی دسترس‌پذیری HTTP(S) اضافه کنید تا حتی وقتی کسی به VPS وارد نشده، خرابی دیده شود.

طراحی دقیق آستانه و هشدار در [مانیتورینگ سرور مجازی]({{< relref "vps-monitoring.md" >}}) آمده است.

## اعتبارسنجی ریبوت {#reboot-validation}

تعداد شگفت‌آوری از استقرارهای اولیه VPS فقط تا اولین ریبوت کار می‌کنند.

پیش از آماده‌دانستن سرور:

```bash
sudo reboot
```

پس از بازگشت تأیید کنید:

- دسترسی SSH؛
- Nginx/Apache؛
- PHP-FPM یا سرویس برنامه؛
- پایگاه داده؛
- کران و پردازشگر صف؛
- HTTPS؛
- صفحات و فرم سایت؛
- پایش؛
- زمان‌بندی پشتیبان.

اگر برنامه فقط پس از اجرای دستی فرمان توسط کسی برمی‌گردد، استقرار کامل نیست.

## چه زمانی میزبانی دستی یا بدون پنل مناسب نیست؟ {#when-manual--no-panel-hosting-is-the-wrong-fit}

به‌جای آن پنل یا خدمات مدیریت به کار ببرید وقتی:

- کسی با SSH و بازیابی خط فرمان راحت نیست؛
- کسی مسئول به‌روزرسانی سیستم‌عامل و امنیت نیست؛
- کسی خرابی وب‌سرور، محیط اجرا و DB را تشخیص نمی‌دهد؛
- پشتیبان ساخته می‌شود اما کسی نمی‌تواند بازیابی کند؛
- قطعی حیاتی کسب‌وکار مسئول رخداد ندارد؛
- تیم مدیریت ایمیل، کاربر و دامنه از رابط هاست را می‌خواهد، نه پیکربندی سرور؛
- پلتفرم مدیریت‌شده برای پشته برنامه مناسب‌تر است.

VPS دستی سربار پنل را کم و کنترل را بیشتر می‌کند، اما مقدار مسئولیت عملیاتی را کم نمی‌کند.

برای انتخاب پنل [سرور مجازی با کنترل پنل]({{< relref "vps-with-control-panel.md" >}}) را ببینید؛ اگر مشکل نبود مسئول عملیات است، [سرور مجازی مدیریت شده یا مدیریت نشده]({{< relref "managed-vs-unmanaged-vps.md" >}}) را بخوانید.

## چک‌لیست پذیرش عملیاتی {#production-acceptance-checklist}

| بررسی | شرط پذیرش |
|---|---|
| دسترسی سرور | ورود مدیر نام‌دار ممکن است؛ کنسول بازیابی در دسترس است |
| به‌روزرسانی | به‌روزرسانی فعلی امنیت و سیستم اعمال شده |
| وب‌سرور | شروع خودکار و موفقیت آزمون پیکربندی |
| نام میزبان | رفتار آگاهانه دامنه اصلی و `www` |
| DNS | حل A/AAAA/CNAME به سرور و مسیر موردنظر |
| HTTPS | گواهی معتبر، نام درست و مسیر تمدید روشن |
| برنامه | صفحات نماینده، ورود، فرم و بارگذاری کار می‌کنند |
| پایگاه داده | کاربر برنامه کار می‌کند؛ پورت DB ناخواسته عمومی نیست |
| فایل | مالکیت درست؛ بدون راه‌حل موقت `777` |
| کارها | شروع و ثبت لاگ درست کران و پردازشگر |
| ریبوت | بازیابی خودکار سرویس‌های لازم |
| لاگ | مسئول می‌داند خطای وب، برنامه و سیستم کجا دیده می‌شود |

| پایش | بررسی بیرونی سایت همراه دید پایه منابع |
| ظرفیت | بررسی CPU، رم و دیسک زیر بار واقعی |

صرف برگشت HTTP 200 از صفحه اصلی، سایت را آماده عملیات نمی‌کند.

## تحویل مسئولیت پشتیبان و پایش {#backups-and-monitoring-handoff}

این صفحه فقط حداقل تحویل را مشخص می‌کند.

پیش از اتکا به سایت:

- پشتیبان را زمان‌بندی کنید؛
- نسخه مستقل و خارج سرور نگه دارید؛

- فشار CPU، رم و DB را زیر نظر بگیرید؛

## پرسش‌های متداول {#faq}

### آیا می‌توانم بدون کنترل پنل روی VPS سایت میزبانی کنم؟ {#can-i-host-a-website-on-a-vps-without-a-control-panel}

بله. VPS لینوکس تمیز با SSH و اجزای وب‌سرور، محیط اجرا و پایگاه داده لازم برنامه می‌تواند سایت میزبانی کند. موضوع بدون پنل بخشی از همین راهنماست، نه صفحه رقیب جدا.

### آیا برای میزبانی سایت روی VPS به Nginx نیاز دارم؟ {#do-i-need-nginx-to-host-a-website-on-vps}

خیر. Nginx و Apache هر دو رایج‌اند. وب‌سروری را انتخاب کنید که با برنامه، پیکربندی و تجربه مدیر سازگار است.

### آیا هر سایت VPS پایگاه داده می‌خواهد؟ {#does-every-vps-website-need-a-database}

خیر. سایت ایستا نمی‌خواهد. MySQL/MariaDB/PostgreSQL را فقط وقتی برنامه نیاز دارد نصب کنید.

### آیا سایت را با root میزبانی کنم؟ {#should-i-use-root-to-host-the-website}

خیر. root برای مدیریت است. سایت را با کاربران و سرویس‌های مناسب غیر root و فقط مجوز لازم اجرا و مستقر کنید.

### چه زمانی کنترل پنل به کار ببرم؟ {#when-should-i-use-a-control-panel}

وقتی مدیریت سایت، دامنه، PHP، DB، کاربر، ایمیل یا پشتیبان از مرورگر آن‌قدر کار تکراری را کم می‌کند که سربار و محدودیت را توجیه کند.

### آیا می‌توان وردپرس را روی VPS بدون cPanel میزبانی کرد؟ {#can-i-host-wordpress-on-a-vps-without-cpanel}

بله. وردپرس وب‌سرور سازگار، PHP، DB، فایل وردپرس، مجوز درست، DNS و HTTPS لازم دارد. پنل اختیاری است.

### چه زمانی DNS را به VPS اشاره دهم؟ {#when-should-i-point-dns-to-the-vps}

برای سایت جدید، وقتی سرور آماده پاسخ‌گویی نام میزبان واقعی است. برای سایت عملیاتی موجود ابتدا آزمایش و برنامه مهاجرت کنترل‌شده اجرا کنید.

### چرا دامنه به VPS اشاره می‌کند اما سایت اشتباه نمایش می‌دهد؟ {#why-does-my-domain-point-to-the-vps-but-show-the-wrong-site}

DNS فقط نام میزبان را به IP می‌فرستد. Nginx/Apache هم باید بلوک سرور یا میزبان مجازی منطبق برای آن نام داشته باشد.

### چه زمانی HTTPS را فعال کنم؟ {#when-should-i-enable-https}

پس از حل نام میزبان عمومی به سرور و کارکرد مسیر اعتبارسنجی. سپس گواهی بگیرید، پوشش دامنه اصلی و `www` را بررسی و ریدایرکت HTTP به HTTPS موردنظر را تنظیم کنید.

### پس از ریبوت VPS چه چیزی را بررسی کنم؟ {#what-should-i-check-after-rebooting-the-vps}

تأیید کنید وب‌سرور، سرویس برنامه یا PHP-FPM، DB، پردازشگر، HTTPS، پایش و سایت بدون دخالت دستی برمی‌گردند.
