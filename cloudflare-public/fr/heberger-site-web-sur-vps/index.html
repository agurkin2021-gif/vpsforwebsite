Comment héberger un site web sur un VPS

Comment héberger un site web sur un VPS : choisissez le déploiement, sécurisez l’accès initial, installez la pile web, reliez le domaine, activez HTTPS et vérifiez le redémarrage et la mise en production.

Comment héberger un site Web sur VPS dépend de l'application que vous déployez. Un site statique a besoin d'un serveur Web et DNS. WordPress ou un autre CMS PHP a également besoin de PHP et d'une base de données. Une application Node.js ou Python fonctionne généralement derrière un proxy inverse. Vous pouvez construire ces pièces manuellement sur un VPS propre ou utiliser un panneau de contrôle pour les gérer via un navigateur.

Ce guide couvre le parcours du VPS vierge au site en ligne. Pour déplacer un site déjà en production avec des données actives, consultez Migration d’un site web vers un VPS pour la bascule et le retour arrière.

Pour la décision d'achat plus large, voir VPS pour site web .

Séquence de déploiement rapide

Un premier déploiement fiable suit cet ordre :

  1. Choisissez et dimensionnez le VPS.
  2. Choisissez une administration manuelle, avec panneau ou infogérée.
  3. Provisionnez un système vierge ou une image actuelle de panneau fournie par l’hébergeur.
  4. Sécurisez l’accès initial et créez un accès administratif sans connexion directe en root.
  5. Mettez à jour le système d’exploitation.
  6. Installez uniquement la pile web nécessaire à l’application.
  7. Configurez le site ou l’application avant la bascule du DNS public lorsque cela est possible.
  8. Déployer des fichiers/codes et configurer la propriété, les secrets et l'accès à la base de données.
  9. Restreignez le pare-feu tout en préservant SSH et les accès HTTP/HTTPS nécessaires.
  10. Testez le serveur de destination avant de modifier le DNS public.
  11. Pointez le domaine vers le VPS.
  12. Activez HTTPS une fois que le nom d'hôte atteint le serveur.
  13. Vérifier cron/processus, journaux, sauvegardes et surveillance externe.
  14. Redémarrez une fois et vérifiez que tous les services nécessaires repartent automatiquement.
  15. Alors seulement, considérez le déploiement comme prêt pour la production.

N'installez pas PHP, MySQL, mail ou un panneau de contrôle simplement parce qu'un guide VPS générique les inclut. Installez les composants dont votre site Web a réellement besoin.

Choisir entre gestion manuelle, panneau et infogérance

Il existe trois modes d’exploitation distincts.

Manuel / pas de panneau de contrôle

Choisissez un VPS Linux propre et administrez la pile via SSH.

Adapté lorsque :

  • vous comprenez la pile d'applications;
  • vous voulez une empreinte de service minimale;
  • vous avez besoin d'une configuration personnalisée de l'environnement Nginx/Apache/execution ;
  • vous utilisez des scripts, Git ou infrastructure-as-code;
  • vous n'avez pas besoin d'une interface de compte d'hébergement traditionnelle.

Cette page regroupe l’ancien sujet VPS sans panneau de contrôle. Nous ne créons pas d’URL concurrente pour la même intention de recherche.

Panneau de contrôle

Utilisez un panneau d’hébergement lorsque la gestion dans le navigateur des sites, domaines, de PHP, des bases de données, de la messagerie ou des utilisateurs élimine une part significative du travail répétitif.

Consultez VPS avec panneau de contrôle. Si vous avez déjà choisi FASTPANEL, consultez Hébergement VPS avec FASTPANEL.

Administration infogérée

Un panneau et une prestation de gestion sont deux choses différentes. Si personne de votre côté ne prend en charge les correctifs, la sécurité, les sauvegardes, la supervision et les incidents, réglez ce point avant le lancement.

Consultez VPS infogéré ou non infogéré.

Évaluation du parcours de déploiement

Cet outil identifie le chemin de pile à examiner. Il ne remplace pas la documentation de l'application.

Sélectionnez la charge de travail et la préférence d'exploitation.

Prérequis

Avant d’intervenir sur le serveur, prévoyez :

  • un VPS dimensionné pour la charge de travail;
  • l'adresse IP du serveur;
  • les identifiants SSH ou l'accès aux clés;
  • un chemin de console/VNC/récupération de fournisseur fonctionnel;
  • un domaine enregistré et un accès DNS;
  • les fichiers du site Web ou le référentiel d'applications;
  • les versions d'environnement d'exécution requises;
  • exigences en matière de base de données;
  • un plan pour les secrets et variables d’environnement ;
  • un emplacement de sauvegarde;
  • une manière externe de tester la disponibilité du site.

Consultez Dimensionnement d’un VPS pour site web avant le déploiement si les ressources nécessaires restent incertaines.

La page VPS standard actuelle de VDSina répertorie les modèles de systèmes d'exploitation purs, y compris Ubuntu 26.04/24.04/22.04/20.04, Debian 13/12/11/10, AlmaLinux, Rocky, CentOS, Oracle Linux et ArchLinux. Ce guide utilise des exemples de style Ubuntu/Debian car la documentation du serveur Web actuel et le flux de paquets sont faciles à suivre.

Choisissez un VPS pour le site web

Transparence : l'éditeur a une relation professionnelle avec VDSina, et ce site peut gagner une commission si vous commandez via ce lien partenaire. Choisissez la taille du serveur et le modèle d'exploitation de la charge de travail, pas de la commission.

Choisissez le système d'exploitation

Pour un serveur de site Web manuel, choisissez un système d'exploitation qui :

  • est pris en charge par l'environnement d'application/exécution ;
  • est maintenue ;
  • est maîtrisé par votre administrateur ;
  • a des packages/documentation actuels pour la pile de logiciels Web;
  • correspond à n'importe quelle exigence de panneau si vous en utilisez un plus tard.

Ne choisissez pas le système d'exploitation uniquement parce qu'il est le plus récent. La compatibilité des applications et la familiarité avec l'administrateur sont plus importantes.

Pour un exemple courant de Linux simple, Ubuntu 24.04 LTS ou Debian 12 sont des cibles de documentation raisonnables. Si votre fournisseur d'application spécifie une autre distribution prise en charge, suivez cette exigence.

Sécuriser le premier accès SSH

Un nouveau VPS vous donne un accès administratif, mais le travail de production ne devrait pas avoir lieu de façon permanente en tant que root.

Une séquence sûre de premier accès est :

  1. se connecter en utilisant les identifiants / clés fournis par le fournisseur VPS;
  2. confirmer que le serveur / IP est celui que vous avez l'intention de créer;
  3. garder la console du fournisseur / VNC / route de récupération fonctionnant;
  4. créer un utilisateur administratif nommé;
  5. n’accorder que les droits sudo/admin requis ;
  6. ajouter l'authentification par clé SSH lorsque cela est possible;
  7. vérifier la nouvelle connexion dans une seconde session avant de désactiver ou de restreindre le mode d’accès initial.

Exemple sur Ubuntu/Debian :

ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy

Ne verrouillez pas le seul chemin d'administration fonctionnel tout en "durcissant" le serveur.

Le durcissement détaillé de SSH et du pare-feu est traité dans Checklist de sécurité VPS ; ce guide conserve uniquement le minimum nécessaire au déploiement.

Mettre à jour le serveur avant d'installer la pile

Sur Ubuntu/Debian :

sudo apt update
sudo apt upgrade -y

Redémarrez si la mise à jour le nécessite, puis vérifiez que vous pouvez vous reconnecter.

N’attendez pas la mise en ligne du site pour appliquer les mises à jour de sécurité.

Déploiement manuel / sans panneau de contrôle

Un VPS manuel ne doit contenir que les services dont l'application a besoin.

Les choix communs sont :

Site statique

Nécessaire :

  • Nginx ou Apache ;
  • fichiers de site Web;
  • DNS;
  • HTTPS.

Pas automatiquement nécessaire :

  • PHP;
  • MySQL / MariaDB / PostgreSQL;
  • serveur de messagerie local.

Site web PHP / WordPress

Habituellement nécessaire :

  • Nginx ou Apache ;
  • PHP-FPM / PHP modules;
  • base de données;
  • fichiers du site et fichiers téléversés ;
  • DNS;
  • HTTPS.

Pour le comportement des ressources WordPress, utilisez VPS pour WordPress .

Node.js / Python / Application personnalisée

Habituellement :

  • environnement dʼexécution dʼapplication;
  • utilisateur d'application non-root dédié;
  • gestionnaire de processus/service systemd;
  • application liée à localhost / socket privé lorsque cela est pratique;
  • Nginx/Apache proxy inverse;
  • base de données uniquement lorsque requis;
  • DNS;
  • HTTPS.

Ne pas exposer un serveur de développement directement à l'Internet public en tant qu'architecture de production.

Installer le serveur web

La documentation actuelle d’Ubuntu Server prend en charge Nginx et Apache. Aucun des deux n’est universellement « meilleur ».

Pour l'exemple Nginx :

sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

À ce stade, l'adresse IP du serveur doit renvoyer la page Nginx par défaut si les règles réseau/pare-feu autorisent HTTP.

Utilisez plutôt Apache lorsque l'application, l'équipe ou la configuration existante convient mieux à Apache.

Configurer le nom d'hôte du site Web

DNS et la configuration du serveur Web sont les deux moitiés d'une même tâche.

Le fournisseur DNS doit pointer le nom d'hôte vers le VPS, et le serveur Web doit savoir quel site doit répondre à ce nom d'hôte.

Pour Nginx, créez un bloc de serveur pour le domaine. Conceptuellement :

server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}

Sur Ubuntu/Debian, les configurations spécifiques au site vivent généralement sous :

  • /etc/nginx/sites-available/
  • /etc/nginx/sites-enabled/

Après modifications:

sudo nginx -t
sudo systemctl reload nginx

Toujours tester la syntaxe de configuration avant de recharger.

Pour une application derrière un proxy inverse, le bloc serveur relaie les requêtes vers le port ou socket local de l’application.

Déployer des fichiers ou un code d'application

Choisissez une méthode de déploiement reproductible.

SFTP/SCP

Idéal pour:

  • petits sites ;
  • déploiements manuels peu fréquents;
  • Projets simples pour la première fois.

Risque : il est facile pour le répertoire de production de s'éloigner du référentiel source.

rsync sur SSH

Utile pour la synchronisation de fichiers répétables et les mises à jour incrémentielles efficaces.

Déploiement basé Git

Utile lorsque les versions de production doivent correspondre à des commits de dépôt.

CI/CD

Utile lorsque le déploiement est suffisamment fréquent pour justifier des étapes automatisées de build/test/release.

Quelle que soit la méthode que vous utilisez :

  • ne pas déployer en tant que root à moins que la tâche n'exige réellement root ;
  • conserver les fichiers d’application détenus par un utilisateur de déploiement/d’application approprié;
  • n'accorder au serveur web que l'accès dont il a besoin;
  • garder des secrets en dehors des racines de documents publics;
  • n’utilisez pas de permissions d’écriture ouvertes à tous comme raccourci.

Chemin PHP / WordPress

Pour un site PHP sur Ubuntu/Debian, installez les paquets PHP-FPM actuellement supportés et les extensions requises pour l'application.

Architecture typique :

navigateur -> Nginx/Apache -> PHP-FPM -> base de données

Ne copiez pas une liste d'extensions aléatoire à partir d'un autre CMS. Installez ce dont l'application a réellement besoin.

Pour WordPress :

  • créer une base de données et un utilisateur DB dédié;
  • configurer les limites de téléchargement / mémoire / exécution PHP à partir des besoins mesurés;
  • protéger les secrets de wp-config.php ;
  • configurer le nom d'hôte du site;
  • activer HTTPS;
  • valider WP-Cron et les tâches de fond ;
  • ajouter une mise en cache en fonction de la charge de travail.

Utilisez VPS pour WordPress pour la taille et les performances des ressources plutôt que de les dupliquer ici.

Déploiement Node.js / Python / application personnalisée

Ne lancez pas simplement une commande de développement à la main dans un terminal pour considérer l’application en production.

Utiliser:

  • un utilisateur dʼapplication dédié;
  • environnement/fichier de configuration avec des autorisations restreintes;
  • systemd ou un gestionnaire de processus de production approprié;
  • redémarrage automatique en cas de panne/redémarrage;
  • écouteur d'application local / privé;
  • Nginx/Apache proxy inverse;
  • des journaux d'application;
  • contrôles de santé.

Flux typique :

navigateur -> HTTPS/Nginx -> application sur 127.0.0.1:PORT -> base de données/services externes

Vérifiez les propres directives de déploiement de la production du framework.

Base de données : installer uniquement si nécessaire

Un site statique n'a pas besoin de base de données.

Pour une application dynamique qui en nécessite une :

  • installer le moteur de base de données supporté;
  • créer une base de données dédiée ;
  • créer un utilisateur spécifique à lʼapplication;
  • n'accorder que les privilèges nécessaires;
  • garder les informations d'identification hors de la racine du Web;
  • n'exposez pas publiquement le port de base de données à moins qu'une architecture sécurisée spécifique ne l'exige ;
  • inclure la base de données dans les plans de sauvegarde et de surveillance.

Le travail de base de données peut devenir le véritable goulot d'étranglement VPS même lorsque le serveur Web est presque inactif.

Propriété des fichiers, autorisations et secrets

Évitez deux erreurs courantes :

  1. l'exécution du site Web en tant que root;
  2. rendre les répertoires de l’application accessibles en écriture à tous pour « corriger » les erreurs de permissions.

Au lieu de cela:

  • utiliser un utilisateur de déploiement/application;
  • comprendre quel processus nécessite un accès en lecture vs en écriture;
  • ne donner aux répertoires d'uploads/cache que l'accès en écriture dont ils ont besoin;
  • protéger les fichiers d'environnement et les informations d'identification;
  • ne pas enregistrer les secrets de production dans Git ;
  • garder des clés privées en dehors des racines de documents publics.

Le propriétaire approprié des fichiers dépend de l’application et du modèle du serveur web ; suivez la documentation applicative plutôt qu’une recette universelle chmod 777.

Test avant le DNS public

Ne faites pas du DNS le premier vrai test de l'application.

Avant la bascule publique, vérifiez le nouveau serveur avec l’une des méthodes suivantes, lorsque cela est possible :

  • accéder à l'adresse IP du serveur pour une simple vérification par défaut / statique;
  • utilisez une entrée dans votre fichier hosts local pour que example.com pointe vers le nouveau VPS uniquement sur votre ordinateur ;
  • utiliser un nom d'hôte privé/de test qui n'est pas autorisé à devenir un duplicata indexé accidentel;
  • Testez l'application via la même configuration de nom d'hôte Nginx/Apache que celle utilisée en production.

Vérifiez plus que la page d'accueil:

  • pages internes importantes;
  • login/admin;
  • les formulaires;
  • téléversements ;
  • ressources statiques ;
  • la base de données lit/écrit;
  • les points d'extrémité de l'application/API;
  • redirections ;
  • journaux.

Un test de fichier hôte est particulièrement utile car de nombreuses applications se comportent différemment sous le nom d'hôte réel que sous l'IP du serveur brut.

Pour un site déjà en ligne, suivez la procédure de bascule plus stricte de Migration d’un site web vers un VPS.

Pointer le domaine vers le VPS

Au fournisseur DNS, configurez les enregistrements qui doivent atteindre ce serveur.

Configuration IPv4 typique :

NomTypeValeur
@AAdresse IPv4 VPS
wwwCNAMEdomaine racine

Un enregistrement A pour www est également possible.

Ajouter un enregistrement AAAA uniquement si IPv6 est réellement configuré et accessible sur le VPS. Un enregistrement AAAA cassé peut faire échouer certains visiteurs même lorsque IPv4 fonctionne.

Le DNS seul ne fait pas fonctionner le site Web : la configuration du site Nginx/Apache doit également avoir le nom d'hôte correspondant.

Pour déplacer un site déjà en production, la bascule DNS et les dernières écritures sont traitées dans Migration d’un site web vers un VPS.

Ajouter HTTPS après résolution DNS

Obtenez un certificat de confiance uniquement après que le nom d’hôte public pointe vers le serveur qui répondra à la demande de validation. Assurez-vous que les règles du pare-feu et du réseau du fournisseur autorisent déjà le mécanisme de validation HTTP/HTTPS prévu.

Pour Nginx/Apache, un client ACME tel que Certbot peut demander et renouveler des certificats Let’s Encrypt. Suivez les instructions Certbot/OS actuelles plutôt que de copier aveuglément une ancienne commande de paquetage.

Vérifier :

  • le certificat couvre les variantes racine et www que vous utilisez;
  • HTTP redirige vers HTTPS comme prévu;
  • le renouvellement du certificat est automatisé;
  • le renouvellement peut passer par la configuration firewall/CDN;
  • l'application génère les URL HTTPS correctes.

N'activez pas une redirection HTTPS avant de savoir que le chemin du certificat fonctionne.

Configurer le pare-feu

Gardez l'accès administratif fonctionnel tout en modifiant les règles du pare-feu.

Un site Web public de base a généralement besoin:

  • SSH à partir de la source/chemin d'administration requis;
  • TCP 80 pour HTTP/ACME/redirects;
  • TCP 443 pour HTTPS.

N'exposez pas publiquement MySQL/PostgreSQL, Redis ou les ports d'application internes simplement parce qu'ils écoutent localement par défaut.

Sur un serveur utilisant UFW, autorisez l’accès SSH nécessaire avant d’activer les règles restrictives.

Le pare-feu et le durcissement détaillés sont traités dans Checklist de sécurité VPS.

Tâches cron, files d’attente et processus de traitement

Les sites Web dynamiques échouent souvent après le déploiement car seul le chemin de requête Web a été configuré.

Inventaire:

  • tâches cron;
  • processus de file d'attente;
  • les actions programmées;
  • les importations/exportations;
  • tâches par courrier électronique;
  • préchargements du cache ;
  • processus de fond.

Veillez à ce qu’ils puissent :

  • s'exécuter en tant qu'utilisateur non root correct;
  • démarrer automatiquement si nécessaire;
  • écrire sur des journaux connus;
  • éviter des chevauchements qui épuiseraient CPU et RAM ;
  • Survivre au redémarrage du serveur.

Journaux et observabilité de base

Avant le trafic de production, savoir où regarder lorsque le site échoue.

Au minimum, identifier :

  • journal d'accès Nginx/Apache;
  • journal des erreurs Nginx/Apache;
  • journal d'application;
  • journal de l'environnement PHP-FPM/execution;
  • journal/état de la base de données;
  • journal système;
  • utilisation du disque;
  • pression mémoire/CPU.

Ajoutez une vérification de disponibilité HTTP(S) externe pour qu'une défaillance du serveur soit visible même lorsque personne n'est connecté au VPS.

Les seuils et alertes détaillés sont traités dans Supervision VPS.

Validation du redémarrage

Un nombre surprenant de premiers déploiements VPS fonctionnent jusqu'au premier redémarrage.

Avant d'appeler le serveur prêt:

sudo reboot

Après son retour, confirmez :

  • accès SSH ;
  • Nginx/Apache;
  • PHP-FPM ou service d'application;
  • base de données;
  • processus cron/queue;
  • HTTPS;
  • pages/formulaires du site Web;
  • supervision ;
  • calendrier de sauvegarde.

Si l'application ne revient qu'après que quelqu'un lance manuellement une commande, le déploiement n'est pas terminé.

Quand l'hébergement manuel / sans panneau est le mauvais choix

Utilisez plutôt un panneau de contrôle ou une administration gérée lorsque :

  • personne n'est à l'aise avec SSH et la récupération en ligne de commande;
  • personne ne prend en charge les mises à jour de sécurité et du système ;
  • personne ne peut diagnostiquer les pannes du serveur web, de l’environnement d’exécution ou de la base de données ;
  • les sauvegardes sont créées mais personne ne peut les restaurer ;
  • personne n’est désigné pour intervenir lors d’une indisponibilité critique ;
  • l'équipe veut que les mails/utilisateurs/domaines soient gérés via une interface utilisateur d'hébergement plutôt qu'une configuration de serveur ;
  • la pile d'applications est mieux servie par une plateforme gérée.

Un VPS manuel peut réduire la consommation de ressources supplémentaires du panneau et maximiser le contrôle, mais il ne réduit pas le niveau de responsabilité opérationnelle.

Consultez VPS avec panneau de contrôle pour choisir un panneau, ou VPS infogéré ou non infogéré si la responsabilité de l’exploitation n’est pas attribuée.

Un site Web n'est pas prêt pour la production simplement parce que la page d'accueil renvoie HTTP 200.

Relais vers les sauvegardes et la supervision

Cette page définit seulement les dispositions minimales de ce relais.

Avant de se fier au site :

  • planifier les sauvegardes;
  • conserver une copie indépendante / hors serveur;
  • inclure la base de données et la configuration / les secrets nécessaires à la récupération;
  • vérifier la capacité de restauration;
  • surveiller la disponibilité du site Web;
  • surveiller la croissance du disque;
  • surveiller la pression CPU/RAM/base de données;
  • surveiller le renouvellement des certificats.

La conception détaillée de la reprise est traitée dans Stratégie de sauvegarde VPS. Les seuils et les alertes relèvent de Supervision VPS.

Plusieurs sites web

Pour plusieurs sites :

  • utiliser un bloc serveur / hôte virtuel séparé par nom d'hôte;
  • racines séparées du document;
  • utiliser des informations d'identification d'application/base de données distinctes;
  • utiliser des utilisateurs du système distincts lorsque le modèle de confiance l'exige;
  • éviter que les cron/import/backups d’un site n’affament les autres ;
  • tenir compte de la charge de pointe combinée;
  • comprendre que tous les sites partagent encore un domaine de défaillance VPS.

Consultez VPS pour plusieurs sites web pour planifier la capacité et l’isolation.

FAQ

Puis-je héberger un site web sur un VPS sans panneau de contrôle ?

Oui. Un VPS Linux propre peut héberger un site Web avec SSH plus les composants de serveur Web / environnement d'exécution / base de données dont l'application a besoin. Cette intention sans panneau fait partie de ce guide plutôt que d'une page concurrente distincte.

Ai-je besoin de Nginx pour héberger un site web sur VPS ?

Non. Nginx et Apache sont deux choix courants. Utilisez le serveur Web qui correspond à l'application, à la configuration et à l'expérience administrateur.

Chaque site VPS a-t-il besoin d’une base de données ?

Non. Les sites statiques n'en ont pas besoin. Installez MySQL/MariaDB/PostgreSQL uniquement lorsque l'application nécessite une base de données.

Dois-je utiliser root pour héberger le site ?

Non. Root est destiné à l'administration. Exécutez/déployez le site Web sous les utilisateurs et services non root appropriés avec uniquement les autorisations dont ils ont besoin.

Quand dois-je utiliser un panneau de contrôle?

Utilisez-en un lorsque la gestion par navigateur de sites, domaines, PHP, bases de données, utilisateurs, courrier ou sauvegardes supprime suffisamment d'administration répétitive pour justifier la consommation de ressources et les contraintes supplémentaires.

Puis-je héberger WordPress sur un VPS sans cPanel ?

Oui. WordPress a besoin d’un serveur Web compatible, PHP, d’une base de données, des fichiers WordPress, des autorisations correctes, DNS et HTTPS. Un panneau est facultatif.

Quand dois-je pointer le DNS vers le VPS ?

Pour un nouveau site, une fois que le serveur est prêt à répondre au vrai nom d'hôte. Pour un site de production existant, testez d'abord et utilisez un plan de bascule / migration contrôlé.

Pourquoi mon domaine pointe-t-il vers le VPS mais affiche-t-il le mauvais site ?

DNS envoie uniquement le nom d'hôte à l'adresse IP du serveur. Nginx/Apache doit également avoir un bloc de serveur/hôte virtuel correspondant pour ce nom d'hôte.

Quand dois-je activer HTTPS ?

Une fois que le nom d’hôte public pointe vers le serveur et que la validation fonctionne. Émettez alors le certificat, vérifiez la couverture du domaine racine et de www, puis configurez la redirection HTTP vers HTTPS prévue.

Que dois-je vérifier après avoir redémarré le VPS ?

Confirmez que le serveur web, le service applicatif ou PHP-FPM, la base de données, les processus, HTTPS, la supervision et le site redémarrent tous sans intervention manuelle.
