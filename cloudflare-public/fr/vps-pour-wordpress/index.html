Les prérequis WordPress ne définissent pas les ressources du VPS

WordPress.org recommande actuellement un hôte qui prend en charge:

  • PHP 8.3 ou supérieur;
  • MariaDB 10.11+ ou MySQL 8.0+;
  • HTTPS;
  • Apache ou Nginx comme choix de serveur web recommandé.

Ces prérequis répondent à la question « ce serveur peut-il exécuter WordPress ? » Ils ne répondent pas à « quelles ressources VPS cette charge de production nécessite-t-elle ? »

Un VPS de production a également besoin de RAM/CPU/stockage pour :

  • Linux;
  • Nginx/Apache;
  • les processus PHP-FPM ;
  • MySQL/MariaDB;
  • OPcache;
  • cache page/objet où utilisé;
  • panneau de contrôle;
  • messagerie, si elle est hébergée localement ;
  • sauvegardes;
  • tâches cron;
  • analyses antimalware et de sécurité ;
  • les importations/exportations;
  • supervision ;
  • marge de capacité opérationnelle.

N’utilisez pas les exigences du logiciel WordPress comme recommandation de ressources de production.

Quand WordPress a réellement besoin d’un VPS

Un site WordPress peut justifier un VPS même sans trafic considérable.

Raisons communes :

  • des limites répétées CPU/mémoire/processus sous charge légitime;
  • besoin d'une configuration d'environnement PHP/exécution personnalisée;
  • besoin de Redis/Memcached ou d'un autre service côté serveur;
  • véritable cron système au lieu d’une planification déclenchée par les visiteurs ;
  • tâches de fond de longue durée;
  • comportement personnalisé Nginx/Apache;
  • plusieurs sites qui ont besoin d’un environnement contrôlé;
  • une plus grande isolation de la charge de travail/compte;
  • surveillance au niveau du serveur ou pare-feu.

Si le seul symptôme est « le site est lent », comparez d’abord VPS et hébergement mutualisé et vérifiez que WordPress lui-même n’est pas le goulot d’étranglement.

Quand WordPress n’a pas besoin d’un VPS

Restez sur un bon hébergement WordPress mutualisé ou infogéré lorsque :

  • le site est léger et stable;
  • le cache fonctionne efficacement ;
  • les compteurs de ressources de l’hôte ne montrent pas de limites répétées;
  • aucun service personnalisé / accès root n'est requis;
  • l'équipe ne veut pas maintenir Linux ;
  • le fournisseur gère déjà suffisamment bien les sauvegardes, la sécurité, les mises à jour ou l'environnement de test;
  • le VPS remplacerait principalement un simple service d'hébergement par un travail plus opérationnel.

Un VPS n’est pas automatiquement plus rapide. Un VPS mal dimensionné ou mal réglé peut faire fonctionner WordPress moins bien qu’une bonne plateforme infogérée.

Processus PHP et RAM

Pour les requêtes non mises en cache, les processus PHP-FPM sont une limite de concurrence majeure.

Chaque processus actif consomme de la mémoire pendant le traitement d'une demande. Plus de processus peuvent gérer des demandes dynamiques simultanées, mais augmenter le nombre de processus sans augmenter le budget de RAM peut causer:

  • utilisation du swap ;
  • pression mémoire;
  • arrêts de processus par manque de mémoire (OOM) ;
  • manque de ressources pour la base de données ;
  • Instabilité du serveur.

Un modèle pratique est :

RAM WordPress = système d’exploitation + serveur web + base de données + cache + processus PHP + panneau/messagerie/tâches + marge

Ensuite:

Nombre de processus PHP possible = RAM disponible pour PHP sans risque / mémoire moyenne mesurée par processus

Ne configurez pas le nombre maximum théorique de processus si cela ne laisse aucune mémoire pour MySQL/MariaDB, le cache ou le système d'exploitation.

Les utilisateurs connectés, wp-admin, les requêtes REST/API, la recherche, les formulaires, la prévisualisation et les pages personnalisées sont plus susceptibles de contourner le cache pleine page et de consommer des processus PHP.

Les couches de cache de WordPress

La mise en cache ne se résume pas à une seule fonction.

CoucheÉléments mis en cacheEffet principal
PHP OPcachebytecode PHP compiléévite de recompiler des scripts PHP sur chaque requête
Cache de pagerendu HTMLpermet à de nombreuses pages vues anonymes de contourner le travail WordPress / PHP
Cache d'objet persistantobjets réutilisables/résultats de requêteréduit le travail répété de base de données/application
Cache navigateur/CDNcontenu statique ou diffusable en périphérie du réseauréduit les transferts et requêtes répétés vers le serveur d’origine

La documentation d’optimisation de WordPress recommande la mise en cache comme outil de performance majeur, mais ces couches résolvent différents problèmes.

N'appelez pas Redis un cache de page. Redis est couramment utilisé comme moteur de cache d'objets persistants ; la mise en cache pleine page est une couche séparée.

Cache objet persistant et Redis

WordPress inclut une API de cache d’objets, mais le cache par défaut ne persiste pas d’une requête à l’autre.

La mise en cache d’objets persistants nécessite un backend / drop-in externe tel que Redis ou Memcached plus l’intégration WordPress appropriée.

Cela peut aider lorsque le site effectue à plusieurs reprises un travail coûteux sur les bases de données / objets, mais ce n'est pas un bouton de vitesse automatique.

Avant d'ajouter Redis:

  • confirmer les avantages de la charge de travail du site/base de données;
  • vérifier qu'il reste suffisamment de RAM pour PHP et la base de données ;
  • surveiller le taux de réussite et la mémoire;
  • Conserver la mise en cache de la page comme une décision distincte.

Un site doté d’un cache pleine page efficace et sollicitant peu la base de données peut moins bénéficier de Redis qu’un espace membres dynamique ou un site effectuant de nombreuses requêtes.

Besoins de la base de données

Les performances de WordPress peuvent être limitées par la base de données avant que le processeur ne soit visiblement saturé.

Vérifier:

  • requêtes lentes;
  • grandes options/données chargées automatiquement;
  • métadonnées de plugin;
  • requêtes de recherche, de filtrage et de rapports ;
  • charges sollicitant fortement les métadonnées postmeta ;
  • un ensemble de données de base de données conservées en mémoire;
  • écritures concurrentes;
  • les importations/exportations;
  • latence de stockage.

Plus de CPU ne répare pas une requête pathologique. Plus de RAM peut aider lorsque la base de données a légitimement besoin d'un ensemble de données plus important conservé en mémoire, mais il ne remplace pas l'indexation / la requête / le travail de plug-in.

Mesurez d'abord, puis dimensionnez.

Plugins, thèmes et tâches en arrière-plan

Un plugin n’est pas seulement de l’espace disque.

Les plugins/thèmes peuvent ajouter :

  • traitements PHP ;
  • les requêtes de base de données;
  • les appels API externes ;
  • tâches planifiées;
  • l'invalidation du cache;
  • requêtes AJAX d’administration ;
  • traitement d'image;
  • analyse de sécurité;
  • sauvegardes;
  • les importations/exportations;
  • analyse et journalisation.

Les tâches lourdes peuvent entrer en collision avec le trafic réel.

Planifiez des sauvegardes, des analyses, des importations et des tâches de traitement d'images en dehors des périodes de pointe lorsque cela est pratique. Si un plugin ou une tâche provoque le pic de ressource, corrigez-le ou reprogrammez-le avant de supposer que le VPS est trop petit.

WP-Cron et les tâches de fond

WP-Cron est déclenché par des requêtes WordPress plutôt que de fonctionner en continu comme un planificateur système.

Cela peut convenir aux sites ordinaires. Pour les charges importantes ou sensibles aux délais, la documentation développeur de WordPress décrit l’utilisation du planificateur du système d’exploitation pour déclencher cron WordPress à intervalles maîtrisés.

Si vous passez à un planificateur système :

  • créer le déclencheur de remplacement en premier;
  • vérifier qu'il fonctionne;
  • ne désactivez le comportement normal de WP-Cron déclenché par le visiteur que si cela fait partie du plan;
  • enregistrer et surveiller les tâches échouées.

Ne désactivez pas WP-Cron sans un autre planificateur.

Stockage, médias, environnement de test et sauvegardes

La planification des disques doit inclure plus que le noyau WordPress.

Budget pour :

  • fichiers téléversés et médias ;
  • base de données;
  • plugins/thèmes ;
  • les journaux;
  • fichiers de cache;
  • fichiers de mise à jour temporaire;
  • espace temporaire pour le traitement des images ;
  • copie de l'environnement de test;
  • archives de sauvegarde avant leur transfert hors du serveur ;
  • croissance attendue.

Un site utilisant 20 GB aujourd'hui peut avoir besoin de plus d'espace temporaire lors d'une tâche de clonage, de restauration, de mise à jour du plugin ou de compression de sauvegarde.

Ne gardez pas la seule sauvegarde sur le VPS.

Manuel, panneau de contrôle ou FASTPANEL?

WordPress peut parfaitement fonctionner sans cPanel ou un autre panneau.

Linux manuel

Adapté si vous souhaitez :

  • une pile minimale ;
  • une administration par SSH ;
  • Configuration personnalisée Nginx/Apache/PHP/base de données;
  • une automatisation ou un déploiement fondé sur Git.

Consultez Comment héberger un site web sur un VPS pour le déploiement manuel.

Panneau de contrôle générique

Utile lorsque la gestion des domaines, de SSL, de PHP, des bases de données, des utilisateurs, de la messagerie ou des sauvegardes dans le navigateur élimine suffisamment de tâches répétitives.

Consultez VPS avec panneau de contrôle.

FASTPANEL

Le flux de travail officiel de FASTPANEL prend en charge la création de sites WordPress. VDSina répertorie actuellement FASTPANEL sur Ubuntu 22 comme option de panneau préconfigurée.

Consultez Hébergement VPS avec FASTPANEL pour l’installation et le dimensionnement propres à ce panneau.

Un panneau de contrôle simplifie l'administration ; il ne gère pas le VPS.

VPS WordPress infogéré ou autogéré

Sur un VPS autogéré, quelqu’un doit prendre en charge :

  • les mises à jour du système d’exploitation et des paquets ;
  • SSH/pare-feu;
  • Mises à jour PHP / serveur Web;
  • administration de la base de données;
  • Mises à jour WordPress / plugin / thème;
  • les sauvegardes et les tests de restauration ;
  • supervision ;
  • incidents.

Si personne ne prend en charge ces tâches, choisissez l’infogérance plutôt que de supposer que WordPress ou un panneau de contrôle administrera le serveur.

Consultez VPS infogéré ou non infogéré.

WooCommerce est une charge de travail WordPress différente

WooCommerce partage la pile WordPress, mais se comporte différemment sous le trafic réel d’une boutique.

Le panier, le passage de commande, les comptes, les commandes, le stock et de nombreuses actions planifiées sont dynamiques : ils ne se traitent pas comme des pages de blog anonymes mises en cache.

Si les transactions de la boutique sont importantes, consultez VPS pour WooCommerce pour le modèle de dimensionnement et d’exploitation dédié.

Plusieurs sites WordPress

Plusieurs sites WordPress partagent :

  • CPU;
  • RAM;
  • service de base de données;
  • processus et pools PHP ;
  • stockage;
  • créneaux des tâches cron et de fond ;
  • temps de sauvegarde;
  • domaine de défaillance.

Dix sites peu sollicités avec un cache efficace peuvent être plus légers qu’un espace membres dynamique très actif.

Utilisez des utilisateurs et des identifiants de base de données distincts lorsque cela convient, et dimensionnez selon la pointe cumulée, pas selon le nombre de domaines.

Consultez VPS pour plusieurs sites web.

Quand augmenter les ressources d’un VPS WordPress

Mise à niveau uniquement après avoir mesuré une contrainte réelle.

Déclencheurs puissants :

  • pression RAM soutenue, utilisation du swap ou événements OOM ;
  • une file d'attente/saturation de processus PHP répétée;
  • saturation CPU soutenue après optimisation cache/requête/plugin;
  • latence de la base de données causée par une pression de travail légitime;
  • croissance du stockage au-delà de la marge de capacité d'exploitation sûre;
  • tâches de fond entrant en collision à plusieurs reprises avec le trafic en direct;
  • plusieurs sites actifs épuisant les ressources partagées.

Si le site Web est lent alors que ces signaux restent sains, un VPS plus grand peut ne pas être la solution.

FAQ

De combien de RAM WordPress a-t-il besoin sur un VPS?

Le cœur de WordPress ne définit pas un besoin de RAM VPS pour la production. La RAM doit couvrir Linux, le serveur web, les processus PHP, la base de données, les caches, le panneau, la messagerie, les tâches de fond et une marge. Un site léger peut tenir dans 2 GB ; 4 GB constituent une base pratique plus confortable pour un site professionnel.

Est-ce que 1 GB de RAM est suffisant pour WordPress VPS?

Il peut exécuter une configuration WordPress très légère / test, mais laisse peu de marge de capacité pour la base de données, les processus PHP et le travail en arrière-plan. Il ne doit pas être traité comme la recommandation de production normale.

Est-ce que 2 GB de RAM suffisent pour WordPress ?

Cela peut suffire pour un petit site avec un cache efficace et une pile légère. Surveillez la mémoire des processus PHP, la RAM de la base de données, les extensions et les tâches de fond.

Est-ce que 4 GB de RAM suffisent pour WordPress ?

Pour de nombreux sites WordPress professionnels, 4 GB constituent un point de départ pratique. Des extensions lourdes, un espace membres actif, WooCommerce, de grandes bases de données, des imports ou plusieurs sites actifs peuvent nécessiter davantage de ressources.

Combien de visiteurs un VPS WordPress peut-il gérer?

Il n’existe pas de nombre universel de visiteurs fiable. Le taux de succès du cache, les requêtes simultanées non servies par le cache, leur durée dans PHP, le coût des extensions, le travail de la base de données et les tâches de fond déterminent la capacité.

Ai-je besoin de Redis pour WordPress sur VPS?

Non, Redis peut fournir une mise en cache d’objets persistante lorsque la charge de travail bénéficie de la mise en cache répétée d’objets / bases de données, mais elle n’est pas requise pour tous les sites WordPress et ne remplace pas la mise en cache pleine page.

Dois-je utiliser Nginx ou Apache pour WordPress VPS?

Les deux conviennent. WordPress.org recommande Apache ou Nginx comme solutions robustes. Utilisez la pile que votre application et votre administrateur peuvent exploiter de manière fiable.

Devrais-je remplacer WP-Cron par cron système ?

Uniquement lorsque la charge de travail bénéficie d'un planificateur contrôlé et que vous configurez un remplacement fonctionnel. Ne désactivez pas WP-Cron sans un autre déclencheur.

WordPress VPS a-t-il besoin d’un panneau de contrôle ?

Non. WordPress peut fonctionner sur un VPS Linux géré manuellement. Un panneau est facultatif et doit être choisi pour la commodité de l'administration, pas comme une exigence de performance.

VDSina inclut-il WordPress préinstallé ?

La page VPS standard actuelle ne répertorie pas WordPress comme une application dédiée préinstallée dans les groupes de modèles / applications visibles. Vérifiez l'écran de commande en direct avant de supposer la disponibilité du modèle.
