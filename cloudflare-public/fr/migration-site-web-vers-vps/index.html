Migration d’un site web vers un VPS

Migration d’un site web vers un VPS : inventoriez la pile actuelle, testez le serveur, maîtrisez les dernières écritures et la bascule DNS, préservez les e-mails et le SEO, et prévoyez un retour arrière.

La migration d’un site web vers un VPS est plus sûre lorsque le nouveau serveur est préparé et testé pendant que l’ancien hébergement continue à servir le trafic. Inventoriez la pile actuelle, dimensionnez la destination, copiez et validez le site, maîtrisez les dernières modifications des données, effectuez la bascule DNS en dernier, puis surveillez les deux environnements jusqu’à pouvoir retirer l’ancien hébergement.

Cette page suppose que la structure du domaine et de l'URL publique reste identique. Si le ou les domaines changent également, le mappage d'URL et les redirections permanentes deviennent une tâche de migration distincte.

Pour la décision d'hébergement plus large, voir VPS pour site web .

Plan de migration rapide

Une migration maîtrisée suit cet ordre :

  1. Inventaire de la source. Enregistrez l'application, l'environnement d'exécution, la base de données, les fichiers, le DNS, le courrier, les tâches cron, les processus, les webhooks et les dépendances externes.
  2. Dimensionnez la destination. Choisissez CPU, RAM et disque à partir de la charge de travail réelle et de la marge de capacité de migration.
  3. Créer une sauvegarde récupérable. Conservez une copie en dehors du serveur source et vérifiez que la base de données et les fichiers dont vous avez besoin sont bien présents.
  4. Construisez le VPS en parallèle. Installez la pile de logiciels Web ou le panneau de contrôle et faites correspondre les exigences de l'application avant que le trafic ne se déplace.
  5. Copiez le premier jeu de données complet. Transférez des fichiers et importez la base de données tant que l'ancien site reste actif.
  6. Testez en privé. Utilisez une substitution de fichier hôte, un nom d'hôte d'aperçu contrôlé ou une méthode équivalente pour exercer le nouveau serveur avant que DNS ne change.
  7. Maîtrisez les dernières écritures. Pour les boutiques, espaces membres, formulaires et autres sites évolutifs, prévoyez un bref gel des écritures ou une synchronisation finale des modifications adaptée à l’application.
  8. Effectuez la bascule DNS en dernier. Ne modifiez que les enregistrements nécessaires et conservez les enregistrements de messagerie et de vérification intacts.
  9. Surveillez les deux serveurs. Vérifiez le trafic, les erreurs, les formulaires, les commandes, les tâches cron, les webhooks, les e-mails, HTTPS et l'exploration de recherche.
  10. Retirez l’ancien hébergement seulement après validation. Gardez-le disponible pendant la période prévue pour le retour arrière.

Il n’existe pas de promesse universelle honnête de migration sans interruption. L’objectif est une bascule maîtrisée, avec l’interruption minimale réalisable et sans perte de données imprévue.

Vérifications préalables à la bascule

Utilisez cette évaluation avant de changer de DNS. Elle ne garantit pas une migration réussie ; elle expose les prérequis manquants qui devraient être résolus en premier.

Marquez les éléments qui sont réellement prêts.

Inventaire du site actuel

Créez un enregistrement de migration avant de toucher la destination.

Consignez :

  • domaine et chaque sous-domaine actif;
  • version de l’application, du CMS ou du framework ;
  • PHP, Node.js, Python ou autre version d'environnement d'exécution;
  • moteur/version de base de données, taille et modèle d'informations d'identification;
  • la racine du document et les répertoires en dehors de celui-ci;
  • uploads/médias et répertoires inscriptibles;
  • règles de redirection et de réécriture ;
  • cron tâches, files d'attente, processus et tâches planifiées;
  • la mise en cache de services tels que Redis, le cas échéant;
  • Configuration SSL/TLS;
  • les enregistrements DNS;
  • boîtes aux lettres, redirections de messagerie et circuit SMTP sortant ;
  • passerelles de paiement, webhooks et rappels API ;
  • les listes d'autorisation IP de tiers;
  • Restrictions CDN/WAF/origine;
  • analytique et vérification Search Console ;
  • l’utilisation et la croissance actuelles du stockage.

L'inventaire est également la liste de contrôle d'acceptation après le déménagement: chaque élément doit soit travailler sur le VPS, soit être délibérément laissé sur un service externe.

Dimensionner et préparer le VPS de destination

Ne migrez pas d'abord et demandez si le VPS est assez grand par la suite.

Choisissez la destination selon la charge actuelle, le comportement de la base de données, la croissance du stockage, les ressources supplémentaires consommées et l’espace de travail nécessaire à la migration. La migration elle-même peut nécessiter un espace disque temporaire pour les archives, les exports de bases de données, les journaux et la préparation locale des sauvegardes.

Utilisez Dimensionnement d’un VPS pour site web pour le calcul des ressources, plutôt que de le reproduire ici.

Une migration implique aussi un choix de mode d’administration. Si l’ancien hébergement prenait en charge l’essentiel de l’administration du serveur, décidez d’abord qui exploitera la destination après la bascule : comparez VPS infogéré ou non infogéré. Décidez ensuite si la destination utilisera un panneau de contrôle ou une pile Linux administrée manuellement ; consultez VPS avec panneau de contrôle pour ce choix.

Créer une sauvegarde permettant un retour arrière

Une sauvegarde n'est utile que si elle contient les données dont vous avez besoin et peut être restaurée.

Avant la migration :

  1. créer une nouvelle copie des fichiers du site Web;
  2. exporter chaque base de données requise;
  3. stocker une copie en dehors du compte d'hébergement source;
  4. enregistrer les fichiers de configuration et les variables d'environnement en toute sécurité;
  5. enregistrer les enregistrements DNS et de courrier séparément;
  6. restaurer la sauvegarde dans un environnement jetable / test lorsque cela est pratique, ou au minimum effectuer une véritable importation de base de données et vérifier les fichiers représentatifs au lieu de vérifier uniquement que l'archive s'ouvre;
  7. confirmer que la copie restaurée contient les données attendues et démarre suffisamment pour permettre le retour arrière ;
  8. rédiger la procédure de retour arrière avant de modifier le DNS.

Pour un site dynamique, la première sauvegarde n’est pas le jeu de données final de production. Les commandes, soumissions de formulaires, commentaires, inscriptions ou fichiers téléversés peuvent continuer à changer après la première copie. Planifiez séparément la synchronisation finale des modifications.

Construisez la destination avant les modifications DNS

La destination doit être en mesure d'exécuter le site avant que le trafic public n'arrive.

Correspondre ou valider délibérément :

  • comportement du serveur Web;
  • PHP/Node/Python ;
  • extensions/modules requis;
  • moteur/version de base de données;
  • la propriété et les permissions des fichiers;
  • limites de téléversement et de taille du corps des requêtes ;
  • environnement de tâches planifiées;
  • les services de cache;
  • réécrire / rediriger les règles;
  • variables d'environnement et secrets;
  • Besoins SMTP/réseau sortant;
  • règles de pare-feu;
  • Chemins spécifiques à l'application.

N'utilisez pas la migration elle-même comme le moment de mettre à niveau chaque environnement d'exécution ou de réécrire la pile à moins que ce changement ne soit nécessaire. Moins de modifications simultanées facilitent le retour à l'état précédent et le diagnostic.

Copier les fichiers et la base de données

La méthode de transfert exacte dépend de l'accès à la source.

Les chemins sources typiques incluent :

  • Exportations cPanel/Gestionnaire de fichiers + phpMyAdmin;
  • SFTP/FTP lorsque l'accès au shell n'est pas disponible ;
  • SSH / rsync lorsque les deux côtés le permettent;
  • outils de migration applicatifs pour les déplacements spécifiques aux CMS;
  • Outils d'exportation/de sauvegarde du fournisseur.

Conservez les fichiers de configuration cachés tels que les règles de réécriture là où l'application en a besoin. Après l'importation, vérifiez l'utilisateur de la base de données, les privilèges, les hypothèses de jeu de caractères/collation et les paramètres de connexion de l'application.

Pour les grands ensembles de données, comparez les tailles, le nombre de lignes ou les sommes de contrôle lorsque cela est pratique au lieu de supposer que «transfert terminé» signifie que «l'ensemble de données est identique».

Testez en privé avant la bascule

Ne pointez pas le DNS sur un serveur non testé.

Testez la destination avec un fichier hosts-override, un nom d'hôte de prévisualisation contrôlé ou une autre méthode privée qui exerce la pile d'applications réelle.

Vérifier:

  • page d'accueil et pages internes représentatives;
  • connexion administrateur;
  • connexion de l'utilisateur;
  • images, CSS, JavaScript et téléchargements;
  • recherche;
  • les formulaires et la livraison;
  • téléversements ;
  • redirections ;
  • les points de terminaison API;
  • le passage de commande et les rappels de paiement;
  • actions cron/programmées;
  • files d'attente/processus;
  • courrier sortant;
  • les journaux d'application, de serveur Web et de base de données;
  • affichage sur mobile et dans les navigateurs.

Un nom d'hôte public temporaire ne doit pas devenir un duplicata accidentel dans la recherche. S'il est accessible publiquement pendant le test, gardez-le hors de l'index et supprimez le blocage temporaire du nom d'hôte de production réel avant la bascule.

Contrôler les nouvelles écritures et la synchronisation finale

C’est la différence la plus importante entre un site vitrine et un site transactionnel.

Si l’ancienne et la nouvelle base de données acceptent toutes deux des écritures pendant la transition DNS, elles peuvent diverger. Une commande enregistrée sur l’ancien serveur n’apparaît pas automatiquement sur le nouveau.

Pour les sites changeants :

  1. choisir un créneau de bascule présentant peu de risques ;
  2. mettre en pause ou contrôler les nouvelles écritures sur la source lorsque cela est pratique;
  3. arrêter ou contrôler les tâches cron et les processus de file d'attente qui pourraient écrire des données deux fois;
  4. exécuter la synchronisation finale de la base de données et copier les téléchargements/fichiers modifiés;
  5. noter l’heure à laquelle la source de référence est figée ;
  6. basculer le trafic ;
  7. vérifier que les nouvelles écritures n'atterrissent maintenant que sur la destination.

Pour VPS pour WooCommerce, incluez le passage de commande, les commandes, les webhooks de paiement, le stock, les actions planifiées et les e-mails transactionnels dans les tests de validation. Pour un site statique ou en cache, une comparaison finale des fichiers peut suffire.

N'appelez pas une migration "zéro temps d'arrêt" à moins que l'application et la méthode de synchronisation ne la prennent vraiment en charge.

Changer de DNS délibérément

Le DNS sert à basculer le trafic ; ce n’est pas la première étape de la migration.

Avant la bascule :

  • exporter ou enregistrer la zone actuelle;
  • identifier exactement quels enregistrements A/AAAA/CNAME/origine doivent changer;
  • réduire le TTL concerné au moins une durée complète de l’ancien TTL avant la bascule prévue, lorsque c’est possible ; par exemple, si le TTL actuel est de 86 400 secondes, le réduire plus de 24 heures avant la bascule ;
  • se rappeler que réduire le TTL maintenant ne vide pas les caches ayant déjà enregistré l’ancien TTL, plus long ;
  • préserver les enregistrements MX, SPF, DKIM, DMARC, TXT, SRV, CAA et autres qui ne bougent pas;
  • Vérifiez à la fois le comportement root et www.

La modification d'un enregistrement A/AAAA est généralement moins risquée que le remplacement des serveurs de noms lorsque le fournisseur DNS lui-même ne change pas. Si les serveurs de noms changent, recréer d'abord la zone requise complète.

Après le changement, vérifiez le DNS public à partir de plus d'un résolveur / réseau et regardez le trafic passer de l'ancien serveur au nouveau.

Éviter une interruption de la messagerie

La migration du site Web et la migration des e-mails sont des tâches distinctes même lorsque l’ancien compte d’hébergement mutualisé les regroupe.

Choisissez un chemin avant la bascule :

  • conserver le courrier avec le fournisseur actuel / géré et préserver les enregistrements MX / TXT existants;
  • transférer le courrier vers un autre fournisseur géré;
  • déplacer le courrier sur le VPS et reconstruire les boîtes aux lettres, le routage, l'authentification et les contrôles de délivrabilité.

Si le courrier se déplace, prenez en compte :

  • Priorités MX;
  • SPF;
  • DKIM;
  • DMARC;
  • DNS inverse / PTR lorsque nécessaire ;
  • des données de boîte aux lettres;
  • alias et redirections de messagerie ;
  • les identifiants SMTP;
  • filtrage anti-spam;
  • sauvegardes et réputation de l'expéditeur.

Ne remplacez pas une zone DNS entière juste pour déplacer le site Web à moins que les enregistrements de courrier et toutes les autres dépendances ne soient reproduits.

Vérifier HTTPS, CDN et les services externes

Si la région de destination est encore indécise, résolvez cela avant la bascule avec Comment choisir l'emplacement VPS . Changer de région ultérieurement peut signifier une autre migration IP/DNS.

Une destination qui fonctionne par IP peut toujours échouer sous le vrai nom d'hôte.

Vérifier :

  • Le certificat TLS couvre les noms d'hôte requis;
  • la redirection HTTP → HTTPS est correcte ;
  • le comportement canonique domaine nu ↔ www reste inchangé ;
  • Les hypothèses HSTS sont comprises;
  • CDN/WAF indique ou autorise la nouvelle origine;
  • la gestion de l’adresse IP réelle du client fonctionne toujours en présence d’un proxy ;
  • webhooks de paiement atteignent la nouvelle origine;
  • Les fournisseurs d'API qui autorisent l'ancienne adresse IP du serveur sont mis à jour;
  • Les identifiants SMTP/API sont valides depuis le nouveau serveur.

Gardez les exceptions temporaires pare-feu/WAF étroites et supprimez-les après acceptation.

Préserver le référencement lorsque les URL restent les mêmes

Un simple changement d'hébergement conserve normalement les mêmes URL publiques. Dans ce cas, la tâche de référencement est principalement parité, pas de mappage de redirection.

Avant et après la bascule comparer:

  • les codes d'état HTTP;
  • les URL canoniques;
  • robots.txt;
  • balises meta robots / noindex accidentel ;
  • URL de sitemap;
  • les liens internes;
  • les données structurées lorsqu’elles sont importantes;
  • le contenu des pages et les ressources rendues;
  • vérification Search Console ;
  • réponses du serveur à Googlebot et aux utilisateurs normaux.

Google Search Central recommande de préparer et tester le nouvel hébergement, de modifier le DNS uniquement lorsque tout est prêt, de surveiller l’ancien et le nouveau serveur, puis de retirer l’ancienne infrastructure après le transfert du trafic. Google recommande aussi de réduire le TTL DNS à l’avance et de maintenir la vérification Search Console opérationnelle.

Si seule l’infrastructure d’hébergement change et que le domaine et les URL restent identiques, n’utilisez pas l’outil Changement d’adresse de Google Search Console. Cet outil sert aux changements de domaine, pas aux migrations d’hébergement conservant les mêmes URL.

Si les chemins du domaine ou de l'URL changent également, utilisez une carte d'URL ancienne à nouvelle et des redirections permanentes côté serveur. C'est un problème de déplacement de site différent d'une migration VPS de même URL.

Validation après migration et retour arrière

Après modification du DNS :

  • surveiller les journaux d'accès / d'erreurs sur les anciens et les nouveaux serveurs;
  • confirmer quʼune nouvelle activité dʼutilisateur atteint la base de données de destination;
  • tester à nouveau les formulaires, le passage de commande, les connexions et les téléversements ;
  • vérifier cron, les files d'attente et les actions planifiées;
  • vérifier le routage des e-mails sortants et du courrier entrant, le cas échéant;
  • surveiller le comportement du processeur, de la RAM, du disque et de la base de données;
  • confirmer le comportement HTTPS et CDN/WAF;
  • vérifier les URL importantes pour la parité 200/redirect;
  • surveiller les signaux d'exploration / indexation de la Search Console;
  • garder l'ancien environnement disponible à travers la fenêtre de stabilité convenue.

Le retour arrière a une limite liée aux données

Un retour arrière précoce peut se limiter à repointer le DNS vers l’ancien serveur uniquement tant que celui-ci reste une source de référence valide.

Dès que des commandes, inscriptions, commentaires ou fichiers téléversés sont enregistrés sur le nouveau serveur, un retour arrière limité au DNS peut perdre ces nouvelles modifications. À ce stade, il faut réconcilier les données ou prévoir une nouvelle synchronisation.

Définissez les déclencheurs du retour arrière avant la migration, par exemple :

  • Erreurs 5xx généralisées;
  • échec du passage de commande ou du paiement ;
  • corruption de base de données ou écritures manquantes;
  • incompatibilité grave de l'environnement d'exécution;
  • authentification cassée;
  • échec critique de mail/webhook qui ne peut pas être résolu dans la fenêtre convenue.

FAQ

Puis-je migrer un site web vers un VPS sans changer de domaine ?

Oui. Une migration d'hébergement peut conserver le même domaine et les mêmes URL publiques. Construisez et testez d'abord la destination, puis modifiez les enregistrements DNS pour envoyer du trafic au nouveau serveur.

Ai-je besoin de redirections 301 lors du déplacement d'un site Web vers un VPS?

Pas lorsque les URL publiques restent identiques. Les redirections sont nécessaires quand les URL changent réellement : nouveau domaine, modification du protocole ou du chemin, ou restructuration du contenu.

Comment puis-je réduire les temps d'arrêt lors d'une migration VPS?

Préparez la destination en parallèle, abaissez le TTL DNS approprié à l'avance, testez en privé, contrôlez les écritures finales, exécutez une synchronisation finale des données, changez de DNS uniquement après acceptation et gardez l'ancien hôte disponible pendant la propagation.

Dois-je également transférer les e-mails vers le VPS ?

Pas automatiquement. Conserver les e-mails sur un service de messagerie géré peut réduire les risques de migration et de délivrabilité. Si la messagerie migre, planifiez séparément les MX, SPF, DKIM, DMARC, les données des boîtes aux lettres, le DNS inverse lorsque nécessaire et les sauvegardes.

Que dois-je tester avant de changer DNS ?

Testez les pages représentatives, la connexion, les formulaires, les téléchargements, la recherche, les rappels de paiement le cas échéant, les tâches planifiées, les API / webhooks, les e-mails sortants, HTTPS, les redirections et les journaux d'application / serveur.

Combien de temps dois-je conserver l'ancien hébergement après la migration?

Conservez-le jusqu’à ce que le trafic DNS ait basculé, que le nouveau serveur soit stable, que les nouvelles écritures soient vérifiées et que la période de retour arrière convenue soit terminée. Appuyez-vous sur les journaux plutôt que sur un nombre universel d’heures ou de jours.

Puis-je migrer WooCommerce sans perdre de commandes ?

Oui, mais pas en s'appuyant sur une seule ancienne copie de base de données. Contrôlez les écritures pendant la bascule et effectuez une synchronisation finale appropriée à l'application afin que les commandes et les changements de stock ne soient pas divisés entre deux bases de données inscriptibles.

Changer d’hébergement nuit-il au SEO ?

Un changement d’hébergement conservant les mêmes URL devrait préserver les signaux de référencement du site si la destination sert le même contenu, les mêmes codes d’état et les mêmes URL canoniques, avec la même accessibilité à l’exploration. Surveillez Search Console et les journaux du serveur après la migration ; le rythme d’exploration peut varier temporairement lors d’un changement d’infrastructure d’hébergement.
