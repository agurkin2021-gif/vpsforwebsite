Un VPS pour WooCommerce doit être dimensionné pour les fonctions de la boutique qui ne peuvent pas se comporter comme un blog mis en cache : panier, passage de commande, comptes, commandes, stocks, rappels de paiement, actions planifiées et écritures en base de données. Le nombre de visites mensuelles ou de produits ne suffit pas à déterminer les ressources serveur nécessaires.

Pour la charge WordPress au sens large, consultez VPS pour WordPress. Pour le parcours principal de choix d’un serveur, consultez VPS pour site web.

Les prérequis WooCommerce ne dimensionnent pas le VPS de production

Les recommandations actuelles de WooCommerce pour les serveurs WooCommerce 10.8+ nécessitent :

  • WordPress 6.9+;
  • PHP 8.3+;
  • MySQL 8.0+ ou MariaDB 10.6+;
  • HTTPS;
  • Limite de mémoire WordPress 256 MB+;
  • Apache ou Nginx comme choix de serveur web recommandé.

Ces valeurs répondent à la question « L’environnement respecte-t-il les prérequis logiciels de WooCommerce ? »

Elles ne précisent pas :

  • le nombre de processus PHP dont vous avez besoin;
  • combien de RAM VPS totale est nécessaire;
  • si les données actives de la base tiennent en mémoire ;
  • si les passages de commande s’accumulent dans une file d’attente sous charge ;
  • si les actions programmées sont en retard;
  • si les sauvegardes ou imports perturbent l’activité des clients ;
  • si les intégrations de paiement / webhook retardent les demandes.

Une limite de mémoire WordPress/PHP de 256 MB n’équivaut pas à 256 MB de RAM pour le VPS. La RAM totale du serveur doit aussi couvrir Linux, le serveur web, la base de données, les processus PHP, le cache, les tâches, le panneau et la messagerie, avec une marge.

Quand WooCommerce a réellement besoin d’un VPS

Une boutique WooCommerce peut justifier un VPS lorsque :

  • l'hébergement mutualisé atteint à plusieurs reprises les limites légitimes CPU / mémoire / processus / E / S;
  • les requêtes de passage de commande ou de compte s’accumulent sous une charge réelle ;
  • les données actives de la base ou la charge d’écriture nécessitent davantage de contrôle ;
  • les extensions ont besoin de services que l'hôte actuel ne permet pas;
  • Une configuration de serveur Redis/Memcached ou personnalisée est requise ;
  • Action Scheduler et les tâches de fond nécessitent une exécution plus fiable ;
  • les importations de produits, les flux ou la synchronisation des stocks entrent en collision avec le trafic client;
  • PHP / environnement d'exécution / paramètres de serveur Web personnalisés sont nécessaires;
  • un environnement de préproduction ou un contrôle d’exploitation propre à la boutique est nécessaire.

Si la boutique est petite, stable et bien prise en charge sur un hébergement WooCommerce ou WordPress infogéré, un VPS n’est pas automatiquement préférable.

Quand un hébergement WooCommerce infogéré peut être préférable

Un VPS autogéré est un mauvais choix lorsque :

  • personne ne prend en charge les mises à jour de sécurité et du système ;
  • personne ne surveille la disponibilité du passage de commande ou les alertes serveur ;
  • les sauvegardes existent mais la restauration n'est pas testée;
  • l’indisponibilité des paiements ou des commandes est critique pour l’activité ;
  • L'équipe veut l'aide de WordPress / WooCommerce plutôt que l'administration Linux;
  • la plate-forme gérée existante résout déjà les performances et la mise à l'échelle de manière adéquate.

Un VPS apporte davantage de contrôle, mais aussi davantage de types de panne à gérer.

Consultez VPS infogéré ou non infogéré avant de placer une boutique critique sur un serveur autogéré.

Le passage de commande et les comptes restent dynamiques

Les recommandations de cache de WooCommerce indiquent que Panier, Mon compte et Commander doivent être exclus du cache pleine page, car ces pages contiennent un état propre au client.

C’est important, car les requêtes les plus critiques pour l’activité peuvent encore exécuter :

  • PHP;
  • logique de session et de panier ;
  • logique d'expédition/fiscalité;
  • code d'intégration des paiements;
  • la base de données lit/écrit;
  • création de commande ;
  • les mises à jour des stocks;
  • hooks et extensions ;

Une boutique peut donc afficher rapidement une page produit mise en cache alors que les passages de commande restent en attente.

Ne dimensionnez pas WooCommerce uniquement à partir du taux de succès du cache du catalogue.

Processus PHP et concurrence dynamique

Pour les requêtes dynamiques WooCommerce, les processus PHP déterminent combien de requêtes peuvent être exécutées simultanément.

Une approximation utile est :

Requêtes dynamiques actives ≈ requêtes par seconde non servies par le cache × durée d’une requête

Si les requêtes de passage de commande, de compte ou d’API durent en moyenne 0,8 seconde en pointe et que 5 requêtes dynamiques par seconde atteignent PHP, environ quatre processus peuvent être occupés simultanément, avant même d’ajouter l’administration, les webhooks ou les tâches de fond.

Chaque processus consomme de la mémoire. Augmenter le nombre de processus sans budget RAM peut priver la base de données de mémoire ou pousser le serveur vers le swap ou des événements OOM.

Utiliser:

RAM WooCommerce = système d’exploitation + serveur web + base de données + cache + processus PHP + tâches + panneau/messagerie + marge

Ensuite, vérifiez la mémoire de processus moyenne / crête au lieu de copier un nombre de processus générique.

Configurer correctement le cache WooCommerce

WooCommerce a besoin d’une stratégie de cache en couches.

Cache pleine page

Utile pour les pages de catalogue/contenu en cache.

Ne mettez pas aveuglément en cache :

  • Panier;
  • la page Commander ;
  • Mon compte;
  • Réponses spécifiques au client/session.

Les instructions officielles de mise en cache de WooCommerce excluent explicitement ces pages.

OPcache

Met en cache le bytecode PHP compilé et réduit le travail de compilation PHP répété.

Cache d'objets persistants

Redis ou Memcached peuvent réduire le travail répété sur les bases de données et les objets lorsque la charge de travail en bénéficie.

Il ne remplace pas la mise en cache pleine page et ne corrige pas automatiquement les requêtes inefficaces.

Navigateur / CDN

Utile pour les ressources statiques et le contenu diffusable en périphérie du réseau.

Un CDN peut réduire les requêtes statiques vers l’origine, mais ne supprime pas le travail dynamique du passage de commande et de la base de données.

Besoins de la base de données et HPOS

WooCommerce crée un comportement de lecture / écriture de base de données plus lourd qu’un site WordPress en cache typique.

Les travaux importants de DB peuvent inclure :

  • création de commandes et mises à jour;
  • données client/compte ;
  • les variations de stock;
  • recherche de produits/catalogues;
  • sessions;
  • métadonnées d'extension;
  • rapports/analyses;
  • recherche/filtrage;
  • tâches programmées.

Le stockage haute performance des commandes (HPOS) de WooCommerce conserve les données des commandes dans des tables dédiées. Il est activé par défaut pour les nouvelles installations depuis WooCommerce 8.2.

HPOS est une amélioration architecturale importante, mais il ne remplace pas:

  • extensions compatibles / code personnalisé;
  • analyse des requêtes et des index ;
  • une mémoire DB adéquate;
  • faible latence de stockage;
  • supervision ;
  • environnement de test / test avant des changements majeurs.

Pour les grandes boutiques existantes, WooCommerce recommande de tester la migration HPOS et les parcours critiques avant la bascule en production.

Action Scheduler et les tâches de fond

WooCommerce utilise Action Scheduler pour des tâches en arrière-plan telles que :

  • les notifications de commande;
  • traitement lié aux paiements;
  • webhooks ;
  • abonnements/renouvellements;
  • les tâches d'extension;
  • Importation/synchronisation.

WooCommerce les expose sous WooCommerce > Statut > Actions planifiées .

Surveillez pour:

  • les actions échouées;
  • les actions en souffrance;
  • arriéré persistant en attente;
  • tâches de longue durée ;
  • les files d'attente qui se développent pendant les pics de clients.

Action Scheduler dépend de la planification WordPress par défaut, donc cron côté serveur peut être utile là où un timing fiable est requis.

Une boutique dont les pages en cache sont rapides peut tout de même rencontrer des problèmes d’exploitation si sa file de tâches planifiées échoue.

Paiements, webhooks, email et intégrations

Un VPS plus grand ne peut pas résoudre chaque échec de paiement.

Les dépendances externes peuvent inclure :

  • passerelles de paiement;
  • les API fiscales;
  • API d'expédition;
  • synchronisation des stocks et de l’ERP ;
  • CRM;
  • email transactionnel ;
  • contrôles antifraude;
  • webhooks ;
  • Recherche externe/services.

Mesurez si la latence provient de votre VPS ou du service externe.

Surveillez :

  • défaillances de rappel de paiement;
  • livraison des webhooks ;
  • les files d'attente de courriels;
  • dépassements de délai des API ;
  • comportement des nouvelles tentatives et des délais d’attente progressifs ;
  • échecs d’Action Scheduler.

N'achetez pas de CPU pour résoudre un goulot d'étranglement d'API tierce.

Catalogue, recherche et filtrage

Les grands catalogues ne créent pas de charge uniquement parce qu'ils contiennent de nombreux produits.

La vraie pression vient de :

  • requêtes complexes de recherche/filtre;
  • requêtes d'attribut/taxonomie;
  • les tables de recherche de produits;
  • nombre de variations;
  • les règles en matière de prix/stocks;
  • les extensions qui ajoutent du SQL ou des appels externes ;
  • résultats personnalisés non mis en cache.

Mesurez les points de terminaison de recherche/filtre séparément de la navigation normale dans la page produit.

Le cache persistant peut aider certaines requêtes répétées, mais la conception de la base de données/requête est toujours importante.

Dimensionner pour les pics de ventes et de campagnes

La charge de pointe de WooCommerce combine souvent plusieurs activités :

  • newsletter/trafic publicitaire ;
  • navigation dans le catalogue;
  • ajouts au panier ;
  • passages de commande ;
  • les rappels de paiement;
  • e-mails de commande;
  • les mises à jour des stocks;
  • admin/traitement des commandes;
  • webhooks ;
  • les actions programmées;
  • analyse et journalisation.

Dimensionnez selon une période de pointe représentative, pas selon une journée moyenne.

Avant une grande promotion :

  1. tester le trafic de paiement représentatif;
  2. vérifier la marge de capacité de processus PHP;
  3. vérifier la latence et les connexions DB;
  4. vérifier l’accumulation de tâches dans Action Scheduler ;
  5. suspendre ou reporter les importations/les sauvegardes/les analyses;
  6. confirmer les API de paiement/expédition/taxes externes;
  7. surveiller les journaux et les métriques de ressources pendant l'événement.

Stockage, sauvegardes et environnement de test

Une sauvegarde WooCommerce doit protéger les fichiers et les données transactionnelles.

Inclure :

  • Fichiers WordPress / WooCommerce;
  • fichiers téléversés et médias des produits ;
  • base de données/données de commande;
  • configuration/secrets nécessaires à la récupération;
  • plugin/thème/code personnalisé ;
  • paramètres d'intégration.

Récupération sensible aux transactions

Si la boutique reçoit des commandes en continu, la fréquence des sauvegardes détermine la perte potentielle de données de commande.

Une sauvegarde quotidienne de la base peut laisser jusqu’à une journée de transactions récentes en dehors du point de restauration.

Choisissez la fréquence des sauvegardes selon l’objectif de point de reprise (RPO) acceptable plutôt que par commodité.

L’architecture de sauvegarde détaillée est traitée dans Stratégie de sauvegarde VPS.

Environnement de test

Testez les modifications apportées à PHP, WooCommerce, plugins, thèmes, HPOS et paiements dans l'environnement de test avant la production lorsque cela est possible.

Mais les copies d'environnement de test consomment également des ressources disque et parfois DB/RAM/sauvegarde, alors incluez-les dans la planification de la capacité.

Panneau de contrôle, FASTPANEL ou pile manuelle

WooCommerce peut fonctionner sur un VPS Linux géré manuellement ou via un panneau de contrôle d'hébergement.

Pour choisir un panneau, consultez VPS avec panneau de contrôle.

Pour le déploiement FASTPANEL propre à VDSina, consultez Hébergement VPS avec FASTPANEL.

Pour un déploiement Linux manuel, consultez Comment héberger un site web sur un VPS.

Un panneau de contrôle simplifie les tâches courantes ; il ne prend pas en charge la fiabilité du passage de commande, les mises à jour WooCommerce et des extensions, le réglage de la base de données, les sauvegardes ou les incidents.

Migrer une boutique active exige de définir la bascule des données

Une migration WooCommerce n’est pas seulement « copier des fichiers et des bases de données ».

Commandes, stocks, paniers, clients et actions planifiées peuvent changer tant que la boutique reste en ligne.

Pour la migration :

  • construire/tester la destination en premier;
  • maîtriser les dernières écritures ;
  • exécuter une synchronisation finale DB/uploads;
  • éviter deux boutiques de production acceptant des écritures et dont les données divergent ;
  • vérifier les points finaux de paiement/webhook;
  • Préserver les emails/DNS ;
  • conserver un plan de retour arrière.

Consultez Migration d’un site web vers un VPS pour l’ensemble de la procédure de bascule.

Quand augmenter les ressources d’un VPS WooCommerce

Augmentez les ressources ou revoyez l’architecture lorsque les mesures montrent :

  • des files d'attente de processus PHP répétées;
  • saturation CPU soutenue après optimisation cache/requête/plugin;
  • Pression RAM, swap ou OOM;
  • latence de la base de données ou pression liée aux données actives en mémoire ;
  • accumulation ou échecs des tâches Action Scheduler dus à un manque de capacité ;
  • erreurs de passage de commande ou de paiement sous une charge de pointe légitime ;
  • la croissance du stockage réduisant la marge de capacité sûre;
  • tâches de sauvegarde/importation/analyse entrant en collision avec les clients;
  • plusieurs boutiques ou services se disputent les ressources d’un même VPS.

Si le paiement est lent alors que les ressources du serveur sont saines, étudiez les causes de paiement / API / plug-in / base de données avant d'acheter un VPS plus grand.

FAQ

De combien de RAM WooCommerce a-t-il besoin sur un VPS?

Il n’existe pas de quantité universelle. Les recommandations de montée en charge de WooCommerce ont utilisé 2 GB comme configuration de base autohébergée. Un VPS de 4 GB constitue toutefois un point de départ plus solide pour de nombreuses boutiques professionnelles, car les processus PHP, la base de données, le cache et les tâches doivent coexister.

Est-ce que 2 GB de RAM suffisent pour WooCommerce ?

Cela peut suffire pour une boutique très petite ou légère, ou pour une configuration contrôlée à faible volume. Vérifiez les passages de commande simultanés, la latence de la base de données, les actions planifiées et la pression mémoire avant de la considérer prête pour la production.

Est-ce que 4 GB de RAM est suffisant pour WooCommerce?

Pour de nombreuses petites boutiques professionnelles, 4 GB constituent un point de départ pratique. Une charge importante, des catalogues ou bases de données plus volumineux, de nombreuses intégrations, des abonnements, des imports ou des pics de ventes peuvent nécessiter davantage de ressources.

Pourquoi WooCommerce est-il plus lourd que WordPress ?

Le panier, le passage de commande, les comptes, les commandes, les stocks et de nombreuses intégrations sont dynamiques. Ces requêtes sollicitent toujours PHP et la base de données, même lorsque les pages publiques du catalogue ou de contenu sont mises en cache.

Puis-je mettre en cache WooCommerce?

La mise en cache pleine page doit exclure le panier, la commande et Mon compte car ces pages contiennent un état spécifique au client. Utilisez d'autres couches de cache pour les données/contenus appropriés.

WooCommerce a-t-il besoin de Redis ?

Non. Redis ou Memcached peuvent fournir une mise en cache d'objet persistante lorsque la charge de travail en bénéficie. Ils ne remplacent pas les exclusions de cache de page correctes ou les requêtes efficaces.

Qu'est-ce que HPOS?

Le stockage haute performance des commandes conserve les commandes WooCommerce dans des tables dédiées. Il est activé par défaut sur les nouvelles installations depuis WooCommerce 8.2. Testez la compatibilité des extensions et du code personnalisé ainsi que les parcours critiques avant de faire basculer une boutique existante.

Quelles sont les actions programmées WooCommerce?

Ce sont des tâches de fond mises en file d’attente et gérées par Action Scheduler, par exemple les notifications de commande, les traitements liés au paiement, les webhooks et les tâches des extensions. Les tâches échouées ou en retard constituent un signal opérationnel.

Est-ce que VDSina inclut WooCommerce préinstallé?

La page VDSina Standard actuelle ne répertorie pas WooCommerce comme une application dédiée préinstallée dans ses groupes de modèles/applications visibles. Vérifiez l'interface de commande en direct avant de supposer la disponibilité du modèle.

Un VPS est-il toujours meilleur pour WooCommerce que l’hébergement géré ?

Non. Un VPS autogéré est utile si vous avez besoin de contrôle ou de ressources et pouvez assurer son exploitation. Un hébergement WooCommerce ou WordPress infogéré peut être plus sûr lorsque la boutique est critique pour l’activité et qu’aucun responsable interne ne prend en charge le serveur.
