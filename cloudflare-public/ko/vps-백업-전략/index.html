VPS 백업 전략

VPS 백업 전략: RPO와 RTO를 정의하고 제공업체 백업 이미지와 독립적인 외부 백업을 결합하며, 데이터베이스와 비밀 정보를 보호하고 보존 정책과 실제 복원 테스트로 복구 가능성을 확인합니다.

현재 VPS 옵션 확인 백업 전략
복구에는 여러 계층의 백업이 필요합니다 빠른 롤백, 독립적인 사본과 검증된 복원은 서로 다른 장애에 대비합니다.
01
제공업체 이미지 빠른 서버 롤백
02
데이터베이스 백업 애플리케이션 상태
03
외부 사본 독립된 장애 영역
04
복원 훈련 실제 RTO 검증
RPO는 허용 가능한 데이터 손실량을, RTO는 허용 가능한 서비스 중단 시간을 정의합니다.

제휴 안내: 편집자는 VDSina와 업무상 관계가 있으며, 제휴 링크를 통한 구매로 수수료를 받을 수 있습니다. 편집 원칙 및 제휴 관계 안내.

VPS 백업 전략은 단순히 “하루에 한 번 스냅샷을 켜는 것”이 아닙니다. 실제로 사용할 수 있는 복구 계획은 허용 가능한 데이터 손실량(RPO), 복구에 걸릴 수 있는 시간(RTO), 반드시 보존해야 하는 데이터, 독립된 사본의 보관 장소, 백업 버전의 보존 기간, 실제로 복원을 수행해 봤는지를 정의해야 합니다.

견고한 VPS 복구 계획은 대체로 제공업체 측의 빠른 복구 방법, 서버 외부의 독립적인 사본, 애플리케이션에 맞는 데이터베이스 백업을 결합합니다. 적절한 구성은 데이터가 얼마나 빨리 변하는지, 서비스 중단 비용이 얼마나 큰지에 따라 달라집니다.

백업 전략에는 담당자도 명확히 지정해야 합니다. 작업 실패, 복원 테스트, 복구 결정을 책임질 사람이 없다면 운영 방식부터 정하세요. 관리형 VPS와 비관리형 VPS를 참고하세요.

서버 선택의 전반적인 기준은 웹사이트용 VPS 호스팅을 참고하세요.

핵심 요약

실용적인 VPS 복구 구조는 여러 계층으로 구성됩니다.

계층주요 역할이것만으로 보장하지 못하는 사항
제공업체 백업 이미지 / 스냅샷서버 전체를 빠르게 이전 상태로 되돌리거나 재구축제공업체 계정 또는 저장소를 사용할 수 없을 때의 독립적인 복구
데이터베이스 일관성을 보장하는 백업애플리케이션 상태와 최근 변경 데이터를 복원서버 전체 설정의 복원
파일 / 설정 백업업로드, 설정, 앱 데이터 및 선택한 파일 복원서버 전체를 신속하게 복구하는 능력
독립적인 외부 사본주 제공업체, 계정 또는 서버 장애에도 데이터 보존복원을 연습하지 않았다면 짧은 RTO 달성
복원 훈련사본, 복구 키와 실행 절차가 실제로 작동함을 입증지속적인 감시가 없다면 이후 백업도 계속 성공한다는 보장

일반적인 웹사이트 VPS 배포에서는 다음 구성을 기본으로 삼을 수 있습니다.

  • 빠른 롤백을 위한 제공업체 측 이미지 또는 스냅샷;
  • 파일, 설정과 데이터베이스를 다른 장애 영역으로 보내는 암호화된 독립 백업;
  • 여러 복구 지점;
  • 허용 가능한 데이터 손실량에 맞춘 데이터베이스 백업 주기;
  • 정기적인 복원 테스트.

단 하나의 “백업 성공” 상태에 의존하는 것보다 훨씬 유용합니다.

VPS 백업 전략 진단

이 진단 도구는 필요한 복구 구조를 판단하는 데 도움을 줍니다. 복구 성공을 보장하지는 않습니다.

실제로 필요한 복구 요건을 선택하세요.

RPO와 RTO부터 정의

전략을 결정하는 핵심 숫자는 두 가지입니다.

복구 시점 목표 — RPO

RPO는 다음 질문에 답합니다.

비즈니스가 최근 데이터 중 얼마나 잃어도 감당할 수 있습니까?

RPO가 다음과 같다면:

  • 24시간 — 하루에 한 번 성공적으로 생성한 복구 지점이 허용될 수 있습니다;
  • 4시간 — 일일 백업만으로는 부족합니다;
  • 1시간 — 변경되는 애플리케이션과 데이터베이스 상태를 최소한 그 주기로 보호해야 합니다;
  • 수분 단위 — 일반적인 예약 백업만으로 충분하지 않을 수 있습니다.

RPO는 서비스 중단 시간이 아니라 데이터 손실량에 관한 지표입니다.

복구 시간 목표 — RTO

RTO는 다음 질문에 답합니다.

웹사이트나 서비스를 얼마나 오랫동안 사용할 수 없어도 됩니까?

백업이 RPO를 충족하더라도 RTO를 충족하지 못할 수 있습니다.

예를 들면 다음과 같습니다.

  • 데이터베이스를 매시간 복사합니다;
  • 최근 데이터의 손실량은 1시간 미만입니다;
  • 그러나 VPS를 다시 만들고 데이터를 내려받아 DB를 복원하고 사이트를 검증하는 데 6시간이 걸립니다.

이 전략은 1시간 RPO를 충족할 수 있지만 실제 RTO는 약 6시간입니다.

NIST의 비상 계획 지침은 RPO를 복구 기준 시점으로, RTO를 허용 가능한 최대 서비스 중단 시간으로 정의합니다. 도구를 선택하기 전에 이 목표부터 정하세요.

무엇을 백업해야 하나요?

서버의 구성 요소를 재구축 가능한 항목과 상태가 있거나 다시 만들기 어려운 항목으로 구분하세요.

재구축 가능한 항목

코드나 자동화로 다시 만들 수 있는 경우가 많습니다.

  • 기본 운영체제;
  • 패키지;
  • 이미 Git에 안전하게 보관된 애플리케이션 코드;
  • 다시 빌드하거나 내려받을 수 있는 컨테이너 이미지;
  • 표준 웹 서버 패키지.

상태가 있거나 복원이 어려운 항목

일반적으로 우선순위가 더 높습니다.

  • 데이터베이스;
  • 사용자 업로드와 미디어;
  • 같은 서버에서 운영하는 경우 메일함;
  • 설정;
  • 복구에 필요한 환경 변수와 비밀 정보;
  • 다시 발급하거나 교체하기 어려운 TLS 인증서와 개인 키;
  • 애플리케이션이 생성한 데이터;
  • 컨트롤 패널과 사이트 설정;
  • cron과 워커 설정;
  • DNS를 VPS에서 운영한다면 DNS 영역 데이터;
  • 다른 곳에 저장되지 않은 맞춤형 스크립트.

데이터베이스나 사이트를 다시 시작하는 데 필요한 비밀 정보를 빠뜨리면서 캐시, 임시 파일, 쉽게 재생성할 수 있는 결과물을 무작정 복사하는 데 백업 공간을 낭비하지 마세요.

스냅샷, 이미지, 파일 백업과 복제는 서로 다릅니다

서로 같은 수단으로 취급하지 마세요.

제공업체 스냅샷 / 서버 이미지

다음 상황에 유용합니다.

  • 위험이 있는 업데이트 후 빠른 롤백;
  • 서버 전체 복구;
  • 가상 머신 복제 또는 재생성.

한계:

  • 제공업체나 계정과 동일한 장애 영역에 있을 수 있습니다;
  • 개별 파일 또는 사이트 단위 복원이 어려울 수 있습니다;
  • 애플리케이션과 데이터베이스의 일관성을 별도로 이해해야 합니다;
  • 최신 이미지 하나만 있으면 이전 시점의 기록이 부족합니다.

파일 단위 백업

다음 항목에 유용합니다.

  • 업로드 파일;
  • 설정;
  • 선택한 애플리케이션 데이터;
  • 세부 항목별 복원.

restic이나 Borg 같은 도구를 사용하면 원격 저장소에 암호화된 여러 버전의 백업을 보관할 수 있습니다.

데이터베이스 백업

데이터베이스 엔진에 맞는 방법을 사용하세요.

  • 논리적 덤프;
  • 데이터베이스 자체 백업 도구;
  • 애플리케이션 일관성을 유지하는 스냅샷 또는 절차.

실행 중인 데이터베이스 파일을 그대로 복사한다고 해서 사용 가능한 DB 백업이 만들어진다고 가정하지 마세요.

복제 / 대기 서버

복제는 복구 시간이나 데이터 손실을 줄일 수 있지만, 그 자체로 과거 시점의 백업은 아닙니다.

잘못된 삭제, 손상 또는 애플리케이션 오류까지 함께 복제될 수 있습니다.

필요한 경우 가용성과 RTO를 위해 복제 및 대기 서버를 사용하되, 과거 시점으로 복구할 수 있도록 버전별 백업도 유지하세요.

VPS에 적용하는 실용적인 3-2-1 모델

일반적인 3-2-1 모델은 다음을 뜻합니다.

  • 중요한 데이터의 사본 3개;
  • 2가지 서로 다른 저장 방식 또는 장애 영역;
  • 1개는 외부, 즉 주 장애 영역 밖에 보관.

VPS에서는 다음과 같이 적용할 수 있습니다.

  1. VPS의 실제 운영 데이터;
  2. 빠른 복구를 위한 제공업체 백업 이미지;
  3. 독립적인 장소에 보관하는 암호화된 외부 파일 및 데이터베이스 백업.

목표는 구호의 숫자를 기계적으로 맞추는 것이 아닙니다. 한 번의 사고로 운영 데이터와 모든 복구 사본이 동시에 사라지는 일을 막는 것입니다.

장애 영역의 예시는 다음과 같습니다.

  • VPS 파일 시스템;
  • 제공업체의 백업 저장소;
  • 제공업체 계정;
  • 별도의 객체 저장소 계정 또는 제공업체;
  • 오프라인 사본 또는 변경할 수 없도록 보호된 사본.

VPS를 장악한 공격자가 같은 자격 증명으로 모든 백업을 삭제할 수 있다면, 사본이 실질적으로 독립되어 있다고 볼 수 없습니다.

데이터베이스 일관성을 보장하는 백업

사이트가 실행되는 동안에도 데이터베이스 상태는 계속 변합니다.

올바른 전략이라면 DB 엔진을 어떤 방식으로 보호하는지 알아야 합니다.

워드프레스, MySQL 또는 MariaDB에서는 다음 방법을 사용할 수 있습니다.

  • 논리적 덤프;
  • DB 전용 백업 도구;
  • 서로 맞춰 수행하는 스냅샷;
  • 데이터베이스 일관성을 명시적으로 처리하는 백업 소프트웨어.

PostgreSQL에서는 필요한 RPO에 따라 PostgreSQL에 맞는 백업과 시점 복구(PITR) 방법을 사용하세요.

중요한 것은 특정 도구가 아니라 복원된 DB의 내부 상태가 일관되고 실제로 사용할 수 있어야 한다는 점입니다.

워드프레스의 애플리케이션 상태와 운영에 대해서는 워드프레스용 VPS를 참고하세요.

다음을 테스트하세요.

  • 덤프 또는 백업 작업이 완료됩니다;
  • 백업 파일이 비어 있지 않습니다;
  • 복원 또는 가져오기가 성공합니다;
  • 대표적인 테이블과 레코드가 존재합니다;
  • 애플리케이션이 접속하여 중요한 데이터 읽기와 쓰기를 수행합니다.

거래가 발생하는 사이트는 다른 RPO가 필요합니다

단순한 소개 사이트는 하루 전 사본으로도 충분할 수 있습니다.

반면 거래가 발생하는 쇼핑몰은 그렇지 않을 수 있습니다.

WooCommerce, 회원 관리, 청구 또는 주문 시스템에서는 최근에 변경된 상태를 얼마나 잃을 수 있는지 정하세요.

  • 주문;
  • 결제;
  • 재고;
  • 고객;
  • 회원 자격;
  • 양식 제출;
  • 업로드.

매시간 주문이 들어오는 쇼핑몰에서는 하루에 한 번의 DB 백업으로 많은 거래 기록을 잃을 수 있습니다.

쇼핑몰 작업 부하는 우커머스용 VPS를 참고하세요. 이 페이지의 백업 주기는 허용 가능한 거래 데이터 손실 시간에 맞춰 정해야 합니다.

백업 빈도와 보존 기간

각 데이터 유형의 백업 주기는 해당 RPO보다 느려서는 안 됩니다.

데이터에 따라 다른 일정이 필요할 수 있습니다.

  • DB: 빈번하게;
  • 업로드: 빈번하게 또는 이벤트 발생 시;
  • OS 및 설정: 중요한 변경 후와 정기 일정에 따라;
  • 제공업체의 전체 이미지: 상대적으로 드물게, 특히 위험한 변경 전후에 유용.

보존 정책은 문제가 늦게 발견되더라도 복구할 수 있도록 해 줍니다.

예를 들면 다음 사본을 유지하는 방식이 있습니다.

  • 최근의 시간별 복구 지점;
  • 여러 개의 일별 사본;
  • 여러 개의 주별 사본;
  • 일부 월별 사본.

정확한 보존 기간은 다음을 기준으로 정하세요.

  • 비즈니스의 복구 필요;
  • 저장 비용;
  • 데이터 변경 속도;
  • 규정 준수와 법적 요구사항;
  • 손상이나 침해가 발견되지 않은 채 지속될 수 있는 시간.

“최신 버전” 하나만 보관하지 마세요.

독립적인 서버 외부 백업 저장소 유지

같은 VPS 디스크에 백업을 보관하면 다음 상황을 막을 수 없습니다.

  • 디스크 또는 파일 시스템 손실;
  • 서버 삭제;
  • root 권한 침해;
  • 랜섬웨어;
  • 계정 관리 실수;
  • 제공업체 측에서 해당 가상 머신이 사라지는 사고.

복구 데이터를 VPS 외부로 전송하거나 직접 스트리밍하세요.

가능한 저장 장소는 다음과 같습니다.

  • 객체 저장소;
  • 다른 백업 서비스 또는 제공업체;
  • 백업 전용으로 사용하는 별도의 VPS;
  • 오프라인 또는 접근을 통제하는 저장소.

가능하다면 제공업체나 계정의 자격 증명도 분리하세요.

백업 암호화와 복구 키 보호

민감한 백업 데이터는 적절한 경우 전송 중과 저장 중 모두 암호화하세요.

하지만 암호화는 또 하나의 복구 의존성을 만듭니다.

백업 비밀번호나 키의 유일한 사본을 다음 장소에만 두지 마세요.

  • VPS 내부에만;
  • 사용할 수 없게 될 수 있는 동일한 비밀번호 금고 또는 계정에만;
  • 암호화된 백업 자체 안에만.

복구 자격 증명과 키는 안전하고 독립적인 장소에 보관하고, 복원 훈련에서 키를 실제로 사용할 수 있는지도 확인하세요.

백업 자격 증명과 삭제 권한 분리

운영 서버가 침해되더라도 공격자가 모든 복구 사본을 자동으로 삭제할 수 있어서는 안 됩니다.

가능하면 다음 방식을 선택하세요.

  • 사용 범위를 제한한 백업 자격 증명;
  • 저장소에서 지원한다면 광범위한 삭제 권한 없이 쓰기 권한만 부여;
  • 별도의 관리자 자격 증명;
  • 필요한 경우 보존 잠금 또는 변경 불가능한 저장 방식;
  • 가치가 높은 데이터를 위한 오프라인 또는 네트워크에서 분리된 사본.

정확한 구성은 저장 서비스에 따라 달라집니다.

이것이 백업을 보안 조치로도 간주하는 이유 중 하나입니다. VPS 보안 점검표를 참고하세요.

백업 작업 모니터링

자동화는 백업 누락을 줄이지만, 자동 작업의 실패는 알아차리지 못한 채 계속될 수 있습니다.

다음 항목을 감시하세요.

  • 마지막 백업 성공 시각;
  • 실패하거나 일부만 완료된 작업;
  • 저장소 접근 가능 여부;
  • 자격 증명 만료;
  • 로컬 임시 파일 저장 전의 디스크 여유 공간;
  • 외부 저장소의 할당량;
  • DB 덤프 실패;
  • 백업 소요 시간 변화;
  • 비정상적으로 작은 백업 크기;
  • 보존 기간 관리 또는 오래된 백업 정리 실패.

cron이나 서비스 상태가 녹색이라는 사실은 명령이 실행되었다는 뜻일 뿐, 복원이 가능하다는 증거는 아닙니다.

서버와 서비스 전반의 알림 설계는 VPS 모니터링에서 다룹니다. 백업 작업의 정상 작동 여부는 복구 전략 자체에서도 관리해야 합니다.

복원을 테스트하고 실제 RTO 측정

백업의 신뢰성은 복원할 수 있을 때 입증됩니다.

분리된 깨끗한 환경에서 복구 훈련을 수행하세요.

전체 절차에서 충분한 부분을 테스트해야 합니다.

  1. 새 VPS 또는 테스트 환경을 준비합니다;
  2. 올바른 백업 지점을 가져옵니다;
  3. 암호화 키와 저장소 자격 증명을 확보합니다;
  4. 파일과 설정을 복원합니다;
  5. 데이터베이스를 복원하거나 가져옵니다;
  6. 필요한 비밀 정보와 인증서를 복원합니다;
  7. 서비스와 네트워크를 설정합니다;
  8. 애플리케이션을 시작합니다;
  9. 중요한 페이지와 거래를 테스트합니다;
  10. 백그라운드 작업과 외부 연동을 확인합니다;
  11. 실제 복구에 걸린 시간을 측정합니다.

측정한 결과를 기록하세요.

비즈니스의 RTO가 4시간인데 테스트에 8시간이 걸린다면, 모든 파일을 정상적으로 복원했더라도 백업 전략이 비즈니스 요구사항을 충족하지 못한 것입니다.

NIST 지침은 정기적인 백업 생성, 복원 테스트와 복구 훈련의 중요성을 강조합니다.

복원 단위도 중요합니다

좋은 전략은 실제로 발생한 장애 범위에 맞춰 복원할 수 있어야 합니다.

개별 파일 또는 사이트 복원

다음 상황에 필요합니다.

  • 업로드 파일 삭제;
  • 잘못된 설정;
  • 한 사이트만 침해된 경우;
  • 특정 데이터베이스 또는 테이블의 잘못된 변경을 되돌릴 때.

서버 전체 복구

다음 상황에 필요합니다.

  • VPS 고장 또는 삭제;
  • 파일 시스템 장애;
  • 심각한 침해;
  • 제공업체 또는 서버 교체.

백업이 전체 디스크 이미지뿐이라면 파일 하나만 복원하기 불편할 수 있습니다.

일부 파일만 백업했다면 VPS 전체를 재구축하는 데 너무 오래 걸릴 수 있습니다.

두 방식을 계층적으로 조합하세요.

여러 웹사이트에는 사이트별 복원이 필요합니다

여러 사이트를 운영하는 VPS에서는 사이트 A를 복원하면서 사이트 B/C/D까지 자동으로 어제 상태로 돌아가도록 복구 구조를 설계하지 마세요.

가능하면 다음 범위를 개별적으로 복원할 수 있어야 합니다.

  • 한 사이트의 문서 루트;
  • 한 데이터베이스;
  • 한 패널 계정 또는 사용자;
  • 한 사이트의 업로드 파일;
  • 필요한 경우에만 VPS 전체.

구조와 장애 영역에 관한 결정은 여러 웹사이트용 VPS를 참고하세요.

백업 작업 자체가 장애를 일으킬 수도 있습니다

백업 작업은 서버 자원을 소비합니다.

가능한 영향:

  • DB 덤프 중 CPU 사용;
  • 압축 작업의 CPU 사용;
  • 디스크 읽기 I/O;
  • 임시 디스크 공간 사용;
  • 객체 저장소 업로드 대역폭;
  • 캐시 퇴출;
  • 가져오기, 스캔 또는 트래픽 최고점과 백업 작업의 겹침.

VPS의 여유 공간이 10 GB뿐인데 로컬에 30 GB 백업 아카이브를 만들도록 설계하지 마세요.

가능하다면 다음을 수행하세요.

  • 백업을 서버 외부로 직접 스트리밍;
  • 임시 디스크 사용량 감시;
  • 무거운 백업 작업을 트래픽이 적을 때 실행;
  • 도구에서 지원하는 경우 속도 제한;
  • 백업 소요 시간 측정.

백업과 마이그레이션을 혼동하지 마세요. 백업은 이전 작업의 안전망이 될 수 있지만, 실제 서비스 전환, 마지막 데이터 쓰기, DNS 및 롤백은 별도의 작업입니다. 웹사이트 VPS 이전을 참고하세요.

FAQ

좋은 VPS 백업 전략이란 무엇인가요?

RPO와 RTO를 정하고 독립적인 복구 사본을 보관하며, 애플리케이션 일관성을 유지하는 방법으로 데이터베이스를 보호하세요. 여러 버전을 보존하고 작업 실패를 감시하며, 깨끗한 테스트 환경에서 정기적으로 복원을 수행해야 합니다.

VPS 스냅샷만으로 충분한가요?

유일한 복구 계층으로 사용하기에는 충분하지 않습니다. 제공업체의 스냅샷과 이미지는 빠른 롤백과 서버 전체 복구에 유용하지만, 같은 제공업체 또는 계정의 장애 영역에 속할 수 있고 개별 항목 복원은 불편할 수 있습니다.

VPS에서 3-2-1 규칙은 무엇을 의미하나요?

실제 운영 데이터와 여러 복구 사본을 서로 독립적인 저장소 또는 장애 영역에 보관하고, 최소한 하나의 사본은 주 VPS 또는 제공업체 장애 경로 밖에 두는 것을 의미합니다.

VPS를 얼마나 자주 백업해야 하나요?

각 데이터 유형의 RPO에 따라 주기를 정하세요. 정적 사이트는 일일 사본으로 충분할 수 있지만, 거래가 발생하는 데이터베이스는 매시간 또는 그보다 자주 보호해야 할 수 있습니다.

RPO와 RTO의 차이는 무엇인가요?

RPO는 허용 가능한 최근 데이터의 최대 손실량입니다. RTO는 서비스를 복구할 때까지 허용할 수 있는 최대 중단 시간입니다.

VPS 전체를 백업해야 하나요, 웹사이트 파일만 백업해야 하나요?

대개 두 계층 모두 유용합니다. 서버 이미지는 전체 복구를 빠르게 해 주고, 파일과 데이터베이스 백업은 개별 항목 복원과 애플리케이션 일관성을 유지한 복원을 쉽게 만듭니다.

MySQL 또는 PostgreSQL을 안전하게 백업하는 방법은 무엇인가요?

해당 엔진의 논리적 덤프나 전용 백업 도구, 또는 애플리케이션과 일관성을 맞춘 방법을 사용하세요. 그런 다음 분리된 테스트 환경에서 실제로 복원하거나 가져와서 검증하세요.

백업을 암호화해야 하나요?

민감한 복구 데이터는 적절한 경우 암호화해야 합니다. 다만 복구 비밀번호와 키는 장애가 발생한 VPS 밖의 안전한 장소에 보관하세요.

복제도 백업인가요?

복제 자체만으로는 백업이 아닙니다. 실수로 인한 삭제, 손상 또는 악의적인 변경까지 복제할 수 있습니다. 복제나 대기 서버와 별도로 과거 시점의 버전별 백업을 유지하세요.

VDSina는 VPS 백업을 제공하나요?

VDSina는 수동 및 예약 백업 사본, 백업에서 복원하거나 서버를 만드는 기능과 다운로드 가능한 백업 이미지를 문서로 안내합니다. 다만 이용약관은 백업 책임을 고객에게 두고 정기적인 복원 테스트를 권장합니다.

복원 테스트를 얼마나 자주 해야 하나요?

정해진 일정에 따라, 그리고 백업이나 시스템 구조가 의미 있게 바뀐 뒤에 수행하세요. 중요도가 높거나 데이터가 빠르게 변하는 시스템에서는 실제 복구 절차를 신뢰할 수 있을 만큼 충분히 자주 테스트해야 합니다.

RTO가 1시간 미만이라면 어떻게 해야 하나요?

백업만 사용하는 구조는 너무 느릴 수 있습니다. 전체 복구 훈련 시간을 측정하고 실제 RTO가 목표를 초과한다면 자동화, 미리 구축한 복구 이미지, 대기 서버 또는 구조 변경을 검토하세요.
