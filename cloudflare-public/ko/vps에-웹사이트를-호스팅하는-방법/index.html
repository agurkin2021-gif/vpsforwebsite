VPS에 웹사이트를 호스팅하는 방법

VPS에 웹사이트를 호스팅하는 방법: 배포 방식 선택, 안전한 첫 접속, 필요한 웹 스택 설치, 도메인 연결, HTTPS 설정, 재부팅 후 복구와 실제 운영 준비 상태 확인까지 안내합니다.

웹사이트에 실제로 필요한 서비스만 설치하세요.

제휴 안내: 편집자는 VDSina와 업무상 관계가 있으며, 제휴 링크를 통한 구매로 수수료를 받을 수 있습니다. 편집 원칙 및 제휴 관계 안내 (영문).

VPS에 웹사이트를 호스팅하는 방법은 배포할 애플리케이션에 따라 달라집니다. 정적 사이트에는 웹 서버와 DNS가 필요합니다. 워드프레스나 다른 PHP CMS에는 PHP와 데이터베이스도 필요합니다. Node.js 또는 Python 애플리케이션은 보통 리버스 프록시 뒤에서 실행합니다. 이러한 구성 요소를 초기 상태의 VPS에 직접 설치하거나, 컨트롤 패널을 사용해 브라우저에서 관리할 수 있습니다.

이 가이드는 새 VPS를 준비해 웹사이트를 실제로 공개하기까지의 절차를 다룹니다. 실제 데이터가 계속 변경되는 기존 운영 사이트를 옮긴다면 웹사이트 VPS 이전에서 서비스 전환과 롤백 절차를 확인하세요.

VPS 구매의 전반적인 판단 기준은 웹사이트용 VPS 호스팅을 참고하세요.

빠른 배포 순서

안정적인 첫 배포는 다음 순서로 진행합니다.

  1. VPS를 선택하고 필요한 사양을 산정합니다.
  2. 수동 관리, 컨트롤 패널 또는 관리형 운영 중 하나를 선택합니다.
  3. 초기 상태의 운영체제나 제공업체의 현재 패널 이미지를 설치합니다.
  4. 첫 접속의 보안을 확보하고 root가 아닌 관리 계정으로 접속할 경로를 만듭니다.
  5. 운영체제를 업데이트합니다.
  6. 애플리케이션에 필요한 웹 스택만 설치합니다.
  7. 가능하다면 공개 DNS를 전환하기 전에 사이트와 애플리케이션을 설정합니다.
  8. 파일과 코드를 배포하고 소유권, 비밀 정보 및 데이터베이스 접근 권한을 설정합니다.
  9. SSH와 필요한 HTTP/HTTPS 접속을 유지하면서 방화벽을 제한합니다.
  10. 공개 DNS를 연결하기 전에 새 서버를 테스트합니다.
  11. 도메인이 VPS를 가리키도록 설정합니다.
  12. 호스트 이름으로 서버에 접근할 수 있게 되면 HTTPS를 활성화합니다.
  13. cron과 워커, 로그, 백업 및 외부 모니터링을 확인합니다.
  14. 한 번 재부팅하여 필요한 모든 서비스가 자동으로 다시 시작되는지 확인합니다.
  15. 이 모든 과정을 마친 뒤에야 실제 운영 준비가 끝났다고 판단합니다.

일반적인 VPS 가이드에 나온다는 이유만으로 PHP, MySQL, 메일 서버 또는 컨트롤 패널을 설치하지 마세요. 웹사이트에 실제로 필요한 구성 요소만 설치하세요.

수동 관리, 패널 또는 관리형 운영 선택

운영 방식은 세 가지로 구분됩니다.

수동 관리 / 컨트롤 패널 없음

초기 상태의 Linux VPS를 선택하고 SSH를 통해 스택을 관리합니다.

다음과 같은 경우에 적합합니다.

  • 애플리케이션 스택을 이해하고 있습니다;
  • 실행되는 서비스의 수와 자원 사용량을 최소화하려고 합니다;
  • Nginx/Apache/런타임을 개별 요구에 맞게 설정해야 합니다;
  • 스크립트, Git 또는 코드형 인프라를 사용합니다;
  • 전통적인 호스팅 계정 관리 화면이 필요하지 않습니다.

기존 컨트롤 패널 없는 VPS라는 주제는 이 절에 통합되어 있습니다. 같은 검색 의도를 두고 경쟁하는 별도의 URL을 만들지 않습니다.

컨트롤 패널

브라우저에서 사이트, 도메인, PHP, 데이터베이스, 메일 또는 사용자를 관리하는 것이 반복 작업을 실질적으로 줄여 준다면 호스팅 패널을 사용하세요.

컨트롤 패널이 있는 VPS를 참고하세요. 이미 FASTPANEL을 선택했다면 FASTPANEL VPS 호스팅을 참고하세요.

관리형 운영

패널과 운영 관리는 서로 다릅니다. 패치, 보안, 백업, 모니터링과 장애 대응을 맡을 사람이 없다면 사이트 공개 전에 책임 주체부터 정하세요.

관리형 VPS와 비관리형 VPS를 참고하세요.

배포 방식 진단

이 도구는 검토할 스택 구성을 알려 줍니다. 애플리케이션 공식 문서를 대신하지는 않습니다.

작업 부하와 선호하는 운영 방식을 선택하세요.

사전 준비 사항

서버를 설정하기 전에 다음을 준비하세요.

  • 작업 부하에 맞는 사양의 VPS;
  • 서버 IP 주소;
  • SSH 자격 증명 또는 키 기반 접속;
  • 정상 작동하는 제공업체 콘솔/VNC/복구 경로;
  • 등록된 도메인과 DNS 접근 권한;
  • 웹사이트 파일 또는 애플리케이션 저장소;
  • 필요한 런타임 버전;
  • 데이터베이스 요구사항;
  • 비밀 정보와 환경 변수 관리 계획;
  • 백업 저장 위치;
  • 웹사이트 가용성을 외부에서 확인할 방법.

필요한 자원이 아직 불확실하다면 배포 전에 웹사이트용 VPS 사양을 확인하세요.

VDSina의 현재 Standard VPS 페이지에는 Ubuntu 26.04/24.04/22.04/20.04, Debian 13/12/11/10, AlmaLinux, Rocky, CentOS, Oracle Linux 및 ArchLinux를 포함한 순수 OS 템플릿이 나열되어 있습니다. 이 가이드는 현재 웹 서버 문서와 패키지 설치 절차를 따라가기 쉬운 Ubuntu/Debian 방식의 예제를 사용합니다. 같은 구조를 다른 지원 Linux 배포판에도 적용할 수 있지만 패키지 및 서비스 명령은 달라집니다.

웹사이트용 VPS 선택

제휴 고지: 편집자는 VDSina와 업무상 관계가 있으며, 이 제휴 링크로 주문하면 사이트가 수수료를 받을 수 있습니다. 수수료가 아니라 실제 작업 부하를 기준으로 서버 사양과 운영 방식을 선택하세요.

운영체제 선택

웹사이트 서버를 직접 관리한다면 다음 조건을 충족하는 운영체제를 선택하세요.

  • 애플리케이션과 런타임이 지원합니다;
  • 유지보수가 계속 제공됩니다;
  • 관리자가 익숙하게 다룰 수 있습니다;
  • 웹 스택에 필요한 최신 패키지와 문서가 있습니다;
  • 나중에 패널을 사용한다면 해당 패널의 요구사항에도 맞습니다.

가장 최신이라는 이유만으로 OS를 선택하지 마세요. 애플리케이션 호환성과 관리자의 숙련도가 더 중요합니다.

현재 Linux 환경을 설명하는 간단한 예제로는 Ubuntu 24.04 LTS 또는 Debian 12를 문서 기준으로 삼을 수 있습니다. 애플리케이션 공급업체가 다른 지원 배포판을 지정했다면 해당 요구사항을 따르세요.

안전한 첫 SSH 접속

새 VPS는 관리자 접근 권한을 제공하지만, 실제 운영 작업을 계속 root로 수행해서는 안 됩니다.

안전한 첫 접속 순서는 다음과 같습니다.

  1. VPS 제공업체가 제공한 자격 증명이나 키로 접속합니다;
  2. 해당 서버와 IP가 의도한 대상인지 확인합니다;
  3. 제공업체 콘솔/VNC/복구 경로를 계속 사용할 수 있게 유지합니다;
  4. 이름이 있는 별도의 관리 사용자를 생성합니다;
  5. 필요한 sudo 또는 관리자 권한만 부여합니다;
  6. 가능하다면 SSH 키 인증을 설정합니다;
  7. 기존 접속 방법을 비활성화하거나 제한하기 전에 두 번째 세션에서 새 계정의 로그인을 확인합니다.

Ubuntu/Debian 예제:

ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy

서버 보안을 강화하는 과정에서 유일하게 작동하는 관리 접속 경로를 차단하지 마세요.

SSH와 방화벽의 상세 보안 강화는 VPS 보안 점검표에서 다룹니다. 이 가이드에는 배포에 필요한 최소 사항만 포함합니다.

스택 설치 전 서버 업데이트

Ubuntu/Debian에서는 다음을 실행합니다.

sudo apt update
sudo apt upgrade -y

업데이트에 재부팅이 필요하다면 재부팅한 뒤 다시 접속할 수 있는지 확인하세요.

웹사이트를 공개한 뒤로 보안 업데이트를 미루지 마세요.

수동 구성 / 컨트롤 패널 없는 방식

직접 관리하는 VPS에는 애플리케이션에 필요한 서비스만 설치해야 합니다.

일반적인 구성은 다음과 같습니다.

정적 웹사이트

필요한 구성 요소:

  • Nginx 또는 Apache;
  • 웹사이트 파일;
  • DNS;
  • HTTPS.

기본적으로 필요하지 않은 구성 요소:

  • PHP;
  • MySQL/MariaDB/PostgreSQL;
  • 로컬 메일 서버.

PHP / 워드프레스 웹사이트

일반적으로 필요한 구성 요소:

  • Nginx 또는 Apache;
  • PHP-FPM / PHP 모듈;
  • 데이터베이스;
  • 웹사이트 파일과 업로드 파일;
  • DNS;
  • HTTPS.

워드프레스의 자원 사용 특성은 워드프레스용 VPS를 참고하세요.

Node.js / Python / 자체 개발 애플리케이션

일반적인 구성 요소:

  • 애플리케이션 런타임;
  • root가 아닌 전용 애플리케이션 사용자;
  • 프로세스 관리자 또는 systemd 서비스;
  • 가능하다면 localhost 또는 전용 소켓에서만 수신하는 애플리케이션;
  • Nginx/Apache 리버스 프록시;
  • 필요한 경우에만 데이터베이스;
  • DNS;
  • HTTPS.

개발 서버를 인터넷에 직접 노출하는 구성을 실제 운영 구조로 사용하지 마세요.

웹 서버 설치

Ubuntu의 현재 서버 문서는 Nginx와 Apache를 모두 지원합니다. 어느 하나가 모든 상황에서 더 좋은 것은 아닙니다.

Nginx 예제:

sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

네트워크와 방화벽 규칙에서 HTTP를 허용했다면 이 단계에서 서버 IP에 접속할 때 기본 Nginx 페이지가 표시되어야 합니다.

애플리케이션, 팀 또는 기존 설정에 Apache가 더 잘 맞는다면 Apache를 사용하세요.

웹사이트 호스트 이름 설정

DNS와 웹 서버 설정은 같은 작업의 두 부분입니다.

DNS 제공업체에서 호스트 이름이 VPS를 가리키도록 설정해야 하며, 웹 서버도 해당 호스트 이름의 요청에 어느 사이트로 응답할지 알아야 합니다.

Nginx에서는 도메인용 server 블록을 만듭니다. 기본 구조는 다음과 같습니다.

server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}

Ubuntu/Debian에서 사이트별 설정은 보통 다음 위치에 있습니다.

  • /etc/nginx/sites-available/
  • /etc/nginx/sites-enabled/

변경한 뒤에는 다음을 실행합니다.

sudo nginx -t
sudo systemctl reload nginx

설정을 다시 불러오기 전에 반드시 구문 검사를 하세요.

리버스 프록시를 사용하는 앱이라면 server 블록에서 요청을 로컬 애플리케이션 포트나 소켓으로 전달하도록 설정합니다.

파일 또는 애플리케이션 코드 배포

반복 가능한 배포 방법을 선택하세요.

SFTP/SCP

다음과 같은 경우에 적합합니다.

  • 작은 사이트;
  • 빈도가 낮은 수동 배포;
  • 처음 시작하는 간단한 프로젝트.

위험: 운영 디렉터리의 내용이 소스 저장소와 쉽게 달라질 수 있습니다.

SSH를 통한 rsync

반복 가능한 파일 동기화와 효율적인 증분 업데이트에 유용합니다.

Git 기반 배포

운영 릴리스를 저장소의 커밋과 일치시켜야 할 때 유용합니다.

CI/CD

자동 빌드·테스트·릴리스 단계를 도입할 만큼 배포가 빈번할 때 유용합니다.

어떤 방법을 사용하든 다음 원칙을 지키세요.

  • 작업에 root가 정말 필요한 경우가 아니라면 root로 배포하지 않습니다;
  • 적절한 배포 또는 애플리케이션 사용자가 애플리케이션 파일을 소유하도록 합니다;
  • 웹 서버에는 필요한 접근 권한만 부여합니다;
  • 비밀 정보는 공개 문서 루트 밖에 보관합니다;
  • 모든 사용자가 쓸 수 있는 권한을 손쉬운 해결책으로 사용하지 않습니다.

PHP / 워드프레스 구성

Ubuntu/Debian에서 PHP 사이트를 운영하려면 애플리케이션이 지원하는 현재 PHP-FPM 패키지와 필요한 확장 모듈을 설치하세요.

일반적인 구조:

브라우저 -> Nginx/Apache -> PHP-FPM -> 데이터베이스

다른 CMS의 확장 모듈 목록을 무작정 복사하지 마세요. 애플리케이션에 실제로 필요한 것만 설치하세요.

워드프레스에서는 다음을 수행합니다.

  • 데이터베이스와 전용 DB 사용자를 만듭니다;
  • 측정한 필요량을 기준으로 PHP 업로드·메모리·실행 제한을 설정합니다;
  • wp-config.php의 비밀 정보를 보호합니다;
  • 사이트 호스트 이름을 설정합니다;
  • HTTPS를 활성화합니다;
  • wp-cron과 백그라운드 작업을 검증합니다;
  • 작업 부하에 맞게 캐싱을 추가합니다.

사양과 성능에 관한 내용은 여기에서 중복 설명하지 않고 워드프레스용 VPS에서 다룹니다.

Node.js / Python / 자체 개발 앱 구성

터미널에서 개발용 명령을 수동으로 실행한 상태를 실제 운영 환경이라고 간주하지 마세요.

다음을 사용하세요.

  • 전용 애플리케이션 사용자;
  • 접근 권한이 제한된 환경 또는 설정 파일;
  • systemd 또는 적절한 운영용 프로세스 관리자;
  • 장애와 재부팅 후 자동 재시작;
  • 로컬 또는 사설 주소의 애플리케이션 리스너;
  • Nginx/Apache 리버스 프록시;
  • 애플리케이션 로그;
  • 상태 확인.

일반적인 흐름:

브라우저 -> HTTPS/Nginx -> 127.0.0.1:PORT의 애플리케이션 -> 데이터베이스/외부 서비스

프레임워크 자체의 운영 환경 배포 지침을 확인하세요.

데이터베이스: 필요한 경우에만 설치

정적 웹사이트에는 데이터베이스가 필요하지 않습니다.

데이터베이스가 필요한 동적 애플리케이션에서는 다음을 수행합니다.

  • 지원되는 데이터베이스 엔진을 설치합니다;
  • 전용 데이터베이스를 만듭니다;
  • 애플리케이션별 사용자를 만듭니다;
  • 필요한 권한만 부여합니다;
  • 자격 증명을 웹 루트 밖에 보관합니다;
  • 보안이 확보된 특정 구조에서 요구하는 경우가 아니라면 데이터베이스 포트를 외부에 공개하지 않습니다;
  • 백업과 모니터링 계획에 데이터베이스를 포함합니다.

웹 서버가 거의 유휴 상태여도 데이터베이스 작업이 VPS의 실제 병목이 될 수 있습니다.

파일 소유권, 권한 및 비밀 정보

다음 두 가지 흔한 실수를 피하세요.

  1. 웹사이트를 root로 실행하는 것;
  2. 권한 오류를 해결한다며 모든 사용자가 애플리케이션 디렉터리에 쓸 수 있도록 만드는 것.

대신 다음 원칙을 지키세요.

  • 배포 또는 애플리케이션 사용자를 사용합니다;
  • 어떤 프로세스에 읽기 또는 쓰기 권한이 필요한지 파악합니다;
  • 업로드와 캐시 디렉터리에는 필요한 쓰기 권한만 부여합니다;
  • 환경 파일과 자격 증명을 보호합니다;
  • 운영 환경의 비밀 정보를 Git에 커밋하지 않습니다;
  • 개인 키는 공개 문서 루트 밖에 보관합니다.

정확한 소유권 설정은 애플리케이션과 웹 서버의 운영 방식에 따라 다릅니다. 만능 해결책처럼 chmod 777을 복사하지 말고 애플리케이션 문서를 따르세요.

공개 DNS 연결 전 테스트

DNS 연결이 애플리케이션의 첫 실제 테스트가 되게 하지 마세요.

공개 트래픽을 전환하기 전에 가능한 방법으로 새 서버를 검증하세요.

  • 서버 IP로 접속하여 기본 페이지나 정적 파일을 간단히 확인합니다;
  • 로컬 hosts 파일을 수정하여 본인의 컴퓨터에서만 example.com이 새 VPS로 연결되게 합니다;
  • 의도치 않게 검색엔진에 중복 색인되지 않도록 통제된 비공개 또는 테스트용 호스트 이름을 사용합니다;
  • 실제 운영에 사용할 것과 같은 Nginx/Apache 호스트 이름 설정을 통해 애플리케이션을 테스트합니다.

홈페이지만 확인해서는 안 됩니다.

  • 중요한 내부 페이지;
  • 로그인과 관리자 화면;
  • 폼;
  • 업로드;
  • 정적 자원;
  • 데이터베이스 읽기와 쓰기;
  • 애플리케이션과 API 엔드포인트;
  • 리다이렉트;
  • 로그.

많은 애플리케이션은 서버 IP로 접근할 때와 실제 호스트 이름으로 접근할 때 다르게 작동하므로 hosts 파일을 이용한 테스트가 특히 유용합니다.

기존 운영 사이트라면 웹사이트 VPS 이전의 더 엄격한 전환 절차를 사용하세요.

도메인을 VPS에 연결

DNS 제공업체에서 이 서버에 도달해야 하는 레코드를 설정하세요.

일반적인 IPv4 설정:

이름유형값
@AVPS IPv4 주소
wwwCNAME루트 도메인

www에 A 레코드를 사용하는 것도 가능합니다.

VPS에 IPv6가 실제로 설정되어 있고 접근할 수 있는 경우에만 AAAA 레코드를 추가하세요. 잘못된 AAAA 레코드가 있으면 IPv4가 작동해도 일부 방문자는 접속하지 못할 수 있습니다.

DNS만으로 웹사이트가 작동하는 것은 아닙니다. Nginx/Apache 사이트 설정에도 일치하는 호스트 이름이 있어야 합니다.

기존 운영 사이트를 옮기는 경우 DNS 전환과 마지막 데이터 쓰기 처리는 웹사이트 VPS 이전에서 다룹니다.

DNS 연결 확인 후 HTTPS 추가

공개 호스트 이름이 인증 요청에 응답할 서버로 연결되는 것을 확인한 뒤에 신뢰할 수 있는 인증서를 발급받으세요. 사용할 HTTP/HTTPS 인증 경로가 방화벽과 제공업체 네트워크 규칙에서 이미 허용되어 있는지 확인하세요.

Nginx/Apache에서는 Certbot과 같은 ACME 클라이언트로 Let’s Encrypt 인증서를 요청하고 갱신할 수 있습니다. 오래된 패키지 명령을 무작정 복사하지 말고 현재 Certbot 및 OS 지침을 따르세요.

다음을 확인하세요.

  • 인증서가 사용하는 루트 도메인과 www 변형을 모두 포함합니다;
  • HTTP가 의도한 대로 HTTPS로 리다이렉트됩니다;
  • 인증서 갱신이 자동화되어 있습니다;
  • 방화벽과 CDN 설정에서도 갱신이 가능합니다;
  • 애플리케이션이 올바른 HTTPS URL을 생성합니다.

인증서 설정이 정상 작동하는지 확인하기 전에 HTTPS 리다이렉트를 활성화하지 마세요.

방화벽 설정

방화벽 규칙을 변경하는 동안에도 관리 접속이 유지되도록 하세요.

기본적인 공개 웹사이트에는 일반적으로 다음이 필요합니다.

  • 필요한 관리 출발지 또는 접속 경로에서의 SSH;
  • HTTP/ACME/리다이렉트용 TCP 80;
  • HTTPS용 TCP 443.

MySQL/PostgreSQL, Redis 또는 애플리케이션 내부 포트가 기본적으로 로컬에서 수신한다는 이유만으로 외부에 공개하지 마세요.

UFW를 사용하는 서버에서는 제한적인 규칙을 활성화하기 전에 필요한 SSH 접속 경로를 허용하세요.

상세 방화벽 설정과 보안 강화는 VPS 보안 점검표에서 다룹니다.

Cron 작업, 큐 및 워커

동적 웹사이트는 웹 요청을 처리하는 경로만 설정해 두어 배포 후 문제가 생기는 경우가 많습니다.

다음 작업을 목록으로 정리하세요.

  • cron 작업;
  • 큐 워커;
  • 예약 작업;
  • 가져오기와 내보내기;
  • 이메일 작업;
  • 캐시 예열 작업;
  • 백그라운드 처리 작업.

이 작업들이 다음 조건을 충족하도록 하세요.

  • 적절한 비root 사용자로 실행됩니다;
  • 필요한 경우 자동으로 시작됩니다;
  • 위치가 명확한 로그에 기록됩니다;
  • CPU/RAM을 고갈시키는 방식으로 겹쳐 실행되지 않습니다;
  • 서버 재부팅 후에도 다시 작동합니다.

로그와 기본 관측 체계

실제 트래픽을 받기 전에 사이트에 문제가 생기면 어디를 확인할지 파악하세요.

최소한 다음 항목의 위치와 확인 방법을 알아 두세요.

  • Nginx/Apache 접근 로그;
  • Nginx/Apache 오류 로그;
  • 애플리케이션 로그;
  • PHP-FPM 또는 런타임 로그;
  • 데이터베이스 로그와 상태;
  • 시스템 저널;
  • 디스크 사용량;
  • 메모리와 CPU 부하.

VPS에 로그인한 사람이 없어도 서버 장애를 알 수 있도록 외부 HTTP(S) 가동 상태 확인을 추가하세요.

임계값과 알림 설계의 상세 내용은 VPS 모니터링에서 다룹니다.

재부팅 검증

처음 구축한 VPS 환경은 첫 재부팅 전까지만 정상 작동하는 경우가 의외로 많습니다.

서버 준비가 끝났다고 판단하기 전에 다음을 실행합니다.

sudo reboot

서버가 다시 켜지면 다음을 확인하세요.

  • SSH 접속;
  • Nginx/Apache;
  • PHP-FPM 또는 앱 서비스;
  • 데이터베이스;
  • cron과 큐 워커;
  • HTTPS;
  • 웹사이트 페이지와 폼;
  • 모니터링;
  • 백업 일정.

누군가 수동으로 명령을 실행해야만 애플리케이션이 다시 작동한다면 배포가 완료된 것이 아닙니다.

수동 관리 / 패널 없는 호스팅이 맞지 않는 경우

다음에 해당한다면 컨트롤 패널이나 관리형 운영을 사용하세요.

  • SSH와 명령줄 복구에 익숙한 사람이 없습니다;
  • OS와 보안 업데이트를 책임지는 사람이 없습니다;
  • 웹 서버, 런타임 또는 데이터베이스 장애를 진단할 사람이 없습니다;
  • 백업은 만들어지지만 복원할 사람이 없습니다;
  • 비즈니스에 중요한 서비스 중단에 대응할 담당자가 없습니다;
  • 팀이 서버 설정 대신 호스팅 UI에서 메일, 사용자와 도메인을 관리하려고 합니다;
  • 애플리케이션 스택이 관리형 플랫폼에 더 적합합니다.

직접 관리하는 VPS는 패널의 자원 사용량을 줄이고 제어 범위를 넓힐 수 있지만 운영 책임까지 줄여 주지는 않습니다.

패널 선택은 컨트롤 패널이 있는 VPS를, 운영 책임 주체가 부족한 경우에는 관리형 VPS와 비관리형 VPS를 참고하세요.

실제 운영 준비 점검표

점검 항목통과 조건
서버 접속별도 관리 계정으로 로그인할 수 있고 복구 콘솔을 계속 사용할 수 있음
업데이트현재 보안 및 시스템 업데이트 적용 완료
웹 서버자동으로 시작되고 설정 검사 통과
사이트 호스트 이름루트 도메인과 www의 동작이 의도한 대로 설정됨
DNSA/AAAA/CNAME이 의도한 서버와 경로로 연결됨
HTTPS신뢰할 수 있는 인증서, 올바른 이름, 파악된 갱신 경로
애플리케이션대표 페이지, 로그인, 폼 및 업로드 정상 작동
데이터베이스애플리케이션 사용자 정상 작동, DB 포트가 의도치 않게 외부에 공개되지 않음
파일올바른 소유권, 777 우회 설정 없음
작업cron과 워커가 올바르게 시작되고 로그를 기록함
재부팅필요한 서비스가 자동으로 복구됨
로그운영자가 웹·앱·시스템 장애 기록 위치를 알고 있음
백업필요한 파일과 데이터베이스가 포함되고 복원 경로가 정해져 있음
모니터링외부 웹사이트 확인과 기본 자원 상태 관찰 가능
용량실제 작업 부하에서 CPU/RAM/디스크 확인 완료

홈페이지가 HTTP 200을 반환한다는 사실만으로 웹사이트의 실제 운영 준비가 끝난 것은 아닙니다.

백업과 모니터링 인계

이 페이지는 운영 인계에 필요한 최소 기준만 정합니다.

사이트를 믿고 운영하기 전에 다음을 수행하세요.

  • 백업 일정을 설정합니다;
  • 독립적인 복사본을 서버 외부에 보관합니다;
  • 복구에 필요한 데이터베이스, 설정과 비밀 정보를 포함합니다;
  • 실제로 복원할 수 있는지 확인합니다;
  • 웹사이트 가용성을 모니터링합니다;
  • 디스크 사용량 증가를 모니터링합니다;
  • CPU/RAM/데이터베이스 부하를 관찰합니다;
  • 인증서 갱신을 확인합니다.

상세 복구 설계는 VPS 백업 전략에서 다룹니다. 모니터링 임계값과 알림 설계는 VPS 모니터링에서 다룹니다.

여러 웹사이트 운영

사이트가 여러 개라면 다음 원칙을 지키세요.

  • 호스트 이름마다 별도의 server 블록 또는 가상 호스트를 사용합니다;
  • 문서 루트를 분리합니다;
  • 애플리케이션과 데이터베이스 자격 증명을 각각 분리합니다;
  • 신뢰 관계에 따른 격리 요구가 있다면 시스템 사용자도 분리합니다;
  • 한 사이트의 cron, 가져오기 또는 백업 작업이 다른 사이트의 자원을 고갈시키지 않도록 합니다;
  • 전체 사이트의 최대 부하를 합산하여 계산합니다;
  • 모든 사이트가 여전히 하나의 VPS 장애 범위를 공유한다는 점을 이해합니다.

용량과 격리 계획은 여러 웹사이트용 VPS를 참고하세요.

FAQ

컨트롤 패널 없이 VPS에 웹사이트를 호스팅할 수 있나요?

예. 초기 상태의 Linux VPS에 SSH와 애플리케이션이 요구하는 웹 서버, 런타임 및 데이터베이스 구성 요소를 갖추면 웹사이트를 호스팅할 수 있습니다. 패널 없는 운영이라는 검색 의도는 별도의 경쟁 페이지가 아니라 이 가이드에서 다룹니다.

VPS에 웹사이트를 호스팅하려면 Nginx가 필요한가요?

아니요. Nginx와 Apache 모두 일반적인 선택입니다. 애플리케이션, 설정과 관리자의 경험에 맞는 웹 서버를 사용하세요.

VPS에서 운영하는 모든 웹사이트에 데이터베이스가 필요한가요?

아니요. 정적 웹사이트에는 필요하지 않습니다. 애플리케이션이 데이터베이스를 요구할 때만 MySQL/MariaDB/PostgreSQL을 설치하세요.

웹사이트를 root로 호스팅해야 하나요?

아니요. Root는 관리 작업을 위한 계정입니다. 필요한 권한만 부여한 적절한 비root 사용자와 서비스로 웹사이트를 실행하고 배포하세요.

컨트롤 패널은 언제 사용해야 하나요?

브라우저에서 사이트, 도메인, PHP, 데이터베이스, 사용자, 메일 또는 백업을 관리하는 것이 패널의 자원 사용량과 제약을 감수할 만큼 반복 관리 작업을 줄여 줄 때 사용하세요.

cPanel 없이 VPS에 워드프레스를 호스팅할 수 있나요?

예. 워드프레스에는 호환되는 웹 서버, PHP, 데이터베이스, 워드프레스 파일, 올바른 권한, DNS와 HTTPS가 필요합니다. 패널은 선택 사항입니다.

DNS를 언제 VPS로 연결해야 하나요?

새 사이트라면 서버가 실제 호스트 이름의 요청에 응답할 준비가 되었을 때 연결하세요. 기존 운영 사이트라면 먼저 테스트한 뒤 통제된 이전 및 전환 계획을 사용하세요.

도메인이 VPS를 가리키는데 왜 다른 사이트가 표시되나요?

DNS는 호스트 이름을 서버 IP로 연결하기만 합니다. Nginx/Apache에도 해당 호스트 이름과 일치하는 server 블록 또는 가상 호스트가 있어야 합니다.

HTTPS는 언제 활성화해야 하나요?

공개 호스트 이름이 서버로 연결되고 인증 경로가 정상 작동한 뒤에 활성화하세요. 그다음 인증서를 발급하고 루트 도메인과 www의 포함 여부를 확인한 뒤 의도한 HTTP-to-HTTPS 리다이렉트를 설정하세요.

VPS 재부팅 후 무엇을 확인해야 하나요?

웹 서버, 애플리케이션 서비스 또는 PHP-FPM, 데이터베이스, 워커, HTTPS, 모니터링과 웹사이트가 모두 수동 조작 없이 다시 작동하는지 확인하세요.
