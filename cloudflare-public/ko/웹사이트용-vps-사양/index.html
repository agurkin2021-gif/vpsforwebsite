사양 계산의 기본: 방문자 수보다 서비스별 자원 사용량

서버에서 어떤 서비스가 자원을 사용하는지 나누어 계산하면 필요한 용량을 더 정확하게 파악할 수 있습니다.

RAM 계산

전체 RAM에는 다음 항목이 모두 들어가야 합니다.

  1. 운영체제와 시스템 서비스
  2. 웹 서버 또는 리버스 프록시
  3. PHP-FPM, Node.js, Python 등의 애플리케이션 실행 환경
  4. 데이터베이스
  5. Redis 등 사용 중인 캐시 서비스
  6. 관리 패널과 패널이 실행하는 서비스
  7. 모니터링·보안·백업 프로세스
  8. 동시에 실행되는 애플리케이션 워커
  9. 순간적인 부하, 배포와 유지보수에 필요한 여유 용량

CMS의 메모리 제한을 서버 전체의 RAM 요구량으로 해석하면 안 됩니다. PHP 메모리 제한이 256 MB라고 해서 1 GB VPS에서 256 MB를 쓰는 PHP 프로세스 네 개와 Linux, 데이터베이스, 나머지 서비스를 동시에 안전하게 실행할 수 있는 것은 아닙니다.

실무에서는 다음과 같이 계산할 수 있습니다.

필요 RAM = 기본 서비스 + 데이터베이스 작업 메모리 + 동시 실행 워커 메모리 + 백그라운드 작업 메모리 + 여유 용량

가능하면 실제 프로세스의 사용량을 측정하세요. 추정치는 시작 사양을 고르는 데 쓰고, 그 사양이 충분한지는 측정 결과로 판단합니다.

RAM 사양 계산기

방문자 수로 어림잡는 대신 각 항목의 가정을 직접 입력해 보세요. 이 계산기는 RAM만 추정합니다. CPU·저장 용량·I/O 성능은 별도로 검증해야 합니다. 입력란의 예시 숫자는 아래 계산 예제와 같으며, 모든 사이트에 적용하는 기본값이 아닙니다. 직접 측정한 값을 입력하세요.

측정한 값을 입력하면 필요한 RAM을 계산할 수 있습니다.

계산 예시: 기본 서비스 450 MB + 데이터베이스 500 MB + 워커 6개 × 120 MB + 패널·캐시·백그라운드 작업 300 MB = 여유분을 제외하고 1,970 MB입니다. 여기에 25%의 여유를 두면 약 2.4 GB가 필요합니다. 이 가정에서는 2 GB VPS가 부족하므로 4 GB 구성이 더 안전한 출발점입니다.

PHP-FPM 같은 워커를 측정할 때 RSS 값을 그대로 더하면 프로세스끼리 공유하는 메모리 페이지와 라이브러리를 중복 계산할 수 있습니다. 프로세스 측정값은 판단 근거로 활용하되, 단순 합계가 정확한 전체 사용량이라고 가정하지 마세요.

CPU 계산

CPU 수요는 같은 시간에 수행해야 하는 작업량에 따라 달라집니다. 캐시된 정적 파일을 전달하는 작업은 비교적 가볍습니다. 반면 애플리케이션 코드 실행, 데이터베이스 조회, 페이지 생성, 이미지 크기 변경, 데이터 가져오기, API 처리 같은 동적 요청은 훨씬 많은 CPU를 사용할 수 있습니다.

다음 신호를 확인하세요.

  • 정상적인 사용자 요청 중 CPU가 지속적으로 포화 상태에 도달하는지
  • CPU가 바쁠 때 애플리케이션 응답 시간이 길어지는지
  • 비용이 큰 동적 요청 여러 개가 동시에 들어오는지
  • cron·백업·데이터 가져오기 작업이 사용자 요청과 겹치는지
  • 비효율적인 인덱스나 과도한 처리 때문에 데이터베이스 쿼리가 CPU를 많이 사용하는지

짧은 CPU 급등만으로 사양을 올릴 필요는 없습니다. 정상적인 작업이 반복적으로 지연될 만큼 포화 상태가 지속되는지가 더 중요한 근거입니다.

동시 요청 수는 다음 식으로 대략 추정할 수 있습니다.

처리 중인 동적 요청 수 ≈ 초당 동적 요청 수 × 요청 처리 시간

예를 들어 캐시되지 않은 동적 요청이 초당 6건이고 p95 처리 시간이 0.8초라면, 이 시간을 적용한 추정치는 약 4.8건입니다. 요청마다 워커 하나가 필요하다면 약 다섯 개의 사용 중인 워커에 대기열과 순간 부하를 감당할 여유를 더해 계획합니다. 각 요청이 CPU 시간 0.12초를 사용한다면 초당 6건은 여유분을 제외하고 매초 약 0.72 CPU초의 작업에 해당합니다. 이는 부하를 이해하기 위한 추정이며 보편적인 vCPU 처리량 보장이 아닙니다. CPU 세대, 자원 경합과 공급업체의 스케줄링 방식에 따라 결과가 달라집니다.

웹사이트 유형별 부하 예시

방문자 수가 같아도 원본 서버가 처리하는 작업량이 다르면 필요한 VPS 사양도 달라집니다.

사이트 유형주요 부하사양 선택 시 고려 사항
정적 콘텐츠 중심이거나 캐시 적용률이 높은 사이트낮은 애플리케이션 CPU 사용량, 적은 동시 워커, 주로 파일 전달작은 구성으로 시작할 수 있지만 OS·로그·백업과 예상치 못한 비캐시 요청도 계산
소규모 워드프레스 사이트PHP 워커, 데이터베이스 읽기, 플러그인·cron 작업월 방문자 수보다 RAM과 워커 여유가 중요한 경우가 많음
우커머스 등 거래 처리 사이트캐시되지 않는 장바구니·결제·계정 세션, 예약 작업, 더 많은 데이터베이스 쓰기동적 동시 요청, 데이터베이스 지연과 피크 중첩을 우선 확인하며, 운영 서버의 기본값을 1–2 GB로 잡지 않음
여러 웹사이트PHP·애플리케이션 워커, 데이터베이스와 cron 작업의 합산 부하, 겹치는 피크전체 피크 수요를 합산하고 한 사이트가 다른 사이트의 자원을 소진할 수 있다면 분리 검토
백그라운드 작업·자동화가 많은 사이트큐, 가져오기·내보내기, API 호출, 이미지 처리, 예약 작업사용자 요청 외의 작업에도 CPU·RAM을 배정하고, 급증하는 작업이 사이트를 방해하면 워커 분리

이는 일반적인 부하 유형이며 플랫폼별 성능 보장이 아닙니다. 가능하면 실제 측정값을 사용하세요.

공유 호스팅의 제한을 VPS 사양 판단에 활용하기

사이트를 이미 공유 호스팅에서 운영한다면, 호스팅 관리 화면에 사양 선택에 필요한 중요한 근거가 있을 수 있습니다.

다음 자료를 모으세요.

  • CPU 사용량과 CPU 제한 발생 기록
  • 물리 메모리 사용량
  • 진입 프로세스(EP) 또는 동시 요청 제한
  • 프로세스 수
  • 디스크 I/O와 IOPS 부하
  • 데이터베이스 크기와 증가량
  • 저장 공간 사용량
  • 월 방문자 수뿐 아니라 시간대별 트래픽 피크
  • 확인할 수 있다면 PHP 워커 또는 애플리케이션 프로세스의 동작

공유 호스팅에서 VPS로 이전하기 전 병목 진단

제한이 발생하는 패턴을 통해 요금제 선택 전에 무엇을 조사해야 할지 확인하세요. 이 도구는 CloudLinux 제한값을 vCPU나 RAM 사양으로 직접 환산하지 않습니다.

CloudLinux를 사용하는 cPanel 호스팅에서는 현재 순간값 하나보다 Resource Usage 사용 이력부터 확인하세요. 반복되는 제한과 발생 시각을 기록하고 트래픽·cron·백업·데이터 가져오기·관리자 작업 시간과 비교합니다.

실제로 관찰한 증상을 선택하세요.

공유 호스팅의 제한값을 그대로 VPS 사양으로 옮기지 마세요. CloudLinux CPU 비율, 진입 프로세스 제한과 메모리 한도는 현재 호스팅 환경의 조건입니다. 병목을 이해하는 근거이지 VPS 자원과 일대일로 대응하는 환산표가 아닙니다.

대신 다음 패턴을 살펴보세요.

CPU는 정상인데 메모리 제한이 반복되는 경우: vCPU를 추가하기 전에 워커·데이터베이스·백그라운드 작업의 메모리를 조사합니다.

정상적인 동적 작업 중 CPU 제한이 반복되는 경우: 애플리케이션과 데이터베이스의 처리 비용을 분석한 뒤, 꼭 필요한 작업에도 CPU가 부족하다면 증설을 검토합니다.

진입 프로세스 또는 워커가 포화되는 경우: 동적 동시 요청 수와 처리 시간을 측정합니다. 요청을 더 빨리 처리하면 서버를 키우지 않아도 대기열이 해소될 수 있습니다.

I/O 부하가 높은 경우: RAM을 추가하면 해결될 것이라고 가정하기 전에 백업·로그·데이터베이스 작업·가져오기·디스크 사용량이 큰 플러그인을 확인합니다.

이렇게 구분해야 실제 용량 부족과 비효율적인 구성 요소 하나 때문에 호스팅 한도에 걸리는 상황을 구별할 수 있습니다.

증상확인할 항목먼저 최적화할 부분증설을 검토할 시점
메모리 제한, 스왑 사용 또는 OOM프로세스 메모리, DB 작업 집합, 동시 워커메모리 누수, 과도하게 큰 워커, 캐시·DB 설정최적화한 부하가 여전히 RAM을 소진할 때
CPU 사용 제한지속적인 CPU 사용량과 요청·DB 처리 시간느린 코드, 캐시되지 않은 작업, 무거운 쿼리필요한 정상 작업이 계속 CPU에 막힐 때
EP·워커 대기열동적 동시 요청과 처리 시간캐시, 느린 엔드포인트, 워커 설정요청당 처리 비용을 줄여도 대기열이 남을 때
I/O 대기·IOPS 제한데이터베이스, 로그, 백업, 가져오기작업 시간 분산, 인덱스, 로그·백업 방식정상적인 작업에서도 저장 장치가 계속 병목일 때

VPS 증설과 웹사이트 최적화 중 무엇이 먼저일까요?

명확한 애플리케이션 문제를 해결한 뒤에도 정상적인 부하가 특정 자원을 반복해서 소진한다면 더 큰 VPS가 필요할 수 있습니다.

다음 원인으로 부하가 생긴다면 먼저 최적화하세요.

  • 느린 플러그인이나 확장 기능 하나
  • 인덱스가 없거나 비정상적으로 비싼 데이터베이스 쿼리
  • 제대로 작동하지 않는 페이지·객체 캐시
  • 악성 봇 트래픽
  • 끝나지 않거나 과도하게 반복되는 cron 작업
  • 지나치게 큰 이미지 처리
  • 피크 시간에 실행되는 백업·악성 코드 검사
  • 메모리 누수
  • 과도한 로그 기록

최적화한 작업에도 용량이 부족하다는 측정 결과가 있을 때 서버 자원을 늘립니다.

비용 측면에서도 이 구분이 중요합니다. 비효율적인 코드를 공유 호스팅에서 큰 VPS로 옮기면 병목을 제거하지 않은 채 잠시 가릴 수 있습니다.

동시 요청에 맞춰 PHP·애플리케이션 워커 계산하기

서버는 요청을 동시에 처리하므로 월 방문자 수만으로 사양을 정하기 어렵습니다.

동적 PHP 작업에서는 각 워커가 요청을 처리하는 동안 메모리와 CPU를 사용합니다. 따라서 워커 용량은 워커당 평균 메모리 사용량뿐 아니라 요청 처리에 걸리는 시간에도 좌우됩니다.

RAM을 간단히 점검하는 식은 다음과 같습니다.

워커용 RAM = 기본 서비스 사용량을 뺀 가용 RAM × 워커에 안전하게 배정할 수 있는 비율

이 용량을 측정한 워커 메모리와 비교하세요. 데이터베이스·캐시·운영체제에 남길 메모리가 없다면 계산상 가능한 최대 워커 수를 그대로 설정해서는 안 됩니다.

캐시 적용 여부도 계산을 바꿉니다. 캐시된 비로그인 방문자용 페이지는 PHP 실행을 완전히 건너뛸 수 있지만, 결제·로그인 세션·wp-admin·API·개인화 페이지는 여전히 애플리케이션에 도달합니다.

워드프레스의 구체적인 동작은 워드프레스용 VPS에서, 거래 처리 부하는 우커머스용 VPS에서 확인하세요.

데이터베이스 부하가 서버 사양을 결정할 수 있습니다

겉으로는 CPU가 부족해 보여도 실제 원인은 데이터베이스 작업일 수 있습니다.

다음 항목을 확인하세요.

  • 느린 쿼리 패턴
  • 데이터베이스 작업 집합의 크기
  • 동시에 실행되는 쿼리 수
  • 누락된 인덱스
  • 큰 자동 로드 데이터 또는 유사한 애플리케이션 메타데이터
  • 비용이 큰 검색·필터링·보고서 작업
  • 가져오기와 유지보수 작업
  • 저장 장치 지연 시간

데이터베이스가 실제로 더 큰 작업 집합을 필요로 한다면 RAM 증설이 도움이 될 수 있습니다. 하지만 비효율적인 쿼리를 고쳐 주지는 않습니다. CPU를 늘리면 처리량이 증가할 수 있지만, 동시에 더 많은 무거운 쿼리가 자원을 놓고 경쟁하게 될 수도 있습니다.

평균 트래픽보다 실제 피크를 기준으로 계획하기

평균값에 맞춰 사양을 고르면 사용자가 실제로 장애를 겪는 짧은 구간을 놓칠 수 있습니다.

캠페인 시작, 할인 행사, 뉴스레터 발송, 신상품 공개, 예약 가져오기, 백업이나 cron 작업이 몰리는 때처럼 현실적으로 가장 바쁜 시간대를 파악하세요. 그때 어떤 요청이 동적으로 처리되고 어떤 요청을 페이지 캐시나 CDN이 흡수할 수 있는지 추정합니다.

다음 작업이 겹칠 때를 위한 여유를 남겨 두세요.

  • 평상시 사용자 요청
  • 피크 시간의 동적 요청
  • 관리자 작업
  • 예약 작업
  • 배포와 캐시 예열
  • 모니터링·백업 프로세스

CDN은 정적 파일 전달과 일부 원본 서버 요청을 줄일 수 있습니다. 그러나 VPS까지 도달하는 동적 애플리케이션·데이터베이스 작업을 없애지는 않습니다.

피크 예시: 사이트가 초당 20건의 요청을 받고 그중 90%를 캐시·CDN이 처리한다면 원본 서버에는 초당 약 2건의 동적 요청이 도달합니다. 캠페인으로 전체 요청이 초당 40건으로 두 배가 되고 캐시 비율이 같다면 애플리케이션은 초당 약 4건을 받습니다. p95 처리 시간 0.8초를 적용하면 동시 동적 요청은 약 3.2건으로 추정됩니다. 여기에 관리자 작업이나 결제·API 요청의 순간 증가를 더해야 합니다.

저장 공간 계산

디스크 용량은 현재 웹사이트 폴더 크기만으로 정할 수 없습니다.

다음 항목을 포함하세요.

  • 웹사이트 파일
  • 데이터베이스
  • 업로드한 미디어
  • 로그
  • 임시 파일
  • 패키지·애플리케이션 캐시
  • 서버 안에 보관하는 스테이징 복사본
  • VPS에서 임시로 생성하는 백업 파일
  • 예상 데이터 증가량

파일 시스템이 거의 가득 차도록 운영하지 마세요. 데이터베이스·업데이트·로그·백업 작업에는 추가 작업 공간이 필요합니다.

실무에서는 다음과 같이 계산할 수 있습니다.

필요 디스크 = 현재 파일 + 데이터베이스 + 임시 작업 공간 + 로컬 백업 생성 공간 + 예상 증가량 + 여유 공간

예시: 현재 사용량 18 GB + 이전·업데이트용 임시 공간 8 GB + 로컬 백업을 잠시 보관할 공간 18 GB + 예상 증가량 6 GB만 합쳐도 안전 여유분을 더하기 전에 40 GB를 넘습니다. 이 상황에서는 80 GB 구성이 더 안전한 출발점입니다. 저장 용량은 IOPS와 저장 장치 지연 시간과 별개입니다. 디스크가 커진다고 느린 데이터베이스가 자동으로 빨라지지는 않습니다.

대역폭과 월 트래픽 계산

월 데이터 전송량은 CPU·RAM·포트 속도와 다른 항목입니다. 연산 자원에 여유가 있어도 큰 파일이나 캐시되지 않은 미디어를 직접 제공하면 트래픽 한도를 초과할 수 있습니다.

대략적인 계산식은 다음과 같습니다.

월 원본 서버 전송량 ≈ 요청당 VPS가 보내는 평균 바이트 × 월 원본 서버 요청 수 + 백업·내보내기·기타 송신량

더 유용한 추정을 위해 캐시할 수 있는 트래픽과 동적 트래픽을 나누어 보세요.

원본 서버 전송량 ≈ 캐시 가능한 콘텐츠의 전체 요청 바이트 × (1 − CDN·캐시 처리 비율) + 비캐시 동적 응답 + 웹 외 송신량

예를 들어 한 달 동안 사용자가 정적 파일·페이지 2 TB를 요청하고 CDN이 원본 서버에 다시 접근하지 않고 그 바이트의 80%를 제공한다면, VPS가 직접 전달하는 해당 캐시 가능 트래픽은 약 400 GB입니다. 여기에 동적 페이지·API 응답·백업·내보내기와 추가 캐시 미스 트래픽이 더해집니다.

CDN을 사용한다고 원본 서버 전송량이 0이 되지는 않습니다. 로그인 페이지, 결제, API, 캐시 미스, 캐시 삭제, 대용량 다운로드와 원본 서버에서 CDN으로 캐시를 채우는 작업도 전송량을 사용합니다. 월 트래픽 제공량과 네트워크 포트 속도도 구분하세요. 포트 속도는 순간적으로 가능한 처리량이고, 트래픽 제공량은 과금 기간 동안 전송할 수 있는 데이터 양입니다.

여러 웹사이트를 운영할 때 달라지는 계산

한 VPS의 여러 사이트는 CPU·RAM·저장 공간·프로세스 용량을 공유합니다. 각각은 작아도 피크 시간이 겹칠 수 있습니다.

전체 부하를 합산해 사양을 정하고, 한 사이트의 백그라운드 작업이 다른 사이트의 자원을 소진하지 않도록 충분한 여유를 남기세요. 격리·장애 영향·자원 경합이 중요해지면 서버 하나를 계속 키우기보다 작업을 나누는 편이 더 유용할 수 있습니다.

여러 사이트를 함께 운영할지 판단하려면 여러 웹사이트용 VPS를 참고하세요.

관리 패널과 메일 서비스도 자원을 사용합니다

관리 패널은 도메인·SSL·데이터베이스·PHP 버전·계정 관리를 쉽게 해 주지만 자체 서비스도 실행합니다. 웹사이트만 계산하지 말고 패널에 필요한 메모리와 저장 공간을 별도로 확보하세요.

메일을 운영하면 SMTP, IMAP/POP, 스팸 필터, 바이러스 검사, 큐, 로그와 메일함 저장 공간 같은 상시 사용량이 추가됩니다. 웹사이트와 메일을 같은 VPS에 올린다면 메일을 자원이 들지 않는 부가 기능으로 여기지 말고 RAM·CPU·저장 공간·백업 계산에 포함하세요.

소규모 사이트에서는 관리형 이메일 서비스로 메일을 옮겨 서버 부하와 운영 위험을 줄일 수 있습니다. VPS에 메일을 유지한다면 DNS 레코드와 공급업체·IP 제한 등 메일 전달 요건도 따로 확인하세요. VPS 사양을 높여도 발신자 평판 문제는 해결되지 않습니다.

패널을 이용해 운영하려면 관리 패널이 포함된 VPS에서 장단점을 비교하세요.

반복해서 적용할 수 있는 VPS 사양 선택 절차

  1. 현재 부하를 측정합니다. CPU·메모리·동적 동시 요청·데이터베이스 동작·저장 공간·피크 시간을 기록합니다.
  2. 병목을 구분합니다. CPU·RAM·워커·데이터베이스·I/O 문제와 소프트웨어 제한을 나눕니다.
  3. 명확한 비효율을 제거합니다. 용량을 구매하기 전에 캐시, 과도한 작업, 비정상적으로 무거운 쿼리와 악성 트래픽을 개선합니다.
  4. 자원별 필요량을 계산합니다. 기본 서비스·데이터베이스·애플리케이션 워커·패널·백그라운드 작업에 필요한 RAM을 확보합니다.
  5. 여유가 있는 시작 구성을 선택합니다. 여유가 전혀 없는 구성도, 근거 없이 과도한 자원을 구매하는 것도 피합니다.
  6. 현실적인 피크를 재현합니다. 유휴 상태의 첫 화면만 보지 말고 대표적인 동적 부하에서 구성을 검증합니다.
  7. 이전 후에도 모니터링합니다. 최초 추정치를 영구적인 정답으로 여기지 말고 측정 결과에 따라 조정합니다. 운영 기준은 VPS 모니터링을 참고하세요.

이전할 서버의 사양을 정했다면 웹사이트 VPS 이전에서 구성 목록, 비공개 테스트, 최종 데이터 동기화, DNS 전환과 되돌리기 계획을 준비하세요.

근거가 있는 사양 권고

유용한 VPS 권고에는 구성과 함께 그 구성을 선택한 이유가 있어야 합니다.

예를 들어 다음과 같이 설명할 수 있습니다.

2 vCPU / 4 GB RAM / 80 GB는 데이터베이스 기반 CMS를 사용하고, 캐시되지 않는 PHP 요청이 상당히 있으며, 관리 패널과 운영 여유가 필요한 기업 사이트의 시작 구성으로 적절할 수 있습니다. 특정 월 방문자 수를 처리한다는 보장은 아닙니다.

방문자 수만 알고 있다면 권고의 신뢰도는 낮아야 합니다. CPU 사용 이력, 메모리 부족, 동적 동시 요청, 워커 메모리, 데이터베이스 동작과 저장 공간 증가량을 알수록 판단 근거가 탄탄해집니다.

신뢰도를 간단히 구분하면 다음과 같습니다.

  • 낮음: 방문자 수, CMS 이름과 대략적인 저장 용량만 알고 있음
  • 보통: 일부 실제 CPU·RAM 이력, 부하 유형과 피크 패턴이 있음
  • 높음: CPU·RAM·I/O 시계열, 비캐시 동시 요청, 워커 메모리, 처리 시간, 데이터베이스 동작과 저장 공간 증가량이 있음

웹사이트용 VPS에는 RAM이 얼마나 필요한가요?

모든 사이트에 통하는 확실한 용량은 없습니다. 가벼운 캐시 사이트는 적은 메모리로 운영할 수 있지만, 데이터베이스·패널·동시 워커를 사용하는 동적 CMS는 훨씬 많은 RAM이 필요할 수 있습니다. 동시에 실행해야 하는 프로세스를 기준으로 계산하고 여유를 남기세요.

웹사이트용 VPS에 RAM 2 GB면 충분한가요?

작고 가벼운 부하라면 충분할 수 있습니다. 하지만 관리 패널, 데이터베이스, 여러 PHP 워커, 백그라운드 작업이나 여러 사이트를 함께 실행하면 빠듯해집니다. RAM 숫자만 보지 말고 실제 메모리 부족 신호를 측정하세요.

RAM 4 GB VPS는 어떤 사이트에 적합한가요?

4 GB VPS는 Linux·데이터베이스·애플리케이션 또는 PHP 워커·캐시에 더 많은 공간을 남길 수 있어 여러 기업용 CMS의 실용적인 시작점이 됩니다. 정확한 적합성은 동적 동시 요청, DB 부하, 백그라운드 작업과 패널 사용량에 달려 있습니다. 워드프레스에 대한 판단은 워드프레스용 VPS를 참고하세요.

VPS는 방문자를 몇 명까지 처리할 수 있나요?

방문자 수만으로 답할 수 없습니다. 캐시 적중률, 동시 요청, 애플리케이션 실행 시간, DB 작업과 백그라운드 작업에 따라 비슷한 방문자 수의 사이트도 필요한 처리 용량이 수십 배 이상 달라질 수 있습니다.

RAM과 CPU 중 무엇을 먼저 늘려야 하나요?

측정 결과에서 부족한 자원을 늘리세요. 메모리 부족, 스왑 사용이나 OOM은 RAM 증설 또는 메모리 최적화를 검토할 근거입니다. 정상적인 작업을 최적화한 뒤에도 CPU가 계속 포화된다면 CPU를 검토합니다. 데이터베이스와 I/O 병목은 따로 진단해야 합니다.

CDN을 사용하면 필요한 VPS 사양이 낮아지나요?

정적 파일 전달과 캐시 가능한 원본 서버 요청을 줄일 수 있습니다. 다만 원본 서버까지 도달하는 동적 애플리케이션 요청과 데이터베이스 작업은 계속 VPS 자원을 사용합니다.

평균 트래픽과 피크 트래픽 중 무엇에 맞춰야 하나요?
