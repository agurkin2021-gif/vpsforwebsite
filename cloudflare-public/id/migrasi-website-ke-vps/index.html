Migrasi Website ke VPS

Migrasi website ke VPS: inventarisasi stack saat ini, uji server baru, kendalikan penulisan data terakhir, alihkan DNS dengan aman, pertahankan email dan SEO, serta siapkan jalur rollback.

Migrasi website ke VPS paling aman ketika server baru disiapkan dan diuji sementara hosting lama masih melayani trafik. Inventarisasi stack saat ini, tentukan spesifikasi server tujuan, salin dan validasi website, kendalikan perubahan data terakhir, alihkan DNS pada tahap akhir, lalu pantau kedua lingkungan hingga hosting lama dapat dihentikan.

Halaman ini mengasumsikan struktur domain dan URL publik tetap sama. Jika domain atau jalur juga berubah, pemetaan URL dan pengalihan permanen menjadi tugas migrasi terpisah.

Untuk keputusan hosting yang lebih luas, lihat VPS untuk website.

Rencana migrasi cepat

Migrasi yang terkendali mengikuti urutan ini:

  1. Inventarisasi sumbernya. Catat aplikasi, runtime, database, file, DNS, mail, tugas cron, worker, webhook dan dependensi eksternal.
  2. Tentukan spesifikasi server tujuan. Pilih CPU, RAM, dan disk berdasarkan beban kerja nyata serta cadangan kapasitas untuk migrasi.
  3. Buat cadangan yang dapat dipulihkan. Simpan salinannya di luar server sumber dan verifikasi bahwa database dan file yang Anda perlukan benar-benar ada.
  4. Bangun VPS secara paralel. Pasang stack web atau panel kontrol dan sesuaikan dengan kebutuhan aplikasi sebelum lalu lintas berpindah.
  5. Salin kumpulan data lengkap pertama. Transfer file dan impor database selagi situs lama tetap aktif.
  6. Uji secara privat. Gunakan penggantian file host, nama host pratinjau terkontrol, atau metode serupa untuk menjalankan server baru sebelum DNS berubah.
  7. Kontrol penulisan akhir. Untuk toko, keanggotaan, formulir, dan situs perubahan lainnya, rencanakan penghentian penulisan singkat atau sinkronisasi delta akhir yang sesuai aplikasi.
  8. Ganti DNS terakhir. Ubah hanya catatan yang perlu dipindahkan dan jaga agar catatan surat/verifikasi tetap utuh.
  9. Pantau kedua server. Verifikasi lalu lintas, kesalahan, formulir, pesanan, tugas cron, webhook, email, HTTPS, dan perayapan pencarian.
  10. Hentikan hosting lama hanya setelah pemeriksaan penerimaan berhasil. Pertahankan ketersediaannya selama periode rollback.

Tidak ada janji universal yang jujur ​​mengenai zero downtime. Sasarannya adalah peralihan terkontrol dengan gangguan praktis terkecil dan tanpa kehilangan data yang tidak direncanakan.

Pemeriksaan Kesiapan Sebelum Peralihan Migrasi

Gunakan pemeriksa ini sebelum mengubah DNS. Hal ini tidak menjamin keberhasilan migrasi; ini memperlihatkan prasyarat yang hilang yang harus diselesaikan terlebih dahulu.

Tandai hanya hal yang benar-benar siap.

Inventarisasi website saat ini

Buat catatan migrasi sebelum menyentuh tujuan.

Rekam:

  • domain dan setiap subdomain aktif;
  • versi aplikasi/CMS/kerangka kerja;
  • PHP, Node.js, Python atau versi runtime lainnya;
  • mesin database/versi, ukuran dan model kredensial;
  • dokumen root dan direktori di luarnya;
  • unggahan/media dan direktori yang dapat ditulisi;
  • aturan redirect dan rewrite;
  • tugas cron, antrean, worker dan tugas terjadwal;
  • layanan cache seperti Redis jika digunakan;
  • konfigurasi SSL/TLS;
  • catatan DNS;
  • kotak surat, penerus dan jalur SMTP keluar;
  • gateway pembayaran, webhook dan panggilan balik API;
  • daftar IP pihak ketiga yang diizinkan;
  • Pembatasan CDN/WAF/origin;
  • Verifikasi Search Console/analitik;
  • penggunaan dan pertumbuhan penyimpanan saat ini.

Inventaris juga merupakan daftar periksa penerimaan setelah pemindahan: setiap item harus berfungsi di VPS atau sengaja ditinggalkan di layanan eksternal.

Tentukan Spesifikasi dan Siapkan VPS Tujuan

Jangan melakukan migrasi terlebih dahulu dan menanyakan apakah VPS sudah cukup besar setelahnya.

Gunakan beban kerja saat ini, perilaku database, pertumbuhan penyimpanan, penggunaan sumber daya tambahan oleh panel/email, dan ruang kerja migrasi untuk memilih server tujuan. Migrasi sendiri membutuhkan ruang disk sementara untuk arsip, dump database, log, dan penampungan backup lokal.

Gunakan penentuan spesifikasi VPS untuk website untuk penghitungan sumber daya alih-alih menduplikasinya di sini.

Migrasi juga merupakan keputusan jalur manajemen. Jika host lama menyembunyikan sebagian besar administrasi server, tentukan terlebih dahulu siapa yang akan mengoperasikan tujuan setelah peralihan: bandingkan VPS Managed vs Unmanaged. Kemudian putuskan apakah tujuan akan menggunakan panel kontrol atau stack Linux yang dikelola secara manual; lihat VPS dengan Control Panel untuk pilihan tersebut.

Pilih VPS tujuan

Pengungkapan: editor memiliki hubungan profesional dengan VDSina, dan situs ini dapat memperoleh komisi jika Anda memesan melalui tautan mitra ini. Panduan migrasi dan kriteria penentuan spesifikasi tidak berubah berdasarkan komisi.

Buat cadangan berkemampuan rollback

Cadangan hanya berguna jika berisi data yang Anda perlukan dan dapat dipulihkan.

Sebelum migrasi:

  1. membuat salinan baru file website;
  2. ekspor setiap database yang diperlukan;
  3. menyimpan salinan di luar akun hosting sumber;
  4. merekam file konfigurasi dan variabel lingkungan dengan aman;
  5. mencatat DNS dan catatan email secara terpisah;
  6. mengembalikan cadangan ke lingkungan sekali pakai/pengujian jika memungkinkan, atau setidaknya melakukan impor database nyata dan memverifikasi file yang mewakili alih-alih hanya memeriksa apakah arsip terbuka;
  7. pastikan salinan yang dipulihkan berisi data yang diharapkan dan dapat dijalankan sampai tahap yang memadai untuk mendukung rollback;
  8. tuliskan urutan rollback sebelum mengubah DNS.

Untuk situs dinamis, cadangan pertama bukanlah kumpulan data produksi akhir. Pesanan, pengiriman formulir, komentar, keanggotaan, atau unggahan dapat terus berubah setelah salinan pertama. Rencanakan delta terakhir secara terpisah.

Bangun tujuan sebelum DNS berubah

Tujuan harus dapat menjalankan situs sebelum lalu lintas umum tiba.

Cocokkan atau sengaja memvalidasi:

  • perilaku server web;
  • Versi PHP/Node/Python;
  • ekstensi/modul yang diperlukan;
  • mesin/versi database;
  • kepemilikan dan izin file;
  • batas unggahan/ukuran body permintaan;
  • lingkungan tugas terjadwal;
  • layanan cache;
  • aturan penulisan ulang/pengalihan;
  • variabel dan rahasia lingkungan;
  • kebutuhan jaringan SMTP/outbound;
  • aturan firewall;
  • jalur khusus aplikasi.

Jangan gunakan migrasi itu sendiri sebagai momen untuk meningkatkan setiap runtime atau menulis ulang stack kecuali perubahan tersebut diperlukan. Lebih sedikit perubahan simultan membuat rollback dan diagnosis lebih mudah.

Salin file dan database

Metode transfer yang tepat bergantung pada akses sumber.

Jalur sumber yang umum meliputi:

  • cPanel/Manajer File + ekspor phpMyAdmin;
  • SFTP/FTP ketika akses shell tidak tersedia;
  • SSH/rsync ketika kedua belah pihak mengizinkannya;
  • alat migrasi sadar aplikasi untuk perpindahan khusus CMS;
  • alat ekspor/cadangan penyedia.

Pertahankan file konfigurasi tersembunyi, seperti aturan rewrite, jika aplikasi memerlukannya. Setelah impor, periksa pengguna database, hak akses, character set/collation, dan pengaturan koneksi aplikasi.

Untuk kumpulan data yang besar, bandingkan ukuran, jumlah baris, atau checksum jika praktis, alih-alih berasumsi “transfer selesai” berarti “kumpulan data identik.”

Uji secara privat sebelum peralihan

Jangan arahkan DNS ke server yang belum teruji.

Uji tujuan dengan penggantian file host, nama host pratinjau terkontrol, atau metode privat lainnya yang menggunakan stack aplikasi sebenarnya.

Periksa:

  • beranda dan halaman internal yang representatif;
  • login admin;
  • login pengguna;
  • gambar, CSS, JavaScript, dan unduhan;
  • pencarian;
  • formulir dan pengiriman;
  • unggahan;
  • pengalihan;
  • titik akhir API;
  • checkout dan panggilan balik pembayaran;
  • cron/tindakan terjadwal;
  • antrean/worker;
  • email keluar;
  • aplikasi, server web dan log database;
  • tata letak dan navigasi seluler.

Nama host publik sementara tidak boleh menjadi duplikat yang tidak disengaja dalam penelusuran. Jika dapat dijangkau secara publik selama pengujian, jauhkan dari indeks dan hapus pemblokiran sementara dari nama host produksi sebenarnya sebelum peralihan.

Kontrol penulisan baru dan sinkronisasi akhir

Inilah perbedaan paling penting antara situs brosur dan situs transaksional.

Jika database lama dan baru dapat menerima penulisan selama transisi DNS, keduanya dapat berbeda. Pesanan yang disimpan di server lama tidak otomatis muncul di server baru.

Untuk website dengan data yang terus berubah:

  1. pilih jendela peralihan berisiko rendah;
  2. menjeda atau mengontrol penulisan baru pada sumber jika memungkinkan;
  3. hentikan atau kendalikan tugas cron dan worker antrean yang dapat menulis data dua kali;
  4. jalankan sinkronisasi database akhir dan salin unggahan/file yang diubah;
  5. mencatat waktu acuan utama terakhir;
  6. mengalihkan lalu lintas;
  7. pastikan penulisan data baru kini hanya dilakukan di server tujuan.

Untuk VPS untuk WooCommerce, sertakan checkout, pesanan, pembayaran webhook, stok, tindakan terjadwal, dan email transaksional dalam tes penerimaan. Situs statis/cache mungkin hanya memerlukan perbandingan file akhir.

Jangan menyebut migrasi sebagai “zero downtime” kecuali aplikasi dan metode sinkronisasi benar-benar mendukungnya.

Ganti DNS dengan sengaja

DNS adalah peralihan lalu lintas, bukan langkah migrasi pertama.

Sebelum peralihan:

  • mengekspor atau mencatat zona saat ini;
  • mengidentifikasi dengan tepat catatan A/AAAA/CNAME/origin mana yang harus diubah;
  • turunkan TTL yang relevan setidaknya satu interval TTL sebelumnya sebelum peralihan yang diinginkan bila memungkinkan; misalnya, jika TTL saat ini adalah 86.400 detik, kurangi lebih dari 24 jam sebelum peralihan;
  • ingat bahwa menurunkan TTL sekarang tidak menghapus cache yang sudah menyimpan TTL lama dengan masa berlaku lebih panjang;
  • menyimpan MX, SPF, DKIM, DMARC, verifikasi TXT, SRV, CAA dan catatan lain yang tidak dipindahkan;
  • memverifikasi perilaku root dan www.

Mengubah catatan A/AAAA biasanya memiliki risiko lebih rendah dibandingkan mengganti server nama ketika penyedia DNS itu sendiri tidak berubah. Jika server nama berubah, buat ulang zona lengkap yang diperlukan terlebih dahulu.

Setelah peralihan, verifikasi DNS publik dari lebih dari satu penyelesai/jaringan dan lihat lalu lintas berpindah dari server lama ke server baru.

Jaga agar email tidak rusak

Migrasi website dan migrasi email adalah tugas yang terpisah meskipun akun hosting bersama yang lama menggabungkan keduanya.

Pilih satu jalur sebelum peralihan:

  • menyimpan email dengan penyedia saat ini/yang dikelola dan menyimpan data MX/TXT yang ada;
  • memindahkan email ke penyedia terkelola lainnya;
  • memindahkan email ke VPS dan membangun kembali kotak surat, perutean, otentikasi, dan kontrol keterkiriman.

Jika surat dipindahkan, perhitungkan:

  • Prioritas MX;
  • SPF;
  • DKIM;
  • DMARC;
  • reverse DNS/PTR jika berlaku;
  • data kotak surat;
  • alias/forwarder;
  • kredensial SMTP;
  • pemfilteran spam;
  • cadangan dan reputasi pengirim.

Jangan mengganti seluruh zona DNS hanya untuk memindahkan website kecuali catatan email dan semua dependensi lainnya direproduksi.

Verifikasi HTTPS, CDN, dan layanan eksternal

Jika wilayah server tujuan belum diputuskan, tentukan sebelum peralihan dengan Cara Memilih Lokasi VPS. Mengubah wilayah di kemudian hari dapat berarti migrasi IP/DNS lagi.

Tujuan yang berfungsi berdasarkan IP masih bisa gagal dengan nama host sebenarnya.

Verifikasi:

  • Sertifikat TLS mencakup nama host yang diperlukan;
  • HTTP → Pengalihan HTTPS benar;
  • root ↔ www perilaku kanonik tidak berubah;
  • Asumsi HSTS dipahami;
  • CDN/WAF menunjuk ke atau mengizinkan origin baru;
  • penanganan IP klien nyata masih berfungsi jika diproksi;
  • pembayaran webhook mencapai origin baru;
  • Penyedia API yang mengizinkan IP server lama diperbarui;
  • Kredensial SMTP/API valid dari server baru.

Jaga agar pengecualian firewall/WAF sementara tetap sempit dan hapus setelah penerimaan.

Pertahankan SEO saat URL tetap sama

Perubahan hosting murni biasanya mempertahankan URL publik yang sama. Dalam hal ini, tugas SEO sebagian besar adalah paritas, bukan pemetaan pengalihan.

Sebelum dan sesudah peralihan bandingkan:

  • kode status HTTP;
  • URL kanonik;
  • robots.txt;
  • meta robot / noindex yang tidak disengaja;
  • URL peta situs;
  • tautan internal;
  • data terstruktur jika penting;
  • konten halaman dan aset yang dirender;
  • Verifikasi Search Console;
  • respons server terhadap Googlebot dan pengguna biasa.

Pusat Penelusuran Google merekomendasikan persiapan dan pengujian hosting baru, mengubah DNS hanya jika sudah siap, memantau hosting lama dan baru, dan menghentikan infrastruktur lama setelah lalu lintas berpindah. Ia juga merekomendasikan untuk menurunkan TTL DNS terlebih dahulu dan menjaga verifikasi Search Console tetap berfungsi.

Jika hanya infrastruktur hosting yang berubah dan domain/URL tetap sama, jangan gunakan alat Ganti Alamat Google Search Console. Alat tersebut ditujukan untuk pemindahan domain, bukan migrasi hosting dengan URL yang sama.

Jika domain atau jalur URL juga berubah, gunakan peta URL lama ke baru dan pengalihan sisi server permanen. Itu adalah masalah perpindahan situs yang berbeda dari migrasi VPS URL yang sama.

Penerimaan pasca-migrasi dan rollback

Setelah DNS berubah:

  • memantau akses/log kesalahan pada server lama dan baru;
  • konfirmasi aktivitas pengguna baru mencapai database tujuan;
  • formulir pengujian, checkout, login dan unggah lagi;
  • verifikasi cron, antrean dan tindakan terjadwal;
  • memverifikasi perutean email keluar dan email masuk jika relevan;
  • perhatikan perilaku CPU, RAM, disk, dan database;
  • mengonfirmasi perilaku HTTPS dan CDN/WAF;
  • periksa URL penting untuk paritas 200/redirect;
  • memantau sinyal perayapan/pengindeksan Search Console;
  • menjaga lingkungan lama tetap tersedia melalui jendela stabilitas yang disepakati.

rollback memiliki batas data

rollback awal bisa sesederhana mengarahkan DNS kembali hanya saat server lama masih menjadi acuan utama yang valid.

Setelah pesanan, pendaftaran, komentar, atau unggahan ditulis ke server baru, rollback khusus DNS dapat kehilangan perubahan baru tersebut. Pada saat itu rollback memerlukan rekonsiliasi data atau sinkronisasi terencana lainnya.

Tentukan pemicu rollback sebelum migrasi, misalnya:

  • kesalahan 5xx yang tersebar luas;
  • checkout/kegagalan pembayaran;
  • database rusak atau penulisan hilang;
  • ketidakcocokan runtime yang parah;
  • otentikasi rusak;
  • kegagalan email kritis/webhook yang tidak dapat diperbaiki dalam jangka waktu yang disepakati.

Pertanyaan Umum

Bisakah saya memigrasikan website ke VPS tanpa mengubah domain?

Ya. Migrasi hosting dapat mempertahankan domain dan URL publik yang sama. Bangun dan uji tujuan terlebih dahulu, lalu ubah data DNS untuk mengirimkan lalu lintas ke server baru.

Apakah saya memerlukan pengalihan 301 saat memindahkan website ke VPS?

Tidak jika URL publiknya tetap sama. Pengalihan diperlukan ketika URL benar-benar berubah, seperti domain baru, perubahan protokol/jalur, atau konten yang direstrukturisasi.

Bagaimana cara mengurangi downtime selama migrasi VPS?

Siapkan tujuan secara paralel, turunkan TTL DNS yang relevan terlebih dahulu, uji secara privat, kendalikan penulisan akhir, jalankan sinkronisasi data akhir, alihkan DNS hanya setelah penerimaan dan pertahankan host lama tetap tersedia selama propagasi.

Haruskah saya memindahkan email ke VPS juga?

Tidak otomatis. Mempertahankan email di layanan email terkelola dapat mengurangi risiko migrasi dan masalah keterkiriman. Jika email dipindahkan, rencanakan MX, SPF, DKIM, DMARC, data kotak surat, reverse DNS jika relevan, serta pencadangannya secara terpisah.

Apa yang harus saya uji sebelum mengubah DNS?

Uji halaman perwakilan, login, formulir, unggahan, pencarian, checkout/panggilan balik pembayaran jika relevan, tugas terjadwal, API/webhook, email keluar, HTTPS, pengalihan, dan log aplikasi/server.

Berapa lama saya harus mempertahankan hosting lama setelah migrasi?

Simpan sampai lalu lintas DNS berpindah, server baru stabil, penulisan baru diverifikasi dan jendela rollback yang disetujui telah berlalu. Gunakan log, bukan jumlah jam atau hari universal yang tetap.
