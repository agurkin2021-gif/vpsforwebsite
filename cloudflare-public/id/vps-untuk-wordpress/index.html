VPS untuk WordPress

VPS untuk WordPress: tentukan CPU dan RAM dari proses PHP, beban database, caching, plugin, dan tugas latar belakang, lalu pilih cara pengelolaan dan migrasi yang tepat.

Lokasi server Pilih wilayah yang dekat dengan audiens utama; RAM tambahan tidak dapat menghilangkan latensi jaringan.

Pengungkapan: editor memiliki hubungan profesional dengan VDSina. Tautan mitra dapat menghasilkan komisi. Pengungkapan editorial dan komersial.

VPS untuk WordPress bermanfaat saat WordPress membutuhkan kontrol, isolasi, atau fitur tingkat server yang tidak tersedia pada shared hosting. Tentukan spesifikasinya berdasarkan pemrosesan PHP tanpa cache, kebutuhan database, plugin, tugas latar belakang, pertumbuhan penyimpanan, dan layanan yang berjalan bersama WordPress, bukan jumlah pengunjung bulanan.

Untuk keputusan server yang lebih luas, lihat VPS untuk website.

Persyaratan WordPress bukan penentuan spesifikasi VPS

WordPress.org saat ini merekomendasikan host yang mendukung:

  • PHP 8.3 atau lebih tinggi;
  • MariaDB 10.11+ atau MySQL 8.0+;
  • HTTPS;
  • Apache atau Nginx sebagai pilihan server web yang direkomendasikan.

Persyaratan ini menjawab “dapatkah server ini menjalankan WordPress?”, bukan “berapa sumber daya VPS yang dibutuhkan beban produksi ini?”

VPS produksi juga memerlukan RAM/CPU/penyimpanan untuk:

  • Linux;
  • Nginx/Apache;
  • worker PHP-FPM;
  • MySQL/MariaDB;
  • OPcache;
  • halaman/objek cache jika digunakan;
  • panel kontrol;
  • email jika dihosting secara lokal;
  • cadangan;
  • tugas cron;
  • pemindaian malware/keamanan;
  • impor/ekspor;
  • pemantauan;
  • cadangan kapasitas operasional.

Jangan gunakan persyaratan perangkat lunak WordPress sebagai rekomendasi sumber daya produksi.

Pemeriksa Kesesuaian VPS WordPress

Gunakan pemeriksa ini sebagai titik awal. Ini tidak menggantikan pengukuran CPU/RAM/database yang sebenarnya.

Gunakan bukti beban kerja nyata jika memungkinkan.

Ketika WordPress sebenarnya membutuhkan VPS

Situs WordPress dapat membenarkan VPS bahkan tanpa lalu lintas yang besar.

Alasan umum:

  • batas CPU/memori/proses berulang saat menjalankan beban yang memang diperlukan;
  • memerlukan konfigurasi khusus PHP/runtime;
  • kebutuhan Redis/Memcached atau layanan sisi server lainnya;
  • cron sistem yang sebenarnya sebagai pengganti penjadwalan yang dipicu pengunjung;
  • tugas latar belakang yang sudah berjalan lama;
  • perilaku Nginx/Apache khusus;
  • beberapa situs yang memerlukan satu lingkungan terkendali;
  • isolasi beban kerja/akun yang lebih kuat;
  • pemantauan tingkat server atau persyaratan firewall.

Jika satu-satunya gejala adalah “situs lambat,” pertama-tama bandingkan VPS vs shared hosting dan verifikasi bahwa WordPress itu sendiri bukanlah hambatannya.

Ketika WordPress tidak memerlukan VPS

Tetap gunakan shared hosting atau hosting WordPress managed yang baik ketika:

  • situsnya ringan dan stabil;
  • cache berfungsi;
  • pengukur sumber daya host tidak menunjukkan batas berulang;
  • tidak diperlukan layanan khusus/akses root;
  • tim tidak ingin mempertahankan Linux;
  • penyedia sudah menangani pencadangan, keamanan, pembaruan atau lingkungan staging dengan cukup baik;
  • VPS pada dasarnya akan menggantikan layanan hosting sederhana dengan tugas yang lebih operasional.

VPS tidak otomatis lebih cepat. VPS yang berukuran buruk atau tidak disetel dapat menjalankan WordPress lebih buruk daripada platform yang dikelola dengan baik.

proses PHP dan RAM

Untuk permintaan tanpa cache, worker PHP-FPM adalah batas konkurensi utama.

Setiap worker yang aktif menggunakan memori saat memproses permintaan. worker yang lebih banyak dapat menangani permintaan dinamis yang lebih simultan, namun meningkatkan jumlah worker tanpa menambah anggaran RAM dapat menyebabkan:

  • penggunaan swap;
  • tekanan memori;
  • penghentian proses oleh OOM;
  • database kekurangan sumber daya;
  • ketidakstabilan server.

Model praktisnya adalah:

WordPress RAM = OS + server web + database + cache + proses PHP + panel/mail/tugas + cadangan kapasitas

Lalu:

Kapasitas proses PHP = RAM yang aman dialokasikan untuk PHP / rata-rata penggunaan memori per proses yang terukur

Jangan mengonfigurasi jumlah maksimum teoretis worker jika hal itu tidak menyisakan memori untuk MySQL/MariaDB, cache, atau sistem operasi.

Pengguna yang masuk, wp-admin, permintaan REST/API, pencarian, formulir, pratinjau, dan halaman yang dipersonalisasi lebih cenderung melewati cache satu halaman penuh dan menggunakan proses PHP.

lapisan cache WordPress

Caching bukanlah satu fitur.

Dokumentasi pengoptimalan WordPress sendiri merekomendasikan caching sebagai alat kinerja utama. Namun lapisan-lapisan ini memecahkan masalah yang berbeda.

Jangan menyamakan Redis dengan cache halaman. Redis umumnya menjadi backend cache objek persisten; caching halaman penuh merupakan lapisan terpisah.

Cache objek persisten dan Redis

WordPress menyertakan API objek-cache, tetapi cache default adalah tidak persisten di seluruh permintaan.

Caching objek persisten memerlukan backend/drop-in eksternal seperti Redis atau Memcached ditambah integrasi WordPress yang sesuai.

Ini dapat membantu ketika situs berulang kali melakukan tugas database/objek yang mahal, tetapi ini bukan tombol kecepatan otomatis.

Sebelum menambahkan Redis:

  • konfirmasi manfaat beban kerja situs/database;
  • verifikasi sisa RAM yang cukup untuk PHP dan database;
  • memantau tingkat hit dan memori;
  • menyimpan cache halaman sebagai keputusan terpisah.

Situs dengan caching satu halaman penuh yang efisien dan tugas database yang ringan mungkin memperoleh keuntungan lebih sedikit dari Redis dibandingkan keanggotaan dinamis atau situs yang banyak permintaan.

Permintaan database

Kinerja WordPress dapat menjadi terbatas pada database sebelum CPU terlihat jenuh.

Periksa:

  • kueri lambat;
  • opsi besar/data yang dimuat secara otomatis;
  • metadata plugin;
  • kueri penelusuran/filter/pelaporan;
  • beban kerja postmeta-berat;
  • set data aktif database;
  • penulisan bersamaan;
  • impor/ekspor;
  • latensi penyimpanan.

Lebih banyak CPU tidak memperbaiki kueri patologis. Lebih banyak RAM dapat membantu ketika database secara sah membutuhkan set data aktif yang lebih besar, tetapi itu tidak menggantikan tugas pengindeksan/kueri/plugin.

Ukur dulu, baru skala.

Plugin, tema, dan tugas latar belakang

Sebuah plugin bukan hanya ruang disk.

Plugin/tema dapat menambahkan:

  • pemrosesan PHP;
  • kueri database;
  • panggilan API eksternal;
  • tugas terjadwal;
  • pembatalan cache;
  • admin AJAX;
  • pemrosesan gambar;
  • pemindaian keamanan;
  • cadangan;
  • impor/ekspor;
  • analitik/pencatatan log.

Tugas berat dapat bertabrakan dengan lalu lintas nyata.

Jadwalkan tugas pencadangan, pemindaian, impor, dan pemrosesan gambar jauh dari periode sibuk jika memungkinkan. Jika satu plugin atau tugas menyebabkan lonjakan sumber daya, perbaiki atau jadwalkan ulang sebelum menganggap VPS terlalu kecil.

WP-cron dan tugas latar belakang

WP-cron dipicu oleh permintaan WordPress daripada berjalan terus menerus seperti penjadwal sistem.

Itu dapat diterima untuk situs biasa. Untuk beban kerja yang sensitif terhadap waktu atau sibuk, dokumentasi pengembang WordPress menjelaskan penggunaan penjadwal sistem operasi untuk memanggil WordPress cron pada interval terkontrol.

Jika Anda berpindah ke penjadwal sistem:

  • buat pemicu pengganti terlebih dahulu;
  • verifikasi berhasil;
  • hanya kemudian nonaktifkan perilaku normal WP-cron yang dipicu pengunjung jika itu adalah bagian dari rencana;
  • mencatat dan memantau tugas yang gagal.

Jangan nonaktifkan WP-cron tanpa penjadwal lain.

Penyimpanan, media, lingkungan staging dan cadangan

Perencanaan disk harus mencakup lebih dari inti WordPress.

Anggaran untuk:

  • unggahan/media;
  • database;
  • plugin/tema;
  • log;
  • file cache;
  • file pembaruan sementara;
  • ruang sementara pemrosesan gambar;
  • salinan lingkungan staging;
  • arsip cadangan sebelum dipindahkan ke luar server;
  • pertumbuhan yang diharapkan.

Situs yang menggunakan 20 GB saat ini mungkin memerlukan lebih banyak ruang sementara selama tugas kloning, pemulihan, pembaruan plugin, atau kompresi cadangan.

Jangan menyimpan satu-satunya cadangan di VPS.

Manual, panel kontrol atau FASTPANEL?

WordPress dapat berjalan dengan baik tanpa cPanel atau panel lainnya.

Linux dengan pengelolaan manual

Cocok bila Anda inginkan:

  • stack minimal;
  • administrasi SSH;
  • konfigurasi Nginx/Apache/PHP/database khusus;
  • otomatisasi atau penerapan berbasis Git.

Gunakan Cara menghosting website di VPS untuk jalur penerapan manual.

Panel kontrol umum

Berguna ketika domain berbasis browser, SSL, PHP, database, pengguna, email, atau cadangan menghilangkan cukup banyak tugas berulang.

Gunakan VPS dengan Panel Kontrol.

FASTPANEL

Alur kerja resmi FASTPANEL mendukung pembuatan situs WordPress. VDSina saat ini mencantumkan FASTPANEL di Ubuntu 22 sebagai opsi panel yang telah dikonfigurasi sebelumnya.

Gunakan Hosting VPS dengan FASTPANEL untuk panduan penyiapan dan penentuan spesifikasi khusus panel tersebut.

Panel kontrol menyederhanakan administrasi; itu tidak membuat VPS terkelola.

VPS WordPress yang dikelola vs yang dikelola sendiri

Pada VPS yang dikelola sendiri, harus ada penanggung jawab untuk:

  • Pembaruan OS/paket;
  • SSH/firewall;
  • Pembaruan PHP/server web;
  • administrasi database;
  • pembaruan WordPress/plugin/tema;
  • pengujian pencadangan dan pemulihan;
  • pemantauan;
  • insiden.

Jika belum ada penanggung jawab tugas tersebut, pilih layanan administrasi terkelola, bukan berasumsi WordPress atau panel kontrol akan mengurus server.

WooCommerce adalah beban kerja WordPress yang berbeda

WooCommerce memakai stack WordPress, tetapi perilakunya berbeda saat melayani trafik toko yang sebenarnya.

Keranjang, checkout, akun, pesanan, stok, dan banyak tindakan terjadwal bersifat dinamis dan tidak dapat diperlakukan seperti halaman blog cache anonim.

Jika transaksi toko penting, gunakan VPS untuk WooCommerce untuk model penentuan spesifikasi/operasi khusus.

Beberapa situs WordPress

Beberapa situs WordPress berbagi:

  • CPU;
  • RAM;
  • layanan database;
  • proses PHP/kumpulan;
  • penyimpanan;
  • cron/jendela tugas latar belakang;
  • waktu pencadangan;
  • domain kegagalan.

Sepuluh situs cache yang tenang bisa lebih ringan daripada satu situs keanggotaan dinamis yang sibuk.

Gunakan pengguna dan kredensial database terpisah bila diperlukan, lalu tentukan spesifikasi berdasarkan gabungan beban puncak, bukan jumlah domain.

Pemicu peningkatan VPS WordPress

Tingkatkan hanya setelah mengukur batasan nyata.

Pemicu kuat:

  • tekanan RAM berkelanjutan, swap atau peristiwa OOM;
  • mengulangi antrean/saturasi proses PHP;
  • saturasi CPU berkelanjutan setelah optimasi cache/query/plugin;
  • latensi database akibat kebutuhan nyata set data aktif yang melebihi kapasitas;
  • pertumbuhan penyimpanan melampaui cadangan kapasitas operasional yang aman;
  • tugas latar belakang berulang kali bertabrakan dengan lalu lintas langsung;
  • beberapa situs aktif menghabiskan sumber daya bersama.

Jika website lambat sementara sinyalnya tetap sehat, VPS yang lebih besar mungkin bukan solusinya.

Pertanyaan Umum

Berapa banyak RAM yang dibutuhkan WordPress pada VPS?

Inti WordPress tidak menentukan persyaratan RAM VPS produksi. RAM harus mencakup Linux, server web, proses PHP, database, cache, tugas panel/mail/latar belakang, dan cadangan kapasitas. Situs ringan mungkin muat 2 GB; 4 GB adalah dasar praktis yang lebih kuat untuk situs bisnis.

Apakah RAM 1 GB cukup untuk VPS WordPress?

Ini dapat menjalankan pengaturan WordPress yang sangat ringan/pengujian, tetapi menyisakan sedikit cadangan kapasitas untuk database, proses PHP dan tugas latar belakang. Ini tidak boleh dianggap sebagai rekomendasi produksi normal.

Apakah RAM 2 GB cukup untuk WordPress?

Ini mungkin cukup untuk situs kecil dengan cache yang baik dan stack ringan. Pantau memori proses PHP, RAM database, plugin, dan tugas latar belakang.

Apakah RAM 4 GB cukup untuk WordPress?

Bagi banyak situs bisnis WordPress, 4 GB adalah titik awal yang praktis. Plugin berat, lalu lintas keanggotaan, WooCommerce, database besar, impor, atau beberapa situs aktif mungkin memerlukan lebih banyak.

Berapa banyak pengunjung yang dapat ditangani oleh VPS WordPress?

Tidak ada jumlah pengunjung universal yang dapat diandalkan. Kapasitas ditentukan oleh rasio cache hit, permintaan tanpa cache yang bersamaan, durasi permintaan PHP, konsumsi sumber daya plugin, pemrosesan database, dan tugas latar belakang.

Apakah saya memerlukan Redis untuk WordPress di VPS?

Tidak. Redis dapat menyediakan cache objek persisten ketika beban kerja mendapat manfaat dari cache objek/database yang berulang, namun hal ini tidak diperlukan untuk setiap situs WordPress dan tidak menggantikan cache halaman penuh.

Haruskah saya menggunakan Nginx atau Apache untuk VPS WordPress?

Keduanya sah. WordPress.org merekomendasikan Apache atau Nginx sebagai pilihan yang kuat. Gunakan stack yang dapat dioperasikan oleh aplikasi dan administrator Anda dengan andal.

Haruskah saya mengganti WP-cron dengan sistem cron?

Hanya ketika beban kerja mendapat manfaat dari penjadwal yang terkontrol dan Anda mengonfigurasi pengganti yang berfungsi. Jangan nonaktifkan WP-cron tanpa pemicu lain.

Apakah VPS WordPress memerlukan panel kontrol?

Tidak. WordPress dapat berjalan pada VPS Linux yang dikelola secara manual. Panel bersifat opsional dan harus dipilih untuk kemudahan administrasi, bukan sebagai persyaratan kinerja.

Apakah VDSina menyertakan WordPress yang sudah diinstal sebelumnya?

Halaman VPS Standar saat ini tidak mencantumkan WordPress sebagai aplikasi pra-instal khusus dalam grup template/aplikasi yang terlihat. Verifikasi layar pesanan langsung sebelum mengasumsikan ketersediaan templat apa pun.
