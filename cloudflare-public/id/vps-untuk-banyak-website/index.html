VPS untuk Banyak Website

VPS untuk banyak website: tentukan spesifikasi dari gabungan beban puncak, pisahkan pengguna dan database, pahami dampak kegagalan satu server, serta ketahui kapan situs atau layanan perlu dipisahkan.

VPS untuk Beberapa Website berfungsi dengan baik ketika beberapa situs dapat dengan aman berbagi satu kumpulan sumber daya, satu model administrasi, dan satu domain kegagalan. Batasan yang penting bukanlah jumlah domain. Ini adalah puncak gabungan dari CPU, RAM, worker PHP/aplikasi, tugas database, penyimpanan, tugas latar belakang, dan pencadangan di setiap situs di server.

Pemeriksa Arsitektur VPS untuk Banyak Website

Gunakan ini untuk memutuskan apakah satu VPS masih merupakan domain kegagalan yang tepat.

Pilih karakteristik portofolio yang benar-benar berlaku.

Hitung beban kerja, bukan domain

Pertanyaan “berapa banyak website yang dapat dihosting oleh satu VPS?” tidak memiliki jawaban tetap yang dapat diandalkan.

Model kapasitas yang berguna adalah:

beban banyak website = gabungan trafik normal + beban dinamis puncak yang bersamaan + database + cron/worker + backup/impor + panel/email/pemantauan + cadangan kapasitas

Contoh:

  • sepuluh situs statis atau cache yang agresif mungkin menggunakan kapasitas PHP/DB yang sangat sedikit;
  • tiga situs bisnis WordPress memerlukan lebih banyak RAM karena masing-masing memiliki proses PHP dan beban kerja database;
  • satu toko WooCommerce dapat mendominasi seluruh server selama checkout atau acara penjualan;
  • satu impor gambar, pencadangan, atau pemindaian keamanan dapat menghabiskan lebih banyak CPU/I/O untuk sementara dibandingkan gabungan beberapa website yang tenang.

Hitung beban kerja simultan terberat, bukan jumlah domain di panel kontrol.

Berapa banyak website yang dapat dihosting oleh satu VPS?

Gunakan hitungan situs hanya sebagai nomor inventaris.

Kapasitas tergantung pada:

  • rasio hit cache;
  • jumlah permintaan tanpa cache yang berjalan bersamaan;
  • penggunaan memori worker PHP/aplikasi;
  • durasi permintaan;
  • set data aktif database;
  • intensitas tulis;
  • tugas terjadwal/latar belakang;
  • lalu lintas bot;
  • pertumbuhan penyimpanan/media;
  • jendela cadangan;
  • penggunaan sumber daya tambahan oleh panel/email;
  • berapa banyak cadangan kapasitas yang tersisa.

Jika Anda tidak dapat mengidentifikasi konsumen sumber daya yang dominan, kepercayaan terhadap estimasi “N website” adalah rendah.

Untuk perilaku khusus WordPress, gunakan VPS untuk WordPress. Toko transaksional perlu dinilai terpisah; lihat VPS untuk WooCommerce.

Satu IP dapat meng-host banyak website

Website modern normal tidak memerlukan satu IP publik per domain.

Dengan hosting virtual berbasis nama:

  1. DNS mengarahkan beberapa domain ke IP VPS yang sama;
  2. browser mengirimkan nama host yang diminta;
  3. Nginx/Apache mencocokkan nama host tersebut dengan blok server/host virtual yang benar;
  4. TLS menggunakan SNI sehingga server dapat menyajikan sertifikat yang sesuai untuk setiap nama host.

Inilah sebabnya mengapa banyak website HTTPS yang tidak terkait dapat berbagi port 80/443 pada satu IP.

IP terpisah masih penting untuk kebijakan jaringan khusus, persyaratan lama, reputasi email, atau layanan non-web, namun ini bukan persyaratan normal untuk setiap website.

Isolasikan setiap situs dengan sengaja

Menempatkan situs di folder berbeda adalah pengorganisasian, bukan isolasi yang kuat.

Untuk website yang tidak terkait/klien, pilih batasan terpisah jika memungkinkan:

Anti-pola yang umum menjalankan setiap situs PHP sebagai pengguna Unix yang sama dengan file konfigurasi yang dapat dibaca. Satu plugin yang disusupi kemudian dapat menjadi kompromi lintas situs.

Panduan keamanan FASTPANEL sendiri merekomendasikan pengguna FASTPANEL terpisah untuk situs terpisah. Jika Anda menginginkan UI hosting, bandingkan VPS dengan Control Panel; alur kerja bermerek tercakup dalam FASTPANEL VPS Hosting.

Pisahkan pool PHP, layanan aplikasi, dan kredensial database

Untuk situs PHP, pool PHP-FPM terpisah dapat membantu mengisolasi:

  • Pengguna/grup Unix;
  • batas worker;
  • Konfigurasi PHP;
  • log;
  • soket;
  • perilaku sumber daya.

Untuk aplikasi Node.js/Python/custom, gunakan pengguna/layanan aplikasi terpisah dan port/soket lokal.

Untuk database:

  • menggunakan database terpisah;
  • gunakan kredensial terpisah;
  • hanya memberikan hak istimewa yang dibutuhkan setiap aplikasi;
  • jangan berikan setiap situs satu akun root/admin DB bersama.

Ini tidak menciptakan isolasi multitenant yang sepenuhnya ketat, tetapi secara signifikan membatasi dampak gangguan dan mempermudah pemecahan masalah.

Beban kerja campuran memerlukan anggaran berbeda

Jangan mengukur portofolio campuran seolah-olah setiap situs adalah sama.

Situs statis/cache

Biasanya ringan pada aplikasi CPU dan DB.

WordPress

Membutuhkan anggaran proses PHP, database, cache dan cron.

WooCommerce / keanggotaan / situs transaksional

Membutuhkan lebih banyak cadangan kapasitas untuk PHP/database dinamis serta perencanaan tugas latar belakang yang cermat.

Aplikasi khusus

Mungkin memerlukan proses yang persisten, antrean, container, runtime yang berbeda, atau port terpisah.

Situs terberat sering kali menentukan apakah keseluruhan VPS perlu lebih besar atau apakah situs tersebut harus dipindahkan.

Website Anda Sendiri Dapat Menghabiskan Sumber Daya Website Lain

VPS mengurangi sebagian ketergantungan pada pelanggan shared hosting lain, tetapi konsolidasi menciptakan situs internal yang dapat menghabiskan sumber daya situs lainnya.

Satu situs dapat mengonsumsi sumber daya yang tidak proporsional melalui:

  • lonjakan lalu lintas;
  • plugin/kueri buruk;
  • serangan bot;
  • pemrosesan gambar;
  • impor/ekspor;
  • pemindaian keamanan;
  • kompresi cadangan;
  • tugas cron yang berjalan tak terkendali;
  • pertumbuhan log yang besar;
  • kunci database/tekanan IO.

Perhatikan penggunaan sumber daya selama acara ini, tidak hanya saat server menganggur.

Jika stack Anda mendukungnya, batas worker/proses per situs atau batas kontainer/cgroup dapat mengurangi kemungkinan satu beban kerja menghabiskan segalanya—tetapi jangan berasumsi panel kontrol secara otomatis menerapkan kuota CPU/RAM keras kecuali dokumentasinya menyatakan demikian.

Puncak gabungan lebih penting daripada penggunaan rata-rata

Server multi-situs gagal ketika puncak independen tumpang tindih.

Misalnya:

  • Situs A menerima lonjakan kampanye;
  • Situs B menjalankan impor database;
  • Situs C memulai pencadangan penuh;
  • Situs D menjalankan pemindaian malware;
  • panel kontrol memutar log;
  • buffer database sudah besar.

Secara individual setiap situs mungkin terlihat kecil. Bersama-sama mereka dapat menghabiskan CPU, RAM, atau I/O.

Rencanakan pemeliharaan dan tugas latar belakang di seluruh portofolio, bukan per situs secara terpisah.

Manual, Panel Kontrol, atau Kontainer?

Blok server manual / host virtual

Baik bila:

  • satu operator yang kompeten mengelola server;
  • jumlah situsnya sedikit;
  • stacknya serupa;
  • otomatisasi/skrip menjaga konfigurasi tetap konsisten.

Jalur penerapan umum tercakup dalam Cara menghosting website di VPS.

Panel kontrol hosting

Berguna ketika:

  • banyak domain/pengguna memerlukan administrasi rutin;
  • akses klien atau pendelegasian akses penting;
  • Anda menginginkan UI untuk SSL, PHP, database, cadangan, dan email.

model pengguna/akun panel lebih penting daripada jumlah domain yang diklaim didukungnya.

Kontainer

Berguna ketika:

  • dependensi/isolasi runtime itu penting;
  • aplikasi memiliki stack yang berbeda;
  • penerapan bersifat container-native;
  • tim sudah mengetahui pengoperasian kontainer.

Kontainer tidak secara otomatis menjadi lebih sederhana. Mereka menambahkan masalah siklus hidup image, jaringan, volume persisten, pencadangan, dan pemantauan.

Website agensi dan klien

Penggunaan agensi adalah kasus multi-situs yang alami, namun kepemilikan klien meningkatkan persyaratan isolasi.

Tentukan:

  • siapa pemilik domain/DNS;
  • akun panel/sistem terpisah;
  • kredensial DB terpisah;
  • akses yang didelegasikan;
  • kepemilikan cadangan per klien;
  • tingkat perincian pemulihan;
  • jalur migrasi/ekspor ketika klien keluar;
  • siapa yang bertanggung jawab atas pembaruan aplikasi;
  • apakah insiden di satu situs klien dapat berdampak pada situs lainnya.

Jangan menjanjikan klien “hosting terisolasi” jika semua situs klien berbagi pengguna Unix dan domain kegagalan yang sama.

Kandidat halaman lama VPS untuk Website Agensi tetap digabungkan di sini, kecuali pemeriksaan SERP/volume pencarian di masa mendatang membuktikan perlunya halaman tersendiri dengan tujuan pencarian yang jelas berbeda.

Jika belum ada anggota tim yang bertanggung jawab atas pembaruan OS, keamanan, verifikasi backup, pemantauan, dan penanganan insiden pada server bersama, tentukan terlebih dahulu sebelum menggabungkan website klien: lihat VPS Managed vs Unmanaged.

Untuk memindahkan portofolio yang sudah ada ke satu VPS, jangan menyalin semua website lalu mengubah seluruh DNS sekaligus. Siapkan lingkungan pengujian, uji, dan lakukan peralihan dengan opsi rollback; gunakan Migrasi Website ke VPS untuk proses migrasinya.

Tingkat Perincian Backup dan Pemulihan

Satu VPS berarti beberapa situs bisa gagal sekaligus.

Desain cadangan yang berguna akan memungkinkan Anda menjawab:

  • bisakah saya memulihkan hanya Situs A?
  • bisakah saya memulihkan databasenya saja?
  • bisakah saya memulihkan VPS penuh setelah disk/server hilang?
  • apakah ada salinan di luar server?
  • berapa banyak data yang bisa hilang di antara pencadangan?
  • bisakah saya memverifikasi pemulihan tanpa menimpa situs lain?

Image server lengkap berguna untuk pemulihan bencana, namun ini bukan satu-satunya metode pemulihan jika memulihkan satu situs yang disusupi akan memaksa setiap situs lain kembali ke titik lama. Untuk penyimpanan, salinan di luar lokasi, RPO/RTO, dan pengujian pemulihan, gunakan Strategi Pencadangan VPS.

Satu VPS adalah satu domain kegagalan

Konsolidasi mengurangi biaya dan duplikasi admin, namun meningkatkan cakupan dampak kegagalan.

Satu peristiwa dapat memengaruhi setiap situs:

  • pemadaman VPS;
  • sistem file penuh;
  • pembaruan OS/stack web yang buruk;
  • kegagalan database;
  • kesalahan firewall;
  • akun admin disusupi;
  • malware/kompromi root;
  • penghapusan tidak disengaja;
  • tugas backup yang menghabiskan ruang disk atau kapasitas I/O.

Pertanyaannya bukanlah apakah risiko ini ada—tetapi memang ada. Pertanyaannya adalah apakah bisnis menerimanya.

Kapan harus membagi situs atau beban kerja

Pisahkan ketika alasannya dapat diukur secara operasional.

Pemicu kuat:

  • satu situs berulang kali mendominasi CPU/RAM/I/O;
  • satu situs yang penting bagi bisnis tidak dapat berbagi risiko pemadaman dengan situs yang berprioritas lebih rendah;
  • beban WooCommerce/toko online mengganggu website yang lebih ringan;
  • ada persyaratan OS/runtime/keamanan yang tidak kompatibel;
  • satu database memerlukan RAM/I/O/penskalaan independen;
  • worker latar belakang/tugas mendominasi sumber daya;
  • jangka waktu pemeliharaan berbeda;
  • batasan klien/kepatuhan memerlukan pemisahan yang lebih kuat;
  • perebutan sumber daya tetap ada setelah pengoptimalan dan penjadwalan.

Kemungkinan pola pemisahan:

  • website kritis -> VPS tersendiri;
  • web -> DB VPS terpisah;
  • web -> VPS terpisah untuk worker latar belakang;
  • agensi -> grup klien terpisah;
  • produksi -> lingkungan staging terpisah;
  • beban dengan banyak penulisan / toko -> server terpisah.

Jangan membagi secara otomatis: setiap VPS tambahan menambahkan pemantauan, pencadangan, patching, jaringan, dan permukaan insiden.

Memantau VPS multi-situs

Pantau pada dua tingkat.

Tingkat server

  • CPU;
  • RAM/swap/OOM;
  • penggunaan disk;
  • waktu tunggu I/O;
  • kesehatan DB;
  • jaringan;
  • kesehatan proses/layanan.

Tingkat situs

  • pemeriksaan HTTP(S) eksternal per nama host penting;
  • waktu respons;
  • kesalahan 5xx;
  • PHP/log aplikasi;
  • lalu lintas per situs/tekanan worker jika tersedia;
  • cron/kegagalan antrean;
  • Pertumbuhan DB/log/penyimpanan.

Sebuah server dapat "aktif" ketika satu host virtual, sertifikat, atau aplikasi rusak. Model peringatan server lengkap + per nama host tercakup dalam Pemantauan VPS.

Pertanyaan Umum

Berapa banyak website yang dapat saya host di satu VPS?

Tidak ada nomor tetap yang dapat diandalkan. Kapasitas bergantung pada gabungan puncak CPU, RAM, worker PHP/aplikasi, tugas database, penyimpanan, dan tugas latar belakang semua situs.

Apakah beberapa website memerlukan alamat IP terpisah?

Biasanya tidak. Hosting virtual berbasis nama dan TLS SNI memungkinkan beberapa domain HTTPS berbagi satu IP publik. IP terpisah mungkin masih berguna untuk persyaratan jaringan/mail/warisan khusus.

Bisakah beberapa situs WordPress berbagi satu VPS?

Ya. Gunakan pengguna/kredensial terpisah dan ukur server untuk beban kerja gabungan PHP/database/latar belakang. Beberapa situs WordPress ringan mungkin cocok; satu situs dinamis yang berat dapat mendominasi server.

Haruskah setiap situs memiliki pool PHP-FPM terpisah?

Untuk situs PHP klien atau tidak terkait, kumpulan terpisah dapat meningkatkan isolasi proses/pengguna dan membuat penyetelan/pencatatan per situs menjadi lebih jelas. Desain pastinya bergantung pada model panel/stack web.

Bisakah satu toko WooCommerce berbagi VPS dengan situs lain?

Bisa, tetapi puncak checkout, database, dan tugas latar belakang toko dapat mendominasi beban. Jika toko penting bagi bisnis atau berulang kali menghabiskan sumber daya situs lain, pisahkan toko tersebut.

Apakah panel kontrol lebih baik untuk menghosting banyak website?

Sering kali ya, untuk administrasi. Panel dapat mempermudah pengelolaan domain, pengguna, SSL, PHP, database, dan backup, tetapi periksa model isolasi pengguna/akunnya serta penggunaan sumber daya tambahan oleh panel.

Apakah container diperlukan untuk beberapa website?

Tidak. Blok server Nginx/virtual host Apache beserta pengguna dan proses terpisah dapat menghosting banyak website. Kontainer berguna ketika manfaat isolasi dependensi/proses sepadan dengan kompleksitas operasional tambahan.

Apa risiko utama menghosting banyak website dalam satu VPS?

cakupan dampak kegagalan. Satu pemadaman, pembaruan yang buruk, kejadian disk penuh, atau kompromi tingkat server dapat memengaruhi setiap situs di VPS tersebut.

Haruskah agensi menempatkan semua klien dalam satu VPS?

Hanya ketika agensi menerima domain kegagalan bersama dan menerapkan isolasi akun/file/DB yang kuat, pencadangan, pemantauan, dan prosedur keluar klien. Klien yang kritis atau tidak kompatibel mungkin memerlukan server terpisah.

Kapan saya harus membagi menjadi beberapa server VPS?

Terpisah ketika satu beban kerja mendominasi sumber daya, situs penting memerlukan isolasi kegagalan independen, stack/batas keamanan tidak kompatibel, atau DB/worker memerlukan penskalaan independen.
