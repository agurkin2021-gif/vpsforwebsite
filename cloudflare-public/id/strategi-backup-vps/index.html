Strategi Backup VPS

Susun strategi backup VPS berdasarkan RPO dan RTO: salinan independen, backup database, retensi, enkripsi, serta uji pemulihan sebelum terjadi gangguan.

Pengungkapan: editor memiliki hubungan profesional dengan VDSina. Tautan mitra dapat menghasilkan komisi. Pengungkapan editorial dan komersial.

Strategi backup VPS mencakup lebih dari jadwal snapshot harian. Rencana yang dapat dijalankan menetapkan batas kehilangan data (RPO), batas waktu pemulihan (RTO), data yang harus disimpan, lokasi salinan independen, lama penyimpanan versi, serta siapa yang menguji pemulihannya.

Rencana pemulihan VPS yang kuat biasanya menggabungkan pemulihan cepat dari sisi penyedia dengan salinan independen di luar server dan backup database yang mempertimbangkan kebutuhan aplikasi. Kombinasi yang tepat bergantung pada kecepatan perubahan data dan besarnya kerugian akibat downtime.

Strategi pencadangan juga memerlukan penanggung jawab yang jelas. Jika tidak ada orang yang bertanggung jawab atas tugas pencadangan yang gagal, pengujian pemulihan, dan keputusan pemulihan, tentukan model operasional tersebut terlebih dahulu: lihat VPS Managed vs Unmanaged.

Untuk memilih konfigurasi server, lihat VPS untuk website.

Untuk banyak website di VPS, mulailah dengan:

  • image/snapshot sisi penyedia untuk rollback yang cepat;
  • backup file, konfigurasi, dan database yang dienkripsi dan disimpan di lingkungan independen;
  • beberapa titik pemulihan;
  • jadwal backup database sesuai batas kehilangan data yang dapat diterima;
  • uji pemulihan berkala.

Keberhasilan pemulihan memberi bukti yang lebih kuat daripada status tugas backup saja.

Pemeriksa Strategi Backup VPS

Pemeriksa ini mengidentifikasi arsitektur pemulihan yang Anda perlukan. Hasilnya tidak menjamin keberhasilan pemulihan.

Pilih persyaratan pemulihan yang benar-benar berlaku.

Mulailah dengan RPO dan RTO

Gunakan dua target berikut sebagai dasar rencana.

RPO: Batas Kehilangan Data

RPO menjawab pertanyaan:

Seberapa banyak data terbaru yang masih dapat ditoleransi bisnis jika hilang?

Jika RPO adalah:

  • 24 jam — titik pemulihan harian yang berhasil mungkin dapat diterima;
  • 4 jam — cadangan harian tidak mencukupi;
  • 1 jam — perubahan status aplikasi/database memerlukan perlindungan setidaknya sesering itu;
  • menit — pencadangan terjadwal biasa saja mungkin tidak cukup.

RPO adalah tentang kehilangan data, bukan waktu henti.

RTO: Batas Waktu Pemulihan

RTO menjawab pertanyaan:

Berapa lama website/layanan boleh tidak tersedia?

Backup dapat memenuhi target RPO tetapi belum memenuhi target RTO.

Contoh:

  • database disalin setiap jam;
  • kehilangan data terbaru kurang dari satu jam;
  • namun penyiapan VPS baru, pengunduhan data, pemulihan database, dan pengujian situs memerlukan enam jam.

RPO satu jam mungkin terpenuhi, tetapi waktu pemulihan sebenarnya hampir enam jam.

Panduan perencanaan kontinjensi NIST mendefinisikan RPO sebagai titik waktu pemulihan dan RTO sebagai jendela ketidaktersediaan maksimum yang dapat diterima. Gunakan target tersebut sebelum memilih alat.

Data Apa yang Perlu Di-backup?

Kelompokkan komponen server menjadi yang dapat dibangun ulang dan yang menyimpan data penting/tidak dapat digantikan.

Komponen yang dapat dibangun ulang

Sering kali dapat direproduksi dari kode atau otomatisasi:

  • sistem operasi dasar;
  • paket;
  • kode aplikasi yang sudah disimpan dengan aman di Git;
  • image container yang dapat dibuat atau diunduh kembali;
  • paket server web standar.

Data yang Sulit Digantikan

Biasanya prioritas lebih tinggi:

  • database;
  • unggahan/media pengguna;
  • kotak surat jika dihosting secara lokal;
  • konfigurasi;
  • konfigurasi lingkungan dan kredensial yang diperlukan untuk pemulihan;
  • sertifikat TLS dan kunci privat yang sulit diganti;
  • data yang dihasilkan aplikasi;
  • konfigurasi panel kontrol/situs;
  • konfigurasi cron/worker;
  • data zona DNS jika DNS dihosting di VPS;
  • skrip khusus yang tidak disimpan di tempat lain.

Utamakan database dan kredensial yang diperlukan untuk menjalankan situs. Hindari memenuhi penyimpanan backup dengan cache, file sementara, atau hasil build yang mudah dibuat ulang.

Snapshot, Image, Backup File, dan Replikasi Memiliki Fungsi Berbeda

Pilih setiap metode sesuai fungsi dan batasannya.

Snapshot penyedia / image server

Berguna untuk:

  • rollback cepat setelah pembaruan berisiko;
  • pemulihan server penuh;
  • mengkloning/membuat ulang VM.

Kelemahan:

  • dapat bergantung pada akun atau infrastruktur penyedia yang sama dengan server utama;
  • pemulihan satu file atau satu situs mungkin kurang praktis;
  • konsistensi aplikasi dan database perlu dipastikan;
  • satu image terbaru hanya menyediakan sedikit riwayat pemulihan.

Pencadangan tingkat file

Berguna untuk:

  • unggahan;
  • konfigurasi;
  • data aplikasi yang dipilih;
  • pemulihan file atau data tertentu.

Alat seperti restic atau Borg dapat menyimpan cadangan berversi terenkripsi pada repositori jarak jauh.

Pencadangan database

Gunakan metode yang sesuai dengan mesin database:

  • dump logis;
  • alat backup bawaan atau khusus mesin database;
  • snapshot/proses yang konsisten dengan aplikasi.

Jangan berasumsi bahwa menyalin file database yang sedang aktif akan menghasilkan backup database yang dapat digunakan.

Replikasi dan Server Siaga

Replikasi dapat mengurangi waktu pemulihan atau kehilangan data, namun ini bukan pencadangan historis dengan sendirinya.

Penghapusan yang keliru, kerusakan data, atau kesalahan aplikasi juga dapat ikut direplikasi.

Gunakan replikasi/siaga untuk ketersediaan/RTO bila diperlukan, dan simpan cadangan berversi untuk pemulihan historis.

Model 3-2-1 praktis untuk VPS

Model umum 3-2-1 berarti:

  • 3 salinan data penting;
  • 2 jenis media penyimpanan;
  • 1 salinan di lokasi terpisah.

Pada VPS, terapkan prinsip tersebut dengan memisahkan risiko kegagalan. Contohnya:

  1. data produksi di VPS;
  2. image backup penyedia untuk pemulihan cepat;
  3. backup file dan database terenkripsi di penyimpanan independen di luar penyedia utama.

Periksa juga ketergantungan media, akun, dan infrastrukturnya. Tiga salinan tidak cukup jika satu kegagalan atau satu akun yang disusupi dapat menghancurkan semuanya.

Contoh komponen yang dapat memiliki risiko kegagalan berbeda:

  • sistem file VPS;
  • penyimpanan cadangan penyedia;
  • akun penyedia;
  • akun/penyedia penyimpanan objek terpisah;
  • salinan offline atau tidak dapat diubah.

Jika penyerang yang mengontrol VPS dapat menghapus setiap cadangan menggunakan kredensial yang sama, salinannya tidak independen.

Jaga Konsistensi Backup Database

Isi database terus berubah selama situs digunakan.

Pilih metode backup yang sesuai dengan cara kerja mesin database.

Untuk WordPress/MySQL/MariaDB ini mungkin:

  • dump logis;
  • alat backup khusus mesin database;
  • snapshot terkoordinasi;
  • perangkat lunak cadangan yang secara eksplisit menangani konsistensi database.

Untuk PostgreSQL, gunakan metode backup/PITR yang dirancang untuk PostgreSQL jika RPO mengharuskannya.

Yang terpenting bukan alat tertentu. Database yang dipulihkan harus konsisten secara internal dan dapat digunakan.

Untuk pengelolaan aplikasi WordPress, lihat VPS untuk WordPress.

Pastikan:

  • proses dump atau backup selesai;
  • file tidak kosong;
  • pemulihan/impor berhasil;
  • tabel dan contoh data yang penting tersedia;
  • aplikasi dapat terhubung serta membaca dan menulis data penting.

Situs transaksional memerlukan RPO yang berbeda

Website profil usaha mungkin masih dapat menggunakan backup dari sehari sebelumnya.

Toko transaksional mungkin tidak.

Untuk WooCommerce, keanggotaan, penagihan, atau pemesanan, tentukan batas kehilangan data terbaru pada:

  • pesanan;
  • pembayaran;
  • stok;
  • pelanggan;
  • keanggotaan;
  • kiriman formulir;
  • unggahan.

Jika pesanan masuk setiap jam, backup database sekali semalam dapat meninggalkan banyak transaksi tanpa salinan pemulihan.

Gunakan VPS untuk WooCommerce untuk beban kerja toko. Pilih jadwal backup berdasarkan periode kehilangan transaksi yang masih dapat diterima.

Frekuensi dan retensi pencadangan

Jarak antar-backup yang berhasil harus memenuhi RPO untuk setiap jenis data yang dilindungi.

Data yang berbeda dapat menggunakan jadwal yang berbeda:

  • DB: sering;
  • unggahan: secara berkala atau setiap ada perubahan;
  • OS dan konfigurasi: setelah perubahan penting serta sesuai jadwal;
  • image seluruh server: dapat lebih jarang, dengan salinan tambahan sebelum perubahan berisiko.

Retensi melindungi terhadap kegagalan yang terlambat ditemukan.

Salah satu contoh pola retensi dapat menyimpan:

  • beberapa titik pemulihan per jam yang terbaru;
  • beberapa salinan harian;
  • beberapa salinan mingguan;
  • salinan bulanan yang dipilih.

Retensi yang tepat harus berasal dari:

  • kebutuhan pemulihan bisnis;
  • biaya penyimpanan;
  • tingkat perubahan data;
  • persyaratan kepatuhan/hukum;
  • berapa lama kerusakan data atau pembobolan mungkin tidak terdeteksi.

Jangan hanya menyimpan “terbaru”.

Simpan Salinan Independen di Luar VPS

Cadangan pada disk VPS yang sama tidak melindungi terhadap:

  • kehilangan disk/sistem file;
  • penghapusan server;
  • penyerang yang mendapat hak root;
  • ransomware;
  • kesalahan akun;
  • hilangnya VM tersebut di sisi penyedia.

Kirim backup ke penyimpanan di luar VPS, baik setelah dibuat maupun langsung selama proses backup.

Kemungkinan tujuan:

  • penyimpanan objek;
  • layanan/penyedia cadangan lainnya;
  • VPS lain yang hanya digunakan untuk cadangan;
  • penyimpanan offline/terkontrol.

Pisahkan kredensial penyedia/akun jika memungkinkan.

Enkripsi cadangan — dan lindungi kunci pemulihan

Enkripsi data cadangan sensitif saat transit dan saat disimpan jika diperlukan.

Pastikan kunci dekripsi tetap tersedia ketika server utama gagal.

Jangan simpan kata sandi/kunci cadangan hanya:

  • di VPS;
  • di brankas kata sandi atau akun yang mungkin ikut tidak tersedia;
  • di dalam backup terenkripsi itu sendiri.

Simpan kredensial/kunci pemulihan di lokasi independen yang aman dan sertakan ketersediaan kunci dalam latihan pemulihan.

Pisahkan kredensial cadangan dan hak penghapusan

Kompromi server produksi seharusnya tidak secara otomatis memberikan izin kepada penyerang untuk menghapus setiap salinan pemulihan.

Utamakan:

  • kredensial backup dengan lingkup akses terbatas;
  • akses tulis tanpa hak penghapusan luas jika penyimpanan mendukungnya;
  • kredensial administratif terpisah;
  • kebijakan retensi terkunci atau penyimpanan immutable jika diperlukan;
  • salinan offline/air-gap untuk data bernilai tinggi.

Desain pastinya bergantung pada layanan penyimpanan.

Inilah salah satu alasan pencadangan juga merupakan kontrol keamanan; lihat Checklist Keamanan VPS.

Pantau tugas pencadangan

Otomatisasi membantu menjaga jadwal backup. Tetap pantau hasilnya agar kegagalan tidak terlewat.

Pantau:

  • waktu pencadangan terakhir yang berhasil;
  • tugas yang gagal atau hanya selesai sebagian;
  • ketersediaan repositori/penyimpanan;
  • masa berlaku kredensial;
  • ruang disk yang tersedia sebelum menampung data backup sementara secara lokal;
  • kuota penyimpanan di luar lokasi;
  • kegagalan dump database;
  • perubahan durasi pencadangan;
  • ukuran backup yang lebih kecil dari biasanya;
  • kegagalan penerapan retensi atau penghapusan versi lama.

Status cron atau layanan hanya menunjukkan proses dijalankan. Buktikan bahwa hasil backup dapat dipulihkan.

Panduan pemantauan server dan layanan tersedia di Monitoring VPS; kesehatan tugas cadangan tetap menjadi bagian dari strategi pemulihan itu sendiri.

Uji Pemulihan dan Ukur RTO yang Sebenarnya

Cadangan menjadi kredibel saat dipulihkan.

Pulihkan backup ke lingkungan bersih yang terisolasi dari produksi.

Uji seluruh tahapan yang diperlukan:

  1. siapkan VPS atau lingkungan pengujian baru;
  2. ambil titik cadangan yang benar;
  3. ambil kunci dekripsi dan kredensial repositori;
  4. pulihkan file serta konfigurasi;
  5. pulihkan atau impor database;
  6. pulihkan kredensial dan sertifikat yang diperlukan;
  7. atur layanan dan jaringan;
  8. jalankan aplikasi;
  9. uji halaman dan transaksi penting;
  10. periksa tugas latar belakang serta integrasi;
  11. ukur total waktu pemulihan.

Catat hasil pengukurannya.

Jika RTO bisnis berdurasi empat jam dan pengujian memakan waktu delapan jam, strategi pencadangan telah gagal memenuhi persyaratan bisnis meskipun setiap file berhasil dipulihkan.

Panduan NIST menekankan pembuatan cadangan rutin, pengujian pemulihan, dan latihan pemulihan.

Pilih Tingkat Pemulihan yang Dibutuhkan

Rencanakan pemulihan untuk jenis gangguan yang mungkin terjadi.

Pemulihan file/situs tunggal

Dibutuhkan untuk:

  • unggahan yang dihapus;
  • konfigurasi rusak;
  • satu situs disusupi;
  • database atau tabel yang perlu dikembalikan setelah pemulihan gagal.

Pemulihan server penuh

Dibutuhkan untuk:

  • VPS mati/terhapus;
  • kegagalan sistem file;
  • pembobolan yang meluas;
  • penggantian penyedia/server.

Jika satu-satunya cadangan adalah image disk penuh, memulihkan satu file mungkin merepotkan.

Jika satu-satunya cadangan adalah file yang dipilih, membangun kembali VPS yang lengkap mungkin memakan waktu terlalu lama.

Gabungkan metode sesuai kebutuhan pemulihan.

Pulihkan Setiap Website Secara Terpisah

Pada VPS dengan banyak website, pemulihan Situs A sebaiknya tidak ikut mengembalikan data Situs B, C, dan D ke versi kemarin.

Pilih metode backup yang memungkinkan pemulihan:

  • satu direktori document root;
  • satu database;
  • satu panel/pengguna;
  • satu set unggahan;
  • VPS lengkap hanya jika diperlukan.

Untuk memilih arsitektur dan memisahkan risiko antarsitus, lihat VPS untuk Banyak Website.

Perhitungkan Beban Proses Backup

Tugas pencadangan menghabiskan sumber daya.

Potensi dampak:

  • penggunaan CPU untuk dump database;
  • penggunaan CPU untuk kompresi;
  • beban baca pada penyimpanan;
  • penggunaan disk sementara;
  • bandwidth unggahan penyimpanan objek;
  • tersingkirnya data dari cache;
  • jadwal backup yang bertepatan dengan impor, pemindaian, atau jam sibuk.

Hindari membuat arsip lokal sebesar 30 GB ketika VPS hanya memiliki 10 GB yang kosong.

Jika praktis:

  • kirim backup langsung ke penyimpanan di luar server;
  • pantau penggunaan ruang sementara;
  • jadwalkan backup berat di luar jam sibuk;
  • batasi kecepatannya jika alat mendukung;
  • ukur durasi prosesnya.

Menggunakan Backup VDSina dalam Rencana Pemulihan

Dokumentasi publik VDSina saat ini menjelaskan beberapa fungsi pemulihan yang berguna:

  • salinan cadangan server manual;
  • pencadangan terjadwal;
  • memulihkan cadangan ke server asalnya;
  • membuat server baru dari cadangan;
  • mengkloning server;
  • pengunduhan image backup.

Dokumentasi unduhan menunjukkan nama file cadangan dalam bentuk:

vXXX.backup.hosted-by-vdsina.com.img.gz

Image yang dapat diunduh tersebut memberikan portabilitas yang berguna karena salinan pemulihan tidak harus hanya tersimpan di panel penyedia.

Namun:

  • gunakan image penyedia sebagai satu lapisan, bukan keseluruhan strategi;
  • uji cara lingkungan pemulihan pilihan Anda menggunakan image yang diunduh;
  • jangan berasumsi setiap hypervisor dapat menggunakannya secara langsung tanpa konversi;
  • simpan backup aplikasi, file, dan database untuk memulihkan data tertentu;
  • simpan salinan independen agar kegagalan penyedia atau akun utama tidak menghilangkan seluruh pilihan pemulihan.

Ketentuan VDSina sendiri secara eksplisit menyatakan bahwa pelanggan bertanggung jawab atas pencadangan dan merekomendasikan proses pencadangan rutin ditambah pengujian pemulihan berkala.

Saat membuat server VDSina baru dari cadangan penyedia, QA mereka mencatat bahwa cadangan/server baru harus memenuhi batasan penyedia seperti penempatan pusat data dan kuota disk yang memadai; pengaturan jaringan mungkin juga memerlukan penyesuaian setelah pemulihan.

Backup membantu mengamankan migrasi. Peralihan trafik, sinkronisasi data terakhir, DNS, dan rollback tetap perlu direncanakan tersendiri; lihat Migrasi Website ke VPS.

Panduan Pelaksanaan Pemulihan

Dokumentasikan proses pemulihan sebelum terjadi gangguan layanan.

Setidaknya, catat:

  • tujuan pencadangan;
  • penamaan/retensi titik pemulihan;
  • kredensial repositori;
  • lokasi pemulihan kunci enkripsi;
  • pembagian database, file, dan konfigurasi;
  • langkah-langkah penyediaan server baru;
  • perangkat lunak/versi runtime;
  • urutan pemulihan;
  • langkah DNS/jaringan;
  • integrasi eksternal/webhook;
  • pengujian untuk menyatakan layanan siap digunakan;
  • penanggung jawab keputusan pemulihan dan rollback.

Simpan panduan di lokasi yang tetap dapat diakses ketika VPS tidak tersedia.

Pertanyaan Umum

Apa strategi pencadangan VPS yang baik?

Tetapkan RPO/RTO, simpan salinan pemulihan independen, lindungi database dengan metode yang konsisten dengan aplikasi, pertahankan beberapa versi, pantau tugas yang gagal, dan pulihkan secara rutin ke lingkungan pengujian yang bersih.

Apakah snapshot VPS cukup?

Bukan sebagai satu-satunya lapisan pemulihan. Snapshot/image penyedia berguna untuk rollback yang cepat dan pemulihan server penuh, namun mungkin berbagi domain kegagalan penyedia/akun yang sama dan kurang nyaman untuk pemulihan granular.

Apa arti 3-2-1 untuk VPS?

Prinsip 3-2-1 adalah tiga salinan data, dua jenis media penyimpanan, dan satu salinan di lokasi terpisah. Pada VPS, periksa juga pemisahan akun serta infrastruktur agar kegagalan penyedia atau akun utama tidak menghapus seluruh salinan.

Seberapa sering saya harus mencadangkan VPS?

Pilih frekuensi dari RPO setiap tipe data. Situs statis mungkin menoleransi salinan harian; database transaksional mungkin memerlukan perlindungan setiap jam atau lebih sering.

Apa perbedaan antara RPO dan RTO?

RPO adalah kehilangan data terkini maksimum yang dapat diterima. RTO adalah waktu henti maksimum yang dapat diterima hingga layanan dipulihkan.

Haruskah saya mencadangkan seluruh VPS atau hanya file website saja?

Biasanya kedua lapisan berguna. Image server mempercepat pemulihan penuh; pencadangan file/database membuat pemulihan granular dan konsisten dengan aplikasi menjadi lebih mudah.

Bagaimana cara mencadangkan MySQL atau PostgreSQL dengan aman?

Gunakan backup logis/native yang sesuai dengan mesin database atau metode terkoordinasi yang menjaga konsistensi aplikasi, lalu buktikan dengan memulihkan atau mengimpornya ke lingkungan pengujian yang terisolasi.

Haruskah cadangan dienkripsi?

Data pemulihan sensitif harus dienkripsi jika diperlukan, tetapi simpan kata sandi/kunci pemulihan dengan aman di luar VPS yang gagal.

Apakah replikasi merupakan cadangan?

Replikasi saja belum cukup. Penghapusan, kerusakan data, atau perubahan berbahaya dapat ikut disalin. Simpan beberapa versi backup selain menggunakan replikasi atau server siaga.

Apakah VDSina menyediakan cadangan VPS?

Dokumentasi VDSina menjelaskan backup manual dan terjadwal, fungsi pemulihan/pembuatan server dari backup, serta image backup yang dapat diunduh. Ketentuannya tetap menempatkan tanggung jawab pencadangan pada pelanggan dan menyarankan pengujian pemulihan secara berkala.

Seberapa sering saya harus menguji pemulihan?

Tetapkan jadwal rutin dan ulangi pengujian setelah perubahan besar pada backup atau arsitektur. Untuk data penting yang cepat berubah, lakukan pengujian cukup sering agar hasil pengukuran waktu pemulihan tetap relevan.

Bagaimana jika RTO saya kurang dari satu jam?

Desain yang hanya mengandalkan backup mungkin terlalu lambat. Ukur durasi latihan pemulihan penuh dan pertimbangkan otomatisasi, image pemulihan siap pakai, server cadangan siap aktif, atau perubahan arsitektur jika RTO terukur tidak memenuhi target.
