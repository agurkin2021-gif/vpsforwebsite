Cara Hosting Website di VPS

Pelajari cara hosting website di VPS: pilih stack, atur SSH, domain, DNS, dan HTTPS. Siapkan backup serta monitoring sebelum website menerima trafik.

Pengungkapan: editor memiliki hubungan profesional dengan VDSina. Tautan mitra dapat menghasilkan komisi. Pengungkapan editorial dan komersial.

Cara menghosting website di VPS bergantung pada aplikasi yang Anda terapkan. Situs statis memerlukan server web dan DNS. WordPress atau CMS PHP lainnya juga membutuhkan PHP dan database. Aplikasi Node.js atau Python biasanya berjalan di belakang reverse proxy. Anda dapat membuat bagian-bagian tersebut secara manual di VPS yang bersih atau menggunakan panel kontrol untuk mengelolanya melalui browser.

Panduan ini membahas alur kerja dari VPS baru hingga website aktif. Jika Anda memindahkan website produksi yang sudah berjalan beserta data aktifnya, gunakan Migrasi Website ke VPS untuk proses peralihan dan rollback.

Urutan menyiapkan website di VPS

Ikuti urutan berikut untuk deployment pertama:

  1. Pilih VPS dan tentukan spesifikasinya.
  2. Pilih pengelolaan manual, panel kontrol, atau layanan managed.
  3. Pasang OS bersih atau gunakan template panel yang tersedia dari penyedia.
  4. Amankan akses pertama dan buat jalur administratif non-root.
  5. Perbarui sistem operasi.
  6. Instal hanya stack web yang dibutuhkan aplikasi.
  7. Konfigurasikan website/aplikasi sebelum peralihan DNS publik jika memungkinkan.
  8. Pasang file atau kode, lalu atur kepemilikan file, kredensial, dan akses database.
  9. Batasi firewall sambil menjaga SSH dan akses HTTP/HTTPS yang diperlukan tetap berfungsi.
  10. Uji server tujuan sebelum mengalihkan DNS publik.
  11. Arahkan domain ke VPS.
  12. Aktifkan HTTPS setelah nama host mencapai server.
  13. Verifikasi cron/worker, log, cadangan, dan pemantauan eksternal.
  14. Reboot sekali dan konfirmasikan setiap layanan yang diperlukan kembali secara otomatis.
  15. Barulah deployment dapat dianggap siap produksi.

Jangan menginstal PHP, MySQL, mail atau panel kontrol hanya karena panduan VPS generik menyertakannya. Instal komponen yang benar-benar dibutuhkan website Anda.

Pilih pengelolaan manual, panel, atau managed

Pilih cara pengelolaan yang sesuai dengan aplikasi dan kemampuan tim.

Manual / tanpa panel kontrol

Pilih VPS Linux yang bersih dan kelola stack melalui SSH.

Cocok bila:

  • Anda memahami stack aplikasi;
  • Anda ingin meminimalkan layanan tambahan;
  • Anda memerlukan konfigurasi Nginx/Apache/runtime khusus;
  • Anda menggunakan skrip, Git atau infrastruktur sebagai kode;
  • Anda tidak memerlukan antarmuka akun hosting tradisional.

Pengelolaan VPS tanpa panel kontrol memerlukan prosedur instalasi, pembaruan, backup, dan pemulihan yang Anda jalankan sendiri.

Panel kontrol

Gunakan panel jika pengelolaan website, domain, PHP, database, email, dan pengguna melalui browser dapat mengurangi pekerjaan rutin.

Lihat VPS dengan Panel Kontrol. Jika FASTPANEL sudah menjadi pilihan Anda, gunakan Hosting VPS FASTPANEL.

Layanan managed

Panel dan layanan pengelolaan adalah dua hal berbeda. Jika belum ada penanggung jawab patch, keamanan, pencadangan, pemantauan, dan penanganan insiden di pihak Anda, tentukan sebelum peluncuran.

Lihat VPS Managed vs Unmanaged.

Pemeriksa Metode Deployment

Alat ini membantu memilih pendekatan instalasi. Ikuti dokumentasi aplikasi untuk konfigurasi produksi yang tepat.

Pilih beban kerja dan preferensi pengoperasian.

Prasyarat

Sebelum menyiapkan server, pastikan tersedia:

  • VPS dengan spesifikasi sesuai beban aplikasi;
  • alamat IP server;
  • kredensial atau kunci SSH;
  • konsol penyedia/VNC/jalur pemulihan yang berfungsi;
  • domain terdaftar dan akses DNS;
  • file website atau repositori aplikasi;
  • versi runtime yang diperlukan;
  • persyaratan database;
  • rencana penyimpanan kredensial dan variabel lingkungan;
  • lokasi cadangan;
  • cara eksternal untuk menguji ketersediaan website.

Gunakan penentuan spesifikasi VPS untuk website sebelum penerapan jika kebutuhan sumber daya masih belum pasti.

Halaman VPS Standar VDSina saat ini mencantumkan templat OS murni termasuk Ubuntu 26.04/24.04/22.04/20.04, Debian 13/12/11/10, AlmaLinux, Rocky, CentOS, Oracle Linux, dan ArchLinux. Panduan ini menggunakan contoh gaya Ubuntu/Debian karena dokumentasi server web saat ini dan alur paket mudah diikuti; arsitekturnya berlaku untuk distribusi Linux lain yang didukung dengan perintah paket/layanan yang berbeda.

Pilih VPS untuk website

Pengungkapan: editor memiliki hubungan profesional dengan VDSina, dan situs ini dapat memperoleh komisi jika Anda memesan melalui tautan mitra ini. Pilih ukuran server dan model operasi dari beban kerja, bukan dari komisi.

Pilih sistem operasi

Untuk server website manual, pilih sistem operasi yang:

  • didukung oleh aplikasi/runtime;
  • masih mendapat pembaruan dan pemeliharaan;
  • dipahami oleh administrator Anda;
  • memiliki paket/dokumentasi terkini untuk stack web;
  • cocok dengan persyaratan panel apa pun jika nanti Anda menggunakannya.

Jangan memilih OS hanya karena terbaru. Kompatibilitas aplikasi dan keakraban administrator lebih penting.

Untuk contoh Linux sederhana saat ini, Ubuntu 24.04 LTS atau Debian 12 adalah target dokumentasi yang masuk akal. Jika vendor aplikasi Anda menentukan distribusi lain yang didukung, ikuti persyaratan tersebut.

Amankan akses SSH pertama

Akses root berguna untuk administrasi awal. Jalankan aplikasi produksi menggunakan akun non-root dengan hak yang sesuai.

Urutan akses pertama yang aman adalah:

  1. terhubung menggunakan kredensial/kunci yang disediakan oleh penyedia VPS;
  2. pastikan server/IP tersebut sesuai dengan yang Anda maksud untuk dibuat;
  3. pastikan konsol penyedia, VNC, atau jalur pemulihan tetap dapat digunakan;
  4. buat akun administrator tersendiri;
  5. berikan hak sudo atau administrator sesuai kebutuhan;
  6. tambahkan otentikasi kunci SSH jika memungkinkan;
  7. verifikasi login baru di sesi kedua sebelum menonaktifkan atau membatasi metode akses asli.

Contoh di Ubuntu/Debian:

ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy

Jangan mengunci satu-satunya jalur administratif yang berfungsi saat “memperkuat” server.

Penguatan keamanan SSH/firewall mendalam tercakup dalam Checklist Keamanan VPSuntuk pengaturan akses dan jaringan yang lebih lengkap.

Perbarui server sebelum memasang stack

Di Ubuntu/Debian:

sudo apt update
sudo apt upgrade -y

Nyalakan ulang jika pembaruan memerlukannya, lalu verifikasi bahwa Anda dapat menyambung kembali.

Jangan menunda pembaruan keamanan hingga website bersifat publik.

Jalur manual / tanpa panel kontrol

VPS manual harus berisi hanya layanan yang dibutuhkan aplikasi.

Pilihan umum adalah:

Website statis

Dibutuhkan:

  • Nginx atau Apache;
  • file website;
  • DNS;
  • HTTPS.

Tidak diperlukan secara otomatis:

  • PHP;
  • MySQL/MariaDB/PostgreSQL;
  • server email lokal.

Website PHP / WordPress

Biasanya dibutuhkan:

  • Nginx atau Apache;
  • modul PHP-FPM / PHP;
  • database;
  • file/unggahan website;
  • DNS;
  • HTTPS.

Untuk perilaku sumber daya WordPress, gunakan VPS untuk WordPress.

Node.js / Python / aplikasi khusus

Biasanya:

  • runtime aplikasi;
  • pengguna aplikasi non-root khusus;
  • manajer proses/layanan systemd;
  • aplikasi terikat ke localhost/soket privat jika memungkinkan;
  • reverse proxy Nginx/Apache;
  • database hanya bila diperlukan;
  • DNS;
  • HTTPS.

Jangan mengekspos server pengembangan langsung ke internet publik sebagai arsitektur produksi.

Instal server web

Dokumentasi server Ubuntu saat ini mendukung Nginx dan Apache. Tidak ada satu pun yang “lebih baik” secara universal.

Untuk contoh Nginx:

sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

Pada titik ini IP server harus mengembalikan halaman Nginx default jika aturan jaringan/firewall mengizinkan HTTP.

Gunakan Apache ketika aplikasi, tim, atau konfigurasi yang ada lebih cocok dengan Apache.

Konfigurasikan nama host website

Konfigurasi DNS dan server web adalah dua bagian dari tugas yang sama.

Penyedia DNS harus mengarahkan nama host ke VPS, dan server web harus mengetahui situs mana yang harus menjawab nama host tersebut.

Untuk Nginx, buat blok server untuk domain. Secara konseptual:

server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}

Di Ubuntu/Debian, konfigurasi khusus situs biasanya berada di bawah:

  • /etc/nginx/sites-available/
  • /etc/nginx/sites-enabled/

Setelah perubahan:

sudo nginx -t
sudo systemctl reload nginx

Selalu uji sintaks konfigurasi sebelum memuat ulang.

Untuk aplikasi dengan reverse proxy, server block meneruskan permintaan ke port atau soket aplikasi lokal.

Pasang file website atau kode aplikasi

Pilih metode deployment yang dapat diulang secara konsisten.

SFTP/SCP

Cocok untuk:

  • situs kecil;
  • penerapan manual yang jarang;
  • proyek awal yang sederhana.

Risiko: isi direktori produksi mudah menjadi tidak sinkron dengan repositori sumber.

rsync melalui SSH

Berguna untuk sinkronisasi file berulang dan pembaruan tambahan yang efisien.

Deployment berbasis Git

Berguna ketika rilis produksi harus sesuai dengan commit repositori.

CI/CD

Berguna jika frekuensi deployment membuat otomatisasi build, pengujian, dan rilis sepadan dengan waktu penyiapannya.

Apapun metode yang Anda gunakan:

  • gunakan root hanya untuk tugas yang memerlukannya;
  • tetapkan kepemilikan file kepada pengguna deployment atau aplikasi yang sesuai;
  • berikan server web hanya akses yang diperlukan;
  • simpan kredensial dan data rahasia di luar document root publik;
  • jangan gunakan izin tulis untuk semua pengguna sebagai jalan pintas.

Jalur PHP / WordPress

Untuk situs PHP di Ubuntu/Debian, instal paket PHP-FPM yang didukung saat ini dan ekstensi yang diperlukan untuk aplikasi tersebut.

Arsitektur khas:

peramban -> Nginx/Apache -> PHP-FPM -> database

Jangan menyalin daftar ekstensi acak dari CMS lain. Instal apa yang sebenarnya dibutuhkan aplikasi.

Untuk WordPress:

  • buat database dan pengguna database khusus;
  • konfigurasikan batas unggahan/memori/eksekusi PHP dari kebutuhan yang diukur;
  • jaga agar kredensial dalam wp-config.php terlindungi;
  • konfigurasikan nama host situs;
  • aktifkan HTTPS;
  • uji WP-Cron dan tugas latar belakang;
  • tambahkan cache sesuai beban website.

Gunakan VPS untuk WordPress untuk menghitung spesifikasi dan mengevaluasi kinerja WordPress.

Instalasi Node.js, Python, atau aplikasi khusus

Aplikasi produksi memerlukan pengelolaan proses yang tetap berfungsi setelah sesi terminal ditutup atau server di-reboot.

Gunakan:

  • pengguna aplikasi khusus;
  • file lingkungan/konfigurasi dengan izin terbatas;
  • systemd atau manajer proses produksi yang sesuai;
  • restart otomatis jika gagal/reboot;
  • port atau soket aplikasi yang hanya dapat diakses secara lokal atau privat;
  • reverse proxy Nginx/Apache;
  • log aplikasi;
  • pemeriksaan kesehatan.

Aliran umum:

browser -> HTTPS/Nginx -> aplikasi pada 127.0.0.1:PORT -> database/layanan eksternal

Ikuti panduan deployment produksi dari framework yang digunakan.

Database: instal hanya jika diperlukan

Website statis tidak memerlukan database.

Untuk aplikasi dinamis yang memerlukannya:

  • instal mesin database yang didukung;
  • buat database khusus;
  • buat pengguna khusus aplikasi;
  • berikan hanya hak akses yang diperlukan;
  • jauhkan kredensial dari web root;
  • jangan mengekspos port database secara publik kecuali ada arsitektur aman tertentu yang memerlukannya;
  • sertakan database dalam rencana backup dan monitoring.

Tugas database dapat menjadi penghambat VPS yang sebenarnya bahkan ketika server web hampir tidak aktif.

Kepemilikan file, izin akses, dan kredensial

Hindari dua kesalahan umum:

  1. menjalankan website sebagai root;
  2. membuat direktori aplikasi dapat ditulis oleh semua pengguna untuk ‘memperbaiki’ kesalahan izin.

Terapkan langkah berikut:

  • gunakan pengguna deployment atau aplikasi yang sesuai;
  • tentukan proses yang memerlukan akses baca atau tulis;
  • batasi akses tulis pada direktori uploads atau cache sesuai kebutuhan;
  • lindungi file environment dan kredensial;
  • jangan memasukkan rahasia produksi ke Git;
  • simpan kunci privat di luar document root publik.

Kepemilikan sebenarnya bergantung pada aplikasi dan model server web; gunakan dokumentasi aplikasi daripada menyalin resep chmod 777 universal.

Uji website sebelum mengalihkan DNS publik

Jangan jadikan DNS sebagai pengujian nyata pertama terhadap aplikasi.

Sebelum peralihan publik, verifikasi server baru menggunakan salah satu metode berikut jika praktis:

  • buka IP server untuk pemeriksaan dasar atau halaman statis;
  • gunakan pengaturan file hosts lokal agar example.com mengarah ke VPS baru hanya di komputer Anda;
  • gunakan nama host pengujian yang tidak dapat terindeks sebagai duplikat website;
  • uji aplikasi dengan konfigurasi nama host yang sama seperti produksi.

Periksa lebih dari beranda:

  • halaman internal penting;
  • masuk/admin;
  • formulir;
  • unggahan;
  • aset statis;
  • pembacaan/penulisan database;
  • endpoint aplikasi atau API;
  • pengalihan;
  • log.

Pengaturan file hosts lokal berguna karena aplikasi dapat berperilaku berbeda saat dibuka melalui domain sebenarnya dibandingkan melalui IP server.

Jika ini adalah situs aktif yang sudah ada, gunakan proses peralihan yang lebih ketat di Migrasi website ke VPS.

Arahkan domain ke VPS

Di penyedia DNS, konfigurasikan catatan yang harus mencapai server ini.

Pengaturan IPv4 umum:

NamaJenisNilai
@AAlamat VPS IPv4
wwwCNAMEdomain root

Record A untuk www juga dapat digunakan.

Tambahkan catatan AAAA hanya jika IPv6 benar-benar dikonfigurasi dan dapat dijangkau di VPS. Catatan AAAA yang rusak dapat membuat beberapa pengunjung gagal bahkan ketika IPv4 berfungsi.

DNS saja tidak membuat website berfungsi: konfigurasi situs Nginx/Apache juga harus memiliki nama host yang cocok.

Untuk situs produksi yang sudah berjalan, rencanakan peralihan DNS dan sinkronisasi data terakhir melalui panduan Migrasi website ke VPS.

Aktifkan HTTPS setelah DNS mengarah dengan benar

Dapatkan sertifikat tepercaya hanya setelah nama host publik ditetapkan ke server yang akan menjawab permintaan validasi. Pastikan aturan jaringan firewall/penyedia sudah mengizinkan jalur validasi HTTP/HTTPS yang ingin Anda gunakan.

Untuk Nginx/Apache, klien ACME seperti Certbot dapat meminta dan memperbarui sertifikat Let's Encrypt. Ikuti instruksi Certbot/OS saat ini daripada menyalin perintah paket lama secara membabi buta.

Verifikasi:

  • sertifikat mencakup domain utama dan varian www yang Anda gunakan;
  • HTTP dialihkan ke HTTPS sebagaimana dimaksud;
  • perpanjangan sertifikat dilakukan secara otomatis;
  • proses perpanjangan dapat melewati aturan firewall atau CDN;
  • aplikasi menghasilkan URL HTTPS yang benar.

Jangan aktifkan pengalihan HTTPS sebelum Anda mengetahui jalur sertifikat berfungsi.

Konfigurasikan firewall

Jaga akses administratif tetap berfungsi saat mengubah aturan firewall.

Website publik dasar biasanya memerlukan:

  • SSH dari sumber/jalur administrasi yang diperlukan;
  • TCP 80 untuk HTTP/ACME/pengalihan;
  • TCP 443 untuk HTTPS.

Jangan mengekspos MySQL/PostgreSQL, Redis atau port aplikasi internal secara publik hanya karena port tersebut mendengarkan secara lokal secara default.

Pada server yang menggunakan UFW, izinkan jalur SSH yang diperlukan sebelum mengaktifkan aturan yang membatasi.

Panduan pengaturan firewall dan keamanan yang lebih rinci tersedia di Checklist Keamanan VPS.

Cron, antrean, dan worker

Website dinamis sering kali gagal setelah penerapan karena hanya jalur permintaan web yang dikonfigurasi.

Inventarisasi:

  • tugas cron;
  • worker antrean;
  • tindakan terjadwal;
  • impor/ekspor;
  • tugas email;
  • proses pengisian awal cache;
  • pemroses latar belakang.

Pastikan setiap tugas:

  • berjalan sebagai pengguna non-root yang sesuai;
  • dimulai otomatis jika diperlukan;
  • mencatat aktivitas di lokasi log yang diketahui;
  • tidak berjalan bersamaan hingga menghabiskan CPU atau RAM;
  • aktif kembali setelah server di-reboot.

Log dan pemantauan dasar

Sebelum lalu lintas produksi, ketahui ke mana harus mencari ketika situs gagal.

Minimal identifikasi:

  • log akses Nginx/Apache;
  • log kesalahan Nginx/Apache;
  • log aplikasi;
  • log PHP-FPM/runtime;
  • log/status database;
  • jurnal sistem;
  • penggunaan disk;
  • tekanan memori/CPU.

Tambahkan pemeriksaan uptime HTTP(S) eksternal sehingga kegagalan server terlihat bahkan ketika tidak ada orang yang login ke VPS.

Panduan menentukan ambang batas dan respons peringatan tersedia di Monitoring VPS.

Uji layanan setelah reboot

Kesalahan konfigurasi startup sering baru terlihat setelah reboot pertama.

Sebelum menganggap server siap:

sudo reboot

Setelah server aktif kembali, periksa:

  • akses SSH;
  • Nginx/Apache;
  • PHP-FPM atau layanan aplikasi;
  • database;
  • cron/worker antrean;
  • HTTPS;
  • halaman/formulir website;
  • pemantauan;
  • jadwal pencadangan.

Jika aplikasi hanya kembali setelah seseorang meluncurkan perintah secara manual, penerapannya belum selesai.

Kapan pengelolaan manual kurang sesuai?

Gunakan panel kontrol atau administrasi terkelola ketika:

  • tidak ada yang merasa nyaman dengan SSH dan pemulihan baris perintah;
  • tidak ada penanggung jawab pembaruan OS/keamanan;
  • tidak ada yang dapat mendiagnosis kegagalan server web/runtime/database;
  • cadangan dibuat tetapi tidak ada yang dapat memulihkannya;
  • waktu henti yang penting bagi bisnis tidak memiliki penanggung jawab insiden;
  • tim ingin email/pengguna/domain dikelola melalui UI hosting daripada konfigurasi server;
  • stack aplikasi dilayani lebih baik oleh platform terkelola.

VPS manual dapat mengurangi penggunaan sumber daya tambahan oleh panel dan memaksimalkan kontrol, namun tidak mengurangi jumlah tanggung jawab operasional.

Gunakan VPS dengan Panel Kontrol untuk pemilihan panel atau VPS Managed vs Unmanaged ketika bagian yang hilang adalah tanggung jawab operasional.

Siapkan backup dan monitoring

Tetapkan penanggung jawab dan prosedur operasional sebelum website digunakan.

Sebelum mengandalkan situs:

  • jadwalkan backup;
  • simpan salinan independen di luar server;
  • sertakan database, konfigurasi, dan kredensial yang diperlukan untuk pemulihan;
  • uji pemulihan;
  • pantau ketersediaan website;
  • pantau pertumbuhan penggunaan disk;
  • perhatikan tekanan CPU/RAM/database;
  • pantau perpanjangan sertifikat.

Rencana pemulihan lebih lengkap dibahas dalam Strategi Backup VPS. Untuk ambang batas dan peringatan, gunakan Monitoring VPS.

Banyak website

Untuk beberapa situs:

  • gunakan server block atau virtual host terpisah untuk setiap nama host;
  • pisahkan document root;
  • gunakan kredensial aplikasi dan database terpisah;

Pertanyaan Umum

Bisakah saya menghosting website di VPS tanpa panel kontrol?

Ya. Anda dapat mengelola VPS Linux melalui SSH dan memasang server web, runtime, serta database sesuai kebutuhan aplikasi. Siapkan sendiri konfigurasi, pembaruan, backup, monitoring, dan prosedur pemulihannya.

Apakah saya memerlukan Nginx untuk menghosting website di VPS?

Tidak. Nginx dan Apache keduanya merupakan pilihan umum. Gunakan server web yang sesuai dengan aplikasi, konfigurasi, dan pengalaman administrator.

Apakah setiap situs VPS memerlukan database?

Tidak. Website statis tidak memerlukannya. Instal MySQL/MariaDB/PostgreSQL hanya jika aplikasi memerlukan database.

Haruskah saya menggunakan root untuk menghosting website?

Gunakan root untuk administrasi yang memerlukan hak tersebut. Jalankan dan deploy website melalui pengguna atau layanan non-root dengan izin yang dibutuhkan saja.

Kapan saya harus menggunakan panel kontrol?

Gunakan panel jika pengelolaan website, domain, PHP, database, pengguna, email, dan backup melalui browser memberi manfaat yang sepadan dengan kebutuhan sumber daya dan batasan panel.

Bisakah saya menghosting WordPress di VPS tanpa cPanel?

Ya. WordPress memerlukan server web yang kompatibel, PHP, database, file WordPress, izin yang benar, DNS dan HTTPS. Panel bersifat opsional.

Kapan saya harus mengarahkan DNS ke VPS?

Untuk website baru, setelah server siap melayani nama host yang sebenarnya. Untuk website produksi yang sudah ada, lakukan pengujian terlebih dahulu dan gunakan rencana migrasi/peralihan yang terkendali.

Mengapa domain saya mengarah ke VPS tetapi menampilkan situs yang salah?

DNS hanya mengirimkan nama host ke IP server. Nginx/Apache juga harus memiliki blok server/host virtual yang cocok untuk nama host tersebut.

Kapan saya harus mengaktifkan HTTPS?

Setelah nama host publik ditetapkan ke server dan jalur validasi berfungsi. Kemudian terbitkan sertifikat, verifikasi cakupan root/www dan konfigurasikan pengalihan HTTP-ke-HTTPS yang dimaksud.

Apa yang harus saya periksa setelah me-reboot VPS?

Konfirmasikan server web, layanan aplikasi/PHP-FPM, database, worker, HTTPS, pemantauan, dan website semuanya kembali tanpa intervensi manual.
