Estratégia de backup para VPS

Estratégia de backup para VPS: defina RPO e RTO, combine imagens do provedor com backups externos independentes, proteja bancos de dados e credenciais, defina a retenção e comprove a recuperação com testes de restauração.

Uma estratégia de backup para VPS não se resume a “ativar snapshots uma vez por dia”. Um plano de recuperação viável define quanto de dados você pode perder (RPO), quanto tempo a recuperação pode levar (RTO), quais dados precisam sobreviver, onde ficam as cópias independentes, por quanto tempo as versões são mantidas e se alguém já as restaurou de fato.

Um plano robusto para VPS geralmente combina recuperação rápida pelo provedor, uma cópia independente fora do servidor e backups de banco de dados consistentes com a aplicação. A combinação exata depende da velocidade com que os dados mudam e do custo da indisponibilidade.

A estratégia de backup também precisa de um responsável definido. Se ninguém cuida das falhas nas tarefas, dos testes de restauração e das decisões de recuperação, resolva primeiro esse modelo operacional: veja VPS gerenciado ou não gerenciado.

Para a decisão mais ampla do servidor, consulte VPS para sites.

Para muitas implantações comuns de VPS do site, uma boa linha de base é:

  • imagem/instantâneo do lado do provedor para rápida reversão;
  • backup independente criptografado de arquivos / config / banco de dados para outro domínio de falha;
  • múltiplos pontos de restauração;
  • frequência de backup do banco de dados escolhida a partir da perda de dados aceitável;
  • Testes regulares de restauração.

Isso é mais útil do que confiar em um status de "backup bem-sucedido".

Avaliação da estratégia de backup do VPS

Esta avaliação identifica a arquitetura de recuperação necessária. Ela não garante a recuperação.

Escolha os requisitos de recuperação que realmente se aplicam.

Comece com RPO e RTO

Dois números devem conduzir a estratégia.

RPO — objetivo de ponto de recuperação

RPO responde:

Quantos dados recentes a empresa pode dar ao luxo de perder?

Se o RPO for:

  • 24 horas - um ponto de recuperação diário bem-sucedido pode ser aceitável;
  • 4 horas - backups diários são insuficientes;
  • 1 hora — as alterações no estado da aplicação/banco de dados precisam de proteção pelo menos com essa frequência;
  • minutos - backups regulares por si só pode não ser suficiente.

RPO se refere à perda de dados, não ao tempo de indisponibilidade.

RTO — objetivo de tempo de recuperação

RTO responde:

Por quanto tempo o site/serviço pode permanecer indisponível?

Um backup pode atender o RPO e ainda falhar o RTO.

Exemplo:

  • banco de dados copiado a cada hora;
  • A perda de dados mais recente é de menos de uma hora;
  • mas reprovisionar o VPS, baixar dados, restaurar o DB e validar o site leva seis horas.

Essa estratégia pode satisfazer um RPO de uma hora, mas tem um RTO real perto de seis horas.

A orientação de planejamento de contingência do NIST define RPO como o ponto de recuperação no tempo e RTO como a janela de indisponibilidade máxima aceitável. Use esses alvos antes de escolher ferramentas.

O que precisa entrar no backup?

Classifique os componentes do servidor em reconstruíveis e com estado persistente/insubstituíveis.

Reconstruível

Muitas vezes reproduzível a partir de código ou automação:

  • sistema operacional base;
  • pacotes;
  • código de aplicação já armazenado em segurança no Git;
  • imagens de contêiner que podem ser reconstruídas/puxadas;
  • Pacotes padrão de servidor web.

Com estado persistente / difíceis de recriar

Geralmente maior prioridade:

  • bancos de dados;
  • uploads de usuários/mídia;
  • caixas de e-mail, se hospedadas localmente;
  • configuração;
  • ambiente/segredos necessários para a recuperação;
  • TLS/chaves privadas onde a substituição não é trivial;
  • dados gerados por aplicativos;
  • configuração do painel de controle/site;
  • configuração cron/processo;
  • Dados da zona DNS se o DNS estiver hospedado no VPS;
  • scripts personalizados não armazenados em outro lugar.

Não desperdice a capacidade de backup copiando caches, arquivos temporários e artefatos reconstruíveis enquanto esquece o banco de dados ou segredos necessários para iniciar o site.

Instantâneo, imagem, backup de arquivos e replicação são diferentes

Não trate isso como intercambiável.

Snapshot / imagem do servidor pelo provedor

Útil para:

  • rápida reversão após uma atualização arriscada;
  • recuperação do servidor completo;
  • Clonagem/recriação da VM.

Fraquezas:

  • pode ficar no mesmo domínio de falha do provedor/conta;
  • pode não fornecer restauração granular de arquivo/site;
  • a consistência da aplicação/banco de dados ainda deve ser compreendida;
  • manter apenas a imagem mais recente oferece pouco histórico.

Backup no nível do arquivo

Útil para:

  • uploads;
  • configuração;
  • dados selecionados do aplicativo;
  • restauração granular.

Ferramentas como restic ou Borg podem armazenar backups com versões criptografadas em repositórios remotos.

Backup de banco de dados

Use um método compatível com o mecanismo do banco de dados:

  • dump lógico;
  • ferramenta de backup nativa;
  • snapshot/processo consistente com aplicação.

Não assuma que copiar arquivos de banco de dados ao vivo produz um backup de banco de dados utilizável.

Replicação / servidor em espera

A replicação pode reduzir o tempo de recuperação ou a perda de dados, mas não é um backup histórico por si só.

Um erro de exclusão, corrupção ou aplicação também pode ser replicado.

Use replicação/standby para disponibilidade/RTO quando necessário e mantenha backups versionados para recuperação histórica.

Um prático modelo 3-2-1 para VPS

O modelo comum 3-2-1 significa:

  • 3 cópias de dados importantes;
  • 2 modos diferentes de armazenamento/falha;
  • 1 cópia externa / fora do domínio principal de falha.

Para um VPS, uma interpretação prática pode ser:

  1. dados de produção sobre o VPS;
  2. imagem de backup do provedor para recuperação rápida;
  3. backup de arquivos/banco de dados externos criptografados em um destino independente.

O objetivo não é satisfazer um slogan literalmente, o objetivo é evitar que um evento destrua a produção e cada cópia de recuperação.

Exemplos de domínios de falha:

  • o sistema de arquivos VPS;
  • armazenamento de backup do provedor;
  • a conta do provedor;
  • uma conta/fornecedor separado de armazenamento de objetos;
  • uma cópia off-line ou imutável.

Se um invasor que controla o VPS pode excluir todos os backups usando as mesmas credenciais, as cópias não são significativamente independentes.

Backups consistentes com banco de dados

O estado do banco de dados muda enquanto o site está ativo.

Uma estratégia válida precisa definir como o mecanismo do banco de dados será protegido.

Para WordPress/MySQL/MariaDB isso pode ser:

  • dumps lógicos;
  • ferramentas de backup DB nativas;
  • instantâneos coordenados;
  • software de backup que lida explicitamente com a consistência do banco de dados.

Para PostgreSQL, use métodos de backup/PITR compatíveis com PostgreSQL quando o RPO os exigir.

O ponto não é a ferramenta exata, o ponto é que o DB restaurado deve ser internamente coerente e utilizável.

Para o estado e as operações do aplicativo específico do WordPress, consulte VPS para o WordPress.

Teste:

  • conclusão do dump/backup;
  • O arquivo não está vazio;
  • restauração/importação é bem-sucedida;
  • tabelas/registros representativos existem;
  • o aplicativo pode conectar e executar leituras/escritas críticas.

Sites transacionais precisam de um RPO diferente

Um site institucional pode tolerar uma cópia do dia anterior.

Uma loja transacional pode não.

Para WooCommerce, sistemas de associação, faturamento ou pedidos, defina quanto estado recente pode ser perdido:

  • pedidos;
  • Pagamentos;
  • estoque;
  • clientes;
  • assinaturas de membros;
  • envios de formulários;
  • uploads.

Se uma loja recebe pedidos a cada hora, um backup noturno do banco de dados pode deixar muitas transações sem recuperação.

Use VPS para WooCommerce para a carga de trabalho da loja. O cronograma de backup aqui deve ser escolhido na janela aceitável de perda de transação.

Frequência de backup e retenção

O intervalo entre backups não deve exceder o RPO da classe de dados protegida.

Dados diferentes podem usar horários diferentes:

  • banco de dados: frequente;
  • uploads: frequentes ou orientados a eventos;
  • OS/config: após alterações importantes + agendadas;
  • imagem completa do provedor: menos frequente, mas útil em torno de mudanças arriscadas.

A retenção protege contra falhas descobertas tarde.

Um padrão ilustrativo pode manter:

  • pontos recentes de restauração por hora;
  • várias cópias diárias;
  • várias cópias semanais;
  • Cópias mensais selecionadas.

A retenção exata deve vir de:

  • necessidades de recuperação de negócios;
  • custo de armazenamento;
  • taxa de mudança de dados;
  • cumprimento/requisitos legais;
  • por quanto tempo uma corrupção de dados ou invasão pode passar despercebida.

Não mantenha apenas a versão “mais recente”.

Mantenha um destino independente fora do servidor

Um backup no mesmo disco VPS não protege contra:

  • perda de disco/sistema de arquivos;
  • exclusão do servidor;
  • comprometimento do acesso root;
  • ransomware;
  • erro de conta;
  • A perda da VM no lado do provedor.

Mova ou transmita dados de recuperação fora do VPS.

Destinos possíveis:

  • armazenamento de objetos;
  • outro serviço de backup/fornecedor;
  • outro VPS usado apenas para backups;
  • Armazenamento offline/controlado.

Separe as credenciais de provedor/conta quando for prático.

Criptografar backups e proteger a chave de recuperação

Criptografe dados de backup confidenciais em trânsito e em repouso quando apropriado.

Mas a criptografia cria outra dependência de recuperação.

Não armazene a senha/chave do backup somente:

  • apenas no VPS;
  • apenas no mesmo cofre/conta de senha que possa estar indisponível;
  • Só dentro do backup criptografado.

Mantenha as credenciais/chaves de recuperação em um local independente seguro e inclua a disponibilidade da chave nos exercícios de restauração.

Separe credenciais de backup e direitos de exclusão

O comprometimento do servidor de produção não deve dar automaticamente ao invasor permissão para apagar todas as cópias de recuperação.

Prefira:

  • credenciais de backup com permissões limitadas;
  • acesso de gravação sem privilégios amplos de exclusão, quando o armazenamento permitir;
  • credenciais administrativas separadas;
  • Bloqueio de retenção/imutabilidade quando apropriado;
  • cópia offline/isolada da rede para dados de alto valor.

O projeto exato depende do serviço de armazenamento.

Esse é um dos motivos pelos quais os backups também são um controle de segurança; veja o Checklist de segurança para VPS.

Monitore as tarefas de backup

A automação reduz os backups esquecidos, mas a automação com falha pode falhar silenciosamente.

Monitore:

  • horário do último backup bem-sucedido;
  • tarefas falhadas/parciais;
  • disponibilidade do repositório/armazenamento;
  • expiração da credencial;
  • espaço livre em disco antes da preparação local do backup;
  • quota de armazenamento externo;
  • falhas nos dumps do banco de dados;
  • alterações na duração do backup;
  • excepcionalmente pequeno tamanho de backup;
  • falhas na retenção/remoção de versões antigas.

Um status verde no cron/serviço comprova que o comando foi executado. Não comprova que a restauração funciona.

O planejamento mais amplo de alertas de servidor/serviço está em Monitoramento de VPS; a integridade das tarefas de backup continua fazendo parte da própria estratégia de recuperação.

Teste as restaurações e meça o RTO real

Um backup torna-se credível quando restaura.

Faça exercícios de recuperação em um destino limpo isolado.

Teste o suficiente da sequência completa:

  1. provisionar um novo ambiente de teste/VPS;
  2. recuperar o ponto de backup correto;
  3. recuperar credenciais de criptografia/repositório;
  4. restaurar arquivos/configuração;
  5. restaurar/importar o banco de dados;
  6. restaurar segredos/certificados necessários;
  7. configurar serviços/rede;
  8. iniciar a aplicação;
  9. testar páginas e transações importantes;
  10. verificar tarefas/integrações em segundo plano;
  11. Meça o tempo de recuperação.

Registre o resultado medido.

Se o RTO do negócio é de quatro horas e o teste leva oito, a estratégia de backup falhou o requisito de negócios, mesmo se cada arquivo restaurado com sucesso.

A orientação do NIST enfatiza a criação regular de backup, testes de restauração e exercícios de recuperação.

A granularidade da restauração importa

Uma boa estratégia permite recuperar o sistema do tipo de falha que realmente ocorreu.

Recuperação de arquivo único/site

Necessário para:

  • upload excluído;
  • configuração quebrada;
  • um site comprometido;
  • recuperação de um banco de dados/tabela com problemas.

Recuperação de servidor completo

Necessário para:

  • VPS morto/excluído;
  • falha do sistema de arquivos;
  • comprometimento grave da segurança;
  • Substituição de provedor/servidor.

Se o único backup for uma imagem de disco completo, restaurar um arquivo pode ser inconveniente.

Se o único backup contiver apenas arquivos selecionados, reconstruir o VPS completo pode demorar demais.

Combine os métodos em camadas.

Vários sites precisam de restauração no nível do site

Em um VPS com vários sites, não planeje a recuperação de modo que corrigir o Site A reverta automaticamente os Sites B/C/D para o estado de ontem.

Prefira backups que permitem restaurar:

  • um diretório raiz de site;
  • um banco de dados;
  • um painel/usuário;
  • um conjunto de uploads;
  • o VPS completo somente quando necessário.

Para a decisão de arquitetura/domínio de falha, consulte VPS para vários sites.

Backups também podem causar interrupções.

O trabalho de backup consome recursos.

Impacto potencial:

  • CPU usada pelo dump do banco de dados;
  • CPU de compressão;
  • I/O de leitura;
  • uso de disco temporário;
  • largura de banda de upload de armazenamento de objetos;
  • expulsão de dados do cache;
  • sobreposição de backups com importações/varreduras/picos de tráfego.

Evite montar um arquivo local de 30 GB quando o VPS tem apenas 10 GB livres.

Onde for prático:

  • transmita os backups diretamente para fora do servidor;
  • monitorar o uso temporário do disco;
  • programar trabalho de backup pesado fora dos picos de tráfego;
  • limite de taxa onde a ferramenta suporta;
  • Meça a duração do backup.

Como backups VDSina se encaixam na estratégia

A documentação pública do VDSina descreve atualmente várias funções de recuperação úteis:

  • cópias manuais de backup do servidor;
  • backups agendados;
  • restaurar um backup para o servidor de onde veio;
  • criar um novo servidor a partir de um backup;
  • clonar um servidor;
  • Baixe uma imagem de backup.

A documentação de download mostra um nome de arquivo de backup no formato:

vXXX.backup.hosted-by-vdsina.com.img.gz

Essa imagem para download é uma camada de portabilidade útil porque uma cópia de recuperação não precisa permanecer apenas dentro do painel do provedor.

No entanto:

  • tratar a imagem do provedor como uma camada , não toda a estratégia;
  • testar como seu ambiente de recuperação escolhido usa a imagem baixada;
  • Não assuma que todo hipervisor pode consumi-lo diretamente sem conversão;
  • manter backups de aplicativo/arquivo/banco de dados para recuperação granular;
  • Mantenha uma cópia independente do domínio de falha onde o risco a justifique.

Os próprios Termos da VDSina declaram explicitamente que o cliente é responsável por backups e recomendam um processo de backup de rotina, além de testes periódicos de restauração.

Ao criar um novo servidor VDSina a partir de um backup do provedor, a seção de perguntas e respostas informa que o backup/novo servidor precisa atender às restrições do provedor, como localização no datacenter e cota de disco suficiente; as configurações de rede também podem precisar de ajustes após a restauração.

Não confunda backup com migração. Um backup pode integrar a proteção de uma migração, mas a virada em produção, as gravações finais, o DNS e a reversão são questões separadas; veja Migração de site para VPS.

Roteiro de recuperação

Anote o processo de recuperação antes da interrupção.

No mínimo:

  • destinos de backup;
  • nomenclatura/retenção dos pontos de restauração;
  • credenciais de repositório;
  • localização de recuperação de chave de criptografia;
  • quais dados são DB/files/config;
  • etapas de provisionamento de um novo servidor;
  • versões de ambiente de software/execução;
  • ordem de restauração;
  • Passos DNS/rede;
  • integrações externas/webhooks;
  • testes de aceitação;
  • quem toma a decisão de recuperação/reversão.

Mantenha o runbook em algum lugar disponível mesmo quando o próprio VPS não estiver disponível.

FAQ

O que é uma boa estratégia de backup VPS?

Defina RPO/RTO, mantenha cópias de recuperação independentes, proteja bancos de dados com um método consistente com aplicativos, retenha várias versões, monitore tarefas com falha e restaure regularmente em um ambiente de teste limpo.

Um instantâneo VPS é suficiente?

Não como a única camada de recuperação. Um instantâneo / imagem do provedor é útil para a reversão rápida para o estado anterior e a recuperação do servidor completo, mas pode compartilhar o mesmo domínio de falha do provedor / conta e é menos conveniente para restaurações granulares.

O que significa 3-2-1 para um VPS?

Mantenha os dados ao vivo e várias cópias de recuperação usando domínios independentes de armazenamento/falha, com pelo menos uma cópia fora do caminho principal de falha do VPS/provedor.

Com que frequência devo fazer backup de um VPS?

Escolha a frequência do RPO de cada tipo de dados. Um site estático pode tolerar cópias diárias; um banco de dados transacional pode exigir proteção horária ou mais frequente.

Qual é a diferença entre RPO e RTO?

RPO é a perda máxima aceitável de dados recentes. RTO é o tempo de inatividade máximo aceitável até que o serviço seja restaurado.

Devo fazer backup de todo o VPS ou apenas arquivos do site?

Normalmente, ambas as camadas são úteis. Uma imagem de servidor acelera a recuperação completa; backups de arquivos/bancos de dados facilitam restaurações granulares e consistentes com aplicativos.

Como faço backup do MySQL ou PostgreSQL com segurança?

Use um backup lógico/nativo compatível com o mecanismo do banco de dados ou um método coordenado que garanta a consistência da aplicação. Depois, comprove seu funcionamento restaurando/importando em um ambiente de teste isolado.

Os backups devem ser criptografados?

Os dados de recuperação sensíveis devem ser criptografados quando apropriado, mas mantenha a senha/chave de recuperação em segurança fora do VPS com falha.

A replicação é um backup?

Não por si só. A replicação pode copiar a exclusão acidental, corrupção ou alterações maliciosas. Mantenha backups históricos / versionados, além de replicação / espera.

A VDSina documenta backups manuais e agendados, funções de restauração/criação de servidor a partir de backup e imagens de backup para download. Seus Termos continuam atribuindo ao cliente a responsabilidade pelos backups e recomendam testes periódicos de restauração.

Quantas vezes devo testar restaurações?

Em um cronograma definido e após mudanças significativas de backup/arquitetura. Sistemas de alto valor ou em rápida mudança devem ser testados com frequência suficiente para que o processo de recuperação medido permaneça confiável.

E se o meu RTO tiver menos de uma hora?

Um design somente de backup pode ser muito lento. Faça um exercício de recuperação completo e considere a automação, imagens de recuperação pré-construídas, servidor de backup pronto para iniciar ou alterações de arquitetura se o RTO medido falhar o alvo.
