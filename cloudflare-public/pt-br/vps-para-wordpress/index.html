VPS para WordPress

VPS para WordPress: dimensione CPU e RAM com base nos processos PHP, na carga do banco de dados, no cache, nos plugins e nas tarefas em segundo plano. Depois, escolha a forma adequada de gerenciamento e migração.

O VPS para WordPress é útil quando o WordPress precisa de mais recursos de controle, isolamento ou nível de servidor do que a hospedagem compartilhada pode fornecer. O VPS deve ser dimensionado em torno de trabalho PHP sem cache, demanda de banco de dados, plugins, tarefas em segundo plano, crescimento de armazenamento e os serviços que são executados ao lado do WordPress , não em torno de um número de visitante mensal.

Para a decisão mais ampla do servidor, consulte VPS para sites.

Os requisitos do WordPress não definem o dimensionamento do VPS

O WordPress.org atualmente recomenda um host que suporte:

  • PHP 8.3 ou maior;
  • MariaDB 10.11+ ou MySQL 8.0+;
  • HTTPS;
  • Apache ou Nginx como opções recomendadas de servidor web.

Esses requisitos respondem "Este servidor pode executar o WordPress?" Eles não respondem "quanto VPS essa carga de trabalho de produção precisa?"

Um VPS de produção também precisa de RAM/CPU/armazenamento para:

  • Linux;
  • Nginx/Apache;
  • Processos PHP-FPM;
  • MySQL/MariaDB;
  • OPcache;
  • cache de página/objeto onde usado;
  • painel de controle;
  • e-mail, se hospedado localmente;
  • backups;
  • tarefas cron;
  • varreduras de malware/segurança;
  • importações/exportações;
  • monitoramento;
  • margem de capacidade operacional.

Não use os requisitos de software do WordPress como uma recomendação de recurso de produção.

Avaliação de adequação de VPS para WordPress

Use essa avaliação como ponto de partida. Não substitui as medições reais da CPU/RAM/banco de dados.

Use evidência de carga de trabalho real sempre que possível.

Quando o WordPress realmente precisa de VPS

Um site WordPress pode justificar VPS mesmo sem tráfego enorme.

Razões comuns:

  • Repetidos limites de CPU/memória/processo sob carga legítima;
  • necessidade de uma configuração de ambiente PHP/execução personalizada;
  • necessidade de Redis/Memcached ou outro serviço do lado do servidor;
  • cron do sistema real em vez de agendamento desencadeado pelo visitante;
  • tarefas em segundo plano de longa duração;
  • comportamento personalizado de Nginx/Apache;
  • vários sites que precisam de um ambiente controlado;
  • maior carga de trabalho/isolamento da conta;
  • Monitoramento de nível de servidor ou requisitos de firewall.

Se o único sintoma for “o site está lento”, compare primeiro VPS vs. hospedagem compartilhada e verifique se o gargalo não está no próprio WordPress.

Quando o WordPress não precisa de VPS

Mantenha-se em uma boa hospedagem WordPress compartilhada ou gerenciada quando:

  • o site é leve e estável;
  • o cache funciona bem;
  • os indicadores de recursos da hospedagem não mostram limites recorrentes;
  • nenhum serviço personalizado/acesso root é necessário;
  • a equipe não quer manter o Linux;
  • o provedor já lida com backups, segurança, atualizações ou ambiente de teste bem o suficiente;
  • O VPS substituiria principalmente um simples serviço de hospedagem por mais trabalho operacional.

O VPS não é automaticamente mais rápido. Um VPS mal dimensionado ou não ajustado pode executar o WordPress pior do que uma boa plataforma gerenciada.

Processos PHP e RAM

Para solicitações sem cache, os processos PHP-FPM são um grande limite de concorrência.

Cada processo ativo consome memória durante o processamento de uma solicitação. Mais processos podem lidar com solicitações dinâmicas mais simultâneas, mas aumentar a contagem de processos sem aumentar o orçamento da RAM pode causar:

  • swap;
  • pressão de memória;
  • encerramento de processos por falta de memória (OOM);
  • falta de recursos para o banco de dados;
  • Instabilidade do servidor.

Um modelo prático é:

RAM para WordPress = sistema operacional + servidor web + banco de dados + cache + processos PHP + painel/e-mail/tarefas + margem de capacidade

Então:

limite de processos PHP = RAM disponível com segurança para PHP / memória média medida por processo

Não configure o número máximo teórico de processos se isso não deixar memória para MySQL/MariaDB, cache ou sistema operacional.

Usuários logados, wp-admin, solicitações REST/API, pesquisa, formulários, visualização e páginas personalizadas são mais propensos a ignorar o cache de página inteira e consumir processos PHP.

A própria documentação de otimização do WordPress recomenda o cache como uma grande ferramenta de desempenho. Mas essas camadas resolvem problemas diferentes.

Não chame Redis de cache de página. Redis é comumente usado como um backend persistente de cache de objeto; o cache de página inteira é uma camada separada.

Cache de objetos persistente e Redis

O WordPress inclui uma API de cache de objetos, mas o cache padrão não é persistente entre solicitações.

O cache de objetos persistente requer um back-end/drop-in externo, como Redis ou Memcached, além da integração apropriada do WordPress.

Pode ajudar quando o site executa repetidamente trabalhos caros de banco de dados/objeto, mas não é um botão de velocidade automática.

Antes de adicionar Redis:

  • confirme que a carga do site ou do banco de dados se beneficia dele;
  • verificar RAM suficiente permanece para PHP e o banco de dados;
  • monitorar a taxa de acerto e memória;
  • Mantenha o cache de página como uma decisão separada.

Um site com cache de página inteira eficiente e pouca carga de banco de dados pode se beneficiar menos do Redis do que uma área de membros dinâmica ou um site com muitas consultas.

Demanda de banco de dados

O desempenho do WordPress pode ficar limitado ao banco de dados antes que a CPU esteja visivelmente saturada.

Verifique:

  • consultas lentas;
  • grandes opções/dados carregados automaticamente;
  • metadados do plugin;
  • consultas de pesquisa/filtro/relatório;
  • cargas com uso intenso de metadados de posts;
  • conjunto de dados de banco de dados mantidos na memória;
  • escrita simultânea;
  • importações/exportações;
  • latência de armazenamento.

Mais CPU não repara uma consulta patológica. Mais RAM pode ajudar quando o banco de dados precisa legitimamente de um conjunto de dados maior mantido na memória, mas não substitui o trabalho de indexação/consulta/plugin.

Meça primeiro, depois escale.

Plugins, temas e tarefas em segundo plano

Um plugin não é apenas espaço em disco.

Plugins/temas podem adicionar:

  • processamento PHP;
  • consultas de banco de dados;
  • chamadas de API externas;
  • tarefas agendadas;
  • invalidação de cache;
  • admin AJAX;
  • processamento de imagem;
  • varredura de segurança;
  • backups;
  • importações/exportações;
  • analytics/logging.

Tarefas pesadas podem colidir com tráfego real.

Agende backups, varreduras, importações e processamento de imagens fora dos horários de pico, quando possível. Se um plugin ou uma tarefa causar o pico de consumo, corrija-o ou mude seu horário antes de concluir que o VPS é pequeno demais.

WP-Cron e tarefas em segundo plano

O WP-Cron é acionado por solicitações do WordPress em vez de funcionar continuamente como um agendador de sistema.

Isso pode ser aceitável para sites comuns. Para cargas de trabalho sensíveis ao tempo ou ocupadas, a documentação do próprio desenvolvedor do WordPress descreve o uso do agendador do sistema operacional para chamar o cron do WordPress em um intervalo controlado.

Se passar a usar um agendador do sistema:

  • criar o gatilho de substituição primeiro;
  • verificar se funciona;
  • só então desabilitar o comportamento normal de WP-Cron desencadeado pelo visitante se isso fizer parte do plano;
  • registrar e monitorar tarefas falhadas.

Não desative o WP-Cron sem outro agendador funcionando.

Armazenamento, mídia, ambiente de teste e backups

O planejamento de disco deve incluir mais do que o núcleo do WordPress.

Orçamento para:

  • uploads/mídia;
  • banco de dados;
  • plugins/temas;
  • logs;
  • arquivos de cache;
  • arquivos de atualização temporária;
  • espaço temporário para processamento de imagens;
  • cópia do ambiente de teste;
  • arquivos de backup antes de serem movidos para fora do servidor;
  • crescimento esperado.

Um site que usa 20 GB hoje pode precisar de mais espaço temporário durante uma tarefa de clone, restauração, atualização de plug-in ou compactação de backup.

Não mantenha o único backup no VPS.

Manual, painel de controle ou FASTPANEL?

O WordPress pode funcionar perfeitamente sem cPanel ou outro painel.

Manual Linux

Bom ajuste quando você quiser:

  • pilha mínima;
  • Administração SSH;
  • configuração personalizada do Nginx/Apache/PHP/database;
  • automação ou implantação baseada em Git.

Use Como hospedar um site no VPS para o caminho de implantação manual.

Painel de controle genérico

Útil quando gerenciar domínios, SSL, PHP, bancos de dados, usuários, e-mail ou backups pelo navegador elimina uma quantidade suficiente de trabalho repetitivo.

Use VPS com Painel de Controle.

FASTPANEL

O fluxo de trabalho oficial do FASTPANEL suporta a criação de sites WordPress. VDSina atualmente lista o FASTPANEL no Ubuntu 22 como uma opção de painel pré-configurado.

Consulte Hospedagem VPS com FASTPANEL para a configuração e o dimensionamento específicos desse painel.

Um painel de controle simplifica a administração, não faz com que o VPS seja gerenciado.

VPS para WordPress gerenciado vs. autogerenciado

Em um VPS autogerenciado, alguém deve ser responsável por:

  • Atualizações do sistema operacional/pacote;
  • SSH/firewall;
  • Atualizações PHP/web-server;
  • administração de banco de dados;
  • Atualizações do WordPress/plugin/tema;
  • backups e testes de restauração;
  • monitoramento;
  • Incidentes.

Se ninguém assumir essas tarefas, escolha administração gerenciada em vez de presumir que o WordPress ou um painel de controle gerenciará o servidor.

Consulte VPS gerenciado vs. não gerenciado.

WooCommerce é uma carga de trabalho diferente do WordPress

WooCommerce compartilha a pilha do WordPress, mas se comporta de forma diferente sob o tráfego da loja real.

Carrinho, checkout, conta, pedidos, estoque e muitas ações agendadas são dinâmicos e não podem ser tratados como páginas anônimas de blog em cache.

Se as transações de loja importam, use VPS para WooCommerce para o modelo dedicado de dimensionamento/operações de recursos.

Vários sites WordPress

Vários sites do WordPress compartilham:

  • CPU;
  • RAM;
  • serviço de banco de dados;
  • processos e pools PHP;
  • armazenamento;
  • janelas de tarefas cron e em segundo plano;
  • tempo de backup;
  • Domínio de falha.

Dez sites tranquilos com cache podem consumir menos recursos do que um site de membros dinâmico e movimentado.

Use usuários e credenciais de banco de dados separados quando apropriado e dimensione pelo pico combinado, não pela quantidade de domínios.

Veja VPS para vários sites.

Quando ampliar o VPS para WordPress

Amplie os recursos somente depois de medir uma limitação real.

Gatilhos fortes:

  • pressão de RAM sustentada, swap ou eventos OOM;
  • fila/saturação de processo PHP repetida;
  • saturação sustentada da CPU após otimização de cache/query/plugin;
  • latência do banco de dados causada pela pressão legítima do conjunto de trabalho;
  • crescimento de armazenamento além da margem de capacidade operacional segura;
  • tarefas em segundo plano repetidamente colidindo com o tráfego ao vivo;
  • vários sites ativos esgotando os recursos compartilhados.

Se o site for lento enquanto esses sinais permanecem saudáveis, um VPS maior pode não ser a solução.

FAQ

Quanta memória RAM o WordPress precisa em um VPS?

O núcleo do WordPress não define um requisito de RAM para VPS em produção. A RAM deve atender ao Linux, ao servidor web, aos processos PHP, ao banco de dados, aos caches, ao painel, ao e-mail, às tarefas em segundo plano e à margem de capacidade. Um site leve pode funcionar com 2 GB; 4 GB oferece uma base prática mais robusta para um site empresarial.

1 GB de RAM é suficiente para o WordPress VPS?

Ele pode executar uma configuração WordPress muito leve / teste, mas deixa pouca margem de capacidade para o banco de dados, processos PHP e trabalho em segundo plano. Não deve ser tratado como a recomendação normal de produção.

2 GB de RAM é suficiente para o WordPress?

Pode ser suficiente para um site pequeno, com cache bem configurado e um ambiente leve. Monitore a memória dos processos PHP, a RAM do banco de dados, os plugins e as tarefas em segundo plano.

4 GB de RAM é suficiente para o WordPress?

Para muitos sites WordPress de negócios, 4 GB é um ponto de partida prático. Plugins pesados, tráfego de membros, WooCommerce, grandes bancos de dados, importações ou vários sites ativos podem exigir mais.

Quantos visitantes um VPS para WordPress suporta?

Não existe uma quantidade universal confiável de visitantes. A taxa de acerto do cache, as requisições simultâneas sem cache, a duração das requisições PHP, o consumo dos plugins, o processamento do banco de dados e as tarefas em segundo plano determinam a capacidade.

Preciso do Redis para WordPress no VPS?

Não. O Redis pode fornecer cache de objeto persistente quando a carga de trabalho se beneficia do cache de objeto / banco de dados repetido, mas não é necessário para todos os sites do WordPress e não substitui o cache de página inteira.

Devo usar Nginx ou Apache para WordPress VPS?

Ambos são válidos. O WordPress.org recomenda Apache ou Nginx como opções robustas. Use um ambiente compatível com a aplicação e que o administrador consiga operar de forma confiável.

Devo substituir o WP-Cron pelo System Cron?

Somente quando a carga se beneficiar de um agendador controlado e você configurar uma substituição funcional. Não desative o WP-Cron sem outro mecanismo de acionamento.

O WordPress VPS precisa de um painel de controle?

Não. O WordPress pode ser executado em um VPS Linux gerenciado manualmente. Um painel é opcional e deve ser escolhido por conveniência de administração, não como requisito de desempenho.

O VDSina inclui o WordPress pré-instalado?

A página atual dos planos VPS Standard não lista o WordPress como uma aplicação pré-instalada específica nos grupos visíveis de modelos e aplicações. Confira a tela atual de contratação antes de presumir a disponibilidade de qualquer modelo.
