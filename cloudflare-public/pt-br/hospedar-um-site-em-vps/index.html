Como hospedar um site em um VPS

Como hospedar um site em um VPS: escolha a forma de implantação, proteja o primeiro acesso, instale os serviços web adequados, conecte o domínio, ative o HTTPS, teste a recuperação após reiniciar e verifique se o ambiente está pronto para produção.

Como hospedar um site no VPS depende do aplicativo que você está implantando. Um site estático precisa de um servidor web e DNS. WordPress ou outro CMS PHP também precisa de PHP e um banco de dados. Um aplicativo Node.js ou Python geralmente é executado atrás de um proxy reverso. Você pode construir essas peças manualmente em um VPS limpo ou usar um painel de controle para gerenciá-las através de um navegador.

Este guia cobre o processo do VPS novo ao site no ar. Se você estiver transferindo um site já em produção com dados em uso, consulte Migração de site para VPS para o processo de virada e reversão.

Para a decisão de compra mais ampla, veja VPS para sites .

Sequência de implantação rápida

Uma primeira implantação confiável segue esta ordem:

  1. Escolha e dimensione o VPS.
  2. Escolha entre administração manual, painel de controle ou administração gerenciada.
  3. Provisionar um sistema operacional limpo ou uma imagem atual do painel do provedor.
  4. Proteja o primeiro acesso e crie uma forma de administração sem usar root diretamente.
  5. Atualizar o sistema operacional.
  6. Instale apenas a pilha de software web que o aplicativo precisa.
  7. Configure o site ou a aplicação antes de alterar o DNS público, sempre que possível.
  8. Implemente arquivos/código e configure propriedade, segredos e acesso ao banco de dados.
  9. Restringir o firewall mantendo o SSH e o acesso HTTP/HTTPS necessário funcionando.
  10. Teste o destino antes do DNS público.
  11. Aponte o domínio para o VPS.
  12. Ativar HTTPS após o nome do host chegar ao servidor.
  13. Verifique cron/processos, registros, backups e monitoramento externo.
  14. Reinicie uma vez e confirme que todos os serviços necessários retornam automaticamente.
  15. Só então considere a implantação pronta para produção.

Não instale PHP, MySQL, e-mail ou um painel de controle apenas porque um guia VPS genérico os inclui. Instale os componentes que seu site realmente precisa.

Escolha manual, painel ou gerenciado

Existem três caminhos operacionais distintos.

Manual / sem painel de controle

Escolha um VPS Linux limpo e administre os serviços por SSH.

Bom ajuste quando:

  • você entende o ambiente de software da aplicação;
  • você quer manter o mínimo possível de serviços instalados;
  • você precisa de configurações personalizadas de Nginx/Apache ou do ambiente de execução;
  • você usa scripts, Git ou infra-estrutura como código;
  • Você não precisa de uma interface tradicional de hospedagem.

Este guia incorpora o tema anterior VPS sem painel de controle. Não criamos outra URL concorrente para a mesma intenção de busca.

Painel de controle

Use um painel de hospedagem quando gerenciar sites, domínios, PHP, bancos de dados, e-mail ou usuários pelo navegador eliminar uma quantidade significativa de trabalho repetitivo.

Consulte VPS com painel de controle. Se você já escolheu o FASTPANEL, consulte Hospedagem VPS com FASTPANEL.

Administração gerenciada

Se ninguém da sua equipe é responsável por atualizações, segurança, backups, monitoramento e incidentes, resolva isso antes do lançamento.

Consulte VPS gerenciado vs. não gerenciado.

Avaliação do caminho de implantação

Esta ferramenta identifica a opção de ambiente a investigar. Ela não substitui a documentação da aplicação.

Selecione a carga de trabalho e a preferência de operação.

Pré-requisitos

Antes de alterar o servidor, tenha:

  • um VPS dimensionado para a carga de trabalho;
  • o endereço IP do servidor;
  • Credenciais SSH ou acesso de chave;
  • acesso funcional ao console, VNC ou recurso de recuperação do provedor;
  • um domínio registrado e acesso DNS;
  • os arquivos do site ou repositório de aplicativos;
  • as versões de ambiente de execução necessárias;
  • requisitos de banco de dados;
  • um plano para credenciais, segredos e variáveis de ambiente;
  • um local de backup;
  • uma maneira externa de testar a disponibilidade do site.

Consulte Dimensionamento de VPS para sites antes de implantar, se a necessidade de recursos ainda não estiver clara.

Escolha o sistema operacional

Para um servidor de site manual, escolha um sistema operacional que:

  • é suportado pelo ambiente de aplicação/execução;
  • Ainda é mantido;
  • seu administrador entende;
  • tem pacotes e documentação atuais para os serviços web;
  • corresponde a qualquer requisito do painel, se você usar um mais tarde.

Não escolha o SO só porque ele é mais novo. Compatibilidade de aplicativos e familiaridade do administrador são mais importantes.

Para um exemplo Linux atual simples, Ubuntu 24.04 LTS ou Debian 12 são alvos de documentação razoáveis. Se o fornecedor do aplicativo especificar outra distribuição suportada, siga esse requisito.

Proteja o primeiro acesso SSH

Um novo VPS lhe dá acesso administrativo, mas o trabalho de produção não deve acontecer permanentemente como root.

Uma sequência segura de primeiro acesso é:

  1. conectar usando as credenciais / chave fornecidas pelo provedor VPS;
  2. confirmar que o servidor/IP é aquele que você pretende criar;
  3. manter o console do provedor/VNC/rota de recuperação funcionando;
  4. criar um usuário administrativo nomeado;
  5. conceder apenas os direitos necessários de sudo/admin;
  6. adicionar autenticação SSH-key onde for prático;
  7. verificar o novo login em uma segunda sessão antes de desabilitar ou restringir o método de acesso original.

Exemplo no Ubuntu/Debian:

ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy

Não bloqueie sua única forma funcional de acesso administrativo ao reforçar a segurança do servidor.

O reforço detalhado da segurança de SSH e firewall é abordado em Checklist de segurança para VPS; este guia inclui apenas o mínimo necessário para implantar o site.

Atualize o servidor antes de instalar os serviços

No Ubuntu/Debian:

sudo apt update
sudo apt upgrade -y

Reinicie se a atualização exigir, então verifique se você pode se reconectar.

Não adie as atualizações de segurança até que o site seja público.

Caminho manual/sem painel de controle

Um VPS manual deve conter apenas os serviços que o aplicativo precisa.

As escolhas comuns são:

Site estático

Necessário:

  • Nginx ou Apache;
  • arquivos do site;
  • DNS;
  • HTTPS.

Não é necessário automaticamente:

  • PHP;
  • MySQL/MariaDB/PostgreSQL;
  • servidor de correio local.

Site PHP / WordPress

Normalmente necessário:

  • Nginx ou Apache;
  • Módulos PHP-FPM / PHP;
  • banco de dados;
  • arquivos do site/uploads;
  • DNS;
  • HTTPS.

Para o comportamento dos recursos do WordPress, use VPS para o WordPress.

Node.js / Python / aplicação personalizada

Normalmente:

  • ambiente de execução de aplicativos;
  • usuário de aplicativo não-root dedicado;
  • systemd ou outro gerenciador de processos e serviços;
  • aplicação vinculada ao localhost / soquete privado onde for prático;
  • Nginx/Apache proxy reverso;
  • banco de dados somente quando necessário;
  • DNS;
  • HTTPS.

Não exponha um servidor de desenvolvimento diretamente à Internet pública como a arquitetura de produção.

Instalar o servidor web

A documentação atual do Ubuntu Server contempla Nginx e Apache. Nenhum é universalmente melhor.

Para o exemplo de Nginx:

sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

Neste ponto, o IP do servidor deve retornar a página Nginx padrão se as regras de rede/firewall permitirem HTTP.

Use o Apache quando o aplicativo, a equipe ou a configuração existente se encaixarem melhor no Apache.

Configurar o nome de host do site

DNS e configuração do servidor web são duas metades da mesma tarefa.

O provedor de DNS deve apontar o nome de host para o VPS, e o servidor web deve saber qual site deve responder a esse nome de host.

Para Nginx, crie um bloco de servidor para o domínio. Conceitualmente:

server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}

No Ubuntu/Debian, as configurações específicas do site geralmente vivem em:

  • /etc/nginx/sites-available/
  • /etc/nginx/sites-enabled/

Após as alterações:

sudo nginx -t
sudo systemctl reload nginx

Sempre teste a sintaxe de configuração antes de recarregar.

Para uma aplicação com proxy reverso, o bloco de servidor encaminha as requisições para a porta ou o socket local da aplicação.

Implantar arquivos ou código de aplicativo

Escolha um método de implantação repetível.

SFTP/SCP

Bom para:

  • sites pequenos;
  • implantações manuais pouco frequentes;
  • Projetos simples pela primeira vez.

Risco: é fácil para o diretório de produção se afastar do repositório de origem.

rsync sobre SSH

Útil para sincronizar arquivos de forma repetível e fazer atualizações incrementais eficientes.

Implantação baseada em Git

Útil quando as versões em produção precisam corresponder a commits do repositório.

CI/CD

Útil quando a frequência de implantação justifica automatizar as etapas de compilação, testes e publicação.

Seja qual for o método que você usa:

  • não faça a implantação como root, a menos que a tarefa realmente exija esse acesso;
  • manter arquivos de aplicativos pertencentes a um usuário de implantação/aplicativo apropriado;
  • conceder ao servidor web apenas o acesso de que necessita;
  • manter segredos fora das raízes de documentos públicos;
  • não use permissões de escrita para todos como atalho.

Caminho PHP / WordPress

Para um site PHP no Ubuntu/Debian, instale os pacotes PHP-FPM com suporte atual e as extensões necessárias para o aplicativo.

Arquitetura típica:

browser -> Nginx/Apache -> PHP-FPM -> banco de dados

Não copie uma lista de extensões aleatórias de outro CMS. Instale o que o aplicativo realmente requer.

Para o WordPress:

  • criar um banco de dados e um usuário DB dedicado;
  • configurar limites de upload/memória/execução do PHP a partir da necessidade medida;
  • manter segredos wp-config.php protegidos;
  • configurar o nome de host do site;
  • Habilitar HTTPS;
  • valide o wp-cron e as tarefas em segundo plano;
  • adicionar cache com base na carga de trabalho.

Use VPS para WordPress para dimensionamento e desempenho de recursos, em vez de duplicar aqui.

Node.js / Python / caminho de aplicativo personalizado

Não execute o comando de desenvolvimento manualmente em um terminal e chame de produção.

Use:

  • um usuário de aplicativo dedicado;
  • arquivo de ambiente/configuração com permissões restritas;
  • systemd ou um gerenciador de processos adequado para produção;
  • reinício automático após falha ou reinicialização do servidor;
  • aplicação escutando em um endereço local ou privado;
  • Nginx/Apache proxy reverso;
  • registros de aplicativos;
  • verificações de funcionamento.

Fluxo típico:

browser -> HTTPS/Nginx -> aplicação em 127.0.0.1:PORT -> banco de dados/serviços externos

Verifique a orientação de implantação de produção do framework.

Banco de dados: instale somente quando necessário

Um site estático não precisa de banco de dados.

Para uma aplicação dinâmica que precisa de banco de dados:

  • instalar o mecanismo do banco de dados suportado;
  • criar um banco de dados dedicado;
  • criar um usuário específico do aplicativo;
  • conceder apenas privilégios necessários;
  • Manter as credenciais fora da raiz da web;
  • não exponha a porta do banco de dados publicamente, a menos que haja uma arquitetura segura específica exigindo isso;
  • Inclua o banco de dados em planos de backup e monitoramento.

O trabalho de banco de dados pode se tornar o verdadeiro gargalo VPS mesmo quando o servidor da Web está quase ocioso.

Propriedade do arquivo, permissões e segredos

Evite dois erros comuns:

  1. rodando o site como root;
  2. permitir que qualquer usuário grave nos diretórios da aplicação para “corrigir” erros de permissão.

Em vez disso:

  • usar um usuário de implantação/aplicativo;
  • entender qual processo precisa de acesso de leitura versus escrita;
  • conceda aos diretórios de uploads e cache apenas as permissões de escrita necessárias;
  • proteger arquivos de ambiente e credenciais;
  • não envie segredos de produção para o Git.
  • Mantenha chaves privadas fora das raízes dos documentos públicos.

A propriedade exata depende do aplicativo e do modelo do servidor web; use a documentação do aplicativo em vez de copiar uma receita universal chmod 777.

Teste antes do DNS público

Não faça do DNS o primeiro teste real da aplicação.

Antes da virada pública, verifique o novo servidor com um destes métodos, quando possível:

  • acessar o IP do servidor para uma simples verificação padrão/estática;
  • ajuste o arquivo hosts local para que example.com aponte para o novo VPS somente no seu computador;
  • usar um nome de host privado/teste que não tenha permissão para se tornar uma duplicata indexada acidental;
  • teste o aplicativo através da mesma configuração de hostname Nginx/Apache que a produção usará.

Verifique mais do que a página inicial:

  • páginas internas importantes;
  • login/admin;
  • formulários;
  • uploads;
  • ativos estáticos;
  • leituras/escritas de banco de dados;
  • endpoints de aplicação/API;
  • redirecionamentos;
  • logs.

Um teste de arquivo de hosts é especialmente útil porque muitos aplicativos se comportam de forma diferente sob o nome de host real do que sob o IP do servidor bruto.

Se for um site já em produção, siga o processo de virada mais rigoroso descrito em Migração de site para VPS.

Aponte o domínio para o VPS

No provedor DNS, configure os registros que devem chegar a este servidor.

Configuração típica do IPv4:

NomeTipoValor
@AEndereço VPS IPv4
wwwCNAMEdomínio raiz

Também é possível usar um registro A para www.

Adicione um registro AAAA somente se o IPv6 estiver configurado e acessível no VPS. Um registro AAAA incorreto pode impedir o acesso de alguns visitantes mesmo quando o IPv4 funciona.

O DNS sozinho não faz o site funcionar: a configuração do site Nginx/Apache também deve ter o nome de host correspondente.

Se estiver transferindo um site já em produção, a alteração do DNS e o controle das gravações finais são abordados em Migração de site para VPS.

Adicionar HTTPS após a resolução do DNS

Obtenha um certificado confiável somente depois que o nome de host público for resolvido para o servidor que responderá à solicitação de validação. Certifique-se de que as regras de rede do firewall/provedor já permitem o caminho de validação HTTP/HTTPS que você pretende usar.

Para o Nginx/Apache, um cliente ACME como o Certbot pode solicitar e renovar certificados Let's Encrypt. Siga as instruções atuais do Certbot/OS em vez de copiar um comando de pacote antigo cegamente.

Verifique:

  • o certificado cobre o domínio raiz e a variante www que você utiliza;
  • HTTP redireciona para HTTPS como pretendido;
  • a renovação do certificado é automatizada;
  • renovação pode passar através da configuração de firewall/CDN;
  • o aplicativo gera os URLs HTTPS corretos.

Não ative um redirecionamento HTTPS antes de saber que o caminho do certificado funciona.

Configurar o firewall

Mantenha o acesso administrativo funcionando enquanto muda as regras de firewall.

Um site público básico geralmente precisa:

  • SSH da fonte/caminho de administração necessária;
  • TCP 80 para HTTP/ACME/redirects;
  • TCP 443 para HTTPS.

Não exponha portas de aplicação MySQL/PostgreSQL, Redis ou internas publicamente só porque elas escutam localmente por padrão.

Em um servidor com UFW, permita o acesso SSH necessário antes de ativar regras restritivas.

Os detalhes de firewall e reforço da segurança estão em Checklist de segurança para VPS.

Tarefas cron, filas e processos de trabalho

Sites dinâmicos geralmente falham após a implantação porque apenas o caminho de solicitação da Web foi configurado.

Faça o inventário de:

  • tarefas cron;
  • processos de fila;
  • ações agendadas;
  • importações/exportações;
  • tarefas de e-mail;
  • tarefas de preenchimento antecipado do cache;
  • processadores em segundo plano.

Configure-os para:

  • executar como o usuário não-root correto;
  • iniciar automaticamente quando necessário;
  • gravar logs em locais conhecidos;
  • evitar sobreposição de maneiras que esgotam CPU / RAM;
  • voltar a funcionar após a reinicialização do servidor.

Logs e observabilidade básica

Antes do tráfego de produção, saiba onde procurar quando o site falhar.

No mínimo, identifique:

  • Registro de acesso Nginx/Apache;
  • Registro de erro Nginx/Apache;
  • registo de aplicações;
  • Registro de ambiente PHP-FPM/execução;
  • log/status do banco de dados;
  • diário do sistema;
  • uso do disco;
  • Pressão de memória/CPU.

Adicione uma verificação de disponibilidade HTTP(S) externa para que uma falha do servidor seja visível mesmo quando ninguém estiver conectado ao VPS.

O planejamento detalhado de limites e alertas está em Monitoramento de VPS.

Validação após reinicializar

Um número surpreendente de primeiras implantações de VPS funciona até a primeira reinicialização.

Antes de chamar o servidor pronto:

sudo reboot

Depois que ele retornar, confirme:

  • Acesso SSH;
  • Nginx/Apache;
  • PHP-FPM ou serviço de aplicativo;
  • banco de dados;
  • cron e processos de filas;
  • HTTPS;
  • páginas e formulários do site;
  • monitoramento;
  • agendamento de backups.

Se o aplicativo só retornar depois que alguém iniciar manualmente um comando, a implantação não estará completa.

Quando a hospedagem manual / sem painel é o ajuste errado

Use um painel de controle ou administração gerenciada quando:

  • Ninguém se sente confortável com SSH e recuperação da linha de comando;
  • ninguém é responsável pelas atualizações do sistema operacional e de segurança;
  • ninguém consegue diagnosticar falhas no servidor web, no ambiente de execução ou no banco de dados;
  • backups são criados, mas ninguém pode restaurá-los;
  • não há um responsável por incidentes em caso de indisponibilidade crítica;
  • a equipe quer e-mail/usuários/domínios gerenciados através de uma interface de hospedagem em vez de configuração do servidor;
  • A pilha de aplicativos é melhor servida por uma plataforma gerenciada.

Um VPS manual pode reduzir o consumo adicional de recursos do painel e maximizar o controle, mas não reduz a quantidade de responsabilidade operacional.

Consulte VPS com painel de controle para escolher um painel ou VPS gerenciado vs. não gerenciado quando faltar um responsável pela operação.

Preparação de backups e monitoramento para a operação

Esta página estabelece apenas o mínimo necessário para iniciar a operação.

Antes de confiar no site:

  • agendamento de backups;
  • manter uma cópia independente/fora do servidor;
  • incluir o banco de dados e configuração/segredos necessários para a recuperação;
  • verificar a capacidade de restauração;
  • monitorar a disponibilidade do site;
  • monitorar o crescimento do disco;
  • acompanhe a demanda de CPU, RAM e banco de dados;
  • acompanhe a renovação dos certificados.

O planejamento detalhado da recuperação está em Estratégia de backup para VPS. Os limites de monitoramento e o planejamento de alertas estão em Monitoramento de VPS.

Vários sites

Para vários sites:

  • usar um bloco de servidor separado / host virtual por nome de host;
  • raízes de documentos separadas;
  • usar credenciais separadas de aplicativo/banco de dados;
  • usar usuários de sistema separados onde o modelo de confiança o requer;
  • evite que tarefas cron, importações e backups de um site esgotem os recursos dos demais;
  • considere a carga de pico combinada;
  • entender que todos os sites ainda compartilham um domínio de falha VPS.

Use VPS para vários sites para planejamento de capacidade e isolamento.

FAQ

Posso hospedar um site em um VPS sem um painel de controle?

Sim. Um VPS Linux limpo pode hospedar um site com SSH e os componentes de servidor web, ambiente de execução e banco de dados de que a aplicação precisa. A hospedagem sem painel faz parte deste guia, em vez de ter uma página concorrente separada.

Preciso do Nginx para hospedar um site no VPS?

Não. Nginx e Apache são escolhas comuns. Use o servidor web que se encaixa na aplicação, configuração e experiência de administrador.

Todo site VPS precisa de um banco de dados?

Não. Os sites estáticos não precisam de um. Instale o MySQL/MariaDB/PostgreSQL somente quando o aplicativo requer um banco de dados.

Devo usar root para hospedar o site?

Não. Root é para administração. Execute/implante o site em usuários e serviços apropriados sem root com apenas as permissões necessárias.

Quando devo usar um painel de controle?

Use um quando o gerenciamento baseado em navegador de sites, domínios, PHP, bancos de dados, usuários, e-mail ou backups remove administração repetitiva suficiente para justificar o consumo adicional de recursos e restrições.

Posso hospedar o WordPress em um VPS sem cPanel?

Sim. WordPress precisa de um servidor web compatível, PHP, um banco de dados, os arquivos WordPress, permissões corretas, DNS e HTTPS. Um painel é opcional.

Quando devo apontar o DNS para o VPS?

Para um site novo, assim que o servidor estiver pronto para responder pelo nome de domínio real. Para um site já em produção, teste primeiro e siga um plano controlado de migração e virada.

Por que meu domínio aponta para o VPS, mas mostra o site errado?

O DNS envia apenas o nome de host para o IP do servidor. O Nginx/Apache também deve ter um bloco de servidor correspondente / host virtual para esse nome de host.

Quando devo habilitar HTTPS?

Depois que o nome de domínio público resolver para o servidor e o processo de validação funcionar. Em seguida, emita o certificado, verifique a cobertura do domínio raiz e de www e configure o redirecionamento de HTTP para HTTPS desejado.

O que devo verificar depois de reiniciar o VPS?

Confirme o retorno do servidor web, serviço de aplicativo/PHP-FPM, banco de dados, processos, HTTPS, monitoramento e site sem intervenção manual.
