VPS para WordPress

Elige la CPU y la RAM de tu VPS para WordPress según los procesos PHP, la base de datos, la caché, los plugins y las tareas en segundo plano. Planifica la administración y la migración.

Un VPS para WordPress es útil cuando necesitas más control, aislamiento o funciones del servidor de lo que ofrece el alojamiento compartido. Dimensiona sus recursos según el trabajo PHP sin caché, la demanda de la base de datos, los plugins, las tareas en segundo plano, el crecimiento del almacenamiento y los servicios que acompañan a WordPress, no según las visitas mensuales.

Para la decisión más amplia del servidor, véase VPS para el sitio web.

Los requisitos de WordPress no determinan los recursos del VPS

WordPress.org actualmente recomienda un host que admita:

  • PHP 8.3 o mayor;
  • MariaDB 10.11+ o MySQL 8.0+;
  • HTTPS;
  • Apache o Nginx como opciones de servidor web recomendadas.

Estos requisitos responden a «¿puede este servidor ejecutar WordPress?». No responden a «¿qué recursos necesita esta carga de producción?».

Un VPS de producción también necesita RAM/CPU/almacenamiento para:

  • Linux;
  • Nginx/Apache;
  • procesos de PHP-FPM;
  • MySQL/MariaDB;
  • OPcache;
  • página/caché de objetos donde se utiliza;
  • panel de control;
  • correo electrónico si está alojado localmente;
  • copias de seguridad;
  • tareas cron;
  • Análisis de malware/seguridad;
  • importaciones/exportaciones;
  • monitorización;
  • margen operativo.

No utilice los requisitos de software de WordPress como una recomendación de recursos de producción.

Utilice este comprobador como punto de partida. No reemplaza las mediciones reales de CPU/RAM/base de datos.

Utilice pruebas reales de carga de trabajo siempre que sea posible.

Cuando WordPress realmente necesita VPS

Un sitio de WordPress puede justificar VPS incluso sin un gran tráfico.

Razones comunes:

  • Límites repetidos de CPU/memoria/proceso bajo carga legítima;
  • necesidad de una configuración personalizada de PHP/en entorno de ejecución;
  • necesidad de Redis/Memcached u otro servicio del lado del servidor;
  • cron del sistema real en lugar de la programación activada por los visitantes;
  • tareas en segundo plano de larga duración;
  • comportamiento personalizado de Nginx/Apache;
  • varios sitios que necesitan un entorno controlado;
  • Mayor aislamiento de la carga de trabajo/cuenta;
  • Monitorización a nivel de servidor o requisitos de firewall.

Si el único síntoma es que el sitio va lento, consulta primero VPS o alojamiento compartido y comprueba que el cuello de botella no esté en el propio WordPress.

Cuando WordPress no necesita VPS

Manténgase en un buen alojamiento compartido o administrado de WordPress cuando:

  • el sitio es ligero y estable;
  • la caché funciona bien;
  • los medidores de recursos del anfitrión no muestran límites repetidos;
  • no se requiere servicio personalizado / acceso root;
  • el equipo no quiere mantener Linux;
  • el proveedor ya gestiona suficientemente bien las copias, la seguridad, las actualizaciones o el entorno de pruebas;
  • El VPS reemplazaría principalmente un servicio de alojamiento simple con más trabajo operativo.

Un VPS mal dimensionado o sin afinar puede ejecutar WordPress peor que una buena plataforma administrada.

Procesos PHP y RAM

Para las solicitudes no cacheadas, los procesos de PHP-FPM son un límite de concurrencia importante.

Cada proceso activo consume memoria mientras procesa una solicitud. Más procesos pueden manejar más solicitudes dinámicas simultáneas, pero aumentar el recuento de procesos sin aumentar el presupuesto de RAM puede causar:

  • uso de memoria de intercambio (swap);
  • presión de memoria;
  • finalización de procesos por falta de memoria (OOM);
  • falta de recursos para la base de datos;
  • Inestabilidad del servidor.

Un modelo práctico es:

RAM para WordPress ≈ sistema operativo + servidor web + base de datos + caché + procesos PHP + panel, correo y tareas + margen

Entonces:

Número de procesos PHP ≈ RAM que puedes dedicar a PHP sin comprometer otros servicios / memoria media medida por proceso

No configure el número máximo teórico de procesos si al hacerlo no deja memoria para MySQL/MariaDB, caché o el sistema operativo.

Los usuarios con sesión iniciada, wp-admin, las solicitudes REST o API, las búsquedas, los formularios, las vistas previas y las páginas personalizadas suelen omitir la caché de página completa y consumir procesos PHP.

Capas de caché de WordPress

La caché no es una única función.

CapaLo que guarda en cachéEfecto principal
OPcache de PHPCódigo de bytes PHP compiladoEvita recompilar scripts PHP en cada solicitud
Caché de páginarenderizado HTMLpermite que muchas páginas anónimas pasen por alto el trabajo de WordPress/PHP
Caché de objetos persistenteresultados de objetos/consultas reutilizablesreduce el trabajo repetido de la base de datos/aplicación
Caché del navegador y de la CDNcontenido estático o distribuible desde nodos cercanos al usuarioreduce la transferencia de origen y las solicitudes repetidas

La propia documentación de optimización de WordPress recomienda el almacenamiento en caché como una herramienta de rendimiento importante, pero estas capas resuelven diferentes problemas.

No llame a Redis una caché de página. Redis se usa comúnmente como un backend persistente de caché de objetos; el almacenamiento en caché de página completa es una capa separada.

Caché de objetos persistente y Redis

WordPress incluye una API de caché de objetos, pero su caché predeterminada no persiste entre solicitudes.

El almacenamiento en caché persistente de objetos requiere un backend / drop-in externo como Redis o Memcached además de la integración adecuada de WordPress.

Puede ayudar cuando el sitio repite operaciones costosas con la base de datos o los objetos, pero no acelera automáticamente cualquier sitio.

Antes de añadir Redis:

  • confirmar los beneficios de la carga de trabajo del sitio/base de datos;
  • verificar que queda suficiente RAM para PHP y la base de datos;
  • monitoriza la tasa de aciertos y el consumo de memoria;
  • mantener el almacenamiento en caché de la página como una decisión separada.

Un sitio con caché de página completa eficiente y un trabajo ligero de base de datos puede ganar menos de Redis que una membresía dinámica o un sitio con muchas consultas.

Demanda de base de datos

La base de datos puede limitar el rendimiento de WordPress antes de que la CPU muestre una saturación evidente.

Compruebe:

  • consultas lentas;
  • grandes opciones / datos cargados automáticamente;
  • metadatos de plugin;
  • consultas de búsqueda, filtrado e informes;
  • cargas con uso intensivo de postmeta;
  • conjunto de datos de base de datos mantenido en memoria;
  • escritura concurrente;
  • importaciones/exportaciones;
  • latencia de almacenamiento.

Más CPU no repara una consulta patológica. Más RAM puede ayudar cuando la base de datos necesita legítimamente un conjunto de datos más grande mantenido en memoria, pero no reemplaza el trabajo de indexación/consulta/plugin.

Mide primero, luego escala.

Plugins, temas y tareas en segundo plano

Un plugin no es solo espacio en disco.

Los plugins/temas pueden añadir:

  • Trabajo PHP;
  • consultas de base de datos;
  • llamadas API externas;
  • tareas programadas;
  • invalidación de caché;
  • admin AJAX;
  • procesamiento de imágenes;
  • escaneo de seguridad;
  • copias de seguridad;
  • importaciones/exportaciones;
  • Analítica/Registro.

Las tareas pesadas pueden chocar con el tráfico real.

Programe copias de seguridad, escaneos, importaciones y tareas de procesamiento de imágenes lejos de los períodos pico cuando sea práctico. Si un complemento o tarea causa el pico de recursos, arréglelo o vuelva a programarlo antes de asumir que el VPS es demasiado pequeño.

WP-Cron y tareas en segundo plano

WP-Cron es activado por solicitudes de WordPress en lugar de ejecutarse continuamente como un planificador del sistema.

Eso puede ser aceptable para sitios ordinarios. Para cargas de trabajo sensibles al tiempo u ocupadas, la documentación del desarrollador de WordPress describe el uso del planificador del sistema operativo para llamar a WordPress cron en un intervalo controlado.

Si pasas a un planificador del sistema:

  • crear el disparador de reemplazo primero;
  • verificar que funciona;
  • solo entonces deshabilitar el comportamiento normal de WP-Cron desencadenado por los visitantes si eso es parte del plan;
  • Registrar y monitorizar trabajos fallidos.

No deshabilite WP-Cron sin otro programador.

Almacenamiento, medios, entorno de pruebas y copias de seguridad

La planificación del disco debe incluir más que el núcleo de WordPress.

Presupuesto para:

  • subidas/medios;
  • base de datos;
  • plugins/temas;
  • logs;
  • archivos de caché;
  • Archivos de actualización temporales;
  • espacio temporal de procesamiento de imágenes;
  • copia de entorno de pruebas;
  • archivos de copia de seguridad antes de que se muevan fuera del servidor;
  • esperado crecimiento.

Un sitio que hoy ocupa 20 GB puede necesitar bastante más espacio temporal al clonarlo, restaurarlo, actualizar plugins o comprimir una copia de seguridad.

No guarde la única copia de seguridad en el VPS.

¿Manual, panel de control o FASTPANEL?

WordPress puede funcionar perfectamente sin cPanel u otro panel.

Administración manual de Linux

Buen ajuste cuando usted quiere:

  • pila mínima;
  • Administración de SSH;
  • configuración personalizada de Nginx/Apache/PHP/base de datos;
  • automatización o implementación basada en Git.

Utilice Cómo alojar un sitio web en VPS para la ruta de implementación manual.

Panel de control genérico

Resulta útil cuando gestionar dominios, SSL, PHP, bases de datos, usuarios, correo o copias desde el navegador reduce suficiente trabajo repetitivo.

Utilice VPS con el Panel de control.

FASTPANEL

El flujo de trabajo oficial de FASTPANEL es compatible con la creación de sitios WordPress. VDSina actualmente enumera FASTPANEL en Ubuntu 22 como una opción de panel preconfigurado.

Utilice alojamiento VPS con FASTPANEL para la ruta de configuración/dimensionamiento de marca.

Un panel de control simplifica la administración; no hace que el VPS sea administrado.

VPS de WordPress administrado vs autogestionado

En un VPS autogestionado, alguien debe hacerse responsable de:

  • Actualizaciones de OS/paquete;
  • SSH/cortafuegos;
  • Actualizaciones de PHP/servidor web;
  • administración de la base de datos;
  • Actualizaciones de WordPress/plugin/tema;
  • copias de seguridad y pruebas de restauración;
  • monitorización;
  • incidentes.

Si nadie asume esas tareas, contrata administración. No esperes que WordPress o un panel se encarguen por sí solos del servidor.

Véase VPS administrados vs no administrados.

WooCommerce es una carga de trabajo diferente de WordPress

WooCommerce utiliza la base tecnológica de WordPress, pero se comporta de forma distinta con el tráfico real de una tienda.

El carrito, el pago, las cuentas, los pedidos, el inventario y muchas acciones programadas son dinámicos. No pueden tratarse como páginas de blog anónimas servidas desde caché.

Si las transacciones de la tienda son importantes, utiliza VPS para WooCommerce, con criterios específicos de recursos y administración.

Varios sitios de WordPress

Varios sitios de WordPress comparten:

  • CPU;
  • RAM;
  • servicio de base de datos;
  • Procesos / grupos de PHP;
  • almacenamiento;
  • cron / ventanas de trabajo en segundo plano;
  • tiempo de copia de seguridad;
  • dominio de fallo.

Diez sitios en caché silenciosos pueden ser más ligeros que un sitio de membresía dinámico ocupado.

Utiliza usuarios y credenciales de base de datos separados cuando corresponda y dimensiona según el pico de carga conjunto, no según el número de dominios.

Ver VPS para múltiples sitios web .

Señales de que debes ampliar el VPS de WordPress

Amplía los recursos solo después de medir una limitación real.

Desencadenantes fuertes:

  • presión de RAM sostenida, eventos swap u OOM;
  • cola/saturación de procesos PHP repetidos;
  • saturación sostenida de la CPU después de la optimización de caché/consulta/plugin;
  • latencia de la base de datos causada por la presión legítima del conjunto de trabajo;
  • crecimiento del almacenamiento más allá de la capacidad operativa de reserva segura;
  • tareas en segundo plano que colisionan repetidamente con el tráfico en vivo;
  • múltiples sitios activos que agotan los recursos compartidos.

Si el sitio web es lento mientras estas señales permanecen saludables, un VPS más grande puede no ser la solución.

Preguntas frecuentes

¿Cuánta RAM necesita WordPress en un VPS?

El núcleo de WordPress no establece cuánta RAM necesita un VPS en producción. La memoria debe cubrir Linux, el servidor web, los procesos PHP, la base de datos, las cachés, el panel, el correo, las tareas en segundo plano y un margen operativo. Un sitio ligero puede funcionar con 2 GB; 4 GB ofrecen una base más holgada para un sitio comercial.

¿Es suficiente 1 GB de RAM para WordPress VPS?

Puede ejecutar una instalación muy ligera de WordPress, pero deja poco margen para la base de datos, los procesos PHP y las tareas en segundo plano. No debe considerarse la recomendación habitual para producción.

¿Son suficientes 2 GB de RAM para WordPress?

Puede bastar para un sitio pequeño con buena caché y servicios ligeros. Monitoriza la memoria de los procesos PHP y la base de datos, los plugins y las tareas en segundo plano.

¿Son suficientes 4 GB de RAM para WordPress?

Para muchos sitios de WordPress de negocios, 4 GB es un punto de partida práctico. Plugins pesados, tráfico de membresía, WooCommerce, grandes bases de datos, importaciones o varios sitios activos pueden requerir más.

¿Cuántos visitantes puede manejar un VPS de WordPress?

No hay un número universal de visitantes confiable. La tasa de aciertos de caché, la concurrencia no en caché, la duración de la solicitud de PHP, el costo del complemento, el trabajo de la base de datos y las tareas en segundo plano determinan la capacidad.

¿Necesito Redis para WordPress en VPS?

No. Redis puede proporcionar almacenamiento en caché persistente de objetos cuando la carga de trabajo se beneficia del almacenamiento en caché repetido de objetos / bases de datos, pero no es necesario para todos los sitios de WordPress y no reemplaza el almacenamiento en caché de página completa.

¿Debería usar Nginx o Apache para VPS de WordPress?

Ambos son válidos. WordPress.org recomienda Apache o Nginx como opciones robustas. Utilice el entorno de software que su aplicación y administrador pueden operar de manera confiable.

¿Debo reemplazar WP-Cron con cron de sistema?

Solo si la carga se beneficia de un planificador controlado y configuras una alternativa que funcione. No desactives WP-Cron sin otro mecanismo que ejecute las tareas.

¿Necesita WordPress VPS un panel de control?

No. WordPress puede ejecutarse en un VPS Linux administrado manualmente. Un panel es opcional y debe elegirse por conveniencia de administración, no como un requisito de rendimiento.

¿VDSina incluye WordPress preinstalado?

La página actual de VPS estándar no muestra WordPress como una aplicación preinstalada dedicada en los grupos de plantillas/aplicaciones visibles. Verifique la pantalla de pedidos en vivo antes de asumir la disponibilidad de cualquier plantilla.
