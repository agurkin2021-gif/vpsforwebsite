VPS para múltiples sitios web funciona bien cuando varios sitios pueden compartir de forma segura un grupo de recursos, un modelo de administración y un dominio de falla. El límite importante no es el número de dominios. Es el pico combinado de CPU, RAM, PHP / procesos de aplicación, trabajo de base de datos, almacenamiento, tareas en segundo plano y copias de seguridad en todos los sitios en el servidor .

Para la decisión de compra más amplia, véase VPS para el sitio web.

Evaluador de arquitectura para varios sitios

Use esto para decidir si un VPS sigue siendo el dominio de falla correcto.

Elija las características de la cartera que realmente se aplican.

Cuenta la carga de trabajo, no los dominios

La pregunta “¿cuántos sitios web puede alojar un VPS?” no tiene una respuesta fija confiable.

Un modelo de capacidad útil es:

Carga de varios sitios ≈ tráfico habitual conjunto + picos dinámicos coincidentes + bases de datos + cron y procesos + copias e importaciones + panel, correo y monitorización + margen

Ejemplos:

  • diez sitios estáticos o agresivamente almacenados en caché pueden usar muy poca capacidad de PHP /DB;
  • tres sitios de negocios de WordPress pueden necesitar materialmente más RAM porque cada uno tiene procesos PHP y una carga de trabajo de base de datos;
  • una tienda WooCommerce puede dominar todo el servidor durante el pago o un evento de venta;
  • Una importación de imágenes, copia de seguridad o análisis de seguridad puede consumir temporalmente más CPU / E / S que varios sitios web silenciosos combinados.

Calcula la carga simultánea más exigente, no el número de dominios del panel.

¿Cuántos sitios web puede alojar un VPS?

Use el conteo del sitio solo como un número de inventario.

La capacidad depende de:

  • tasa de aciertos de caché;
  • Concurrencia de solicitudes no almacenadas en caché;
  • Memoria PHP/proceso de aplicaciones;
  • duración de la solicitud;
  • conjunto de datos de base de datos mantenido en memoria;
  • intensidad de escritura;
  • tareas programadas / de fondo;
  • tráfico de bots;
  • almacenamiento/crecimiento de medios;
  • ventanas de copia de seguridad;
  • consumo del panel y del correo;
  • ¿Cuánta capacidad sobrante dejas?

Si no puede identificar a los consumidores de recursos dominantes, la confianza de cualquier estimación de “sitios web N” es baja.

Para el comportamiento específico de WordPress, use VPS para WordPress. Una tienda transaccional debe tratarse por separado; vea VPS para WooCommerce.

Una IP puede alojar muchos sitios web

Los sitios web modernos normales no necesitan una IP pública por dominio.

Con el alojamiento virtual basado en nombres:

  1. DNS apunta varios dominios a la misma IP de VPS;
  2. el navegador envía el nombre de host solicitado;
  3. Nginx/Apache hace coincidir ese nombre de host con el bloque de servidor / host virtual correcto;
  4. TLS utiliza SNI para que el servidor pueda presentar el certificado apropiado para cada nombre de host.

Esta es la razón por la que muchos sitios web HTTPS no relacionados pueden compartir puertos 80/443 en una IP.

Una IP separada aún puede ser importante para políticas de red especiales, requisitos heredados, reputación de correo electrónico o servicios no web, pero no es un requisito normal para cada sitio web.

Aislar cada sitio deliberadamente

Poner sitios en diferentes carpetas es organización, no un fuerte aislamiento.

Para sitios web no relacionados/clientes, prefiera límites separados cuando sea práctico:

LímitePor qué importa
Usuario del panel/sistemareduce la exposición de archivos/credenciales entre sitios no relacionados
Raíz del documentomantiene separados los archivos y las rutas de despliegue
Grupo PHP-FPM o servicio de aplicaciónpermite que cada sitio se ejecute bajo su propia configuración de usuario / proceso
Base de datos + usuario de base de datoslimita las credenciales y el alcance de la copia de seguridad/restauración
Registroshace que la resolución de problemas y la atribución de incidentes sean más claras
Archivos secretos/envEvita que una aplicación lea las credenciales de otra aplicación
Conjunto de copia de seguridadadmite la restauración específica del sitio sin revertir toda la cartera

Un anti-patrón común está ejecutando cada sitio PHP como el mismo usuario de Unix con archivos de configuración legibles. Un plugin comprometido puede convertirse en un compromiso entre sitios.

La propia guía de seguridad de FASTPANEL recomienda usuarios de FASTPANEL separados para sitios separados. Si desea una interfaz de usuario de alojamiento, compare VPS con Panel de control; el flujo de trabajo de marca se cubre en alojamiento VPS con FASTPANEL.

Grupos de PHP separados, servicios de aplicaciones y credenciales de bases de datos

Para sitios PHP, grupos PHP-FPM separados pueden ayudar a aislar:

  • Usuario/grupo de Unix;
  • límites de procesos;
  • Configuración PHP;
  • logs;
  • sockets;
  • comportamiento de los recursos.

Para las aplicaciones Node.js/Python/custom, utilice usuarios/servicios de aplicaciones independientes y puertos/zócalos locales.

Para bases de datos:

  • utilizar bases de datos separadas;
  • utilizar credenciales separadas;
  • conceder solo los privilegios que necesita cada aplicación;
  • no le dé a cada sitio una cuenta compartida de raíz/admin DB.

Esto no crea una multitenencia dura perfecta, pero mejora materialmente la contención y la resolución de problemas.

Las cargas de trabajo mixtas necesitan diferentes presupuestos

No dimensione una cartera mixta como si todos los sitios fueran iguales.

Sitios estáticos / en caché

Normalmente consumen poca CPU de aplicación y pocos recursos de base de datos.

WordPress

Necesitan recursos para procesos PHP, base de datos, caché y cron.

WooCommerce / membresía / sitios transaccionales

Necesita más margen de recursos dinámica de PHP/DB y una cuidadosa planificación del trabajo en segundo plano.

Aplicaciones personalizadas

Puede necesitar procesos persistentes, colas, contenedores, diferentes entornos de ejecución o puertos separados.

El sitio más pesado a menudo determina si todo el VPS debe ser más grande o si ese sitio debe salir.

Sus propios sitios pueden convertirse en vecinos ruidosos

Un VPS reduce la dependencia de clientes ajenos del alojamiento compartido, pero agrupar sitios en él puede crear competencia interna por los recursos.

Un sitio puede consumir recursos desproporcionados a través de:

  • pico de tráfico;
  • plugin/consulta mal;
  • ataque de bot;
  • procesamiento de imágenes;
  • importación/exportación;
  • escaneo de seguridad;
  • compresión de copia de seguridad;
  • cron fuera de control;
  • crecimiento elevado de los registros;
  • bloqueo de base de datos / presión IO.

Observe el uso de recursos durante estos eventos, no solo cuando el servidor está inactivo.

Si tu plataforma lo permite, los límites de procesos por sitio o de contenedores/cgroups pueden reducir el riesgo de que una sola carga de trabajo consuma todos los recursos. No des por hecho que un panel aplica cuotas estrictas de CPU y RAM, salvo que su documentación lo indique.

Los picos combinados importan más que el uso promedio

Los servidores multisitio fallan cuando los picos independientes se superponen.

Por ejemplo:

  • El sitio A recibe un pico de campaña;
  • El sitio B ejecuta una importación de base de datos;
  • El sitio C inicia una copia de seguridad completa;
  • El sitio D ejecuta un análisis de malware;
  • el panel rota los registros;
  • el buffer de la base de datos ya es grande.

Individualmente, cada sitio puede parecer pequeño. Juntos pueden agotar la CPU, RAM o E / S.

Planifique el mantenimiento y el trabajo en segundo plano en toda la cartera, no por sitio de forma aislada.

¿Manual, panel de control o contenedores?

Bloques de servidores manuales / hosts virtuales

Bueno cuando:

  • un operador competente gestiona el servidor;
  • el recuento del sitio es modesto;
  • las pilas son similares;
  • Automatización / scripts mantienen la configuración consistente.

La ruta de implementación general está cubierta en Cómo alojar un sitio web en VPS.

Panel de control de hosting

Útil cuando:

  • muchos dominios/usuarios necesitan una administración rutinaria;
  • importa el acceso de clientes o administradores delegados;
  • desea una interfaz de usuario para SSL, PHP, bases de datos, copias de seguridad y correo electrónico.

El modelo de usuarios y cuentas del panel importa más que el número de dominios que anuncia.

Contenedores

Útil cuando:

  • dependencia/aislamiento en entorno de ejecución es importante;
  • las aplicaciones tienen diferentes pilas;
  • los despliegues son nativos de contenedores;
  • el equipo ya conoce las operaciones de contenedores.

Los contenedores no son automáticamente más simples. Agregan preocupaciones sobre el ciclo de vida de la imagen, redes, volumen persistente, respaldo y monitorización.

Agencia y sitios web de clientes

El uso de la agencia es un caso natural de múltiples sitios, pero la propiedad del cliente aumenta el requisito de aislamiento.

Definir:

  • Quién es el responsable del dominio / DNS
  • cuentas separadas de panel/sistema;
  • credenciales de base de datos separadas;
  • acceso delegado;
  • propiedad de copia de seguridad por cliente;
  • restaurar la granularidad;
  • ruta de migración/exportación cuando un cliente se va;
  • quién es responsable de las actualizaciones de la aplicación;
  • si el incidente de un cliente puede afectar a otros.

No prometa un cliente "hosting aislado" si todos los sitios de clientes comparten el mismo dominio de usuario y error de Unix.

El tema propuesto anteriormente, VPS para sitios de agencias, sigue integrado en esta página mientras un nuevo análisis de resultados de búsqueda y volumen no justifique una página independiente.

Si nadie del equipo se encarga de las actualizaciones, la seguridad, la verificación de copias, la monitorización y los incidentes del servidor compartido, resuélvelo antes de agrupar sitios de clientes. Consulta VPS administrado o no administrado.

Para trasladar una cartera de sitios a un VPS, no copies todos los sitios y cambies todos los registros DNS a la vez. Prepara el traslado por etapas, prueba y cambia el tráfico con un plan de reversión. Consulta Migración de un sitio web a un VPS para seguir el proceso.

Copias y restauración por sitio

Un VPS significa que varios sitios pueden fallar a la vez.

Un diseño de copia de seguridad útil debería permitirte responder:

  • ¿Puedo restaurar solo el Sitio A?
  • ¿Puedo restaurar solo su base de datos?
  • ¿Puedo recuperar el VPS completo después de la pérdida del disco/servidor?
  • ¿Hay una copia fuera del servidor?
  • ¿Cuántos datos se pueden perder entre copias de seguridad?
  • ¿Puedo verificar las restauraciones sin sobrescribir los otros sitios?

Una imagen de servidor completo es útil para la recuperación de desastres, pero no debería ser el único método de recuperación si la restauración de un sitio comprometido obligaría a todos los demás sitios a volver a un punto anterior. Para la retención, copias externas, RPO / RTO y pruebas de restauración, use estrategia de copias de seguridad para un VPS.

Un VPS es un dominio de fallo

La consolidación reduce el costo y la duplicación de administración, pero aumenta el alcance del impacto.

Un evento puede afectar a todos los sitios:

  • Apagones de VPS;
  • sistema de archivos completo;
  • mal OS / actualización de la pila web;
  • Fallo de la base de datos;
  • error de firewall;
  • cuenta de administrador comprometida;
  • malware/compromiso raíz;
  • eliminación accidental;
  • trabajo de copia de seguridad agotando disco / E / S.

La cuestión no es si este riesgo existe, sino si la empresa lo acepta.

Cuándo dividir sitios o cargas de trabajo

Dividir cuando la razón es medible operacionalmente.

Desencadenantes fuertes:

  • un sitio domina repetidamente la CPU/RAM/I/O;
  • un sitio crítico para el negocio no puede compartir el riesgo de interrupción con sitios de menor prioridad;
  • una carga de trabajo de WooCommerce / tienda perturba los sitios silenciosos;
  • existen requisitos incompatibles del sistema operativo/entorno de ejecución/seguridad;
  • una base de datos necesita RAM/I/O/escalado independiente;
  • los procesos y las tareas en segundo plano dominan el consumo;
  • las ventanas de mantenimiento difieren;
  • un límite cliente/cumplimiento requiere una separación más fuerte;
  • La contención de recursos permanece después de la optimización y la programación.

Posibles patrones divididos:

  • sitio crítico → su propio VPS;
  • web → VPS separado para la base de datos;
  • web → VPS separado para tareas en segundo plano;
  • agencias → grupos de clientes separados;
  • producción → entorno de pruebas separado;
  • tienda o carga con muchas escrituras → servidor separado.

No se divida automáticamente: cada VPS adicional agrega monitorización, copias de seguridad, parches, redes y superficie de incidentes.

Monitorización de un VPS multisitio

Monitorizar en dos niveles.

Nivel de servidor

  • CPU;
  • RAM/swap/OOM;
  • uso del disco;
  • espera de E/S;
  • estado de la base de datos;
  • red;
  • estado de los procesos y servicios.

Nivel del sitio

  • Verificaciones HTTP(S) externas por nombre de host importante;
  • tiempo de respuesta;
  • 5xx errores;
  • Registros de PHP/aplicación;
  • tráfico por sitio / presión de los procesos cuando esté disponible;
  • cron/fallos de la cola;
  • Crecimiento DB/log/storage.

Un servidor puede estar “up” mientras un host virtual, certificado o aplicación está roto. El modelo completo de alerta de servidor + por nombre de host se cubre en monitorización de un VPS.

Preguntas frecuentes

¿Cuántos sitios web puedo alojar en un VPS?

No hay un número fijo confiable. La capacidad depende de la CPU pico combinada, RAM, procesos PHP / aplicación, trabajo de base de datos, almacenamiento y tareas en segundo plano de todos los sitios.

¿Necesitan varios sitios web direcciones IP separadas?

Normalmente no. El alojamiento virtual basado en nombres y TLS SNI permiten que varios dominios HTTPS compartan una IP pública. Las IP separadas aún pueden ser útiles para requisitos especiales de red / correo electrónico / legado.

¿Pueden varios sitios de WordPress compartir un VPS?

Sí. Utilice usuarios/credenciales independientes y dimensione el servidor para la carga de trabajo combinada de PHP/base de datos/fondo. Varios sitios ligeros de WordPress pueden encajar bien; un sitio dinámico pesado puede dominar el servidor.

¿Debería cada sitio tener un grupo PHP-FPM separado?

Para sitios PHP no relacionados o clientes, grupos separados pueden mejorar el aislamiento de proceso/usuario y hacer más claro el ajuste/registro por sitio. El diseño exacto depende del modelo de entorno de panel/software web.

¿Puede una tienda WooCommerce compartir un VPS con otros sitios?

Puede, pero los picos de pago / base de datos / fondo de la tienda pueden convertirse en la carga de trabajo dominante. Si la tienda es crítica para el negocio o repetidamente mata de hambre a otros sitios, divídala.

¿Es mejor un panel de control para alojar múltiples sitios web?

A menudo para la administración. Un panel puede simplificar dominios, usuarios, SSL, PHP, bases de datos y copias de seguridad, pero verificar su modelo de aislamiento de usuario / cuenta y el consumo de recursos adicionales.

¿Se requieren contenedores para múltiples sitios web?

No. Los hosts virtuales Nginx/Apache más usuarios/procesos separados pueden alojar muchos sitios. Los contenedores son útiles cuando la dependencia/aislamiento de procesos justifica la complejidad operativa adicional.

¿Cuál es el principal riesgo de alojar muchos sitios web en un solo VPS?

Una interrupción, una actualización incorrecta, un evento lleno de disco o un compromiso a nivel de servidor pueden afectar a todos los sitios en ese VPS.

¿Deberían las agencias poner a todos los clientes en un VPS?

Solo cuando la agencia acepta el dominio de fallas compartidas e implementa un aislamiento sólido de cuentas/archivos/DB, copias de seguridad, monitorización y procedimientos de salida del cliente. Los clientes críticos o incompatibles pueden merecer servidores separados.

¿Cuándo conviene separar los sitios en varios VPS?

Dividir cuando una carga de trabajo domina los recursos, un sitio crítico necesita aislamiento de fallas independiente, las pilas / límites de seguridad son incompatibles, o DB / procesos necesitan escalado independiente.
