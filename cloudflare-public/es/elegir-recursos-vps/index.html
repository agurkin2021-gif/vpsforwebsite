El modelo de dimensionamiento: reserve recursos antes de contar el tráfico

Un presupuesto VPS útil separa el servidor en consumidores de recursos.

Presupuesto RAM

La RAM total debe cubrir:

  1. el sistema operativo y los servicios del sistema;
  2. el servidor web o el proxy inverso;
  3. PHP-FPM, Node.js, Python u otra aplicación en entorno de ejecución;
  4. la base de datos;
  5. servicios de caché como Redis cuando se utilizan;
  6. el panel de control y sus servicios;
  7. procesos de monitorización, seguridad y respaldo;
  8. procesos de aplicaciones concurrentes;
  9. margen de recursos de seguridad para ráfagas, despliegues y mantenimiento.

No confundas el límite de memoria del CMS con la RAM necesaria del servidor. Un límite PHP de 256 MB no significa que un VPS de 1 GB pueda ejecutar con seguridad cuatro procesos simultáneos de 256 MB, además de Linux, la base de datos y los demás servicios.

Un modelo práctico es:

RAM necesaria = servicios básicos + memoria de trabajo de la base de datos + memoria de procesos simultáneos + memoria de tareas en segundo plano + margen

Mida los procesos reales siempre que sea posible. Las estimaciones son útiles para elegir un nivel inicial; las mediciones deciden si el nivel es realmente suficiente.

Estimador de presupuesto RAM

Use este estimador para exponer las suposiciones en lugar de adivinar a partir del número de visitantes. Estima solo el nivel de RAM; CPU, almacenamiento y E/S aún necesitan validación por separado. Ingrese sus propias mediciones; los marcadores de posición reflejan el ejemplo trabajado a continuación y no son valores predeterminados universales.

Ingrese sus medidas y calcule el presupuesto.

Ejemplo: 450 MB de servicios básicos + 500 MB para la base de datos + 6 procesos × 120 MB + 300 MB para panel, caché y tareas en segundo plano = 1,970 MB antes de añadir margen. Con un 25% de margen, el cálculo ronda los 2.4 GB. Por tanto, un VPS de 2 GB resulta demasiado ajustado con estos supuestos; 4 GB ofrece un punto de partida más seguro.

Cuando mida PHP-FPM o procesos similares, recuerde que el RSS sin procesar puede contar dos veces las páginas y bibliotecas compartidas en todos los procesos. Trate las mediciones de procesos como evidencia, no como una contabilidad perfectamente aditiva.

Presupuesto de CPU

La demanda de CPU depende de la cantidad de trabajo que se debe ejecutar al mismo tiempo. Los archivos estáticos servidos desde la caché pueden ser económicos. Las solicitudes dinámicas que ejecutan código de aplicación, consultan la base de datos, generan páginas, redimensionan imágenes, ejecutan importaciones o realizan trabajos de API pueden consumir mucho más CPU.

Busca:

  • Saturación sostenida de la CPU durante el tráfico legítimo;
  • largos tiempos de solicitud de aplicaciones mientras la CPU está ocupada;
  • varias solicitudes dinámicas costosas que llegan juntas;
  • tareas cron, copias o importaciones que coinciden con el tráfico de usuarios;
  • consultas de base de datos que consumen CPU debido a índices ineficientes o trabajo excesivo.

Un breve pico de CPU no es automáticamente una razón para actualizar. La saturación persistente que retrasa el trabajo legítimo es una evidencia más fuerte.

Una estimación práctica de la concurrencia es:

Solicitudes dinámicas activas ≈ solicitudes dinámicas por segundo × duración de la solicitud

Ejemplo: 6 solicitudes dinámicas sin caché por segundo, con una duración p95 de 0.8 segundos, suponen aproximadamente 4.8 solicitudes activas en ese momento. Si la aplicación necesita un proceso por solicitud activa, prevé unos cinco procesos ocupados más margen para la cola. Si cada solicitud consume 0.12 segundos de CPU, 6 solicitudes por segundo representan unos 0.72 segundos de CPU por segundo antes de añadir margen. Es una estimación de carga, no una garantía universal de vCPU: la generación de la CPU, la competencia por los recursos y la planificación del proveedor pueden variar.

Traducir los límites de alojamiento compartido en requisitos de VPS

Si el sitio web ya se ejecuta en alojamiento compartido, la evidencia de tamaño más útil ya puede existir en el panel de control de alojamiento.

Recoger:

  • Uso de CPU y eventos de límite de CPU;
  • uso de memoria física;
  • procesos de entrada o límites de solicitud concurrentes;
  • recuento de procesos;
  • presión de E/S y IOPS del disco;
  • Tamaño y crecimiento de la base de datos;
  • uso de almacenamiento;
  • el tráfico alcanza su punto máximo por hora en lugar de solo visitas mensuales;
  • Proceso PHP o comportamiento del proceso de aplicación donde sea visible.

Diagnóstico de alojamiento compartido a VPS

Utilice el patrón de error para identificar qué investigar antes de seleccionar un nivel. La herramienta deliberadamente no convierte un límite de CloudLinux directamente en vCPU o RAM.

En el alojamiento de cPanel con CloudLinux, comience con el historial de uso de recursos en lugar de una sola lectura en vivo. Capture fallas repetidas y el momento en que ocurren, luego compárelas con tráfico, cron, copia de seguridad, importación y actividad de administración.

Elige las señales que realmente observas.

No copie un límite de alojamiento compartido directamente en una especificación VPS.Un porcentaje de CPU, límite de proceso de entrada o límite de memoria de CloudLinux describe el entorno de alojamiento actual; es evidencia del cuello de botella, no una conversión VPS uno a uno.

Utilice el patrón en su lugar:

Repetidos eventos de límite de memoria con CPU normal: investigar la memoria del proceso, la memoria de la base de datos y las tareas en segundo plano antes de agregar vCPU.

Repetidos eventos de límite de CPU durante el trabajo dinámico legítimo: perfilar la aplicación y la base de datos, luego considerar CPU adicional si el trabajo es realmente necesario.

Saturación de procesos de entrada o procesos: mide la concurrencia dinámica y la duración de las solicitudes. Acelerar las solicitudes puede eliminar las colas sin ampliar el servidor.

Presión de E/S: identificar copias de seguridad, registros, actividad de bases de datos, importaciones o plugins pesados en almacenamiento antes de asumir que más RAM lo resolverá.

Esto separa un problema de capacidad real de un límite del plan de alojamiento que puede ser desencadenado por un componente ineficiente.

¿VPS o optimización de sitios web?

Un VPS más grande se justifica cuando la carga de trabajo legítima agota repetidamente un recurso después de que se han abordado problemas obvios de aplicación.

Optimice primero cuando la presión proviene de:

  • un plug-in lento o una extensión;
  • una consulta de base de datos no indexada o patológica;
  • caché de páginas u objetos que funciona incorrectamente;
  • bots abusivos;
  • trabajos de cron fuera de control;
  • procesamiento de imágenes de gran tamaño;
  • copias de seguridad o escaneos de malware programados durante el tráfico pico;
  • fugas de memoria;
  • generación excesiva de registros.

Aumente los recursos del servidor cuando las mediciones muestren que la carga de trabajo optimizada aún necesita más capacidad.

La distinción es importante económicamente. Mover el código ineficiente de alojamiento compartido a un VPS más grande puede ocultar el cuello de botella temporalmente sin eliminarlo.

Dimensiona los procesos PHP y de aplicación según la concurrencia

Las visitas mensuales son un dato poco preciso para dimensionar: el servidor debe atender solicitudes simultáneas.

Para las cargas de trabajo dinámicas de PHP, cada proceso activo de PHP consume memoria y CPU mientras procesa una solicitud. por lo tanto, la capacidad del proceso depende tanto de la memoria promedio por proceso como de cuánto tiempo permanecen ocupadas las solicitudes.

Una comprobación de RAM simplificada es:

RAM para procesos = RAM utilizable después de los servicios básicos × proporción que se puede asignar con seguridad a los procesos

Luego, compare ese presupuesto con la memoria de proceso medida. No configure el número máximo teórico de procesos si al hacerlo no dejaría memoria para la base de datos, caché o sistema operativo.

El almacenamiento en caché cambia este cálculo. Una página anónima en caché puede omitir PHP por completo, mientras que el proceso de pago, las sesiones iniciadas, wp-admin, las API y las páginas personalizadas aún llegan a la aplicación.

Para ver el comportamiento específico de WordPress, consulte VPS para WordPress.Para cargas de trabajo transaccionales, vea VPS para WooCommerce.

La demanda de base de datos puede establecer el tamaño del servidor

Un sitio web puede aparecer limitado por la CPU cuando el problema subyacente es el trabajo de base de datos.

Compruebe:

  • patrones de consulta lenta;
  • tamaño del conjunto de trabajo de la base de datos;
  • concurrencia de consultas;
  • falta de índices;
  • grandes datos cargados automáticamente o metadatos de aplicaciones equivalentes;
  • costosas operaciones de búsqueda, filtrado o informes;
  • trabajos de importación y mantenimiento;
  • latencia de almacenamiento.

Más RAM puede ayudar cuando la base de datos necesita legítimamente un conjunto de datos más grande en la memoria, pero no repara las consultas ineficientes. Más CPU puede aumentar el rendimiento, pero también puede permitir que las consultas más caras compitan a la vez.

Planificar el tráfico máximo, no el tráfico promedio

Dimensionar según el promedio oculta los periodos en los que los usuarios realmente sufren fallos.

Identifica un intervalo realista de máxima actividad: campañas, ofertas, envíos de boletines, lanzamientos de productos, importaciones programadas, copias o acumulación de tareas cron. Estima qué solicitudes seguirán siendo dinámicas y cuáles podrá absorber la caché de páginas o una CDN.

Mantenga el margen de recursos para la combinación de:

  • tráfico normal de usuarios;
  • el tráfico pico dinámico;
  • actividad administrativa;
  • tareas programadas;
  • despliegues y calentamiento de caché;
  • Procesos de monitorización y backup.

Una CDN puede reducir la entrega estática y algunas solicitudes de origen. No elimina el trabajo dinámico de la aplicación o la base de datos que todavía llega al VPS.

Ejemplo de pico: si un sitio recibe 20 solicitudes/s y el 90% se sirve desde la caché o CDN, al origen llegan unas 2 solicitudes dinámicas/s. Una campaña que duplique el tráfico total a 40 solicitudes/s, manteniendo la misma proporción de caché, enviará unas 4 solicitudes dinámicas/s a la aplicación. Con una duración p95 de 0.8 segundos, son aproximadamente 3.2 solicitudes dinámicas activas simultáneamente, antes de sumar las tareas administrativas o las ráfagas de pagos y API.

Tamaño de almacenamiento

La capacidad de disco no es solo el directorio actual del sitio web.

Incluye:

  • archivos del sitio web;
  • base de datos;
  • medios subidos;
  • logs;
  • archivos temporales;
  • cachés de paquetes y aplicaciones;
  • copias del entorno de pruebas, si se guardan localmente;
  • archivos de copia de seguridad si las copias de seguridad se crean temporalmente en el VPS;
  • esperado crecimiento.

No llene el sistema de archivos cerca de su límite. Las bases de datos, actualizaciones, registros y operaciones de copia de seguridad necesitan espacio de trabajo.

Un presupuesto de capacidad práctica es:

Disco necesario = archivos actuales + base de datos + espacio temporal de operaciones + preparación local de copias + crecimiento previsto + margen libre de trabajo

Ejemplo: 18 GB ocupados + 8 GB temporales para actualización o migración + 18 GB para preparar una copia local + 6 GB de crecimiento previsto ya superan un disco de 40 GB, incluso antes de añadir margen de seguridad. En ese caso, 80 GB son un punto de partida más seguro. La capacidad es independiente de las IOPS y la latencia: un disco más grande no acelera automáticamente una base de datos lenta.

Ancho de banda y tamaño de transferencia mensual

La transferencia mensual es distinta de la CPU, la RAM y la velocidad del puerto de red. Un servidor puede tener capacidad de cómputo de sobra y aun así superar su cuota de transferencia si entrega directamente archivos grandes o contenido multimedia sin caché.

Una estimación aproximada es:

Transferencia mensual del origen ≈ bytes medios enviados por el VPS por solicitud × solicitudes mensuales al origen + copias, exportaciones y demás tráfico saliente

Para una estimación más útil, separa el tráfico dinámico y almacenable en caché:

Transferencia del origen ≈ bytes totales solicitados × (1 − proporción servida por CDN o caché) + respuestas dinámicas sin caché + tráfico saliente ajeno a la web

Ejemplo: si los usuarios solicitan 2 TB de recursos y páginas al mes y una CDN sirve el 80% de esos bytes sin consultar al origen, el VPS podría entregar unos 400 GB de ese tráfico apto para caché. A ello se suman las páginas dinámicas, respuestas de API, copias, exportaciones y solicitudes no resueltas desde la caché.

No supongas que una CDN elimina toda la transferencia del origen. Las páginas con sesión iniciada, los pagos, las API, las respuestas ausentes de caché, los vaciados de caché, las descargas grandes y el llenado de la CDN desde el origen pueden seguir consumiéndola. Distingue también la transferencia mensual incluida de la velocidad del puerto de red: esta última indica el caudal potencial, mientras que la primera indica cuántos datos se pueden enviar durante el periodo de facturación.

Varios sitios web cambian el cálculo

Varios sitios web en un VPS comparten la misma capacidad de CPU, RAM, almacenamiento y proceso. Sus picos pueden superponerse incluso si cada sitio es pequeño individualmente.

Dimensione el servidor de la carga de trabajo combinada y reserve suficiente margen de recursos para que la tarea en segundo plano de un sitio no agote a los demás. Si el aislamiento, el impacto de fallas o la contención de recursos se vuelven importantes, dividir las cargas de trabajo puede ser más útil que continuar ampliando un servidor.

Ver VPS para múltiples sitios web para la decisión de múltiples sitios.

Incluye el consumo del panel y del correo en el cálculo de recursos

Un panel simplifica la gestión de dominios, SSL, bases de datos, versiones de PHP y cuentas, pero también ejecuta sus propios servicios. Reserva memoria y almacenamiento para el panel, además de los recursos del sitio.

Los servicios de correo electrónico pueden agregar otra capa de recursos persistente: SMTP, IMAP/POP, filtrado de spam, análisis antivirus, colas, registros y almacenamiento de buzones. Si el VPS alojará el sitio web + correo electrónico, incluya ese consumo de recursos adicional en la RAM, CPU, almacenamiento y presupuesto de respaldo en lugar de asumir que el correo electrónico es gratuito.

Para un sitio web pequeño, mover el correo electrónico a un proveedor de correo electrónico administrado puede reducir la carga del servidor y el riesgo operativo. Si el correo electrónico permanece en el VPS, verifique los requisitos de capacidad de entrega, como los registros DNS y las restricciones del proveedor / IP por separado; un VPS más grande no resuelve la reputación del remitente.

Si prefiere la administración basada en panel, compare las compensaciones en VPS con el panel de control.

Un flujo de trabajo de dimensionamiento VPS repetible

  1. Mide la carga de trabajo actual. Graba CPU, memoria, concurrencia dinámica, comportamiento de la base de datos, almacenamiento y períodos pico.
  2. Identifica el cuello de botella. Distingue entre limitaciones de CPU, RAM, procesos, base de datos, E/S y software.
  3. Eliminar la ineficiencia obvia. Corrige el almacenamiento en caché, los trabajos fuera de control, las consultas patológicas y el tráfico abusivo antes de comprar capacidad.
  4. Construye el presupuesto de recursos. Reserva RAM para servicios de línea de base, base de datos, procesos de aplicaciones, panel y trabajo en segundo plano.
  5. Elige un plan inicial con margen. Evita tanto quedarte sin capacidad de reserva como contratar recursos excesivos sin datos que lo justifiquen.
  6. Reproducir un pico realista. Validar la configuración bajo carga dinámica representativa, no solo una página de inicio inactiva.
  7. Monitoriza después de la migración. Ajusta los recursos según las mediciones; la estimación inicial no tiene por qué ser permanente. Consulta Monitorización de un VPS para establecer las comprobaciones básicas en producción.

Una vez que se dimensiona el destino, use Migración del sitio web a VPS para planificar el inventario, la prueba privada, la sincronización final de datos, el cambio de servidor de DNS y la reversión a la ruta de estado anterior.

Recomendación basada en pruebas

Una recomendación VPS útil debe indicar tanto la configuración como el motivo de la misma.

Por ejemplo:

2 vCPU / 4 GB RAM / 80 GB puede ser un punto de partida razonable cuando un sitio web empresarial ejecuta un CMS respaldado por una base de datos, tiene una actividad PHP no almacenada en caché significativa, necesita un panel de control y requiere capacidad operativa adicional. No es una garantía de que el servidor admita un número específico de visitantes mensuales.

La confianza debe ser menor cuando la única entrada es el número de visitantes. La confianza aumenta cuando se conoce el historial de la CPU, la presión de la memoria, las solicitudes dinámicas concurrentes, la memoria del proceso, el comportamiento de la base de datos y el crecimiento del almacenamiento.

Use una etiqueta de confianza simple:

  • Confianza baja: número de visitantes, nombre del CMS y almacenamiento aproximado solamente.
  • Confianza media: algo de historial real de CPU/RAM más tipo de carga de trabajo y patrón de pico.
  • Alta confianza: CPU/RAM/I/O de serie temporal, concurrencia no cacheada, memoria de proceso, duración de la solicitud, comportamiento de la base de datos y crecimiento del almacenamiento.

Una etiqueta de confianza más alta significa que las suposiciones son mejores, no que el tráfico futuro esté garantizado.

Preguntas frecuentes

¿Cuánta RAM necesita un sitio web VPS?

No hay una cantidad universal confiable. Un sitio en caché ligero puede usar poca memoria, mientras que un CMS dinámico con una base de datos, un panel y procesos de aplicación concurrentes pueden requerir sustancialmente más. Calcula la RAM de los procesos que deben coexistir y dejar margen de recursos.

¿Es suficiente 2 GB de RAM para un sitio web VPS?

Puede ser suficiente para una carga de trabajo pequeña y ligera. Se vuelve restrictivo cuando un panel de control, base de datos, varios procesos PHP, tareas en segundo plano o múltiples sitios deben ejecutarse juntos. Mide la presión de la memoria en lugar de depender solo del número de RAM.

¿Para qué sirve un VPS de 4 GB?

Un VPS de 4 GB es un punto de partida práctico para muchas cargas de trabajo de CMS empresarial porque deja más espacio para Linux, la base de datos, los procesos de aplicaciones / PHP y el almacenamiento en caché. El ajuste exacto depende de la concurrencia dinámica, la demanda de base de datos, el trabajo en segundo plano y el consumo de recursos adicionales del panel. Para la decisión específica de WordPress, use VPS para WordPress .

¿Cuántos visitantes puede manejar un VPS?

El número de visitas no basta para responder. La proporción de aciertos de caché, las solicitudes simultáneas, la duración de la ejecución, el trabajo de la base de datos y las tareas en segundo plano pueden cambiar enormemente la capacidad entre dos sitios con tráfico parecido.

¿Debo agregar RAM o CPU primero?

La presión de memoria, el uso de swap o los eventos OOM apuntan a optimizar el consumo o ampliar la RAM. La saturación sostenida de CPU durante una carga legítima y ya optimizada apunta a ampliar la CPU. Los cuellos de botella de base de datos y E/S requieren un diagnóstico aparte.

¿Una CDN reduce los requisitos de VPS?

Puede reducir la entrega de archivos estáticos y las solicitudes al origen que admiten caché. Las solicitudes dinámicas y el trabajo de base de datos que llegan al origen siguen consumiendo recursos del VPS.

¿Debo medir el tráfico promedio o máximo?

Dimensiona para un pico realista con margen operativo. El promedio puede ocultar intervalos breves en los que coinciden muchas solicitudes dinámicas y tareas programadas.
