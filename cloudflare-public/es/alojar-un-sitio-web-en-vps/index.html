Cómo alojar un sitio web en un VPS

Cómo alojar un sitio web en un VPS: elige el método de despliegue, protege el acceso, instala los servicios necesarios, configura el dominio y HTTPS y comprueba que el sitio esté listo para producción.

Cómo alojar un sitio web en VPS depende de la aplicación que está implementando. Un sitio estático necesita un servidor web y DNS. WordPress u otro PHP CMS también necesita PHP y una base de datos. Una aplicación Node.js o Python generalmente se ejecuta detrás de un proxy inverso. Puede construir esas piezas manualmente en un VPS limpio o usar un panel de control para administrarlas a través de un navegador.

Esta guía explica el proceso desde un VPS nuevo hasta una web publicada. Si trasladas un sitio en producción con datos activos, consulta cómo migrar un sitio web a un VPS para planificar el cambio y la reversión.

Para la decisión de compra más amplia, véase VPS para el sitio web.

Secuencia de despliegue rápido

Un primer despliegue fiable sigue este orden:

  1. Selecciona y dimensiona el VPS.
  2. Elige administración manual, panel de control o un servicio de administración.
  3. Proporcionar un sistema operativo limpio o una imagen actual del panel de proveedores.
  4. Asegurar el primer acceso y crear una ruta administrativa no raíz.
  5. Actualizar el sistema operativo.
  6. Instale solo el entorno de software web que necesita la aplicación.
  7. Configurar el sitio/aplicación antes de cambiar la migración pública de DNS cuando sea práctico.
  8. Despliega archivos y código y configura propietarios, permisos, credenciales y acceso a la base de datos.
  9. Restringe el cortafuegos sin bloquear SSH ni el acceso HTTP o HTTPS necesario.
  10. Prueba el destino antes del DNS público.
  11. Apunte el dominio al VPS.
  12. Habilitar HTTPS después de que el nombre de host llegue al servidor.
  13. Verificar cron/workers, registros, copias de seguridad y monitorización externo.
  14. Reiniciar una vez y confirmar que cada servicio requerido vuelve automáticamente.
  15. Solo entonces llama a la implementación lista para producción.

No instale PHP, MySQL, correo electrónico o un panel de control simplemente porque una guía genérica de VPS los incluye. Instale los componentes que su sitio web realmente necesita.

Elija manual, panel o administrado

Hay tres caminos operativos distintos.

Manual / sin panel de control

Elija un VPS Linux limpio y administre la pila a través de SSH.

Buen ajuste cuando:

  • usted entiende la pila de aplicaciones;
  • desea una cantidad mínima de servicios;
  • necesita una configuración personalizada de Nginx/Apache/entorno de ejecución;
  • utiliza scripts, Git o infraestructura como código;
  • no necesita una interfaz de cuenta de hosting tradicional.

La opción de VPS sin panel de control se desarrolla en esta misma guía, sin crear otra página que cubra la misma necesidad.

Panel de control

Utilice un panel de alojamiento cuando el sitio basado en navegador, dominio, PHP, base de datos, correo electrónico o administración de usuarios elimine el trabajo repetitivo significativo.

Consulte VPS con Panel de control. Si FASTPANEL ya es su elección, utilice alojamiento VPS con FASTPANEL.

Administración contratada

El panel y la administración son cosas distintas. Si nadie de tu equipo se ocupa de los parches, la seguridad, las copias, la monitorización y los incidentes, resuélvelo antes del lanzamiento.

Véase VPS administrados vs no administrados.

Evaluador del método de despliegue

La herramienta identifica qué tipo de instalación conviene estudiar. No sustituye la documentación de la aplicación.

Seleccione la carga de trabajo y la preferencia de operación.

Prerrequisitos

Antes de configurar el servidor, prepara:

  • un VPS dimensionado para la carga de trabajo;
  • la dirección IP del servidor;
  • credenciales SSH o acceso de clave;
  • una ruta de recuperación/VNC/consola del proveedor en funcionamiento;
  • un dominio registrado y acceso DNS;
  • los archivos del sitio web o el repositorio de aplicaciones;
  • las versiones en entorno de ejecución requeridas;
  • requisitos de la base de datos;
  • un plan para los secretos/variables ambientales;
  • una ubicación de copia de seguridad;
  • una forma externa de probar la disponibilidad del sitio web.

Utilice VPS dimensionamiento para el sitio web antes de la implementación si el requisito de recursos es aún incierto.

En la página VPS estándar actual de VDSina se incluyen plantillas de sistema operativo puro, como Ubuntu 26.04/24.04/22.04/20.04, Debian 13/12/11/10, AlmaLinux, Rocky, CentOS, Oracle Linux y ArchLinux. Esta guía utiliza ejemplos de estilo Ubuntu/Debian porque la documentación del servidor web actual y el flujo de paquetes son fáciles de seguir; la arquitectura se aplica a otras distribuciones de Linux compatibles con diferentes comandos de paquete/servicio.

Elija el sistema operativo

Para un servidor web manual, elija un sistema operativo que:

  • es compatible con la aplicación / entorno de ejecución;
  • todavía se mantiene;
  • su administrador entiende;
  • tiene paquetes / documentación actuales para el entorno de software web;
  • coincide con cualquier requisito de panel si más tarde usa uno.

No elijas un sistema solo por ser el más nuevo. Importan más la compatibilidad con la aplicación y la experiencia del administrador.

Para un simple ejemplo actual de Linux, Ubuntu 24.04 LTS o Debian 12 son objetivos de documentación razonables. Si su proveedor de aplicaciones especifica otra distribución compatible, siga ese requisito.

Asegure el primer acceso SSH

Un nuevo VPS le da acceso administrativo, pero el trabajo de producción no debe ocurrir permanentemente como root.

Una secuencia de primer acceso segura es:

  1. conectarse utilizando las credenciales/clave proporcionadas por el proveedor de VPS;
  2. confirmar que el servidor/IP es el que pretendías crear;
  3. mantener funcionando la consola del proveedor/VNC/ruta de recuperación;
  4. crear un usuario administrativo con nombre;
  5. conceder solo los derechos sudo/admin requeridos;
  6. agregar autenticación de clave SSH cuando sea práctico;
  7. comprueba el nuevo acceso en una segunda sesión antes de desactivar o restringir el método original.

Ejemplo en Ubuntu/Debian:

ssh root@SERVER_IP
adduser deploy
usermod -aG sudo deploy

No bloquee la única ruta administrativa de trabajo mientras “endurece” el servidor.

El endurecimiento profundo de SSH/firewall está cubierto en la lista de comprobación de seguridad de un VPS; esta guía mantiene solo el mínimo necesario para el despliegue.

Actualizar el servidor antes de instalar la pila

En Ubuntu/Debian:

sudo apt update
sudo apt upgrade -y

Reinicie si la actualización lo requiere, luego verifique que pueda volver a conectarse.

No posponga las actualizaciones de seguridad hasta que el sitio web sea público.

Camino manual / sin panel de control

Un VPS manual debe contener solo los servicios que la aplicación necesita.

Las opciones comunes son:

Sitio web estático

Necesario:

  • Nginx o Apache;
  • archivos del sitio web;
  • DNS;
  • HTTPS.

No se necesita automáticamente:

  • PHP;
  • MySQL/MariaDB/PostgreSQL;
  • servidor de correo electrónico local.

Sitio web PHP / WordPress

Por lo general es necesario:

  • Nginx o Apache;
  • Módulos PHP-FPM / PHP;
  • base de datos;
  • archivos/archivos subidos del sitio web;
  • DNS;
  • HTTPS.

Para el comportamiento de los recursos de WordPress, use VPS para WordPress.

Node.js / Python / aplicación personalizada

Por lo general:

  • entorno de ejecución de la aplicación;
  • usuario dedicado de la aplicación no raíz;
  • administrador de procesos/servicio systemd;
  • aplicación vinculada a localhost/private socket donde sea práctico;
  • Proxy inverso Nginx/Apache;
  • base de datos solo cuando sea necesario;
  • DNS;
  • HTTPS.

No exponga un servidor de desarrollo directamente a la Internet pública como arquitectura de producción.

Instalar el servidor web

La documentación actual de Ubuntu Server cubre Nginx y Apache. Ninguno es la mejor opción para todos los casos.

Para el ejemplo de Nginx:

sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

En este punto, la IP del servidor debe devolver la página predeterminada de Nginx si las reglas de red/firewall permiten HTTP.

Use Apache en su lugar cuando la aplicación, el equipo o la configuración existente se ajusten mejor a Apache.

Configurar el nombre de host del sitio web

DNS y configuración de servidor web son dos mitades del mismo trabajo.

El proveedor de DNS debe apuntar el nombre de host al VPS, y el servidor web debe saber qué sitio debe responder a ese nombre de host.

Para Nginx, cree un bloque de servidor para el dominio. Conceptualmente:

server {
    listen 80;
    listen [::]:80;

    server_name example.com www.example.com;
    root /var/www/example.com/public;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}

En Ubuntu/Debian, las configuraciones específicas del sitio comúnmente viven bajo:

  • /etc/nginx/sites-available/
  • /etc/nginx/sites-enabled/

Tras los cambios:

sudo nginx -t
sudo systemctl reload nginx

Pruebe siempre la sintaxis de configuración antes de volver a cargar.

Para una aplicación con proxy inverso, el bloque del servidor reenvía las solicitudes al puerto o socket local de la aplicación.

Implementar archivos o código de aplicación

Elija un método de implementación repetible.

SFTP/SCP

Bueno para:

  • Sitios pequeños;
  • despliegues manuales poco frecuentes;
  • Proyectos sencillos por primera vez.

Riesgo: es fácil que el directorio de producción se aleje del repositorio fuente.

rsync sobre SSH

Útil para la sincronización de archivos repetible y actualizaciones incrementales eficientes.

Despliegue basado en Git

Útil cuando las versiones de producción deben corresponder a commits de repositorio.

CI/CD

Útil cuando la implementación es lo suficientemente frecuente como para justificar los pasos automatizados de compilación/prueba/liberación.

Cualquiera que sea el método que utilices:

  • no se despliegue como root a menos que la tarea realmente requiera root;
  • mantener archivos de aplicación propiedad de un usuario apropiado de implementación/aplicación;
  • conceder al servidor web solo el acceso que necesita;
  • mantener secretos fuera de las raíces de los documentos públicos;
  • no utilices permisos de escritura para todos como atajo.

Ruta PHP / WordPress

Para un sitio PHP en Ubuntu/Debian, instale los paquetes PHP-FPM compatibles actuales y las extensiones necesarias para la aplicación.

Arquitectura típica:

navegador → Nginx/Apache → PHP-FPM → base de datos

No copie una lista de extensiones aleatorias de otro CMS. Instale lo que la aplicación realmente requiere.

Para WordPress:

  • crear una base de datos y un usuario de base de datos dedicado;
  • configurar los límites de carga / memoria / ejecución de PHP a partir de la necesidad medida;
  • protege las credenciales de wp-config.php;
  • configurar el nombre de host del sitio;
  • habilitar HTTPS;
  • validar trabajos wp-cron/segundo plano;
  • agregar almacenamiento en caché basado en la carga de trabajo.

Utilice VPS para WordPress para dimensionar y rendimiento en lugar de duplicarlo aquí.

Node.js / Python / ruta de la aplicación personalizada

No ejecute el comando de desarrollo manualmente en un terminal y llámelo producción.

Uso:

  • un usuario de aplicación dedicado;
  • archivo de entorno/configuración con permisos restringidos;
  • systemd o un gestor de procesos de producción apropiado;
  • reinicio automático en caso de fallo/reinicio;
  • aplicación escuchando en una interfaz local o privada;
  • Proxy inverso Nginx/Apache;
  • registros de aplicaciones;
  • comprobaciones de funcionamiento.

Flujo típico:

navegador → HTTPS/Nginx → aplicación en 127.0.0.1:PORT → base de datos o servicios externos

Verifique la propia guía de implementación de producción del marco.

Base de datos: instalar solo cuando sea necesario

Un sitio web estático no necesita una base de datos.

Para una aplicación dinámica que lo necesite:

  • instalar el motor de base de datos compatible;
  • crear una base de datos dedicada;
  • crear un usuario específico de la aplicación;
  • conceder sólo los privilegios necesarios;
  • mantener las credenciales fuera de la raíz web;
  • no exponga públicamente el puerto de la base de datos a menos que haya una arquitectura segura específica que lo requiera;
  • incluir la base de datos en los planes de copia de seguridad y monitorización.

El trabajo de la base de datos puede convertirse en el verdadero cuello de botella del VPS, incluso cuando el servidor web está casi inactivo.

Propiedad de archivos, permisos y secretos

Evita dos errores comunes:

  1. ejecutar el sitio web como root;
  2. dar permiso de escritura a todo el mundo en los directorios de la aplicación para resolver errores de permisos.

En su lugar:

  • utilizar un usuario de implementación/aplicación;
  • entender qué proceso necesita acceso de lectura vs escritura;
  • dar a los directorios de subidas/caché solo el acceso de escritura que requieren;
  • proteger los archivos y credenciales del entorno;
  • no incluyas credenciales de producción en los commits de Git;
  • mantener las claves privadas fuera de las raíces públicas de los documentos.

La propiedad exacta depende de la aplicación y del modelo de servidor web; use la documentación de la aplicación en lugar de copiar una receta universal chmod 777.

Prueba antes de DNS público

No haga del DNS la primera prueba real de la aplicación.

Antes de cambiar la migración pública, verifique el nuevo servidor utilizando uno de estos métodos cuando sea práctico:

  • acceder a la IP del servidor para una comprobación estática/default sencilla;
  • usar una entrada local en el archivo hosts local, por lo que example.com resuelve el nuevo VPS solo en su computadora;
  • utilizar un nombre de host privado/de prueba que no pueda convertirse en un duplicado indexado accidental;
  • probar la aplicación a través de la misma configuración de nombre de host Nginx/Apache que utilizará la producción.

Compruebe más que la página de inicio:

  • páginas internas importantes;
  • login/admin;
  • formularios;
  • subidas;
  • activos estáticos;
  • la base de datos lee/escribe;
  • puntos finales de aplicación/API;
  • redirecciona;
  • Logs.

Una prueba de archivo hosts es especialmente útil porque muchas aplicaciones se comportan de manera diferente bajo el nombre de host real que bajo la IP del servidor raw.

Si este es un sitio en vivo existente, use el proceso de cambio de servidor más estricto en Migración del sitio web a VPS.

Apunte el dominio al VPS

En el proveedor DNS, configure los registros que deben llegar a este servidor.

Configuración típica de IPv4:

NombreTipoValor
@ADirección IPv4 de VPS
wwwCNAMEdominio raíz

También puedes utilizar un registro A para www.

Agregue un registro AAAA solo si IPv6 está realmente configurado y accesible en el VPS. Un registro AAAA roto puede hacer que algunos visitantes fallen incluso cuando IPv4 funciona.

El DNS solo no hace que el sitio web funcione: la configuración del sitio Nginx/Apache también debe tener el nombre de host correspondiente.

Si está moviendo un sitio en vivo existente, el cambio de servidor DNS y el manejo de escritura final pertenecen a la migración del sitio web a VPS.

Agregar HTTPS después de la resolución de DNS

Obtenga un certificado de confianza solo después de que el nombre de host público se resuelva en el servidor que responderá a la solicitud de validación. Asegúrese de que las reglas del firewall/proveedor de red ya permitan la ruta de validación HTTP/HTTPS que desea usar.

Para Nginx/Apache, un cliente ACME como Certbot puede solicitar y renovar certificados Let’s Encrypt. Siga las instrucciones actuales de Certbot/OS en lugar de copiar un comando de paquete antiguo a ciegas.

Verificar:

  • el certificado cubre las variantes root y www que utilices;
  • HTTP redirige a HTTPS según lo previsto;
  • La renovación del certificado está automatizada;
  • renovación puede pasar a través de la configuración de firewall/CDN;
  • la aplicación genera las URL HTTPS correctas.

No habilite una redirección HTTPS antes de saber que la ruta del certificado funciona.

Configurar el firewall

Mantenga el acceso administrativo funcionando mientras cambia las reglas del firewall.

Un sitio web público básico comúnmente necesita:

  • SSH de la fuente/ruta de administración requerida;
  • TCP 80 para HTTP/ACME/redireccionamientos;
  • TCP 443 para HTTPS.

No exponga los puertos de aplicaciones MySQL/PostgreSQL, Redis o internos públicamente solo porque escuchan localmente por defecto.

En un servidor que usa UFW, permita la ruta SSH requerida antes habilitando reglas restrictivas.

Los detalles profundos de firewall/endurecimiento pertenecen a lista de comprobación de seguridad de un VPS.

Tareas cron, colas y procesos de trabajo

Los sitios web dinámicos a menudo fallan después de la implementación porque solo se configuró la ruta de solicitud web.

Inventario:

  • tareas cron;
  • procesos que consumen las colas;
  • acciones programadas;
  • importaciones/exportaciones;
  • Trabajos de correo electrónico;
  • tareas que preparan o llenan la caché;
  • procesos en segundo plano.

Configúralos para:

  • ejecutar como el usuario no root correcto;
  • iniciar automáticamente cuando sea necesario;
  • escribir en registros conocidos;
  • evitar la superposición de formas que agotan la CPU / RAM;
  • volver a ejecutarse después de reiniciar el servidor.

Registros y observabilidad básica

Antes del tráfico de producción, sepa dónde buscar cuando el sitio falla.

Como mínimo identificar:

  • Registro de acceso de Nginx/Apache;
  • Registro de errores de Nginx/Apache;
  • registro de aplicaciones;
  • PHP-FPM/registro de entorno de ejecución;
  • registro/estado de la base de datos;
  • diario del sistema;
  • uso del disco;
  • presión de memoria/CPU.

Agregue una comprobación de disponibilidad HTTP(S) externa para que un fallo del servidor sea visible incluso cuando nadie haya iniciado sesión en el VPS.

El diseño profundo del umbral/alerta pertenece a monitorización de un VPS.

Validación tras reiniciar

Una sorprendente cantidad de primeras implementaciones de VPS funcionan hasta el primer reinicio.

Antes de llamar al servidor listo:

sudo reboot

Después de que regrese, confirme:

  • Acceso SSH;
  • Nginx/Apache;
  • PHP-FPM o servicio de aplicaciones;
  • base de datos;
  • tareas cron y procesos de las colas;
  • HTTPS;
  • páginas/formularios del sitio web;
  • monitorización;
  • programación de las copias de seguridad.

Si la aplicación solo regresa después de que alguien inicie manualmente un comando, la implementación no está completa.

Cuando el alojamiento manual / sin panel es el ajuste incorrecto

Utilice un panel de control o administración contratada en su lugar cuando:

  • nadie se siente cómodo con SSH y la recuperación de la línea de comandos;
  • nadie se encarga de actualizaciones de sistema operativo / seguridad;
  • nadie puede diagnosticar fallos de servidor web/entorno de ejecución/base de datos;
  • Se crean copias de seguridad, pero nadie puede restaurarlas.
  • El tiempo de inactividad crítico para el negocio no tiene responsable de incidente;
  • el equipo quiere correo electrónico / usuarios / dominios administrados a través de una interfaz de usuario de alojamiento en lugar de la configuración del servidor;
  • La pila de aplicaciones está mejor servida por una plataforma administrada.

Un VPS manual puede reducir la sobrecarga del panel y maximizar el control, pero no reduce la cantidad de responsabilidad operativa.

Utilice VPS con Panel de control para la selección del panel o VPS administrado vs no administrado cuando la pieza faltante sea responsabilidad operativa.

Copias de seguridad y supervisión del traspaso

Esta página solo establece el traspaso mínimo.

Antes de confiar en el sitio:

  • programar copias de seguridad;
  • mantener una copia independiente/fuera del servidor;
  • incluir la base de datos y la configuración/secretos necesarios para la recuperación;
  • verificar la capacidad de restauración;
  • supervisar la disponibilidad del sitio web;
  • monitorizar el crecimiento del disco;
  • ver la presión de CPU/RAM/base de datos;
  • ver la renovación del certificado.

El diseño de recuperación más profundo pertenece a estrategia de copias de seguridad para un VPS. Los umbrales de monitorización y el diseño de alerta pertenecen a monitorización de un VPS.

Múltiples sitios web

Para varios sitios:

  • usar un bloque de servidor / host virtual separado por nombre de host;
  • raíces de documentos separadas;
  • utilizar credenciales separadas de aplicaciones/bases de datos;
  • utilizar usuarios del sistema separados cuando el modelo de confianza lo requiera;
  • evita que las tareas cron, importaciones o copias de un sitio dejen a los demás sin recursos;
  • calcula el pico de carga conjunto;
  • entienda que todos los sitios aún comparten un dominio de falla de VPS.

Utilice VPS para múltiples sitios web para la planificación de capacidad y aislamiento.

Preguntas frecuentes

¿Puedo alojar un sitio web en un VPS sin un panel de control?

Sí. Un VPS Linux sin panel puede alojar una web mediante SSH y los servicios web, entornos de ejecución y bases de datos que necesite la aplicación. Esta guía incluye esa opción.

¿Necesito Nginx para alojar un sitio web en VPS?

No. Nginx y Apache son opciones comunes. Utilice el servidor web que se ajuste a la aplicación, la configuración y la experiencia del administrador.

¿Todos los sitios web de VPS necesitan una base de datos?

No. Los sitios web estáticos no necesitan uno. Instale MySQL/MariaDB/PostgreSQL solo cuando la aplicación requiera una base de datos.

¿Debo usar root para alojar el sitio web?

No. Root es para administración. Ejecutar / implementar el sitio web bajo usuarios y servicios apropiados que no sean root con solo los permisos que necesitan.

¿Cuándo debo usar un panel de control?

Use uno cuando la administración basada en el navegador de sitios, dominios, PHP, bases de datos, usuarios, correo electrónico o copias de seguridad elimine suficiente administración repetitiva para justificar el consumo y las restricciones de recursos adicionales.

¿Puedo alojar WordPress en un VPS sin cPanel?

Sí. WordPress necesita un servidor web compatible, PHP, una base de datos, los archivos de WordPress, permisos correctos, DNS y HTTPS. Un panel es opcional.

¿Cuándo debo dirigir el DNS al VPS?

Para un nuevo sitio, una vez que el servidor esté listo para responder al nombre de host real. Para un sitio de producción existente, pruebe primero y use un plan de conmutación de migración/migración controlado.

¿Por qué mi dominio apunta al VPS pero muestra el sitio equivocado?

El DNS solo envía el nombre de host a la IP del servidor. Nginx/Apache también debe tener un bloque de servidor / host virtual coincidente para ese nombre de host.

¿Cuándo debo habilitar HTTPS?

Después de que el nombre de host público se resuelva en el servidor y la ruta de validación funcione, emita el certificado, verifique la cobertura root/www y configure el redireccionamiento HTTP a HTTPS deseado.

¿Qué debo comprobar después de reiniciar el VPS?

Confirme el servidor web, el servicio de aplicaciones / PHP-FPM, la base de datos, los procesos, HTTPS, la monitorización y el sitio web, todos regresan sin intervención manual.
