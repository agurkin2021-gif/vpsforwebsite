Cómo elegir la ubicación de un VPS

Elige la ubicación de tu VPS según la audiencia, las rutas de red, el tráfico dinámico, las dependencias, la CDN y los requisitos de ubicación de los datos. Incluye pruebas y una lista de comprobación.

La mejor ubicación de un VPS no tiene por qué ser el país más cercano a ti. Elige la región según los usuarios y sistemas que intercambian con el servidor tráfico sensible a la latencia y comprueba las rutas de red reales antes de contratar.

Para la mayoría de los sitios web, comience cerca de la audiencia más grande o valiosa. Luego revise el enrutamiento, el tráfico dinámico, las dependencias de la base de datos / API, el comportamiento de CDN y cualquier requisito real de ubicación de datos.

Para la decisión más amplia de VPS, véase VPS para el sitio web.

Respuesta rápida

Utilice este orden:

  1. Encontrar los usuarios importantes. Mapa de dónde provienen realmente los clientes de pago, los usuarios conectados y el tráfico en horas punta.
  2. Identificar la dependencia importante. La base de datos, la API privada o el servicio upstream pueden importar tanto como el navegador.
  3. Preselecciona regiones cercanas. La geografía te permite identificar opciones, pero no da la respuesta definitiva.
  4. Prueba rutas reales. Compara la latencia, la estabilidad de ruta y la pérdida de paquetes de redes representativas.
  5. Separar el tráfico de CDN del tráfico de origen. Los activos almacenados en caché pueden moverse al borde; las solicitudes dinámicas aún alcanzan el origen.
  6. Aplicar restricciones de ubicación de datos. Los requisitos legales, contractuales u organizativos pueden anular la opción de latencia más baja.
  7. Seleccione los recursos por separado. La ubicación no reemplaza el tamaño de CPU/RAM/almacenamiento.

No hay un “mejor país VPS” universal. La mejor ubicación es específica para la carga de trabajo.

Evaluador de ubicación del VPS

Utilice la evaluación para identificar el patrón de decisión correcto antes de comparar proveedores. No predice una latencia garantizada ni selecciona una ubicación específica del proveedor.

Utilice datos reales de la audiencia y la ruta; no seleccione una región solo de un mapa.

Comience con la audiencia

La primera pregunta no es “¿Dónde estoy?” Es:

¿Dónde están las personas que deben esperar este servidor?

Para un sitio web público, eso generalmente significa visitantes y clientes. Para una aplicación interna, puede significar empleados. Para una API, puede ser otro sistema en lugar de un navegador humano.

Una primera lista de favoritos sensata es la región cerca de la mayor concentración de tráfico sensible a la latencia.

No alojes automáticamente cerca de:

  • el responsable del sitio;
  • el desarrollador;
  • la dirección de facturación;
  • el registrador de dominios;
  • la sede de la empresa.

Esas ubicaciones importan solo si también representan el tráfico importante.

Pondera el tráfico según su importancia para el negocio

El número total de visitantes, por sí solo, puede resultar engañoso.

Suponga:

  • el 60% de las visitas corresponde a lectores anónimos del blog de un continente;
  • el 30% corresponde a clientes de pago que acceden desde otra región;
  • El 10% es personal interno.

Si el blog está muy almacenado en caché, pero los clientes golpean repetidamente los puntos finales de cuenta dinámica, pago o API, la región del cliente más pequeña puede ser más importante para la ubicación del origen.

Los pesos útiles de la audiencia incluyen:

  • usuarios que generan ingresos;
  • sesiones iniciadas;
  • Pago/tráfico de cuenta;
  • usuarios de soporte/admin;
  • simultaneidad en horas pico;
  • volumen de solicitud de API;
  • países o ciudades críticos para el negocio.

Usa las estadísticas de visitas y los registros del servidor para identificar de dónde procede el tráfico sensible a la latencia del servidor de origen, en lugar de considerar solo el total de páginas vistas.

La ubicación importa más a medida que las solicitudes se vuelven más dinámicas

Una página estática a menudo se puede almacenar en caché cerca de los usuarios. Una solicitud dinámica generalmente tiene que llegar al origen, ejecutar la lógica de la aplicación, consultar una base de datos y devolver.

Eso hace que la ubicación sea más importante para:

  • Carrito de WooCommerce y pago;
  • cuentas/páginas de inicio de sesión;
  • paneles de administración;
  • APIs;
  • cuadros de mando;
  • buscar/filtrar puntos finales;
  • solicitudes de WordPress no almacenadas en caché;
  • Webhooks que requieren una respuesta rápida;
  • aplicaciones con muchos viajes de ida y vuelta secuenciales del servidor.

Para una tienda, consulte VPS para WooCommerce para la carga de trabajo del lado de la aplicación. La ubicación es solo una parte del rendimiento de pago.

La geografía da una lista corta, no el ganador

La distancia física crea un límite inferior en la latencia, pero el tráfico de Internet no viaja en línea recta entre dos pines en un mapa.

El verdadero camino depende de:

  • Enrutamiento ISP;
  • acuerdos de peering;
  • proveedores de tránsito;
  • congestión;
  • trayectorias de cable;
  • fallos de red;
  • Cambios de ruta;
  • cómo el proveedor de VPS se conecta a la red de destino.

Un centro de datos que está geográficamente más cerca todavía puede tener un camino peor a un ISP particular que una región ligeramente más lejana.

Por lo tanto:

Más cerca en el mapa ≠ menor latencia real garantizada

Utilice la geografía para eliminar las opciones obviamente distantes. Utilice las medidas para elegir entre los plausibles.

Pruebe la ruta, no solo el mapa

Pídale a un proveedor una IP de prueba, un archivo de prueba, un espejo u otro punto final actual para cada región candidata. Si no hay ninguno disponible y el compromiso es pequeño, una instancia de corta duración puede ser una prueba más confiable que adivinar.

Prueba de redes que se asemejan a la audiencia real.

Para un sitio web para consumidores, las fuentes de prueba útiles pueden incluir:

  • banda ancha doméstica en el mercado objetivo;
  • redes móviles;
  • las redes de oficinas/empresas, cuando proceda;
  • sondas de monitorización remoto cerca de la audiencia;
  • más de un ISP cuando el mercado es importante.

No pruebe solo desde la computadora portátil del administrador si el administrador está en otro continente.

Compara mediciones repetidas de latencia, no un solo ping

Un solo ping es una evidencia débil.

Usar muestras repetidas:

ping -c 30 TEST_IP

En Windows:

ping -n 30 TEST_IP

Compare candidatos en momentos similares del día.

Busca:

  • RTT típico;
  • coherencia;
  • Picos grandes;
  • pérdida de paquetes de punto final;
  • si el rendimiento cambia en las horas pico.

No hay un número universal de RTT que haga que un VPS sea “bueno”. La comparación útil es entre regiones candidatas para la carga de trabajo real.

Inspeccione la ruta con MTR o traceroute

En Linux, un informe típico de MTR:

mtr -rwzc 50 TEST_IP

Traceroute:

traceroute TEST_IP

Windows:

tracert TEST_IP

MTR/traceroute puede revelar:

  • desvíos geográficos inesperados;
  • tránsito inestable;
  • grandes saltos de latencia;
  • Cambios de ruta;
  • donde un camino parece volverse ineficiente.

No interprete automáticamente la pérdida de paquetes que se muestra en un salto intermedio como pérdida de extremo a extremo. Los enrutadores pueden limitar la velocidad del tráfico de diagnóstico mientras reenvían el tráfico real normalmente. El destino y el comportamiento repetido de extremo a extremo importan más.

Probar HTTP, no solo ICMP

Ping mide el comportamiento de ida y vuelta de la red. Los usuarios experimentan HTTP.

Si existe un punto final de prueba representativo, compare la conexión y el tiempo de respuesta:

curl -o /dev/null -s -w 'connect=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://candidate.example/

Para una aplicación de producción, TTFB también incluye trabajo de origen. Eso es útil después de la implementación, pero significa que no se puede culpar a un TTFB lento solo por la distancia.

Después del lanzamiento, utilice monitorización de un VPS para mantener la latencia externa y el estado de las aplicaciones bajo observación.

Prueba las redes que importan

Una ruta que es excelente de un ISP puede ser mediocre de otro.

Para un mercado importante, pruebe:

  • al menos un ISP de consumo principal;
  • móvil si una gran parte de los usuarios son móviles;
  • rutas corporativas/VPN si la aplicación es B2B;
  • la API ascendente o dependencia real si la latencia de servidor a servidor es importante.

El objetivo no es encontrar una región que gane cada prueba, sino encontrar la región con el mejor compromiso para el tráfico importante.

Mantén cerca las dependencias con intercambios frecuentes

La ruta de usuario a VPS es solo una ruta.

Una solicitud dinámica puede ser como:

navegador → VPS → base de datos → API privada → VPS → navegador

Si el VPS está cerca de los usuarios pero la base de datos está lejos, la aplicación puede pasar más tiempo esperando en la base de datos que en la conexión del navegador.

Mantenga componentes estrechamente acoplados en la misma región o red de baja latencia cuando sea práctico:

  • servidor web/app y base de datos primaria;
  • PHP/procesos de aplicaciones y Redis;
  • aplicación y API privada;
  • servidor de aplicaciones y servicio de archivos/objetos cuando las solicitudes son síncronas y frecuentes.

No divida los componentes entre continentes simplemente porque cada servicio parece más barato en una ubicación diferente.

Si una dependencia externa se fija a una región, mida ambos lados:

  1. usuario → VPS;
  2. VPS → dependencia.

Luego decide qué camino domina la carga de trabajo.

Las API y los servicios de terceros pueden cambiar la mejor ubicación

Para algunas cargas de trabajo, el destino que importa no es el usuario.

Ejemplos:

  • una aplicación que realiza muchas llamadas a una API de región fija;
  • un panel privado utilizado globalmente pero respaldado por una base de datos regional;
  • Automatización que se comunica principalmente con otro servidor.
  • integraciones de pago o inventario con ventanas de respuesta estricta.

Si la aplicación realiza varias llamadas síncronas a la misma dependencia remota para cada solicitud de página, acercar el VPS a los usuarios puede hacer que la ruta del navegador sea más corta al tiempo que hace que la ruta de la aplicación sea más larga.

Mide la transacción completa.

CDN vs ubicación de origen

Una CDN cambia la decisión de ubicación, pero no hace irrelevante la geografía del origen.

Una CDN puede servir archivos almacenables en caché cerca de los usuarios, incluyendo:

  • imágenes;
  • CSS;
  • JavaScript;
  • descargas;
  • HTML en caché donde se configura de forma segura.

Eso puede reducir en gran medida la distancia recorrida para esas solicitudes.

Pero el origen sigue siendo importante para el tráfico como:

  • login;
  • carrito y pago;
  • páginas de cuenta;
  • solicitudes de CMS no almacenadas en caché;
  • HTML personalizado;
  • Llamadas API;
  • solicitudes no resueltas desde la caché;
  • eventos de purga/relleno;
  • tráfico de administración.

Un sitio web global cargado de estática puede tolerar un origen más central si una CDN maneja la mayoría de los bytes orientados al usuario. Un sitio altamente dinámico debería preocuparse mucho más por la ubicación del origen.

Google también describe las CDN como una forma de reducir la latencia al servir contenido desde ubicaciones más cercanas a los usuarios; eso no significa que el origen desaparezca de la arquitectura.

Una CDN no hace que cada región sea equivalente

Dos regiones de origen detrás de la misma CDN todavía pueden producir un rendimiento real diferente.

Las solicitudes dinámicas y las que no se pueden resolver desde la caché llegan al origen. La propia CDN también debe recuperar del origen el contenido actualizado.

Para una audiencia global, prueba:

  • rendimiento de la página en caché;
  • rendimiento de página no cacheada;
  • puntos finales de inicio de sesión/cuenta/API;
  • origen TTFB;
  • comportamiento cuando el contenido no está en la caché.

No seleccione un origen lejano únicamente porque la página de inicio se ve rápido desde el caché.

Audiencia global: ¿un origen + CDN o multirregión?

Una audiencia global no justifica automáticamente múltiples regiones VPS.

Un origen + CDN

Esta suele ser la primera arquitectura más simple cuando:

  • la mayoría del contenido es almacenable en caché;
  • una región contiene la audiencia dinámica más grande o más valiosa;
  • la aplicación/base de datos tiene estado;
  • el equipo operativo es pequeño;
  • Es aceptable una latencia adicional corta para usuarios dinámicos distantes.

Elija el origen en torno al tráfico dinámico y las dependencias más importantes. Utilice la CDN para la entrega distribuida en caché.

Multirregión puede estar justificada

Múltiples regiones de aplicación pueden tener sentido cuando:

  • Los usuarios dinámicos están genuinamente distribuidos;
  • Los presupuestos de latencia son ajustados;
  • La conmutación por error regional es un requisito comercial;
  • la aplicación está diseñada para el estado distribuido;
  • bases de datos/colas/sesiones se pueden replicar de forma segura;
  • El equipo puede operar más de un dominio de falla.

Multirregión introduce complejidad:

  • replicación de datos;
  • coherencia de las escrituras;
  • manejo de sesiones;
  • invalidación de caché;
  • conmutación por fallo;
  • coordinación del despliegue;
  • monitorización;
  • El costo.

No agregue regiones simplemente porque el proveedor las ofrece.

Las audiencias de dos regiones necesitan una decisión ponderada

Si la audiencia está dividida entre dos regiones, hay tres patrones comunes:

ModeloCuando encaja
Origen cerca de la audiencia más grande / más valiosauna región claramente importa más para el tráfico dinámico
Región central + CDNEl tráfico dinámico es moderado y la calidad de la ruta es aceptable para ambos lados.
Aplicación multirregionalEl tráfico dinámico es importante en ambos lados y la aplicación puede manejar el estado distribuido

No elija el punto medio geográfico sin realizar pruebas. El enrutamiento de Internet no garantiza que el punto medio ofrezca el mejor camino para ambos mercados.

Localización física vs geolocalización IP

Una dirección IP puede ser etiquetada por una base de datos de geolocalización de manera diferente a donde se encuentra físicamente el hardware del servidor.

Cuando la colocación física importa, verifique:

  • la ciudad/región del centro de datos declarado por el proveedor;
  • el punto final de servicio real;
  • características de la ruta de red;
  • redacción contractual de la ubicación de los datos cuando sea necesario.

No inferir la ubicación física de un sitio web GeoIP.

GeoIP puede ser importante para aplicaciones, sistemas de fraude o servicios localizados, pero ese es un problema separado de la latencia real de la red.

Jurisdicción y residencia de datos

La ubicación puede ser limitada por algo más que el rendimiento.

Los condicionantes pueden incluir:

  • requisitos contractuales de residencia de datos;
  • datos de clientes regulados;
  • política interna de la empresa;
  • requisitos de contratación del cliente;
  • restricciones al procesamiento o almacenamiento transfronterizos.

Si un requisito es real, primero defina qué regiones son legalmente / contractualmente elegibles. Luego optimice el rendimiento dentro de ese conjunto.

Esta página no proporciona asesoramiento legal. Para datos regulados o restringidos contractualmente, confirme el requisito con una guía legal / de cumplimiento calificada y la documentación contractual actual del proveedor.

¿La ubicación de VPS afecta el SEO?

No elija un país VPS porque alguien promete un aumento de clasificación directo.

La guía actual de Google dice que la ubicación del servidor puede ser una señal sobre la audiencia prevista de un sitio, pero no es definitiva , especialmente porque los sitios pueden usar CDN o alojar en países con mejor infraestructura.

Para la orientación regional explícita, Google señala señales como:

  • URLs específicas de localización;
  • hreflang;
  • los dominios con código de país, cuando proceda;
  • Estructura explícita del sitio regional/idioma.

Por lo tanto:

Elige la ubicación del VPS principalmente según los usuarios, las rutas de red, las dependencias y los requisitos operativos y de datos; no como un atajo de SEO.

Para un sitio global, una arquitectura rápida y confiable además de una correcta orientación internacional es más defendible que mover el origen únicamente para perseguir las clasificaciones.

Ubicación y tamaño de los recursos son decisiones separadas

Un servidor más cercano no compensa la insuficiencia de CPU, RAM o almacenamiento.

Un VPS más grande no elimina la distancia de red.

Trátelos como dos preguntas diferentes:

  1. ¿Dónde debe estar el servidor? → esta página.
  2. ¿Cuántos recursos necesita el servidor? → Cómo dimensionar un VPS para tu sitio web.

Un servidor mal dimensionado en la ciudad perfecta todavía puede ser lento. Un servidor poderoso en la ruta de red incorrecta aún puede sentirse lento para los usuarios.

Ubicación y múltiples sitios web

Un VPS multisitio puede tener varias audiencias.

Si todos los sitios sirven a un mercado, la ubicación es sencilla.

Si los sitios de clientes se dirigen a diferentes continentes, un solo VPS crea un compromiso: todos los sitios web comparten una región de origen incluso si sus audiencias difieren.

Para carteras mixtas, clasifique los sitios por:

  • geografía de la audiencia;
  • tráfico dinámico;
  • importancia del negocio;
  • Restricciones de cumplimiento.

Si un sitio tiene un requisito de ubicación materialmente diferente, puede merecer un VPS separado en lugar de forzar cada sitio a una región.

Utilice VPS para múltiples sitios web para la decisión de consolidación/aislamiento.

También importan los ámbitos de fallo

La región más rápida para producción no tiene por qué albergar todas las copias y los sistemas auxiliares.

Dependiendo del riesgo del negocio, considere separar las dependencias críticas de recuperación/monitorización del mismo dominio de fallas:

  • copias de seguridad fuera del servidor;
  • verificaciones externas dla disponibilidad;
  • notificaciones de incidentes;
  • Copias secundarias.

El objetivo no es “poner todo muy lejos”. Es evitar que un fallo regional/proveedor/red inhabilite tanto la producción como los sistemas necesarios para detectarla o recuperarse de ella.

Utilice estrategia de copias de seguridad para un VPS para el diseño de recuperación y monitorización de un VPS para verificaciones de disponibilidad independientes.

¿Y si eliges el lugar equivocado?

Cambiar de región más tarde puede ser simple o perjudicial dependiendo del proveedor y la aplicación.

Las posibles consecuencias incluyen:

  • crear un VPS de sustitución;
  • copiar archivos y bases de datos;
  • recibir una nueva dirección IP;
  • cambiar el DNS;
  • actualizar las listas de permisos de firewall/IP;
  • cambiar la configuración de origen de CDN;
  • actualizar los destinos de webhook o las IP de confianza;
  • validación de TLS e integraciones externas;
  • planificación de una ventana de conmutación de migración.

Es por eso que probar las ubicaciones de los candidatos antes de la producción es más barato que tratar la selección de la región como un menú desplegable cosmético.

Para el proceso de conmutación de migración real, use Migración del sitio web a VPS.

Un flujo de trabajo práctico de selección de regiones

1. Identifica el tráfico sensible a la latencia del origen

Registro:

  • los principales países/ciudades;
  • concentración geográfica de los clientes de pago;
  • tráfico con sesión iniciada;
  • ubicación de la hora pico;
  • Consumidores API.

2. Identifica las dependencias

Registra con qué servicios se comunica la aplicación de forma síncrona:

  • base de datos;
  • Redis/caché;
  • servicio de objetos/archivos;
  • pago/API;
  • sistemas internos;
  • SaaS externo.

3. Aplica los requisitos obligatorios de ubicación

Eliminar cualquier ubicación que viole un requisito real de política contractual, legal o interna.

4. Regiones plausibles preseleccionadas

Utilice la geografía solo para crear la lista corta.

5. Prueba de redes representativas

Compare latencia repetida y calidad de ruta. Si es posible, incluya más de un ISP importante.

6. Pruebe el comportamiento dinámico de la aplicación

No juzgues solo el tiempo de carga de la página principal en caché.

7. Elija la arquitectura más simple que satisfaga el requisito

Prefiere un origen bien elegido + CDN hasta que las mediciones o los requisitos comerciales justifiquen una mayor complejidad.

8. Monitoriza después del lanzamiento

Comprueba la latencia real desde el exterior, el TTFB, los errores y el funcionamiento que perciben los usuarios. Una prueba previa a la compra aporta datos, pero no es una garantía permanente.

Preguntas frecuentes

¿Qué ubicación de VPS debo elegir?

Comience con la región cerca de la audiencia más grande o más valiosa sensible a la latencia, luego verifique el enrutamiento real desde redes representativas. También tenga en cuenta las dependencias de base de datos / API y cualquier requisito de ubicación de datos duros.

¿Debo elegir la ubicación de VPS más cercana a mí?

Solo si tú también eres el usuario principal. La ubicación de un sitio público debe elegirse normalmente según sus visitantes, clientes y dependencias críticas, no según dónde esté el administrador.

¿El centro de datos más cercano es siempre el más rápido?

No. La distancia física es importante, pero el peering y el enrutamiento pueden hacer que una región ligeramente más lejana funcione mejor para un ISP específico. Prueba la ruta real.

¿Cómo puedo probar una ubicación VPS antes de comprar?

Utilice IPs de prueba de proveedores, archivos de prueba, un espejo o una instancia de corta duración. Compare ping / RTT repetido, MTR / traceroute y, cuando sea posible, el tiempo HTTP de redes representativas de sus usuarios.

¿Una CDN hace que la ubicación de VPS sea irrelevante?

No. Una CDN puede servir contenido apto para caché cerca de los usuarios, pero las solicitudes dinámicas, el inicio de sesión, los pagos, las API, las solicitudes no resueltas desde la caché y la recuperación de contenido siguen dependiendo del origen.

¿Dónde debería alojar un sitio web global su VPS?

A menudo, un origen cerca de la audiencia dinámica más grande / más valiosa más una CDN es el punto de partida más simple. La multirregión solo se justifica cuando la latencia dinámica, los requisitos de resiliencia y la arquitectura de aplicaciones admiten la complejidad adicional.

¿Debería el VPS estar cerca de la base de datos?

En una aplicación dinámica que intercambia datos con frecuencia, normalmente sí. Los viajes de ida y vuelta repetidos entre la aplicación y una base de datos en otra región pueden dominar el tiempo de respuesta, aunque el VPS esté cerca de los usuarios.

¿La ubicación del servidor VPS mejora el ranking de Google?

No lo trates como un atajo de clasificación directa. Google dice que la ubicación del servidor puede ser una señal de configuración regional, pero no es definitiva. Usa orientación internacional explícita, como URL específicas de la configuración regional y hreflang donde sea relevante.

¿Es la geolocalización IP lo mismo que la ubicación física del servidor?

No. Las bases de datos GeoIP pueden etiquetar una dirección de manera diferente a la ubicación real del centro de datos. Verifique la ubicación física por separado cuando sea importante.

¿Puedo moverme a otra región de VPS más tarde?

Por lo general, pero el proceso puede requerir un nuevo VPS o IP, migración de datos, cambios DNS, actualizaciones de lista de permisos / CDN y un cambio de servidor.Prueba antes de la producción para reducir la posibilidad de un movimiento posterior.
