Plan de migración rápida

Un movimiento controlado sigue este orden:

  1. Inventario de la fuente. Grabar la aplicación, entorno de ejecución, base de datos, archivos, DNS, correo electrónico, tareas cron, procesos, webhooks y dependencias externas.
  2. Dimensiona el destino. Elige CPU, RAM y disco de entre la carga de trabajo real y el margen de recursos de migración.
  3. Crea una copia de seguridad recuperable. Guarda una copia fuera del servidor de origen y verifica que la base de datos y los archivos que necesitas estén realmente presentes.
  4. Construye el VPS en paralelo. Instala el entorno de software web o el panel de control y cumple con los requisitos de la aplicación antes de que se mueva el tráfico.
  5. Copiar el primer conjunto de datos completo. Transferir archivos e importar la base de datos mientras el antiguo sitio permanece activo.
  6. Prueba privadamente. Usa una entrada local en el archivo hosts, un nombre de host de vista previa controlada o un método equivalente para ejercer el nuevo servidor antes de que cambie el DNS.
  7. Controla las escrituras finales. Para tiendas, membresías, formularios y otros sitios cambiantes, planifica una congelación de escritura corta o una sincronización delta final apropiada para la aplicación.
  8. Cambiar DNS por último. Cambie solo los registros que necesitan moverse y mantenga intactos los registros de correo electrónico/verificación.
  9. Monitorizar ambos servidores. Verificar tráfico, errores, formularios, pedidos, tareas cron, webhooks, correo electrónico, HTTPS y rastreo de búsqueda.
  10. Retire el antiguo host solo después de aceptarlo. Manténgalo disponible a través de la ventana de reversión.

No se puede prometer cero interrupciones para cualquier migración. El objetivo es un cambio controlado, con la menor interrupción posible y sin pérdidas de datos imprevistas.

Comprobación previa al cambio de servidor

Utilice esta evaluación antes de cambiar DNS. No garantiza una migración exitosa; expone los requisitos previos faltantes que deben resolverse primero.

Marque los elementos que están realmente listos.

Inventario del sitio web actual

Cree un registro de migración antes de tocar el destino.

Registro:

  • dominio y cada subdominio activo;
  • versión de aplicación/CMS/framework;
  • PHP, Node.js, Python u otra versión en entorno de ejecución;
  • motor/versión de base de datos, tamaño y modelo de credenciales;
  • directorio raíz del sitio y directorios externos a él;
  • archivos subidos, contenido multimedia y directorios con permiso de escritura;
  • reglas de redirección y reescritura;
  • cron trabajos, colas, procesos y tareas programadas;
  • servicios de almacenamiento en caché como Redis donde se utilizan;
  • Configuración SSL/TLS;
  • Registros DNS;
  • buzones, reenviadores y ruta SMTP de salida;
  • pasarelas de pago, webhooks y devolución de llamadas API;
  • listas de IP de terceros;
  • CDN/WAF/restricciones de origen;
  • verificaciones de Search Console y de analítica;
  • uso y crecimiento actuales del almacenamiento.

El inventario también es la lista de verificación de aceptación después del traslado: cada elemento debe funcionar en el VPS o dejarse deliberadamente en un servicio externo.

Dimensionar y preparar el VPS de destino

No migre primero y pregunte si el VPS es lo suficientemente grande después.

Elige el destino según la carga actual, la base de datos, el crecimiento del almacenamiento, el consumo adicional del panel y el correo y el espacio necesario durante la migración. El traslado puede requerir disco temporal para archivos comprimidos, volcados, registros y preparación local de copias.

Consulta cómo dimensionar un VPS para tu sitio web para realizar el cálculo de recursos.

Una migración también es una decisión de ruta de administración. Si el antiguo host ocultó la mayor parte de la administración del servidor, primero decida quién operará el destino después del cambio de servidor: compare VPS administrado o no administrado. Luego decida si el destino usará un panel de control o un entorno de software Linux administrado manualmente; vea VPS con Panel de control para esa opción.

Crear una copia de seguridad con capacidad de reversión

Una copia de seguridad solo es útil si contiene los datos que necesita y se puede restaurar.

Antes de la migración:

  1. crear una nueva copia de los archivos del sitio web;
  2. exportar todas las bases de datos requeridas;
  3. almacenar una copia fuera de la cuenta de alojamiento de origen;
  4. grabar archivos de configuración y variables de entorno de forma segura;
  5. registrar los registros de DNS y correo electrónico por separado;
  6. restaurar la copia de seguridad en un entorno desechable / de prueba donde sea práctico, o como mínimo realizar una importación de base de datos real y verificar archivos representativos en lugar de solo verificar que se abre el archivo;
  7. confirmar que la copia restaurada contiene los datos esperados y puede ponerse en marcha lo suficiente como para permitir la reversión;
  8. Anote la secuencia de reversión antes de cambiar el DNS.

Para un sitio dinámico, la primera copia de seguridad no es el conjunto de datos de producción final. Los pedidos, envíos de formularios, comentarios, membresías o archivos subidos pueden seguir cambiando después de la primera copia. Planifique el delta final por separado.

Cree el destino antes de que cambie el DNS

El destino debe ser capaz de ejecutar el sitio antes de que llegue el tráfico público.

Reproduce o valida expresamente:

  • comportamiento del servidor web;
  • Versión PHP/Nodo/Python;
  • extensiones/módulos requeridos;
  • motor/versión de la base de datos;
  • propiedad de archivos y permisos;
  • límites de carga/tamaño del cuerpo;
  • entorno de las tareas programadas;
  • servicios de caché;
  • reglas de reescritura/redirección;
  • variables de entorno y credenciales;
  • Necesidades de redes SMTP/salientes;
  • reglas del cortafuegos;
  • rutas específicas de la aplicación.

No utilice la migración en sí como el momento para actualizar cada entorno de ejecución o reescribir el entorno de software a menos que se requiera ese cambio. Menos cambios simultáneos facilitan la reversión al estado anterior y el diagnóstico.

Copiar archivos y bases de datos

El método de transferencia exacto depende del acceso a la fuente.

Las rutas de origen típicas incluyen:

  • cPanel / Administrador de archivos + exportaciones de phpMyAdmin;
  • SFTP/FTP cuando el acceso al shell no está disponible;
  • SSH/rsync cuando ambos lados lo permiten;
  • herramientas de migración adaptadas a la aplicación para traslados específicos del CMS;
  • herramientas de exportación o copia del proveedor.

Conserva los archivos de configuración ocultos, como las reglas de reescritura que necesite la aplicación. Después de importar, verifica el usuario de la base de datos, sus permisos, el juego de caracteres, la intercalación y la configuración de conexión.

Para conjuntos de datos grandes, compare tamaños, recuentos de filas o sumas de comprobación donde sea práctico en lugar de suponer que "transferencia completada" significa que "el conjunto de datos es idéntico".

Pruebe de forma privada antes del cambio de servidor

No apunte DNS a un servidor no probado.

Pruebe el destino con una entrada local en el archivo hosts, un nombre de host de vista previa controlada u otro método privado que ejercite el entorno de software de aplicación real.

Compruebe:

  • página de inicio y páginas internas representativas;
  • admin inicio de sesión;
  • inicio de sesión del usuario;
  • imágenes, CSS, JavaScript y descargas;
  • búsqueda;
  • formularios y entrega de sus mensajes;
  • subidas;
  • redirecciona;
  • Endpoints API;
  • proceso de compra y notificaciones de las pasarelas de pago;
  • cron/acciones programadas;
  • colas/procesos;
  • correo electrónico saliente;
  • registros de aplicaciones, servidores web y bases de datos;
  • Diseño móvil y navegación.

Un nombre de host público temporal no debe convertirse en un duplicado accidental en la búsqueda. Si se puede acceder públicamente durante las pruebas, manténgalo fuera del índice y elimine el bloqueo temporal del nombre de host de producción real antes del cambio de servidor.

Controla las nuevas escrituras y la sincronización final

Esta es la diferencia principal entre un sitio informativo y uno transaccional.

Si las bases de datos antigua y nueva aceptan escrituras durante la transición de DNS, pueden divergir. Un pedido guardado en el servidor anterior no aparecerá automáticamente en el nuevo.

Para sitios cuyos datos cambian:

  1. elegir una ventana de conmutación de migración de bajo riesgo;
  2. pausa o controla las nuevas escrituras en el origen cuando sea posible;
  3. detener o controlar tareas cron y procesos de cola que podrían escribir datos dos veces;
  4. ejecutar la sincronización final de la base de datos y copiar archivos subidos/archivos modificados;
  5. registra el momento final en que los datos del origen se toman como referencia;
  6. cambiar el tráfico;
  7. verifique que las nuevas escrituras ahora aterrizan solo en el destino.

En VPS para WooCommerce, incluye en las pruebas de aceptación el proceso de compra, los pedidos, los webhooks de pago, el inventario, las acciones programadas y el correo transaccional. Un sitio estático o servido desde caché puede necesitar únicamente una comparación final de archivos.

No llame a una migración “cero tiempo de inactividad” a menos que la aplicación y el método de sincronización realmente lo soporten.

Cambiar DNS deliberadamente

DNS es el conmutador de tráfico, no el primer paso de migración.

Antes del cambio de servidor:

  • exportar o registrar la zona actual;
  • identificar exactamente qué registros de A/AAAA/CNAME/origen deben cambiar;
  • cuando sea posible, reduce el TTL de los registros afectados con una antelación mínima equivalente al TTL anterior completo; por ejemplo, si es de 86,400 segundos, redúcelo más de 24 horas antes del cambio;
  • recuerde que la reducción de TTL ahora no borra cachés que ya almacenaban el TTL más antiguo y más largo;
  • preservar registros MX, SPF, DKIM, DMARC, TXT de verificación, SRV, CAA y otros que no se estén moviendo;
  • Verificar el comportamiento root y www.

Cambiar un registro A/AAAA es generalmente de menor riesgo que reemplazar servidores de nombres cuando el proveedor DNS en sí no cambia. Si los servidores de nombres cambian, recree primero la zona completa requerida.

Después del cambio, verifique el DNS público de más de un resolutor/red y observe cómo el tráfico se mueve del servidor antiguo al nuevo.

Evita interrumpir el correo electrónico

La migración de sitios web y la migración de correo electrónico son trabajos separados, incluso cuando la antigua cuenta de alojamiento compartido los incluía.

Elija una ruta antes del cambio de servidor:

  • mantener el correo electrónico con el proveedor actual / administrado y preservar los registros MX / TXT existentes;
  • mover el correo electrónico a otro proveedor administrado;
  • mover el correo electrónico al VPS y reconstruir buzones, enrutamiento, autenticación y controles de entregabilidad.

Si el correo electrónico se mueve, ten en cuenta:

  • Prioridades MX;
  • SPF;
  • DKIM;
  • DMARC;
  • DNS/PTR inversos, cuando proceda;
  • datos de buzón;
  • alias/enviadores;
  • Credenciales SMTP;
  • filtrado de spam;
  • copias de seguridad y reputación del remitente.

No reemplace una zona DNS completa solo para mover el sitio web a menos que se reproduzcan los registros de correo electrónico y todas las demás dependencias.

Verificar HTTPS, CDN y servicios externos

Si aún no has elegido la región de destino, resuélvelo antes del traslado con cómo elegir la ubicación de un VPS. Cambiar de región después puede exigir otra migración de IP y DNS.

Un destino que funciona por IP todavía puede fallar bajo el nombre de host real.

Verificar:

  • El certificado TLS cubre los nombres de host requeridos;
  • la redirección de HTTP a HTTPS es correcta;
  • se conserva la dirección canónica, con o sin www;
  • Se entienden los supuestos HSTS;
  • CDN/WAF señala o permite el nuevo origen;
  • se sigue identificando correctamente la IP real del cliente cuando se utiliza un proxy;
  • los webhooks de pago llegan al nuevo origen;
  • se actualizan las listas de IP permitidas de las API que autorizaban la dirección anterior;
  • Las credenciales SMTP/API son válidas desde el nuevo servidor.

Mantenga las excepciones temporales de cortafuegos / WAF estrechas y retírelas después de la aceptación.

Preservar el SEO cuando las URL permanecen iguales

Un cambio exclusivo de alojamiento suele conservar las URL públicas. En ese caso, el trabajo de SEO consiste sobre todo en mantener un comportamiento equivalente, no en crear un mapa de redirecciones.

Compara antes y después del cambio:

  • Códigos de estado HTTP;
  • URL canónicas;
  • robots.txt;
  • meta robots / noindex accidental;
  • URL de mapa del sitio;
  • enlaces internos;
  • datos estructurados cuando sea importante;
  • contenido de las páginas y recursos que se cargan;
  • Verificación de Search Console;
  • Respuestas del servidor a Googlebot y usuarios normales.

Google Search Central recomienda preparar y probar el nuevo alojamiento, cambiar DNS solo cuando esté listo, monitorizar tanto el alojamiento antiguo como el nuevo y retirar la infraestructura antigua después de que el tráfico se haya movido. También recomienda reducir el DNS TTL por adelantado y mantener la verificación de Search Console funcionando.

Si solo cambia la infraestructura de alojamiento y el dominio / URL permanece igual, no use la herramienta Cambio de dirección de Google Search Console . Esa herramienta es para movimientos de dominio, no una migración de alojamiento de la misma URL.

Si las rutas de dominio o URL también cambian, use un mapa de URL antiguo a nuevo y redirecciones permanentes del lado del servidor. Ese es un problema de movimiento de sitio diferente de una migración VPS de la misma URL.

Aceptación y reversión post-migración

Después de los cambios de DNS:

  • supervisar los registros de acceso/error en servidores antiguos y nuevos;
  • confirmar que la nueva actividad del usuario está llegando a la base de datos de destino;
  • formularios de prueba, pago, inicios de sesión y archivos subidos nuevamente;
  • verificar cron, colas y acciones programadas;
  • verificar el correo electrónico saliente y el enrutamiento de correo electrónico entrante si es relevante;
  • ver el comportamiento de la CPU, RAM, disco y base de datos;
  • confirmar el comportamiento HTTPS y CDN/WAF;
  • comprobar URLs importantes para 200/paridad redirigida;
  • monitorizar las señales de rastreo/indexación de Search Console;
  • mantener el viejo entorno disponible a través de la ventana de estabilidad acordada.

La reversión tiene un límite de datos

Al principio puede bastar con devolver el DNS al servidor anterior, pero solo mientras sus datos sigan siendo una referencia válida.

Una vez que los pedidos, registros, comentarios o archivos subidos se escriben en el nuevo servidor, una reversión solo de DNS al estado anterior puede perder esos nuevos cambios. En ese punto, la reversión al estado anterior requiere reconciliación de datos u otra sincronización planificada.

Definir los desencadenadores de reversión antes de la migración, por ejemplo:

  • errores 5xx generalizados;
  • proceso de pago/fallo de pago;
  • corrupción de bases de datos o escrituras faltantes;
  • Incompatibilidad severa en entorno de ejecución;
  • autenticación rota;
  • fallo crítico de correo o webhook que no pueda corregirse dentro del plazo acordado.

Preguntas frecuentes

¿Puedo migrar un sitio web a un VPS sin cambiar el dominio?

Sí. Una migración de alojamiento puede mantener el mismo dominio y las URL públicas. Cree y pruebe primero el destino, luego cambie los registros DNS para enviar tráfico al nuevo servidor.

¿Necesito redirecciones 301 al mover un sitio web a un VPS?

No si las URL públicas siguen siendo las mismas. Las redirecciones son necesarias cuando cambia el dominio, el protocolo, la ruta o la estructura del contenido.

¿Cómo puedo reducir el tiempo de inactividad durante una migración de VPS?

Prepare el destino en paralelo, baje el TTL DNS relevante por adelantado, pruebe de forma privada, controle las escrituras finales, ejecute una sincronización de datos final, cambie el DNS solo después de la aceptación y mantenga el host antiguo disponible durante la propagación.

¿Debo mover el correo electrónico al VPS también?

No necesariamente. Mantener el correo en un servicio administrado puede reducir los riesgos de migración y entrega. Si lo trasladas, planifica aparte MX, SPF, DKIM, DMARC, buzones, DNS inverso cuando corresponda y copias de seguridad.

¿Qué debo probar antes de cambiar el DNS?

Pruebe páginas representativas, inicio de sesión, formularios, archivos subidos, búsqueda, devoluciones de llamada de pago / pago donde sea relevante, tareas programadas, API / webhooks, correo electrónico saliente, HTTPS, redirecciones y registros de aplicaciones / servidores.

¿Cuánto tiempo debo mantener el antiguo hosting después de la migración?

Consérvalo hasta que el tráfico se haya trasladado, el nuevo servidor sea estable, las escrituras se hayan verificado y termine el periodo de reversión acordado. Decide según los registros, no con una cifra universal de horas o días.

¿Puedo migrar WooCommerce sin perder pedidos?

Sí, pero no basta con una única copia antigua de la base de datos. Controla las escrituras durante el cambio y realiza una sincronización final adaptada a la aplicación, para que los pedidos y cambios de inventario no queden repartidos entre dos bases de datos que aceptan escrituras.

¿Cambiar de alojamiento perjudica al SEO?

Un mismo cambio de alojamiento de URL debe preservar las señales de búsqueda del sitio cuando el destino sirve el mismo contenido, códigos de estado, canónicos y rastreabilidad.Monitorizar Search Console y los registros del servidor después del traslado; pueden ocurrir cambios temporales de velocidad de rastreo durante un cambio de infraestructura de alojamiento.
