Monitorización de un VPS

Monitoriza tu VPS con comprobaciones externas, métricas de CPU, RAM, disco y red, registros y alertas útiles. Incluye herramientas, umbrales y una lista de comprobación.

La monitorización de un VPS debe responder a algo más que «¿Está encendido el servidor?». En producción, necesita comprobaciones externas de disponibilidad, historial de métricas del servidor, estado de servicios y aplicaciones, registros, alertas que permitan actuar y un responsable de respuesta identificado.

Un VPS puede responder a ping mientras Nginx está roto, la base de datos está estancada, el disco está lleno o el certificado TLS está a punto de expirar. Por lo tanto, la supervisión debe cubrir tanto el servidor como el sitio web orientado al usuario.

Para la decisión más amplia del servidor, véase VPS para el sitio web.

No ejecute el único monitor de disponibilidad en el mismo VPS que se supone que debe ver. Si ese VPS o su ruta de red fallan por completo, el monitor puede desaparecer con él.

Evaluador de monitorización básica del VPS

Utilice este comprobador para encontrar puntos ciegos. No garantiza la disponibilidad.

Marque solo la monitorización que realmente está recopilando datos y entregando alertas.

Monitorizar el sitio web desde fuera del VPS

Un comando interno puede decirle que Nginx se está ejecutando. No puede probar que un usuario real en Internet pueda llegar al sitio web.

Utilice un monitor externo para nombres de host importantes.

Los controles útiles incluyen:

  • Disponibilidad HTTP/HTTPS;
  • código de estado esperado;
  • tiempo de respuesta;
  • comprobación de palabras clave/contenido;
  • Resolución de DNS;
  • Estado/caducidad del certificado TLS;
  • Controles de puerto TCP cuando sea relevante.

Cuando sea importante evitar falsos positivos, exige fallos repetidos o confirmación desde varias ubicaciones antes de avisar al responsable de guardia.

Herramientas de alojamiento propio como Uptime Kuma permiten comprobar HTTP(S), palabras clave, TCP, ping y DNS. Instala el monitor fuera del ámbito de fallo del VPS de producción.

Un servidor de monitorización que comparte el mismo VPS, red de proveedores o falla de DNS puede ser útil para los paneles, pero no es una verificación de disponibilidad independiente.

El diagnóstico en tiempo real no es una monitorización histórica

Comandos tales como:

top
htop
free -h
df -h
ss -s

Son útiles cuando ya está investigando un problema.

Ellos no te dicen:

  • lo que sucedió a las 03:12;
  • si la RAM creció constantemente durante seis horas;
  • si la latencia del disco se disparó durante una copia de seguridad;
  • si el sitio web estuvo inactivo durante diez minutos;
  • Si un problema empeora semana a semana.

Conservar el historial de series temporales para las señales que afectan la disponibilidad y la capacidad.

Para un solo VPS, un agente de monitorización ligero puede ser suficiente. Para una flota o paneles de retención / personalizados más largos, Prometheus + Node Exporter + Grafana es una arquitectura común.

Prometheus Node Exporter expone métricas del servidor y del kernel que Prometheus puede recopilar, incluidos datos de CPU, sistema de archivos y red.

Monitorizar CPU, memoria, disco y red

CPU

No alerte sobre cada pico corto.

Miren:

  • utilización sostenida de la CPU;
  • promedio de carga con respecto al recuento de vCPU;
  • CPU por proceso;
  • tiempo de CPU no disponible para la máquina virtual (steal), si la plataforma lo muestra;
  • latencia de la aplicación y las solicitudes durante ese mismo intervalo.

Una breve ráfaga del 100% durante el calentamiento de la caché o una tarea cron puede ser inofensiva. La saturación sostenida de la CPU más la creciente latencia / colas es una evidencia más fuerte de un verdadero cuello de botella.

Memoria, intercambio y OOM

Linux a menudo usa RAM de repuesto para la caché del sistema de archivos, por lo que "90% de RAM utilizada" no es automáticamente un error.

Miren:

  • memoria disponible;
  • actividad de swap;
  • crecimiento de swaps;
  • Eventos de OOM-killer;
  • crecimiento de la memoria del proceso;
  • Memoria PHP/proceso de aplicaciones;
  • memoria de base de datos.

Una fuga de memoria puede parecer normal al mediodía y matar el proceso durante la noche. Los datos históricos de tendencias son los que lo exponen.

Capacidad de disco

Observe la utilización del sistema de archivos antes de que llegue al punto donde fallan las bases de datos, los registros o las actualizaciones de paquetes.

Como ejemplo inicial, podrías fijar los umbrales de advertencia y estado crítico en el 80% y el 90% de uso. No constituyen un SLA universal: una base de datos que crece deprisa puede exigir actuar mucho antes.

También supervise el espacio de trabajo libre requerido por:

  • copias de seguridad;
  • mantenimiento de la base de datos;
  • actualizaciones del paquete;
  • subidas;
  • logs;
  • entornos de pruebas y tareas de importación.

Inodos

Un sistema de archivos puede quedarse sin inodos mientras que muchos GB permanecen libres.

Esto puede ocurrir con:

  • directorios de caché;
  • sesiones;
  • colas de correo electrónico;
  • un gran número de pequeños archivos;
  • archivos temporales fuera de control.

Rastree el uso de inodo por separado del disco GB.

E/S de disco y latencia

El disco puede convertirse en el cuello de botella antes de que la capacidad esté llena.

Miren:

  • espera de E/S;
  • latencia de lectura/escritura;
  • profundidad de cola cuando esté disponible;
  • tiempo de respuesta de la base de datos;
  • intervalos de ejecución de copias e importaciones.

Una mayor capacidad de disco no corrige automáticamente la E/S de almacenamiento lento.

Red

Rastrea más que el ancho de banda total:

  • rendimiento de entrada/salida;
  • cambios repentinos de tráfico;
  • errores de conexión;
  • pérdida/latencia de paquetes cuando sea medible;
  • tráfico de salida inusual;
  • Errores de interfaz.

Las métricas de red ayudan a separar la lentitud de las aplicaciones de los problemas del proveedor / ruta.

Monitorizar los servicios y la salud de las aplicaciones

Un VPS puede ser accesible mientras el sitio web está roto.

Monitorizar servicios importantes tales como:

  • Nginx/Apache;
  • PHP-FPM;
  • Servicio de aplicación Node/Python;
  • MySQL/MariaDB/PostgreSQL;
  • Redis donde se utiliza;
  • procesos que consumen las colas;
  • servicio de tareas programadas;
  • panel de control donde crítico para el negocio.

En un sistema Linux con systemd, systemctl --failed ayuda durante el diagnóstico. La monitorización continua debe avisar de los fallos o reinicios repetidos de los servicios necesarios.

No se detenga en “el proceso existe”. Un proceso puede estar vivo pero no puede servir solicitudes válidas.

HTTP 200 no siempre es saludable

Una aplicación puede devolver HTTP 200 con:

  • página de mantenimiento;
  • error de base de datos dentro de una plantilla;
  • contenido vacío/incorrecto;
  • flujo de inicio de sesión roto;
  • contenido desactualizado en caché.

Para los sitios críticos, utilice la comprobación útil más estrecha:

  • palabra clave/texto esperado;
  • punto final de salud;
  • Respuesta API;
  • URL pública crítica;
  • inicio de sesión/transacción sintéticos solo cuando el valor del negocio justifica la complejidad.

No haga que los controles sintéticos muten los datos de producción a menos que estén diseñados específicamente para hacerlo de manera segura.

Monitorizar TLS y DNS

El VPS puede estar saludable mientras el sitio web no está disponible debido a un error de certificado o DNS.

Supervisa:

  • vencimiento del certificado;
  • discordancia del nombre de host del certificado;
  • fallida renovación;
  • Resolución de DNS;
  • cambios accidentales de registros donde las herramientas lo soportan.

Un ejemplo útil es advertir mucho antes de la expiración del certificado, como 14 días, luego escalar más cerca de la expiración, como 7 días. La ventana exacta debe coincidir con la rapidez con la que alguien puede reparar la renovación.

Supervisar la base de datos como una dependencia de la aplicación

Para sitios web respaldados por bases de datos, supervise lo suficiente como para saber si la base de datos es el cuello de botella o la dependencia fallida.

Dependiendo del motor/carga de trabajo, las señales útiles incluyen:

  • disponibilidad del servicio;
  • recuento de conexiones;
  • errores de conexión;
  • latencia de consulta;
  • bloqueos/síntomas de contención;
  • actividad de consulta lenta;
  • presión de memoria;
  • crecimiento del almacenamiento;
  • estado de replicación/copia de seguridad donde se utilice.

No avise en todas las métricas de la base de datos. Alerta sobre las condiciones relacionadas con el impacto del usuario o un modo de fallo conocido.

Supervisar cron, colas y tareas en segundo plano

Que la página de inicio responda correctamente no demuestra que las tareas en segundo plano funcionen bien.

Realice un seguimiento de los trabajos que importan a la aplicación:

  • cron;
  • procesos que consumen las colas;
  • importaciones programadas;
  • webhooks;
  • Trabajos de correo electrónico;
  • WP-Cron de WordPress o cron del sistema;
  • Action Scheduler de WooCommerce;
  • suscripciones/renovaciones;
  • Sincronización de inventario.

Señales útiles:

  • última ejecución correcta;
  • longitud de la cola y tareas pendientes;
  • tareas fallidas;
  • el trabajo más antiguo pendiente;
  • reintentos repetidos;
  • proceso detenido/reiniciado.

Para WooCommerce, una creciente cola de Action Scheduler puede ser un problema operativo incluso si las páginas del catálogo aún se cargan.

Supervisa la antigüedad de las copias de seguridad

La tarea de copia forma parte de la estrategia de recuperación, pero la antigüedad de la última copia es una señal de monitorización.

Alerta cuando:

  • falla la copia de seguridad programada;
  • La úÚltima copia de seguridad exitosa es más antigua que el RPO definido;
  • El volcado de DB falla;
  • falla el envío de la copia al almacenamiento externo;
  • expiran las credenciales del repositorio;
  • el tamaño de la copia de seguridad cambia sospechosamente;
  • El trabajo de poda/retención falla.

Que cron haya ejecutado una tarea no demuestra que exista una copia de seguridad utilizable.

Para RPO/RTO, retención, copias independientes y ejercicios de restauración, use estrategia de copias de seguridad para un VPS.

Correlacionar registros con métricas

Las métricas te dicen lo que cambió. Los registros a menudo te dicen por qué.

Correlacionar la misma ventana de tiempo a través de:

  • Registros de acceso/error Nginx/Apache;
  • Registros de PHP-FPM/en entorno de ejecución;
  • registros de aplicaciones;
  • registros de la base de datos;
  • diario del sistema;
  • registros de autenticación;
  • Registros de respaldo/trabajo.

Ejemplo:

  • La CPU aumenta a las 14:03;
  • 5xx sube a las 14:03;
  • El registro de aplicaciones muestra los tiempos de espera de la base de datos;
  • El registro de DB muestra la contención de bloqueo.

Eso es más procesable que una alerta genérica de "alto CPU".

Mantenga suficiente retención de registros para investigar incidentes, pero no permita que los registros llenen el sistema de archivos de producción.

Crear alertas accionables

Una alerta debe decirle al operador qué falló y qué verificar primero.

Prioriza:

  • advertencia investigar antes del impacto del usuario;
  • crítico impacto del usuario o fallo inminente;
  • duración y filtrado de oscilaciones: evita avisar al responsable por picos de un segundo;
  • agrupación/desduplicación: evite 40 notificaciones por una interrupción;
  • claro host/servicio afectado;
  • enlace al dashboard/log/procedimiento documentado;
  • Primera acción/escalada conocida.

Prometheus Alertmanager es un ejemplo de un sistema diseñado para agrupar, deduplicar y enrutar alertas.

Evita los umbrales universales

Los umbrales deben coincidir con la carga de trabajo.

Ejemplos de lógica de arranque razonable:

  • CPU: alta utilización sostenida + síntomas de latencia / cola en lugar de pico aislado;
  • RAM: poca memoria disponible junto con swap u OOM, en lugar de basarse solo en «RAM utilizada > 80%»;
  • disco: alerta temprana mientras queda suficiente capacidad operativa de repuesto;
  • TLS: advierta días antes de la expiración;
  • HTTP: Fallo repetido o confirmación de múltiples ubicaciones donde los falsos positivos importan;
  • copia de seguridad: último éxito anterior a RPO;
  • 5xx/latencia: desviación sostenida de la línea base normal de la aplicación.

Ajusta los umbrales después de observar el comportamiento habitual en producción.

Mantenga la ruta de notificación independiente

Una alerta es inútil si su sistema de entrega muere en el mismo incidente.

Cuando sea práctico, envíe alertas importantes a través de un camino fuera del VPS:

  • proveedor de correo electrónico externo;
  • Servicio externo de chat/notificación;
  • herramienta de incidencia alojada;
  • una instancia de monitorización en otro dominio de fallo.

No confíe solo en un servidor SMTP o panel alojado en el mismo VPS roto.

Cada alerta necesita un responsable y un procedimiento de respuesta

Antes de crear una alerta, responda:

  • ¿Quién lo recibe?
  • ¿A quién se le permite actuar?
  • ¿Cuál es el primer paso de diagnóstico?
  • ¿Qué dashboard/log se debe abrir?
  • ¿Cuándo se escala el incidente?
  • ¿Cuándo es seguro silenciar la alerta?
  • ¿Qué ocurre fuera del horario comercial?

Si nadie es responsable de la respuesta, el sistema de monitorización solo ha convertido una interrupción en una notificación.

Para obtener una decisión más amplia sobre la responsabilidad de las operaciones, consulte VPS administrado o no administrado.

Elija la pila de monitorización por complejidad

No despliegue una gran plataforma de observación porque es popular.

Panel de proveedores como capa inicial

Si el proveedor de VPS expone el historial de CPU, RAM, disco o red, úselo como una capa inicial conveniente a nivel de host.

No confundas los gráficos de infraestructura del proveedor con una monitorización completa del sitio. No pueden comprobar la ruta HTTP(S) pública desde fuera del proveedor, el contenido de la aplicación, el estado de la base de datos, las tareas en segundo plano, la renovación TLS ni quién responde a las alertas.

Trate la monitorización del proveedor como una fuente de evidencia, luego agregue las verificaciones externas y de nivel de aplicación requeridas por la carga de trabajo.

Camino ligero de un solo VPS

Una práctica configuración pequeña puede combinar:

  • monitor de disponibilidad externa;
  • Netdata u otro agente y panel de métricas del servidor;
  • registros del sistema/aplicación;
  • notificaciones.

Es bueno cuando un operador administra una o varias instancias de VPS.

Ruta Prometheus / Grafana

Útil cuando lo necesite:

  • métricas de múltiples servidores;
  • mayor retención histórica;
  • consultas personalizadas;
  • métricas de servicio/exportador;
  • cuadros de mando compartidos;
  • Reglas de alerta estructuradas.

Node Exporter suministra métricas de host Linux; Prometheus las almacena / consulta; Grafana las visualiza; Alertmanager puede enrutar / agrupar / deduplicar alertas.

Ruta de monitorización alojada

Útil cuando:

  • el monitor debe ser independiente de su VPS/proveedor;
  • desea que opere menos infraestructura de monitorización;
  • las notificaciones gestionadas y las integraciones con servicios de guardia son valiosas.

El sistema de monitorización en sí es una infraestructura de producción. Mantenga su complejidad proporcional al riesgo que reduce.

Asegure la pila de monitorización

Los agentes de monitorización y los paneles pueden exponer datos operativos confidenciales.

Proteger:

  • cuadros de mando;
  • exportadores;
  • puntos finales de métricas;
  • tokens de API;
  • webhooks de notificación;
  • sistemas de almacenamiento de registros.

No exponga los paneles de Prometheus, Node Exporter, Grafana o admin abiertamente a Internet sin un modelo explícito de acceso seguro.

Aplica un cortafuegos, una red privada o autenticación mediante proxy inverso según corresponda.

La monitorización no reemplaza el endurecimiento; use lista de comprobación de seguridad de un VPS para la línea base del servidor.

Consumo de recursos de la monitorización

La monitorización consume:

  • RAM;
  • CPU;
  • disco para la retención de métricas/registros;
  • red;
  • capacidad de respaldo.

Un agente pequeño suele ser barato, pero las métricas / registros de retención prolongada pueden convertirse en una carga de trabajo de almacenamiento real.

Mire la pila de monitorización en sí:

  • estado del agente y de los servicios;
  • fallos en la recopilación de métricas;
  • crecimiento del almacenamiento;
  • retención;
  • entrega de notificaciones.

No permita que la observabilidad llene el disco que se supone debe proteger.

Utilizar las tendencias para la planificación de la capacidad

La monitorización histórica es la mejor evidencia para la próxima decisión de dimensionamiento.

Utiliza las tendencias para responder:

  • ¿Se mantiene la saturación de la CPU u ocasional?
  • ¿La RAM disponible disminuye con el paso de las semanas?
  • ¿Aparece el swap/OOM bajo carga legítima?
  • ¿Qué tan rápido está creciendo el disco?
  • ¿La latencia de la base de datos aumenta durante el tráfico máximo?
  • ¿Se forman colas de PHP/app?
  • ¿Los trabajos de backup/importación están creando una contención predecible?

No actualice simplemente porque un tablero de instrumentos se volvió rojo brevemente.

Amplía los recursos cuando la carga legítima y optimizada agote repetidamente algún recurso o cuando la arquitectura necesite ampliarse por componentes independientes.

Monitorizar múltiples sitios web en dos niveles

En un VPS de varios sitios, monitoriza:

Nivel de servidor

  • CPU/RAM/intercambio;
  • disco/inodos/I/O;
  • base de datos;
  • red;
  • servicios básicos.

Nivel del sitio

  • cada nombre de host importante;
  • TLS;
  • tiempo de respuesta;
  • 5xx;
  • Fallas de la aplicación / trabajo;
  • registros por sitio o presión del proceso cuando esté disponible.

Un servidor puede ser saludable mientras que un host virtual, certificado o sitio web está roto.

Utilice VPS para múltiples sitios web para la decisión de consolidación/dominio de fallo.

Preguntas frecuentes

¿Qué debo monitorizar en un VPS?

Como mínimo, supervisa la disponibilidad del sitio desde el exterior, CPU, RAM disponible, swap, OOM, capacidad del disco, inodos, servicios principales, estado de la aplicación, caducidad TLS, antigüedad de las copias y entrega de alertas.

¿La CPU es siempre mala en más del 80%?

No. Las ráfagas cortas de alta CPU pueden ser normales. Investigue la utilización sostenida junto con la carga, la latencia de las solicitudes, las colas y el proceso que realiza el trabajo.

¿Por qué la RAM de Linux está casi llena?

Linux utiliza memoria libre para la caché. Supervise la memoria disponible, la actividad de intercambio, los eventos OOM y el crecimiento del proceso en lugar de alarmar solo con el porcentaje utilizado.

¿Qué debo vigilar para detectar problemas en el disco?

Supervisa la capacidad del sistema de archivos, el uso de inodos, el crecimiento del almacenamiento y la latencia o espera de E/S. Los GB libres, por sí solos, no permiten detectar todos los fallos del disco.

¿Basta con ping para supervisar la disponibilidad?

No. Ping puede tener éxito mientras el sitio web, la base de datos o la ruta TLS están rotos. Utilice HTTP (S) y verificaciones de aplicaciones / servicios para el estado de cara al usuario.

¿Debería funcionar el monitor de disponibilidad en el mismo VPS?

No como único monitor. Un fallo completo del VPS o de la red puede dejar fuera de servicio tanto el sitio como el monitor. Mantén al menos las comprobaciones críticas de disponibilidad y la entrega de notificaciones fuera de ese ámbito de fallo.

¿Qué herramienta de monitorización de VPS es mejor?

No existe una herramienta universalmente superior. Para un solo VPS, pueden bastar comprobaciones externas de disponibilidad y un agente ligero de métricas. Una flota puede justificar Prometheus, Grafana y Alertmanager. Elige según la visibilidad, el historial y la complejidad operativa que necesites.

¿Necesito Prometheus y Grafana para un VPS?

No necesariamente. Son potentes cuando necesita métricas a largo plazo, consultas personalizadas y múltiples servidores, pero un agente ligero más monitorización de disponibilidad externa puede ser suficiente para una implementación pequeña.

¿Cómo debo monitorizar las copias de seguridad?

Alerta sobre tareas fallidas y sobre la antigüedad de la úÚltima copia de seguridad exitosa en comparación con el RPO. A continuación, verifique la recuperabilidad por separado con las pruebas de restauración.

¿Cuándo deberían los datos de monitorización justificar una ampliación del VPS?

Cuando la evidencia histórica muestra que una carga de trabajo legítima optimizada agota repetidamente la CPU, RAM, almacenamiento / E / S u otro recurso. Un pico aislado no es suficiente evidencia.
