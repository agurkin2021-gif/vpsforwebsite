Un VPS para WooCommerce debe dimensionarse para las partes de la tienda que no funcionan como un blog con caché: carrito, pago, cuenta, pedidos, inventario, notificaciones de pago, acciones programadas y escrituras en la base de datos. Las visitas mensuales o el número de productos, por sí solos, no indican cuántos recursos necesita la tienda.

Los requisitos de WooCommerce no determinan los recursos de un VPS en producción

Las recomendaciones de servidor actuales de WooCommerce para WooCommerce 10.8+ requieren:

  • WordPress 6.9+;
  • PHP 8.3+;
  • MySQL 8.0+ o MariaDB 10.6+;
  • HTTPS;
  • Límite de memoria de WordPress de 256 MB o más;
  • Apache o Nginx como opciones de servidor web recomendadas.

Esos valores responden "¿cumple el entorno con la línea de base del software de WooCommerce?"

Ellos no responden:

  • cuántos procesos PHP necesita;
  • Cuánta RAM VPS total se requiere;
  • si la memoria disponible basta para los datos que utiliza activamente la base de datos;
  • si las solicitudes de pago se acumulan en una cola bajo carga;
  • si las acciones programadas se retrasan;
  • si las copias de seguridad/importaciones chocan con los clientes;
  • si las integraciones de pago/webhook están retrasando las solicitudes.

Un límite de memoria WordPress/PHP de 256 MB no es 256 MB de RAM VPS La RAM total del servidor también debe cubrir Linux, servidor web, DB, procesos PHP, caché, tareas, panel/correo electrónico y margen de recursos.

Cuando WooCommerce realmente necesita VPS

Una tienda WooCommerce puede justificar VPS cuando:

  • El alojamiento compartido golpea repetidamente los límites legítimos de CPU / memoria / proceso / E / S;
  • cola de solicitudes de pago/cuenta bajo carga real;
  • el conjunto de datos de BD mantenido en memoria o carga de escritura necesita más control;
  • extensiones necesitan servicios que el host actual no permite;
  • Se requiere la configuración del servidor Redis/Memcached o personalizado;
  • Los trabajos del Action Scheduler / segundo plano necesitan una ejecución más confiable;
  • las importaciones de productos, los feeds o la sincronización del inventario chocan con el tráfico del cliente;
  • Se requieren ajustes personalizados de PHP/entorno de ejecución/web-server;
  • se necesita un entorno de pruebas o control operativo específico de la tienda.

Si la tienda es pequeña, estable y bien compatible con el alojamiento administrado de WooCommerce / WordPress, VPS no es automáticamente la mejor opción.

Cuándo puede ser mejor el alojamiento administrado para WooCommerce

Un VPS autogestionado es un mal ajuste cuando:

  • nadie se encarga de actualizaciones de OS/seguridad;
  • nadie monitoriza la disponibilidad de pago o las alertas del servidor;
  • existen copias de seguridad, pero la restauración no se ha probado;
  • El tiempo de inactividad del pago/pedido es crítico para el negocio;
  • el equipo quiere ayuda de WordPress / WooCommerce en lugar de administración de Linux;
  • la plataforma administrada existente ya resuelve el rendimiento y el escalado adecuadamente.

Un VPS ofrece más control, pero también te hace responsable de más posibles fallos.

Vea VPS administrado o no administrado antes de poner una tienda de ingresos críticos en un servidor autogestionado.

El tráfico del proceso de pago y de las cuentas sigue siendo dinámico

La guía de caché de WooCommerce indica que Carrito, Mi cuenta y Finalizar compra deben excluirse de la caché de página completa porque contienen datos específicos de cada cliente.

Eso es importante porque las solicitudes más importantes comercialmente todavía pueden ejecutar:

  • PHP;
  • lógica de sesión/carro;
  • lógica de envío / impuestos;
  • código de integración de pagos;
  • la base de datos lee/escribe;
  • creación de orden;
  • actualizaciones de stock;
  • ganchos/extensiones.

Por eso una tienda puede servir rápidamente una página de producto desde la caché y, al mismo tiempo, acumular solicitudes de pago en espera.

No dimensiones WooCommerce basándote solo en la proporción de aciertos de caché del catálogo.

Procesos PHP y concurrencia dinámica

Para las solicitudes dinámicas de WooCommerce, los procesos de PHP determinan cuántas solicitudes pueden ejecutarse simultáneamente.

Una aproximación útil es:

Solicitudes dinámicas activas ≈ solicitudes por segundo que no se sirven desde caché × duración de la solicitud

Si las solicitudes de pago / cuenta / API promedian 0.8 segundos en el pico y 5 solicitudes dinámicas por segundo llegan a PHP, aproximadamente cuatro procesos pueden estar ocupados a la vez antes de que se agreguen tareas de administración, webhooks o en segundo plano.

Cada proceso consume memoria. Aumentar el recuento de procesos sin un presupuesto de RAM puede privar a la base de datos o empujar al servidor hacia swap/OOM.

Uso:

RAM de WooCommerce = sistema operativo + servidor web + base de datos + caché + procesos PHP + tareas + panel/correo + margen

A continuación, verifique la memoria media/máxima del proceso en lugar de copiar un recuento genérico de procesos.

Configura correctamente la caché de WooCommerce

WooCommerce necesita una estrategia de caché en capas.

Caché de página completa

Útil para páginas de catálogo/contenido almacenables en caché.

No almacenes indiscriminadamente en caché:

  • Carrito;
  • Finalizar compra;
  • Mi cuenta
  • Respuestas específicas del cliente/sesión.

La guía oficial de almacenamiento en caché de WooCommerce excluye explícitamente esas páginas.

OPcache

Almacena el bytecode compilado de PHP y reduce la compilación repetida del mismo código.

Caché de objetos persistente

Redis o Memcached pueden reducir el trabajo repetido de la base de datos/objeto cuando la carga de trabajo se beneficia.

No reemplaza el almacenamiento en caché de página completa y no corrige automáticamente las consultas ineficientes.

Navegador / CDN

Útil para recursos estáticos y contenido distribuido desde nodos cercanos al usuario.

Una CDN puede reducir las solicitudes de origen estático, pero no elimina el trabajo dinámico de pago/base de datos.

Demanda de base de datos y HPOS

WooCommerce crea un comportamiento de lectura / escritura de bases de datos más pesado que un sitio típico de WordPress en caché.

El trabajo de DB importante puede incluir:

  • creación y actualización de pedidos;
  • datos de clientes/cuentas;
  • cambios en las existencias;
  • búsquedas de productos/catálogos;
  • sesiones;
  • metadatos de extensión;
  • informes/análisis;
  • búsqueda/filtrado;
  • tareas programadas.

WooCommerce Almacenamiento de pedidos de alto rendimiento (HPOS) almacena datos de pedidos en tablas dedicadas y está habilitado de forma predeterminada para nuevas instalaciones desde WooCommerce 8.2.

HPOS es una mejora arquitectónica importante, pero no es un sustituto de:

  • extensiones compatibles / código personalizado;
  • consulta/revisión de índices;
  • una memoria DB adecuada;
  • baja latencia de almacenamiento;
  • monitorización;
  • Entorno de pruebas/prueba antes de cambios importantes.

Para tiendas grandes ya existentes, WooCommerce recomienda probar la migración a HPOS y los flujos críticos antes de aplicar el cambio en producción.

Action Scheduler y tareas en segundo plano

WooCommerce utiliza Action Scheduler para tareas en segundo plano como:

  • notificaciones de pedidos;
  • procesamiento relacionado con el pago;
  • webhooks;
  • suscripciones/renovaciones;
  • Trabajos de extensión;
  • importaciones/sincronización.

WooCommerce muestra estas tareas en WooCommerce → Estado → Acciones programadas.

Atentos a:

  • acciones fallidas;
  • acciones vencidas;
  • acumulación persistente de acciones pendientes;
  • trabajos de larga duración;
  • colas que crecen durante los picos de clientes.

Action Scheduler utiliza por defecto la programación de WordPress. Por eso, un cron del servidor puede ser útil cuando se necesita ejecutar las tareas con puntualidad.

Una tienda con páginas en caché rápida todavía puede tener problemas operativos si su cola programada está fallando.

Pagos, webhooks, correo electrónico e integraciones

Un VPS más grande no puede corregir cada error de pago.

Las dependencias externas pueden incluir:

  • pasarelas de pago;
  • API de impuestos;
  • API de envío;
  • sincronización de inventario/ERP;
  • CRM;
  • correo electrónico transaccional;
  • controles de fraude;
  • webhooks;
  • Búsqueda/servicios externos.

Mida si la latencia se origina desde su VPS o desde el servicio externo.

Monitor:

  • fallos de devolución de llamada de pago;
  • entrega de webhook;
  • colas de correo electrónico;
  • Tiempos de espera API;
  • comportamiento de los reintentos y sus intervalos de espera;
  • Errores del Action Scheduler.

No compre CPU para resolver un cuello de botella de API de terceros.

Catálogo, búsqueda y filtrado

Los grandes catálogos no crean carga solo porque contienen muchos productos.

La verdadera presión proviene de:

  • consultas complejas de búsqueda/filtro;
  • consultas de atributo/taxonomía;
  • tablas de búsqueda de productos;
  • recuentos de variaciones;
  • precios/reglas de stock;
  • extensiones que agregan llamadas SQL o externas;
  • resultados personalizados no almacenados en caché.

Mide los puntos finales de búsqueda / filtro por separado de la navegación normal de la página del producto.

La caché persistente puede ayudar a algunas consultas repetidas, pero el diseño de bases de datos/consultas sigue siendo importante.

Dimensiona el VPS para los picos de ventas y campañas

La carga máxima de WooCommerce a menudo combina varias cosas a la vez:

  • tráfico de boletines/anuncios;
  • navegación por catálogo;
  • añadir al carrito;
  • proceso de pago;
  • devoluciones de llamada de pago;
  • correos de confirmación de pedidos;
  • actualizaciones de stock;
  • administración / procesamiento de pedidos;
  • webhooks;
  • acciones programadas;
  • Analítica/Registro.

Dimensiona el servidor para un intervalo representativo de máxima carga, no para un día promedio.

Antes de una promoción importante:

  1. prueba un volumen representativo de solicitudes de pago;
  2. verificar el margen de recursos del proceso PHP;
  3. verificar la latencia y las conexiones de DB;
  4. comprueba las tareas pendientes de Action Scheduler;
  5. pausar o reprogramar las importaciones/copias de seguridad/escaneos;
  6. confirmar APIs externas de pago/envío/impuestos;
  7. ver registros y métricas de recursos durante el evento.

Almacenamiento, copias de seguridad y entorno de pruebas

Una copia de seguridad de WooCommerce debe proteger tanto los archivos como los datos transaccionales.

Incluye:

  • Archivos WordPress/WooCommerce;
  • archivos subidos e imágenes de productos;
  • datos de base de datos/pedido;
  • configuración/secretos necesarios para la recuperación;
  • plugin/tema/código personalizado;
  • Configuración de integración.

Recuperación que tenga en cuenta las transacciones

Si la tienda recibe pedidos continuamente, la frecuencia de copia de seguridad define la posible pérdida de datos de pedidos.

Una copia de seguridad diaria de la base de datos puede significar que hasta un día de transacciones recientes está fuera de ese punto de restauración.

Elige la frecuencia de las copias según el objetivo de punto de recuperación (RPO) aceptable, no solo por comodidad.

La arquitectura de copia de seguridad profunda pertenece a estrategia de copias de seguridad para un VPS.

Entorno de pruebas

Pruebe los cambios en PHP, WooCommerce, plugins, temas, HPOS y pagos antes de la producción donde sea práctico.

Las copias del entorno de pruebas también consumen disco y, en ocasiones, recursos de base de datos, RAM y copias de seguridad. Inclúyelas al planificar la capacidad.

Panel de control, FASTPANEL o pila manual

WooCommerce puede ejecutarse en un VPS Linux administrado manualmente o a través de un panel de control de alojamiento.

Migrar una tienda activa exige definir el punto final de sincronización de los datos

Una migración de WooCommerce no es solo “copiar archivos y bases de datos”.

Los pedidos, el stock, los carritos, los clientes y las acciones programadas pueden cambiar mientras la tienda está activa.

Para la migración:

  • construir/probar el destino primero;
  • controla las últimas escrituras;
  • ejecuta una sincronización final de la base de datos y los archivos subidos;
  • evita que dos tiendas en producción acepten escrituras y sus datos diverjan;
  • verificar los puntos finales de pago/webhook;
  • conservar el correo electrónico/DNS;
  • mantener un plan de reversión.

Consulta Migración de un sitio web a un VPS para seguir el proceso completo de cambio de servidor.

Señales de que debes ampliar el VPS de WooCommerce

Escalar o rediseñar cuando las mediciones muestran:

  • colas de procesos PHP repetidas;
  • saturación sostenida de la CPU después de la optimización de caché/consulta/plugin;
  • Presión RAM, swap u OOM;
  • latencia de la base de datos o presión sobre su conjunto de datos activo;
  • Action Scheduler atrasos / fallas causadas por la capacidad;
  • errores al finalizar la compra o procesar pagos durante un pico legítimo de carga;
  • crecimiento del almacenamiento reduciendo el margen de recursos segura;
  • trabajos de copia de seguridad / importación / escaneo que colisionan con los clientes;
  • múltiples tiendas/servicios que compiten por un VPS.

Si el proceso de pago es lento mientras los recursos del servidor están sanos, investigue las causas de pago/API/plugin/base de datos antes de comprar un VPS más grande.

Preguntas frecuentes

¿Cuánta RAM necesita WooCommerce en un VPS?

No hay una cifra universal. WooCommerce ha utilizado 2 GB como punto de partida para una instalación propia, mientras que 4 GB ofrece más margen para muchas tiendas empresariales: los procesos PHP, la base de datos, la caché y las tareas deben funcionar al mismo tiempo.

¿Es suficiente 2 GB de RAM para WooCommerce?

Puede ser suficiente para una tienda muy pequeña / ligera o una configuración controlada de bajo volumen. Validar la concurrencia de pago, la latencia de la base de datos, las acciones programadas y la presión de memoria antes de tratarla como lista para producción.

¿Son suficientes 4 GB de RAM para WooCommerce?

Para muchas tiendas de pequeñas empresas, 4 GB es un punto de partida práctico. El tráfico pesado, catálogos / bases de datos más grandes, muchas integraciones, suscripciones, importaciones o picos de venta pueden requerir más.

¿Por qué WooCommerce es más pesado que WordPress?

El carrito, el pago, la cuenta, los pedidos, el stock y muchas integraciones son dinámicos. Esas solicitudes aún ejecutan PHP y trabajo de base de datos incluso cuando las páginas de catálogo / contenido público están en caché.

¿Puedo almacenar en caché el proceso de pago de WooCommerce?

El almacenamiento en caché de página completa debe excluir Carrito, Pago y Mi cuenta porque esas páginas contienen el estado específico del cliente. Utilice otras capas de caché para obtener los datos/contenido apropiados.

¿Necesita WooCommerce Redis?

No. Redis o Memcached pueden proporcionar caché de objetos persistente cuando la carga de trabajo se beneficia. No reemplazan las exclusiones de caché de página correctas ni las consultas eficientes.

¿Qué es HPOS?

El almacenamiento de pedidos de alto rendimiento guarda los pedidos de WooCommerce en tablas específicas. Está activado por defecto en las instalaciones nuevas desde WooCommerce 8.2. Al cambiar una tienda existente, prueba la compatibilidad de las extensiones y del código personalizado, así como los flujos críticos de la tienda.

¿Qué son las acciones programadas de WooCommerce?

Son tareas en cola en segundo plano administradas por Action Scheduler para tareas como notificaciones de pedidos, procesamiento relacionado con pagos, webhooks y tareas de extensión. Las colas fallidas o vencidas son una señal operativa.

¿Incluye VDSina WooCommerce preinstalado?

La página actual de VDSina Standard no muestra WooCommerce como una aplicación preinstalada dedicada en sus grupos visibles de plantillas/aplicaciones. Verifique la interfaz de pedido en vivo antes de asumir cualquier disponibilidad de plantillas.

¿Es un VPS siempre mejor para WooCommerce que el hosting administrado?

No. Un VPS autogestionado es útil cuando necesitas control o recursos y puedes operar el servidor. El alojamiento administrado de WooCommerce o WordPress puede ser más seguro si la tienda es crítica para el negocio y no hay un responsable interno de administrar el servidor.
