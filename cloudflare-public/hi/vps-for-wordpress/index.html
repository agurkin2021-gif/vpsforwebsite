WordPress के लिए VPS तब उपयोगी है जब शेयर्ड होस्टिंग से अधिक नियंत्रण, अलगाव या सर्वर स्तर की सुविधाएँ चाहिए। VPS के संसाधन बिना कैश वाले PHP कार्य, डेटाबेस की माँग, प्लगइन, बैकग्राउंड कार्य, बढ़ते स्टोरेज और WordPress के साथ चलने वाली सेवाओं के अनुसार तय होने चाहिए, मासिक विज़िटर संख्या के अनुसार नहीं।

व्यापक सर्वर निर्णय के लिए, वेबसाइट के लिए VPS देखें।

यदि साइट वास्तविक स्टोर है, जिसमें डायनेमिक कार्ट, चेकआउट, अकाउंट, ऑर्डर या स्टॉक है, तो उसे सामान्य कैश किए हुए WordPress की तरह मानने के बजाय WooCommerce के लिए VPS गाइड देखें।

गहन क्रॉस-स्टैक संसाधन गणना के लिए, वेबसाइट के लिए VPS संसाधन आकलन का उपयोग करें।

WordPress आवश्यकताएँ VPS संसाधन नहीं हैं

WordPress.org वर्तमान में एक होस्ट की अनुशंसा करता है जो समर्थन करता है:

  • PHP 8.3 या अधिक;
  • MariaDB 10.11+ या MySQL 8.0+;
  • HTTPS;
  • अनुशंसित वेब-सर्वर विकल्पों के रूप में Apache या Nginx।

ये आवश्यकताएँ “क्या यह सर्वर WordPress चला सकता है?” का उत्तर देती हैं। ये “इस प्रोडक्शन वर्कलोड के लिए VPS में कितने संसाधन चाहिए?” का उत्तर नहीं देतीं।

एक प्रोडक्शन VPS को इसके लिए RAM/CPU/भंडारण की भी आवश्यकता है:

  • Linux;
  • Nginx/Apache;
  • PHP-FPM वर्कर;
  • MySQL/MariaDB;
  • OPcache;
  • पेज/ऑब्जेक्ट कैश जहां उपयोग किया गया;
  • कंट्रोल पैनल;
  • मेल यदि स्थानीय रूप से होस्ट किया गया हो;
  • बैकअप;
  • cron कार्य;
  • मैलवेयर/सुरक्षा स्कैन;
  • आयात/निर्यात;
  • निगरानी;
  • संचालन के लिए अतिरिक्त क्षमता।

प्रोडक्शन संसाधन अनुशंसा के रूप में WordPress सॉफ़्टवेयर आवश्यकताओं का उपयोग न करें।

WordPress VPS उपयुक्तता जाँच

इस चेकर को शुरुआती बिंदु के रूप में उपयोग करें। यह वास्तविक CPU/RAM/डेटाबेस माप को प्रतिस्थापित नहीं करता है।

जहां संभव हो वास्तविक कार्यभार साक्ष्य का उपयोग करें।

जब WordPress को वास्तव में VPS की आवश्यकता होती है

एक WordPress साइट भारी ट्रैफ़िक के बिना भी VPS को उचित ठहरा सकती है।

सामान्य कारण:

  • वैध लोड के तहत बार-बार CPU/मेमोरी/प्रक्रिया सीमाएं;
  • एक कस्टम PHP/रनटाइम कॉन्फ़िगरेशन की आवश्यकता;
  • Redis/Memcached या किसी अन्य सर्वर-साइड सेवा की आवश्यकता;
  • विज़िटर-ट्रिगर शेड्यूलिंग के बजाय वास्तविक सिस्टम cron;
  • लंबे समय से चल रही पृष्ठभूमि वाली कार्य;
  • कस्टम Nginx/Apache व्यवहार;
  • कई साइटें जिन्हें एक नियंत्रित वातावरण की आवश्यकता होती है;
  • मजबूत कार्यभार/खाता अलगाव;
  • सर्वर-स्तरीय निगरानी या फ़ायरवॉल आवश्यकताएँ।

यदि एकमात्र लक्षण "साइट धीमी है" है, तो पहले तुलना करें VPS बनाम शेयर्ड होस्टिंग और सत्यापित करें कि WordPress स्वयं बाधा नहीं है।

जब WordPress को VPS की आवश्यकता नहीं है

अच्छी साझा या प्रबंधित WordPress होस्टिंग पर बने रहें जब:

  • साइट हल्की और स्थिर है;
  • कैशिंग ठीक काम कर रही है;
  • मेजबान के संसाधन मीटर बार-बार सीमाएं नहीं दिखा रहे हैं;
  • किसी कस्टम सेवा/root एक्सेस की आवश्यकता नहीं है;
  • टीम Linux का रखरखाव नहीं करना चाहती;
  • प्रदाता पहले से ही बैकअप, सुरक्षा, अपडेट या स्टेजिंग को काफी अच्छी तरह से संभालता है;
  • VPS मुख्य रूप से अधिक परिचालन कार्य के साथ एक सरल होस्टिंग सेवा को प्रतिस्थापित करेगा।

VPS स्वचालित रूप से तेज़ नहीं है। एक ख़राब आकार का या बिना ट्यून किया हुआ VPS एक अच्छे प्रबंधित प्लेटफ़ॉर्म की तुलना में WordPress को ख़राब चला सकता है।

PHP वर्कर और RAM

बिना कैश वाले अनुरोधों के लिए, PHP-FPM वर्कर एक प्रमुख समवर्ती सीमा है।

प्रत्येक सक्रिय वर्कर अनुरोध संसाधित करते समय मेमोरी की खपत करता है। अधिक वर्कर एक साथ अधिक गतिशील अनुरोधों को संभाल सकता है, लेकिन RAM बजट को बढ़ाए बिना वर्कर गिनती बढ़ाने से निम्न कारण हो सकते हैं:

  • स्वैप का उपयोग;
  • स्मृति दबाव;
  • मेमोरी की कमी से प्रोसेस बंद होना (OOM kills);
  • डेटाबेस को पर्याप्त संसाधन न मिलना;
  • सर्वर अस्थिरता।

एक व्यावहारिक मॉडल है:

WordPress RAM = OS + वेब सर्वर + डेटाबेस + कैश + PHP वर्कर + पैनल/मेल/कार्य + अतिरिक्त क्षमता

फिर:

PHP वर्कर बजट = RAM सुरक्षित रूप से PHP के लिए उपलब्ध/मापी गई औसत वर्कर मेमोरी

वर्कर की सैद्धांतिक अधिकतम संख्या को कॉन्फ़िगर न करें यदि ऐसा करने से MySQL/MariaDB, कैश या ऑपरेटिंग सिस्टम के लिए कोई मेमोरी नहीं बचती है।

लॉग-इन उपयोगकर्ता, wp-admin, REST/API अनुरोध, खोज, फ़ॉर्म, पूर्वावलोकन और वैयक्तिकृत पृष्ठ पूर्ण-पृष्ठ कैश को बायपास करने और PHP वर्कर का उपभोग करने की अधिक संभावना रखते हैं।

WordPress कैशिंग परतें

कैशिंग कोई एकल सुविधा नहीं है।

परतयह क्या कैश करता हैमुख्य प्रभाव
PHP OPcacheकंपाइल किया हुआ PHP बाइटकोडप्रत्येक अनुरोध पर PHP स्क्रिप्ट को पुन: संकलित करने से बचता है
पेज कैशरेंडर किया हुआ HTMLकई अज्ञात पृष्ठ दृश्यों को WordPress/PHP कार्य को बायपास करने देता है
पर्सिस्टेंट ऑब्जेक्ट कैशपुन: प्रयोज्य वस्तुएं/क्वेरी परिणामबार-बार डेटाबेस/एप्लिकेशन कार्य को कम करता है
ब्राउज़र/CDN कैशस्थिर/एज-डिलीवर करने योग्य सामग्रीबार-बार ऑरिजिन से डेटा ट्रांसफ़र और अनुरोधों को कम करता है

WordPress का स्वयं का अनुकूलन दस्तावेज़ एक प्रमुख प्रदर्शन उपकरण के रूप में कैशिंग की सिफारिश करता है। लेकिन ये परतें विभिन्न समस्याओं का समाधान करती हैं।

Redis को पेज कैश न कहें। Redis का उपयोग आमतौर पर एक सतत ऑब्जेक्ट-कैश बैकएंड के रूप में किया जाता है; पूर्ण-पृष्ठ कैशिंग एक अलग परत है।

पर्सिस्टेंट ऑब्जेक्ट कैश और Redis

WordPress में ऑब्जेक्ट-कैश API है, लेकिन डिफ़ॉल्ट कैश एक अनुरोध से अगले अनुरोध तक बना नहीं रहता।

लगातार ऑब्जेक्ट कैशिंग के लिए बाहरी बैकएंड/ड्रॉप-इन जैसे Redis या Memcached और उपयुक्त WordPress एकीकरण की आवश्यकता होती है।

जब साइट बार-बार महंगा डेटाबेस/ऑब्जेक्ट कार्य करती है तो यह मदद कर सकता है, लेकिन यह स्वचालित गति बटन नहीं है।

Redis जोड़ने से पहले:

  • साइट/डेटाबेस कार्यभार लाभों की पुष्टि करें;
  • सत्यापित करें कि PHP और डेटाबेस के लिए पर्याप्त RAM अवशेष मौजूद हैं;
  • मॉनिटर हिट दर और मेमोरी;
  • पेज कैशिंग को एक अलग निर्णय के रूप में रखें।

कुशल पूर्ण-पृष्ठ कैशिंग और हल्के डेटाबेस कार्य वाली साइट को गतिशील सदस्यता या क्वेरी-भारी साइट की तुलना में Redis से कम लाभ मिल सकता है।

डेटाबेस की मांग

CPU के स्पष्ट रूप से संतृप्त होने से पहले WordPress प्रदर्शन डेटाबेस-सीमित हो सकता है।

जांचें:

  • धीमी क्वेरीज़;
  • बड़े विकल्प/ऑटोलोडेड डेटा;
  • प्लगइन मेटाडेटा;
  • खोज/फ़िल्टर/रिपोर्टिंग क्वेरीज़;
  • पोस्टमेटा-भारी कार्यभार;
  • डेटाबेस सक्रिय डेटा सेट;
  • समवर्ती डेटा राइट;
  • आयात/निर्यात;
  • भंडारण विलंबता।

अधिक CPU खराब क्वेरी को ठीक नहीं करता। जब डेटाबेस को वास्तव में बड़े सक्रिय डेटा सेट के लिए मेमोरी चाहिए, तो अधिक RAM मदद कर सकती है; लेकिन यह इंडेक्स, क्वेरी या प्लगइन की समस्या ठीक करने का विकल्प नहीं है।

पहले मापें, फिर पैमाना।

प्लगइन्स, थीम और बैकग्राउंड कार्य

एक प्लगइन केवल डिस्क स्थान नहीं है।

प्लगइन्स/थीम जोड़ सकते हैं:

  • PHP कार्य;
  • डेटाबेस क्वेरीज़;
  • बाहरी API कॉल;
  • निर्धारित कार्य;
  • कैश अमान्यकरण;
  • व्यवस्थापक AJAX;
  • छवि प्रसंस्करण;
  • सुरक्षा स्कैनिंग;
  • बैकअप;
  • आयात/निर्यात;
  • एनालिटिक्स/लॉगिंग।

VPS पर WordPress को कितना RAM चाहिए?

WordPress कोर प्रोडक्शन VPS RAM आवश्यकता को परिभाषित नहीं करता है। RAM में Linux, वेब सर्वर, PHP वर्कर, डेटाबेस, कैश, पैनल/मेल/बैकग्राउंड कार्य और अतिरिक्त क्षमता शामिल होना चाहिए। एक हल्का साइट 2 GB में फिट हो सकती है; 4 GB एक व्यावसायिक साइट के लिए एक मजबूत व्यावहारिक आधार रेखा है।

क्या 1 GB RAM WordPress VPS के लिए पर्याप्त है?

यह बहुत हल्का/परीक्षण WordPress सेटअप चला सकता है, लेकिन डेटाबेस, PHP वर्कर और बैकग्राउंड कार्य के लिए बहुत कम अतिरिक्त क्षमता छोड़ता है। इसे सामान्य प्रोडक्शन अनुशंसा के रूप में नहीं माना जाना चाहिए।

क्या 2 GB RAM WordPress के लिए पर्याप्त है?

यह कम स्टैक वाली छोटी, अच्छी तरह से कैश्ड साइट के लिए पर्याप्त हो सकता है। मॉनिटर PHP वर्कर मेमोरी, डेटाबेस RAM, प्लगइन्स और बैकग्राउंड कार्य।

क्या 4 GB RAM WordPress के लिए पर्याप्त है?

कई व्यावसायिक WordPress साइटों के लिए, 4 GB एक व्यावहारिक प्रारंभिक बिंदु है। भारी प्लगइन्स, सदस्यता ट्रैफ़िक, WooCommerce, बड़े डेटाबेस, आयात या कई सक्रिय साइटों के लिए और अधिक की आवश्यकता हो सकती है।

एक WordPress VPS कितने आगंतुकों को संभाल सकता है?

कोई विश्वसनीय सार्वभौमिक आगंतुक संख्या नहीं है। कैश हिट दर, बिना कैश वाले समवर्ती, PHP अनुरोध अवधि, प्लगइन लागत, डेटाबेस कार्य और बैकग्राउंड कार्य क्षमता निर्धारित करती हैं।

क्या मुझे VPS पर WordPress के लिए Redis की आवश्यकता है?

नहीं। जब कार्यभार बार-बार ऑब्जेक्ट/डेटाबेस कैशिंग से लाभान्वित होता है तो Redis लगातार ऑब्जेक्ट कैशिंग प्रदान कर सकता है, लेकिन यह प्रत्येक WordPress साइट के लिए आवश्यक नहीं है और पूर्ण-पृष्ठ कैशिंग को प्रतिस्थापित नहीं करता है।

क्या मुझे WordPress VPS के लिए Nginx या Apache का उपयोग करना चाहिए?

दोनों मान्य हैं। WordPress.org मजबूत विकल्प के रूप में Apache या Nginx की अनुशंसा करता है। उस स्टैक का उपयोग करें जिससे आपका एप्लिकेशन और व्यवस्थापक विश्वसनीय रूप से काम कर सकें।

क्या मुझे WP-Cron को सिस्टम cron से बदलना चाहिए?

केवल तभी जब कार्यभार एक नियंत्रित शेड्यूलर से लाभान्वित होता है और आप एक कार्यशील प्रतिस्थापन को कॉन्फ़िगर करते हैं। किसी अन्य ट्रिगर के बिना WP-Cron को अक्षम न करें।

क्या WordPress VPS को कंट्रोल पैनल की आवश्यकता है?
