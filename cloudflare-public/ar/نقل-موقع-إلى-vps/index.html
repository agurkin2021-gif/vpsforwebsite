نقل موقع إلى VPS

يكون نقل الموقع إلى VPS أكثر أمانًا عند بناء الخادم الجديد واختباره بينما تستمر الاستضافة القديمة في خدمة الزيارات. احصر البيئة الحالية وحدد موارد الوجهة وانسخ الموقع وتحقق منه واضبط التغييرات النهائية للبيانات، ثم غيّر DNS أخيرًا وراقب البيئتين حتى يمكن إيقاف الاستضافة القديمة.

تفترض هذه الصفحة بقاء النطاق وبنية عناوين URL العامة كما هما. إذا تغير النطاق أو المسارات أيضًا، تصبح مطابقة العناوين وإعادة التوجيه الدائمة مهمة نقل منفصلة.

خطة نقل سريعة

يتبع النقل المنضبط هذا الترتيب:

  1. احصر المصدر. سجل التطبيق وبيئة التشغيل وقاعدة البيانات والملفات وDNS والبريد ومهام cron وعمليات المعالجة والويب هوك والخدمات الخارجية المعتمد عليها.
  2. حدد موارد الوجهة. اختر المعالج والذاكرة والقرص وفق عبء العمل الفعلي وهامش موارد النقل.
  3. أنشئ نسخة قابلة للاستعادة. احتفظ بنسخة خارج الخادم المصدر، وتحقق من وجود قاعدة البيانات والملفات المطلوبة فعلًا.
  4. جهز VPS بالتوازي. ثبّت مكونات الاستضافة أو لوحة التحكم وطابق متطلبات التطبيق قبل نقل الزيارات.
  5. انسخ مجموعة البيانات الكاملة أول مرة. انقل الملفات واستورد قاعدة البيانات بينما يبقى الموقع القديم متاحًا.
  6. اختبر بشكل خاص. استخدم تجاوزًا عبر ملف hosts أو اسم مضيف معاينة مضبوطًا أو طريقة مكافئة لاختبار الخادم الجديد قبل تغيير DNS.
  7. اضبط آخر عمليات الكتابة. للمتاجر والعضويات والنماذج والمواقع المتغيرة الأخرى، خطط لتجميد قصير للكتابة أو مزامنة فروق نهائية تناسب التطبيق.
  8. غيّر DNS أخيرًا. غيّر فقط السجلات التي تحتاج إلى النقل، واترك سجلات البريد والتحقق سليمة.
  9. راقب الخادمين. تحقق من الزيارات والأخطاء والنماذج والطلبات ومهام cron والويب هوك والبريد وHTTPS وزحف محركات البحث.
  10. لا توقف الاستضافة القديمة قبل القبول. أبقها متاحة طوال فترة إمكانية التراجع.

لا يمكن تقديم وعد صادق عام بعدم حدوث أي توقف. الهدف هو تحويل منضبط بأقل انقطاع عملي ودون فقد بيانات غير مخطط له.

فحص ما قبل تحويل الموقع

استخدم هذه الأداة قبل تغيير DNS. هي لا تضمن نجاح النقل، بل تُظهر المتطلبات الناقصة التي ينبغي استكمالها أولًا.

حدد العناصر الجاهزة فعلًا.

احصر الموقع الحالي

أنشئ سجلًا للنقل قبل إجراء أي تغيير في الوجهة.

سجل:

  • النطاق وكل نطاق فرعي نشط؛
  • إصدار التطبيق أو نظام المحتوى أو إطار العمل؛
  • إصدار PHP أو Node.js أو Python أو بيئة التشغيل الأخرى؛
  • محرك قاعدة البيانات وإصداره وحجمه ونموذج بيانات الاعتماد؛
  • جذر المستندات والمجلدات خارجه؛
  • الملفات المرفوعة والوسائط والمجلدات القابلة للكتابة؛
  • إعادة التوجيه وقواعد إعادة كتابة العناوين؛
  • مهام cron والطوابير وعمليات المعالجة والمهام المجدولة؛
  • خدمات التخزين المؤقت مثل Redis عند استخدامها؛
  • إعداد SSL/TLS؛
  • سجلات DNS؛
  • صناديق البريد وإعادة توجيهه ومسار SMTP الصادر؛
  • بوابات الدفع والويب هوك واستدعاءات API الراجعة؛
  • قوائم IP المسموح بها لدى الجهات الخارجية؛
  • قيود CDN/WAF والخادم الأصلي؛
  • التحقق في Search Console والتحليلات؛
  • استخدام التخزين الحالي ونموه.

يصبح الحصر أيضًا قائمة قبول بعد النقل: يجب أن يعمل كل عنصر على VPS أو يُترك عمدًا على خدمة خارجية.

حدد موارد VPS الوجهة وجهزه

لا تنقل أولًا ثم تسأل إن كانت موارد VPS كافية.

استخدم عبء العمل الحالي وسلوك قاعدة البيانات ونمو التخزين واستهلاك اللوحة والبريد ومساحة عمل النقل لاختيار الوجهة. قد تحتاج عملية النقل نفسها إلى قرص مؤقت للأرشيفات وتفريغات قاعدة البيانات والسجلات وتجهيز النسخ المحلية.

استخدم تحديد موارد VPS للمواقع لحساب الموارد بدل تكرار الحساب هنا.

النقل قرار بشأن مسار الإدارة أيضًا. إذا كانت الاستضافة القديمة تخفي معظم مهام إدارة الخادم، فحدد أولًا من سيتولى تشغيل الوجهة بعد التحويل: قارن VPS المدار مقابل غير المدار. ثم حدد إن كانت الوجهة ستستخدم لوحة تحكم أو بيئة Linux مدارة يدويًا؛ راجع VPS مع لوحة تحكم لهذا الاختيار.

أنشئ نسخة احتياطية تتيح التراجع

لا تفيد النسخة الاحتياطية إلا إذا احتوت البيانات المطلوبة وأمكنت استعادتها.

قبل النقل:

  1. أنشئ نسخة حديثة من ملفات الموقع؛
  2. صدّر كل قاعدة بيانات مطلوبة؛
  3. احتفظ بنسخة خارج حساب الاستضافة المصدر؛
  4. سجل ملفات الإعداد ومتغيرات البيئة بطريقة آمنة؛
  5. سجل سجلات DNS والبريد بشكل منفصل؛
  6. استعد النسخة في بيئة اختبار أو بيئة مؤقتة متى أمكن، أو نفذ على الأقل استيرادًا فعليًا لقاعدة البيانات وتحقق من ملفات ممثلة بدل الاكتفاء بالتأكد من فتح الأرشيف؛
  7. تأكد من أن النسخة المستعادة تتضمن البيانات المتوقعة ويمكن تشغيلها بما يكفي لدعم التراجع؛
  8. اكتب تسلسل التراجع قبل تغيير DNS.

في الموقع الديناميكي، ليست النسخة الأولى مجموعة بيانات الإنتاج النهائية. فقد تستمر الطلبات وإرساليات النماذج والتعليقات والعضويات والملفات المرفوعة في التغير بعد النسخ الأول. خطط للفروق النهائية بشكل منفصل.

جهز الوجهة قبل تغيير DNS

يجب أن تستطيع الوجهة تشغيل الموقع قبل وصول الزيارات العامة.

طابق أو تحقق عمدًا من:

  • سلوك خادم الويب؛
  • إصدار PHP/Node/Python؛
  • الإضافات والوحدات المطلوبة؛
  • محرك قاعدة البيانات وإصداره؛
  • ملكية الملفات وصلاحياتها؛
  • حدود حجم الرفع وجسم الطلب؛
  • بيئة المهام المجدولة؛
  • خدمات التخزين المؤقت؛
  • قواعد إعادة الكتابة والتوجيه؛
  • متغيرات البيئة والأسرار؛
  • احتياجات SMTP والشبكة الصادرة؛
  • قواعد الجدار الناري؛
  • المسارات الخاصة بالتطبيق.

لا تجعل النقل نفسه مناسبة لترقية كل بيئات التشغيل أو إعادة بناء المكونات، إلا إذا كان التغيير مطلوبًا. تقليل التغييرات المتزامنة يجعل التراجع والتشخيص أسهل.

انسخ الملفات وقاعدة البيانات

تعتمد طريقة النقل الدقيقة على صلاحيات الوصول إلى المصدر.

تشمل مسارات المصدر المعتادة:

  • cPanel/File Manager مع التصدير عبر phpMyAdmin؛
  • SFTP/FTP عند غياب الوصول إلى الطرفية؛
  • SSH/rsync عندما يسمح الطرفان به؛
  • أدوات نقل تراعي التطبيق عند نقل نظام إدارة محتوى معين؛
  • أدوات التصدير أو النسخ الاحتياطي لدى المزود.

حافظ على ملفات الإعداد المخفية، مثل قواعد إعادة الكتابة، حيث يحتاج إليها التطبيق. وبعد الاستيراد، تحقق من مستخدم قاعدة البيانات وصلاحياته وافتراضات الترميز والترتيب اللغوي وإعدادات اتصال التطبيق.

لمجموعات البيانات الكبيرة، قارن الأحجام أو أعداد الصفوف أو مجاميع التحقق متى أمكن، بدل افتراض أن «اكتمال النقل» يعني «تطابق البيانات».

اختبر بشكل خاص قبل التحويل

لا توجّه DNS إلى خادم لم يُختبر.

اختبر الوجهة بتجاوز عبر ملف hosts أو اسم مضيف معاينة مضبوط أو وسيلة خاصة أخرى تختبر مكونات التطبيق الفعلية.

تحقق من:

  • الصفحة الرئيسية وصفحات داخلية ممثلة؛
  • تسجيل دخول الإدارة؛
  • تسجيل دخول المستخدمين؛
  • الصور وCSS وJavaScript والتنزيلات؛
  • البحث؛
  • النماذج ووصول إرسالياتها؛
  • رفع الملفات؛
  • إعادة التوجيه؛
  • نقاط نهاية API؛
  • إتمام الشراء واستدعاءات الدفع الراجعة؛
  • cron والإجراءات المجدولة؛
  • الطوابير وعمليات المعالجة؛
  • البريد الصادر؛
  • سجلات التطبيق وخادم الويب وقاعدة البيانات؛
  • تنسيق الجوال والتنقل.

يجب ألا يتحول اسم مضيف عام مؤقت إلى نسخة مكررة في البحث بالخطأ. إذا أمكن الوصول إليه علنًا أثناء الاختبار، فأبقِه خارج الفهرس، وأزل الحظر المؤقت عن اسم مضيف الإنتاج الحقيقي قبل التحويل.

اضبط الكتابات الجديدة والمزامنة النهائية

هذا أهم فرق بين موقع تعريفي وموقع معاملات.

إذا قبلت قاعدتا البيانات القديمة والجديدة الكتابة أثناء انتقال DNS، فقد تختلف بياناتهما. فالطلب المحفوظ على الخادم القديم لا يظهر تلقائيًا على الجديد.

للمواقع المتغيرة:

  1. اختر فترة تحويل منخفضة المخاطر؛
  2. أوقف الكتابات الجديدة على المصدر أو اضبطها متى أمكن؛
  3. أوقف أو اضبط مهام cron وعمليات الطوابير التي قد تكتب البيانات مرتين؛
  4. نفذ المزامنة النهائية لقاعدة البيانات وانسخ الملفات المرفوعة والملفات التي تغيرت؛
  5. سجل وقت اعتماد المصدر النهائي للبيانات؛
  6. حوّل الزيارات؛
  7. تحقق من أن الكتابات الجديدة تصل الآن إلى الوجهة فقط.

عند استخدام VPS لووكومرس، ضمّن في اختبار القبول إتمام الشراء والطلبات وويب هوك الدفع والمخزون والإجراءات المجدولة والبريد الخاص بالمعاملات. وقد يحتاج الموقع الثابت أو المخزن مؤقتًا إلى مقارنة ملفات نهائية فقط.

لا تصف النقل بأنه «دون توقف» إلا إذا كان التطبيق وطريقة المزامنة يدعمان ذلك فعلًا.

غيّر DNS بتخطيط

DNS هو مفتاح تحويل الزيارات، وليس أول خطوة في النقل.

قبل التحويل:

  • صدّر منطقة DNS الحالية أو سجلها؛
  • حدد بدقة سجلات A/AAAA/CNAME أو الأصل التي يجب تغييرها؛
  • اخفض TTL للسجلات المعنية قبل التحويل المقصود بفترة تساوي TTL السابق كاملًا على الأقل متى أمكن؛ مثلًا، إذا كان TTL الحالي 86,400 ثانية، فاخفضه قبل التحويل بأكثر من 24 ساعة؛
  • تذكر أن خفض TTL الآن لا يمحو التخزين المؤقت الذي احتفظ سابقًا بقيمة TTL الأطول؛
  • حافظ على MX وSPF وDKIM وDMARC وسجلات TXT للتحقق وSRV وCAA وسائر السجلات التي لا تنتقل؛
  • تحقق من سلوك النطاق الجذري وwww معًا.

يكون تغيير سجل A/AAAA عادةً أقل مخاطرة من استبدال خوادم الأسماء عندما لا يتغير مزود DNS نفسه. وإذا تغيرت خوادم الأسماء، فأعد إنشاء المنطقة المطلوبة كاملةً أولًا.

بعد التحويل، تحقق من DNS العام عبر أكثر من محلل أسماء أو شبكة، وراقب انتقال الزيارات من الخادم القديم إلى الجديد.

حافظ على عمل البريد

نقل الموقع ونقل البريد مهمتان منفصلتان، حتى إذا جمعتهما الاستضافة المشتركة القديمة في حساب واحد.

اختر مسارًا قبل التحويل:

  • أبقِ البريد لدى المزود الحالي أو المدار، وحافظ على سجلات MX/TXT القائمة؛
  • انقل البريد إلى مزود مدار آخر؛
  • انقل البريد إلى VPS وأعد إنشاء صناديقه وتوجيهه ومصادقته وضوابط قابلية التسليم.

إذا انتقل البريد، فاحسب:

  • أولويات MX؛
  • SPF؛
  • DKIM؛
  • DMARC؛
  • DNS العكسي وPTR حيث ينطبقان؛
  • بيانات صناديق البريد؛
  • الأسماء البديلة وإعادة التوجيه؛
  • بيانات اعتماد SMTP؛
  • تصفية الرسائل المزعجة؛
  • النسخ الاحتياطية وسمعة المرسل.

لا تستبدل منطقة DNS كاملة لمجرد نقل الموقع، إلا بعد إعادة إنشاء سجلات البريد وكل ما يعتمد عليها.

تحقق من HTTPS وCDN والخدمات الخارجية

إذا لم تُحسم منطقة الوجهة، فاحسمها قبل التحويل عبر كيفية اختيار موقع خادم VPS. قد يعني تغيير المنطقة لاحقًا نقلًا آخر لعنوان IP وDNS.

قد تعمل الوجهة بعنوان IP وتفشل مع اسم المضيف الحقيقي.

تحقق من:

  • أن شهادة TLS تغطي أسماء المضيف المطلوبة؛
  • صحة إعادة التوجيه من HTTP إلى HTTPS؛
  • بقاء سلوك العنوان الأساسي بين النطاق الجذري وwww كما كان؛
  • فهم افتراضات HSTS؛
  • أن CDN/WAF يوجّه إلى الأصل الجديد أو يسمح به؛
  • استمرار معالجة عنوان IP الحقيقي للعميل عند استخدام وكيل؛
  • وصول ويب هوك الدفع إلى الأصل الجديد؛
  • تحديث مزودي API الذين يسمحون بعنوان IP القديم للخادم؛
  • صلاحية بيانات اعتماد SMTP/API من الخادم الجديد.

اجعل الاستثناءات المؤقتة للجدار الناري أو WAF محدودة، وأزلها بعد القبول.

حافظ على SEO عند بقاء عناوين URL

يحافظ تغيير الاستضافة وحدها عادةً على عناوين URL العامة نفسها. في هذه الحالة تكون مهمة SEO أساسًا الحفاظ على التكافؤ، لا إعداد خريطة إعادة توجيه.

قارن قبل التحويل وبعده:

  • رموز حالة HTTP؛
  • العناوين الأساسية canonical؛
  • robots.txt؛
  • وسم meta robots وأي noindex غير مقصود؛
  • عناوين خريطة الموقع؛
  • الروابط الداخلية؛
  • البيانات المنظمة حيث تكون مهمة؛
  • محتوى الصفحات وملفات العرض؛
  • التحقق في Search Console؛
  • استجابات الخادم لـ Googlebot والمستخدمين العاديين.

توصي Google Search Central بتجهيز الاستضافة الجديدة واختبارها، وعدم تغيير DNS قبل الجاهزية، ومراقبة الاستضافتين القديمة والجديدة، وإيقاف البنية القديمة بعد انتقال الزيارات. وتوصي أيضًا بخفض TTL مسبقًا والحفاظ على عمل التحقق في Search Console.

إذا تغيرت البنية التحتية للاستضافة فقط وبقي النطاق وعناوين URL كما هما، فلا تستخدم أداة Change of Address في Google Search Console. هذه الأداة لنقل النطاقات، لا لنقل استضافة مع بقاء العناوين.

إذا تغير النطاق أو مسارات URL أيضًا، فاستخدم خريطة من العناوين القديمة إلى الجديدة وإعادة توجيه دائمة على الخادم. هذه مهمة نقل موقع مختلفة عن النقل إلى VPS مع بقاء العناوين.

بمجرد كتابة طلبات أو تسجيلات أو تعليقات أو ملفات مرفوعة على الخادم الجديد، قد يؤدي التراجع عبر DNS وحده إلى فقد تلك التغييرات. عندئذ يتطلب التراجع تسوية البيانات أو مزامنة أخرى مخططًا لها.

حدد شروط تفعيل التراجع قبل النقل، مثل:

  • أخطاء 5xx واسعة الانتشار؛
  • فشل إتمام الشراء أو الدفع؛
  • تلف قاعدة البيانات أو فقد عمليات كتابة؛
  • عدم توافق خطير في بيئة التشغيل؛
  • تعطل المصادقة؛
  • فشل حرج في البريد أو الويب هوك يتعذر إصلاحه ضمن الفترة المتفق عليها.
