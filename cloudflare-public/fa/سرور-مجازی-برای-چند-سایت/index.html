بررسی معماری VPS برای چند سایت

با این ابزار بررسی کنید آیا یک VPS همچنان دامنه خرابی مناسبی است.

ویژگی‌هایی را انتخاب کنید که واقعاً در مجموعه سایت‌ها وجود دارند.

بار کاری را بشمارید، نه دامنه‌ها را

پرسش «یک VPS چند سایت میزبانی می‌کند؟» پاسخ ثابت قابل اتکا ندارد.

مدل مفید ظرفیت:

بار چند سایت = مجموع ترافیک عادی + اوج‌های پویای هم‌پوشان + پایگاه‌های داده + کران و پردازشگر + پشتیبان و ورود داده + پنل و ایمیل و پایش + ظرفیت ذخیره

نمونه‌ها:

  • ده سایت ایستا یا با کش گسترده شاید ظرفیت PHP و DB بسیار کمی مصرف کنند؛
  • سه سایت کسب‌وکار وردپرس ممکن است رم بسیار بیشتری بخواهند، چون هرکدام پردازشگر PHP و بار DB دارند؛
  • یک فروشگاه ووکامرس می‌تواند هنگام تسویه‌حساب یا فروش ویژه کل سرور را درگیر کند؛
  • یک ورود تصویر، پشتیبان یا اسکن امنیتی ممکن است موقتاً CPU و ورودی/خروجی بیشتری از مجموع چند سایت آرام مصرف کند.

سنگین‌ترین بار هم‌زمان را حساب کنید، نه تعداد دامنه پنل را.

یک VPS چند سایت میزبانی می‌کند؟

تعداد سایت را فقط برای فهرست دارایی‌ها استفاده کنید.

ظرفیت به این‌ها بستگی دارد:

  • نرخ موفقیت کش؛
  • هم‌زمانی درخواست بدون کش؛
  • حافظه پردازشگر PHP یا برنامه؛
  • مدت درخواست؛
  • مجموعه داده فعال DB؛
  • شدت نوشتن؛
  • کار زمان‌بندی‌شده و پس‌زمینه؛
  • ترافیک ربات؛
  • رشد ذخیره‌سازی و رسانه؛
  • بازه پشتیبان‌گیری؛
  • سربار پنل و ایمیل؛
  • مقدار ظرفیت آزادی که می‌گذارید.

اگر مصرف‌کنندگان اصلی منابع را نمی‌شناسید، اطمینان هر برآورد «N سایت» کم است.

برای رفتار خاص وردپرس، سرور مجازی برای وردپرس را ببینید. فروشگاه تراکنشی را جدا ارزیابی کنید؛ سرور مجازی برای ووکامرس به آن می‌پردازد.

یک IP می‌تواند میزبان چند سایت باشد

سایت‌های معمول امروزی برای هر دامنه به IP عمومی جدا نیاز ندارند.

در میزبانی مجازی مبتنی بر نام:

  1. DNS چند دامنه را به یک IP سرور اشاره می‌دهد؛
  2. مرورگر نام میزبان درخواستی را می‌فرستد؛
  3. Nginx/Apache آن نام را با بلوک سرور یا میزبان مجازی درست تطبیق می‌دهد؛
  4. TLS از SNI استفاده می‌کند تا سرور گواهی مناسب هر نام میزبان را ارائه دهد.

به همین دلیل چند سایت نامرتبط HTTPS می‌توانند پورت‌های 80/443 یک IP را شریک باشند.

IP جدا برای سیاست خاص شبکه، نیاز قدیمی، اعتبار ایمیل یا سرویس غیر وب هنوز ممکن است مهم باشد، اما الزام عادی هر سایت نیست.

هر سایت را آگاهانه جدا کنید

پوشه‌های جدا سازمان‌دهی‌اند، نه جداسازی قوی.

برای سایت نامرتبط یا مشتری، هرجا عملی است مرزهای جدا ایجاد کنید:

مرزاهمیت
کاربر سیستم یا پنلکاهش دسترسی متقابل به فایل و اطلاعات ورود سایت نامرتبط
ریشه اسنادجدانگه‌داشتن فایل برنامه و مسیر استقرار
pool در PHP-FPM یا فرایند برنامهاجرای هر سایت با کاربر و تنظیم فرایند خودش
پایگاه داده و کاربر DBمحدودکردن دسترسی و دامنه پشتیبان و بازیابی
لاگعیب‌یابی و تشخیص منشأ رخداد روشن‌تر
اطلاعات محرمانه و فایل محیطیجلوگیری از خواندن اطلاعات ورود برنامه دیگر
مجموعه پشتیبانبازیابی یک سایت بدون عقب‌بردن کل مجموعه

الگوی غلط رایج اجرای همه سایت‌های PHP با یک کاربر Unix و فایل پیکربندی قابل خواندن مشترک است. در این حالت نفوذ از یک افزونه می‌تواند به نفوذ چند سایت تبدیل شود.

راهنمای امنیت خود FASTPANEL کاربران جدا برای سایت‌های جدا توصیه می‌کند. اگر رابط هاست می‌خواهید، سرور مجازی با کنترل پنل را مقایسه کنید؛ روند اختصاصی در میزبانی سرور مجازی با FASTPANEL آمده است.

جداسازی poolهای PHP، سرویس برنامه و اطلاعات ورود DB

برای سایت PHP، poolهای جدا در PHP-FPM به جداسازی این‌ها کمک می‌کنند:

  • کاربر و گروه Unix؛
  • سقف پردازشگر؛
  • پیکربندی PHP؛
  • لاگ؛
  • سوکت؛
  • رفتار منابع.

برای Node.js، Python و برنامه اختصاصی، کاربر و سرویس جدا و پورت یا سوکت محلی جدا استفاده کنید.

برای پایگاه داده:

  • پایگاه‌های داده جدا داشته باشید؛
  • اطلاعات ورود جدا استفاده کنید؛
  • فقط مجوز لازم هر برنامه را بدهید؛
  • یک حساب root یا مدیر DB مشترک به همه سایت‌ها ندهید.

این جداسازی کامل و سخت چندمستاجری ایجاد نمی‌کند، اما مهار آسیب و عیب‌یابی را به‌طور محسوسی بهتر می‌کند.

بارهای ترکیبی بودجه متفاوت می‌خواهند

منابع مجموعه ترکیبی را طوری نسنجید که گویی همه سایت‌ها یکسان‌اند.

سایت ایستا یا کش‌شده

معمولاً CPU برنامه و DB کمی مصرف می‌کند.

وردپرس

بودجه پردازشگر PHP، پایگاه داده، کش و کران می‌خواهد.

ووکامرس، عضویت یا سایت تراکنشی

ظرفیت آزاد بیشتری برای PHP و DB پویا و برنامه دقیق پس‌زمینه می‌خواهد.

برنامه اختصاصی

شاید فرایند دائمی، صف، کانتینر، محیط اجرای متفاوت یا پورت جدا بخواهد.

سنگین‌ترین سایت اغلب تعیین می‌کند کل VPS باید بزرگ‌تر شود یا همان سایت باید بیرون برود.

سایت‌های خودتان هم می‌توانند همسایه پرمصرف شوند

VPS بخشی از وابستگی به مشتریان نامرتبط هاست اشتراکی را حذف می‌کند، اما تجمیع همسایه پرمصرف داخلی می‌سازد.

یک سایت می‌تواند از این راه‌ها سهم نامتناسب منابع بگیرد:

  • جهش ترافیک؛
  • افزونه یا پرس‌وجوی بد؛
  • حمله ربات؛
  • پردازش تصویر؛
  • ورود یا خروج داده؛
  • اسکن امنیتی؛
  • فشرده‌سازی پشتیبان؛
  • کران مهارنشده؛
  • رشد زیاد لاگ؛
  • قفل پایگاه داده یا فشار ورودی/خروجی.

مصرف منابع را هنگام این رویدادها ببینید، نه فقط در حالت بیکار سرور.

اگر پشته پشتیبانی می‌کند، سقف پردازشگر و فرایند هر سایت یا محدودیت کانتینر و cgroup می‌تواند احتمال مصرف همه منابع توسط یک بار را کم کند؛ اما سهمیه سخت CPU و رم توسط پنل را فرض نکنید مگر مستندات آن صریحاً بگوید.

اوج مجموع بار از میانگین مهم‌تر است

سرور چندسایتی هنگام هم‌پوشانی اوج‌های مستقل دچار مشکل می‌شود.

برای مثال:

  • سایت A جهش کمپین دارد؛
  • سایت B داده وارد پایگاه می‌کند؛
  • سایت C پشتیبان کامل شروع می‌کند؛
  • سایت D اسکن بدافزار اجرا می‌کند؛
  • کنترل پنل لاگ‌ها را می‌چرخاند؛
  • بافر پایگاه داده هم از قبل بزرگ است.

هر سایت جداگانه کوچک به نظر می‌رسد، اما با هم می‌توانند CPU، رم یا ورودی/خروجی را تمام کنند.

نگهداری و پس‌زمینه را برای کل مجموعه برنامه‌ریزی کنید، نه برای هر سایت به‌تنهایی.

مدیریت دستی، کنترل پنل یا کانتینر؟

بلوک سرور یا میزبان مجازی دستی

مناسب است وقتی:

  • یک مسئول توانمند سرور را اداره می‌کند؛
  • تعداد سایت متوسط است؛
  • پشته‌ها مشابه‌اند؛
  • خودکارسازی و اسکریپت پیکربندی را یکدست نگه می‌دارند.

مسیر عمومی استقرار در نحوه میزبانی سایت روی سرور مجازی آمده است.

کنترل پنل هاست

مفیدند وقتی:

  • دامنه‌ها و کاربران زیاد مدیریت روزمره می‌خواهند؛
  • دسترسی مشتری یا واگذارشده مهم است؛
  • رابطی برای SSL، PHP، پایگاه داده، پشتیبان و ایمیل می‌خواهید.

مدل کاربر و حساب پنل از تعداد دامنه‌ای که ادعا می‌کند پشتیبانی می‌کند مهم‌تر است.

کانتینرها

مفیدند وقتی:

  • جداسازی وابستگی و محیط اجرا مهم است؛
  • برنامه‌ها پشته متفاوت دارند؛
  • استقرارها از ابتدا مبتنی بر کانتینرند؛
  • تیم از قبل عملیات کانتینر را می‌شناسد.

کانتینر خودکار ساده‌تر نیست؛ چرخه عمر ایمیج، شبکه، حجم پایدار، پشتیبان و پایش را اضافه می‌کند.

سایت‌های آژانس و مشتریان

آژانس نمونه طبیعی میزبانی چند سایت است، اما مالکیت مشتری نیاز به جداسازی را افزایش می‌دهد.

مشخص کنید:

  • مالک دامنه و DNS کیست؛
  • حساب‌های جدا پنل و سیستم؛
  • اطلاعات ورود جدا DB؛
  • دسترسی واگذارشده؛
  • مسئول پشتیبان هر مشتری؛
  • دقت تفکیک در بازیابی؛
  • مسیر مهاجرت یا خروجی هنگام خروج مشتری؛
  • مسئول به‌روزرسانی برنامه؛
  • اینکه رخداد سایت یک مشتری مجاز است بر بقیه اثر بگذارد یا نه.

اگر همه سایت‌های مشتریان کاربر Unix و دامنه خرابی یکسان دارند، به مشتری وعده «میزبانی مجزا» ندهید.

موضوع پیشنهادی قبلی VPS برای سایت‌های آژانس فعلاً در همین صفحه ادغام می‌ماند، مگر بررسی آینده نتایج جست‌وجو و حجم تقاضا، موضوع مستقل روشنی را ثابت کند.

اگر کسی در تیم مسئول به‌روزرسانی سیستم‌عامل، امنیت، تأیید پشتیبان، پایش و رخداد سرور مشترک نیست، پیش از تجمیع سایت مشتری این مسئله را حل کنید؛ سرور مجازی مدیریت شده یا مدیریت نشده را ببینید.

برای انتقال مجموعه موجود به یک VPS، همه سایت‌ها را کپی و همه DNSها را یکجا عوض نکنید. مرحله‌بندی، آزمون و انتقال با مسیر بازگشت انجام دهید؛ روند در انتقال سایت به سرور مجازی آمده است.

پشتیبان و تفکیک در بازیابی

یک VPS یعنی چند سایت می‌توانند هم‌زمان خراب شوند.

طراحی مفید پشتیبان باید پاسخ این پرسش‌ها را روشن کند:

  • آیا فقط سایت A را می‌توانم بازیابی کنم؟
  • آیا فقط پایگاه داده آن را می‌توانم بازیابی کنم؟
  • آیا پس از ازدست‌رفتن دیسک یا سرور، کل VPS بازیابی می‌شود؟
  • نسخه خارج سرور هست؟
  • بین پشتیبان‌ها چه مقدار داده ممکن است از بین برود؟
  • آیا می‌توانم بازیابی را بدون بازنویسی بقیه سایت‌ها بررسی کنم؟

ایمیج کامل سرور برای بازیابی بحران مفید است، اما اگر بازیابی یک سایت آلوده همه سایت‌های دیگر را هم عقب ببرد، نباید تنها روش بازیابی باشد. برای نگهداری، نسخه خارج سایت، RPO/RTO و آزمون بازیابی، استراتژی پشتیبان گیری سرور مجازی را ببینید.

یک VPS، یک دامنه خرابی

تجمیع هزینه و مدیریت تکراری را کم می‌کند، اما دامنه اثر خرابی را بزرگ‌تر می‌کند.

یک رویداد می‌تواند همه سایت‌ها را درگیر کند:

  • قطعی VPS؛
  • پرشدن فایل‌سیستم؛
  • به‌روزرسانی بد سیستم‌عامل یا پشته وب؛
  • خرابی پایگاه داده؛
  • اشتباه فایروال؛
  • نفوذ به حساب مدیر؛
  • بدافزار یا نفوذ root؛
  • حذف تصادفی؛
  • پشتیبان‌گیری که دیسک یا ورودی/خروجی را تمام می‌کند.

پرسش وجود ریسک نیست؛ ریسک وجود دارد. پرسش این است که کسب‌وکار آن را می‌پذیرد یا نه.

چه زمانی سایت یا بار را جدا کنید؟

وقتی دلیل از نظر عملیاتی قابل اندازه‌گیری است، تفکیک کنید.

نشانه‌های قوی:

  • یک سایت مرتب CPU، رم یا ورودی/خروجی را در اختیار می‌گیرد؛
  • سایت حیاتی نمی‌تواند ریسک قطعی را با سایت کم‌اولویت شریک شود؛
  • بار ووکامرس یا فروشگاه سایت‌های آرام دیگر را مختل می‌کند؛
  • نیازهای ناسازگار سیستم‌عامل، محیط اجرا یا امنیت وجود دارند؛
  • یک پایگاه داده رم، ورودی/خروجی یا رشد مستقل می‌خواهد؛
  • پردازشگرها و کارهای پس‌زمینه منابع را غالباً مصرف می‌کنند؛
  • بازه نگهداری متفاوت است؛
  • مرز مشتری یا الزام انطباق، جداسازی قوی‌تر می‌خواهد؛
  • رقابت منابع پس از بهینه‌سازی و زمان‌بندی باقی مانده است.

الگوهای ممکن تفکیک:

  • سایت حیاتی -> VPS خودش؛
  • وب -> VPS جدا برای DB؛
  • وب -> VPS جدا برای پردازشگر پس‌زمینه؛
  • آژانس -> گروه‌های جدا مشتری؛
  • محیط عملیاتی -> محیط آزمایشی جدا؛
  • بار فروشگاهی یا پرنوشتن -> سرور جدا.

خودکار تفکیک نکنید؛ هر VPS اضافه، پایش، پشتیبان، وصله، شبکه و سطح رخداد را بیشتر می‌کند.

پرسش‌های متداول

روی یک VPS چند سایت می‌توانم میزبانی کنم؟

عدد ثابت قابل اتکا وجود ندارد. ظرفیت به اوج مجموع CPU، رم، پردازشگر PHP یا برنامه، کار پایگاه داده، ذخیره‌سازی و پس‌زمینه همه سایت‌ها بستگی دارد.

آیا چند سایت IPهای جدا لازم دارند؟

معمولاً نه. میزبانی مجازی مبتنی بر نام و TLS SNI اجازه می‌دهد چند دامنه HTTPS یک IP عمومی را شریک شوند. IP جدا برای نیاز خاص شبکه، ایمیل یا سامانه قدیمی هنوز ممکن است مفید باشد.

آیا چند سایت وردپرس می‌توانند یک VPS را شریک شوند؟

بله. کاربران و اطلاعات ورود را جدا کنید و سرور را برای مجموع بار PHP، پایگاه داده و پس‌زمینه بسنجید. چند وردپرس سبک ممکن است خوب جا شوند؛ یک سایت پویای سنگین می‌تواند سرور را غالباً مصرف کند.

آیا هر سایت باید pool جدا در PHP-FPM داشته باشد؟

برای سایت PHP نامرتبط یا مشتری، pool جدا جداسازی کاربر و فرایند و تنظیم و لاگ هر سایت را روشن‌تر می‌کند. طراحی دقیق به مدل پنل و پشته وب بستگی دارد.

آیا یک فروشگاه ووکامرس می‌تواند VPS را با سایت‌های دیگر شریک شود؟

می‌تواند، اما اوج تسویه‌حساب، پایگاه داده و پس‌زمینه فروشگاه ممکن است بار غالب شود. اگر فروشگاه حیاتی است یا مرتب منابع بقیه را می‌گیرد، جدا کنید.

آیا کنترل پنل برای میزبانی چند سایت بهتر است؟

اغلب از نظر مدیریت بله. پنل مدیریت دامنه، کاربر، SSL، PHP، DB و پشتیبان را ساده می‌کند، اما مدل جداسازی کاربر و حساب و سربار منابع آن را بررسی کنید.

آیا برای چند سایت کانتینر لازم است؟

خیر. میزبان مجازی Nginx/Apache با کاربران و فرایندهای جدا می‌تواند چند سایت میزبانی کند. کانتینر وقتی مفید است که جداسازی وابستگی و فرایند، پیچیدگی عملیاتی اضافه را توجیه کند.

ریسک اصلی چند سایت روی یک VPS چیست؟

دامنه اثر خرابی. یک قطعی، به‌روزرسانی بد، پرشدن دیسک یا نفوذ سطح سرور می‌تواند همه سایت‌های VPS را درگیر کند.

آیا آژانس باید همه مشتریان را روی یک VPS بگذارد؟

فقط وقتی دامنه خرابی مشترک را می‌پذیرد و جداسازی قوی حساب، فایل و DB، پشتیبان، پایش و روند خروج مشتری را اجرا می‌کند. مشتری حیاتی یا ناسازگار ممکن است سرور جدا بخواهد.

چه زمانی به چند VPS تفکیک کنم؟

وقتی یک بار منابع را غالباً مصرف می‌کند، سایت حیاتی جداسازی مستقل خرابی می‌خواهد، پشته یا مرز امنیتی ناسازگار است، یا DB و پردازشگر رشد مستقل لازم دارند.
