Главный предел — не количество доменов, а суммарная пиковая нагрузка на CPU, ОЗУ, процессы PHP и приложений, базы данных и диски с учётом фоновых заданий и резервного копирования всех сайтов сервера.

Проверка архитектуры VPS для нескольких сайтов

Определите, подходит ли вашим сайтам общая область отказа одного VPS.

Выберите характеристики, соответствующие вашему набору сайтов.

Оценивайте нагрузку, а не число доменов

Вопрос «Сколько сайтов может разместить один VPS?» не имеет надежного фиксированного ответа.

Полезная модель расчёта ресурсов:

нагрузка нескольких сайтов = суммарный обычный трафик + совпадающие пики динамики + базы данных + cron/рабочие процессы + копирование/импорт + панель/почта/мониторинг + запас ресурсов

Примеры:

  • десять статических сайтов или сайтов с активным кешированием могут потреблять совсем немного ресурсов PHP и БД;
  • трем бизнес-сайтам WordPress может потребоваться значительно больше оперативной памяти, потому что каждый из них имеет процессы PHP и рабочую нагрузку базы данных;
  • один магазин WooCommerce может доминировать над всем сервером во время оформления заказа или распродажи;
  • Один импорт изображения, резервное копирование или сканирование безопасности может временно потреблять больше CPU / I / O, чем несколько тихих веб-сайтов вместе взятых.

Подсчитайте самую тяжелую одновременную рабочую нагрузку, а не количество доменов в панели управления.

Сколько сайтов может разместить один VPS?

Количество сайтов используйте лишь для учёта их состава.

Необходимые ресурсы зависят от:

  • доли попаданий в кеш;
  • числа одновременных некешируемых запросов;
  • потребления памяти рабочими процессами PHP и приложений;
  • длительность запроса;
  • набор данных базы данных, хранящийся в памяти;
  • интенсивность записи;
  • плановые/фоновые задания;
  • трафик ботов;
  • роста данных и медиафайлов;
  • периодов резервного копирования;
  • панельное/почтовое дополнительное потребление ресурсов;
  • оставленного запаса ресурсов.

Если вы не можете определить доминирующих потребителей ресурсов, доверие к любой оценке «N веб-сайтов» низкое.

Для конкретного поведения WordPress используйте VPS для WordPress. Транзакционный магазин следует рассматривать отдельно; см. VPS для WooCommerce.

Один IP может содержать несколько веб-сайтов

Обычные современные веб-сайты не нуждаются в одном публичном IP на домен.

С именным виртуальным хостингом:

  1. DNS указывает несколько доменов на один и тот же VPS IP;
  2. браузер отправляет запрошенное имя хоста;
  3. Nginx / Apache соответствует имени хоста правильному серверному блоку / виртуальному хосту;
  4. TLS использует SNI, чтобы сервер мог представить соответствующий сертификат для каждого имени хоста.

Вот почему многие несвязанные HTTPS-сайты могут совместно использовать порты 80/443 на одном IP.

Отдельный IP может по-прежнему иметь значение для специальных сетевых политик, устаревших требований, репутации почты или не веб-сервисов, но это не является обычным требованием для каждого веб-сайта.

Размещение сайтов в разных папках — это организация, а не сильная изоляция.

Типичная ошибка — запускать все PHP-сайты под одним пользователем Unix с доступными для чтения конфигурационными файлами. Тогда взлом одного плагина может привести к взлому соседних сайтов.

Рекомендации FASTPANEL по безопасности предусматривают отдельных пользователей FASTPANEL для разных сайтов. Выбор интерфейса управления хостингом рассматривается на странице «VPS с панелью управления», а работа с конкретной панелью — на странице «VPS-хостинг с FASTPANEL».

Отдельные пулы PHP, сервисы приложений и учетные данные базы данных

Для сайтов PHP отдельные пулы PHP-FPM могут помочь изолировать:

  • Unix пользователь/группа;
  • ограничения рабочих процессов;
  • PHP конфигурация;
  • журналы;
  • сокеты;
  • потребление ресурсов.

Для приложений Node.js/Python/custom используйте отдельные пользователи/сервисы приложений и локальные порты/сокеты.

Для баз данных:

  • использовать отдельные базы данных;
  • использовать отдельные учетные данные;
  • предоставлять только те привилегии, которые нужны каждому приложению;
  • не давайте каждому сайту одну общую учетную запись root/admin DB.

Это не создаёт полной жёсткой изоляции клиентов, но заметно ограничивает последствия инцидентов и упрощает диагностику.

Смешанные рабочие нагрузки требуют разных бюджетов

Не рассчитывайте ресурсы разнородного набора сайтов так, словно все сайты одинаковы.

Статические / кешированные сайты

Обычно мало нагружают CPU приложения и БД.

WordPress

Нужны ресурсы для процессов PHP, базы данных, кеша и cron.

WooCommerce, сайты с подписками и транзакционные сайты

Нужен больший запас ресурсов PHP и БД для динамических запросов и тщательное планирование фоновых заданий.

Собственные приложения

Могут потребоваться постоянные процессы, очереди, контейнеры, различные среды выполнения или отдельные порты.

Самый тяжёлый сайт часто определяет, нужно ли увеличивать весь VPS или переносить этот сайт отдельно.

Собственные сайты могут стать шумными соседями

VPS снижает зависимость от посторонних клиентов виртуального хостинга, но объединение сайтов создаёт собственных «шумных соседей».

Один сайт может потреблять непропорциональные ресурсы за счет:

  • всплеск трафика;
  • плохой плагин/запрос;
  • бот-атака;
  • обработка изображений;
  • импорт/экспорт;
  • сканирование безопасности;
  • сжатие резервных копий;
  • вышедшие из-под контроля задачи cron;
  • быстрый рост журналов;
  • блокировки БД и высокая нагрузка на ввод-вывод.

Наблюдайте за использованием ресурсов во время этих событий, а не только когда сервер простаивает.

Если стек это поддерживает, ограничения рабочих процессов для отдельных сайтов или лимиты контейнеров/cgroup снижают риск захвата всех ресурсов одной нагрузкой. Но не считайте, что панель автоматически обеспечивает жёсткие квоты CPU и ОЗУ, если это не указано в документации.

Комбинированные пики имеют большее значение, чем среднее использование

Многосайтовые серверы выходят из строя, когда независимые пики перекрываются.

Например:

  • сайт A получает всплеск трафика от рекламной кампании;
  • Сайт B запускает импорт базы данных;
  • Сайт C начинает полное резервное копирование;
  • Сайт D запускает сканирование вредоносных программ;
  • панель управления выполняет ротацию журналов;
  • Буфер базы данных уже большой.

Индивидуально каждый сайт может выглядеть небольшим. Вместе они могут исчерпать CPU, ОЗУ или I/O.

Планируйте обслуживание и фоновые работы для всего набора сайтов, а не для каждого сайта отдельно.

Ручная настройка, панель или контейнеры?

Ручные серверные блоки / виртуальные хосты

Хорошо, когда:

  • один компетентный оператор управляет сервером;
  • количество сайтов скромное;
  • стеки аналогичны;
  • автоматизация и скрипты поддерживают согласованность конфигурации.

Общий путь развертывания описан в Как разместить веб-сайт на VPS.

Панель управления хостингом

Полезно, когда:

  • многие домены/пользователи нуждаются в рутинном администрировании;
  • важен доступ клиентов или делегирование прав;
  • Вам нужен пользовательский интерфейс для SSL, PHP, баз данных, резервных копий и почты.

Модель пользователей и учётных записей панели важнее заявленного числа поддерживаемых доменов.

контейнеры

Полезно, когда:

  • Важное значение имеет изоляция среды зависимости/выполнения;
  • приложения имеют разные стеки;
  • Развертывание является контейнерным;
  • Команда уже знает о контейнерных операциях.

Контейнеры не делают всё автоматически проще. Они требуют управления жизненным циклом образов, сетью, постоянными томами, копиями и мониторингом.

Сайты агентств и клиентов

Для агентства размещение нескольких сайтов естественно, но принадлежность сайтов разным клиентам повышает требования к изоляции.

Определить:

  • кому принадлежит домен/DNS;
  • отдельные учётные записи в панели и системе;
  • отдельные учетные данные БД;
  • делегированный доступ;
  • ответственность за копии каждого клиента;
  • возможность выборочного восстановления;
  • путь миграции/экспорта, когда клиент уходит;
  • кто отвечает за обновление приложений;
  • Может ли инцидент одного сайта клиента повлиять на другие.

Не обещайте клиенту «изолированный хостинг», если все клиентские сайты работают под одним пользователем Unix и находятся в общей области отказа.

Прежняя тема-кандидат «VPS для сайтов агентств» остаётся частью этой страницы, пока анализ поисковой выдачи и частотности не подтвердит необходимость отдельной страницы с самостоятельным поисковым намерением.

Если никто в команде не отвечает за обновления ОС, безопасность, проверку копий, мониторинг и инциденты общего сервера, решите это до объединения сайтов клиентов: см. «Управляемый и неуправляемый VPS».

При переносе набора действующих сайтов на один VPS не копируйте все сайты с одновременным изменением всего DNS. Подготовьте среду, проверьте и переключайте с возможностью отката; порядок описан в руководстве «Перенос сайта на VPS».

Резервные копии и выборочное восстановление

Один VPS означает, что несколько сайтов могут выйти из строя одновременно.

Полезный дизайн резервного копирования должен позволить вам ответить:

  • Могу ли я восстановить только сайт А?
  • можно ли восстановить только его базу данных?
  • Могу ли я восстановить полный VPS после потери диска/сервера?
  • Есть ли внесерверная копия?
  • Сколько данных можно потерять между резервными копиями?
  • Могу ли я проверить восстановление без перезаписи других сайтов?

Образ всего сервера полезен для аварийного восстановления, но не должен быть единственным способом, если восстановление одного взломанного сайта вынуждает откатить все остальные. Сроки хранения, внешние копии, RPO/RTO и проверка восстановления описаны в стратегии резервного копирования VPS.

Один VPS — одна общая область отказа

Консолидация снижает затраты и дублирование администратора, но увеличивает масштаб воздействия.

Одно событие может повлиять на каждый сайт:

  • отключение VPS;
  • заполнение файловой системы;
  • плохое обновление ОС/веб-стека;
  • сбой базы данных;
  • ошибка брандмауэра;
  • скомпрометированный аккаунт администратора;
  • вредоносное ПО или взлом с правами root;
  • случайное удаление;
  • задача копирования, исчерпывающая место на диске или пропускную способность ввода-вывода.

Вопрос не в том, существует ли этот риск, а в том, принимает ли его бизнес.

Когда разделять сайты или рабочие нагрузки

Разделяйте сайты, когда для этого есть измеримая эксплуатационная причина.

Веские основания:

  • один сайт многократно доминирует над CPU/ОЗУ/I/O;
  • один критически важный для бизнеса сайт не может разделить риск отключения с менее приоритетными сайтами;
  • нагрузка WooCommerce или другого магазина мешает остальным малонагруженным сайтам;
  • существуют несовместимые требования к ОС/среде выполнения/безопасности;
  • одна база данных нуждается в независимом ОЗУ/I/O/масштабировании;
  • фоновые процессы/задачи доминируют над ресурсами;
  • окна технического обслуживания отличаются;
  • разделение клиентов или нормативные требования требуют более строгой изоляции;
  • Конкуренция ресурсов остается после оптимизации и планирования.

Возможные шаблоны разделения:

  • критический сайт -> собственный VPS;
  • веб-сервер -> отдельный VPS для БД;
  • веб-сервер -> отдельный VPS для фоновых обработчиков;
  • агентства -> отдельные группы клиентов;
  • рабочая среда -> отдельная тестовая среда;
  • интенсивная запись или магазин -> отдельный сервер.

Не разделяйте автоматически: каждый дополнительный VPS требует мониторинга, копий, обновлений и настройки сети, а также создаёт новые возможные точки инцидентов.

Мониторинг многосайтового VPS

Мониторинг осуществляется на двух уровнях.

Уровень сервера

  • ЦП;
  • ОЗУ/swap/OOM;
  • использование диска;
  • I/O ожидание;
  • состояние БД;
  • сеть;
  • работоспособность процессов и служб.

Уровень сайта

  • внешние HTTP(S) проверки на каждое важное имя хоста;
  • время отклика;
  • 5xx ошибки;
  • Журналы PHP/app;

Частые вопросы

Сколько сайтов я могу разместить на одном VPS?

Надёжного фиксированного числа нет. Ресурсы определяются суммарной пиковой нагрузкой всех сайтов на CPU, ОЗУ, процессы PHP и приложений, базы данных и диски с учётом фоновых заданий.

Нужны ли нескольким сайтам отдельные IP-адреса?

Обычно нет. Виртуальные хосты по имени и TLS SNI позволяют нескольким HTTPS-доменам использовать один публичный IP. Отдельные IP могут потребоваться для особых сетевых, почтовых требований или совместимости со старыми системами.

Могут ли несколько сайтов WordPress использовать один VPS?

Да. Используйте отдельных пользователей и учётные данные, рассчитывайте сервер по суммарной нагрузке PHP, БД и фоновых задач. Несколько лёгких сайтов WordPress могут хорошо уживаться; один тяжёлый динамический сайт способен занять основную часть ресурсов.

Должен ли каждый сайт иметь отдельный пул PHP-FPM?

Для несвязанных или клиентских PHP-сайтов отдельные пулы могут улучшить изоляцию процесса / пользователя и сделать более четкой настройку / журналирование каждого сайта. Точный дизайн зависит от модели панели / веб-стека.

Может ли один магазин WooCommerce поделиться VPS с другими сайтами?

Может, но пики оформления заказов, БД и фоновых задач магазина способны стать основной нагрузкой. Если магазин критичен для бизнеса или регулярно лишает другие сайты ресурсов, выделите его отдельно.

Является ли панель управления лучше для размещения нескольких веб-сайтов?

Часто для администрирования. Панель может упростить домены, пользователей, SSL, PHP, DB и резервные копии, но проверить свою модель изоляции пользователя / учетной записи и потребление дополнительных ресурсов.

Требуются ли контейнеры для нескольких веб-сайтов?

Нет. Виртуальные хосты Nginx/Apache плюс отдельные пользователи/процессы могут размещать много сайтов. Контейнеры полезны, когда изоляция зависимости/процесса оправдывает дополнительную операционную сложность.

Каков основной риск размещения нескольких сайтов на одном VPS?

Масштаб последствий сбоя. Один простой, неудачное обновление, заполнение диска или взлом сервера может затронуть каждый сайт на этом VPS.

Должны ли агентства размещать всех клиентов на одном VPS?

Только если агентство принимает общий риск отказа и обеспечивает строгую изоляцию учётных записей, файлов и БД, копии, мониторинг и порядок переноса при уходе клиента. Критичным или несовместимым проектам могут понадобиться отдельные серверы.

Когда я должен разделиться на несколько VPS-серверов?

Когда одна нагрузка занимает основную часть ресурсов, критичному сайту нужна независимая защита от общих отказов, стеки или требования безопасности несовместимы либо БД и обработчикам нужно независимое масштабирование.
