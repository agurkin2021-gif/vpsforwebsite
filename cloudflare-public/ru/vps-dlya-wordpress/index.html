Требования WordPress не определяют ресурсы VPS

Сейчас WordPress.org рекомендует хостинг с поддержкой:

  • PHP 8.3 или выше;
  • MariaDB 10.11+ или MySQL 8.0+;
  • HTTPS;
  • Apache или Nginx как рекомендуемые варианты веб-сервера.

Эти требования отвечают на вопрос «может ли сервер запустить WordPress?» Они не отвечают на вопрос «какие ресурсы VPS нужны этой рабочей нагрузке?»

Рабочему VPS также нужны ОЗУ, CPU и хранилище для:

  • Linux;
  • Nginx/Apache;
  • PHP-FPM процессы;
  • MySQL/MariaDB;
  • OPcache;
  • кеш страницы/объекта, где используется;
  • панель управления;
  • почта, если размещена локально;
  • резервные копии;
  • задачи cron;
  • сканирование вредоносных программ/безопасности;
  • импорт/экспорт;
  • мониторинг;
  • эксплуатационного запаса ресурсов.

Не используйте программные требования WordPress как рекомендацию по ресурсам рабочего сервера.

Проверка выбора VPS для WordPress

Используйте этот инструмент как отправную точку. Он не заменяет реальные замеры CPU, ОЗУ и базы данных.

Когда WordPress действительно нужен VPS

Сайту WordPress может быть нужен VPS даже без огромного трафика.

Общие причины:

  • регулярное достижение лимитов CPU, памяти или процессов при нормальной нагрузке;
  • необходимость особой конфигурации PHP или среды выполнения;
  • необходимость Redis/Memcached или другого серверного сервиса;
  • настоящий системный cron вместо запуска задач при посещениях;
  • длительные фоновые задания;
  • пользовательское поведение Nginx/Apache;
  • несколько сайтов в единой контролируемой среде;
  • более строгая изоляция нагрузок и учётных записей;
  • требования к серверному мониторингу или межсетевому экрану.

Если единственный симптом — «сайт медленно работает», сначала изучите сравнение VPS и виртуального хостинга и убедитесь, что узкое место не в самом WordPress.

Когда WordPress не нужен VPS

Оставайтесь на хорошем виртуальном или управляемом WordPress-хостинге, если:

  • сайт легкий и стабильный;
  • кеширование работает;
  • показатели ресурсов хостинга не указывают на регулярное достижение лимитов;
  • не требуется пользовательский сервис / root-доступ;
  • команда не хочет поддерживать Linux;
  • провайдер уже достаточно хорошо обеспечивает резервное копирование, безопасность, обновления или тестовую среду;
  • переход на VPS в основном заменит простой хостинг дополнительной работой по эксплуатации.

VPS не становится быстрее автоматически. VPS с неверно подобранными ресурсами или без настройки может обслуживать WordPress хуже, чем хорошая управляемая платформа.

Процессы PHP и ОЗУ

Для некешируемых запросов процессы PHP-FPM — одно из основных ограничений параллельной обработки.

Каждый активный процесс потребляет память во время обработки запроса. Больше процессов могут обслуживать больше одновременных динамических запросов, но увеличение их числа без увеличения бюджета ОЗУ может вызвать:

  • использование swap;
  • нехватку памяти;
  • завершение процессов из-за OOM;
  • нехватку ресурсов у базы данных;
  • нестабильность сервера.

Практическая модель это:

ОЗУ для WordPress = ОС + веб-сервер + база данных + кеш + процессы PHP + панель/почта/задачи + запас

Тогда:

Бюджет процессов PHP = ОЗУ, которую безопасно выделить PHP / измеренная средняя память одного процесса

Не устанавливайте теоретически максимальное число процессов, если при этом не остаётся памяти для MySQL/MariaDB, кеша или ОС.

Авторизованные пользователи, wp-admin, запросы REST/API, поиск, формы, предпросмотр и персонализированные страницы чаще обходят полностраничный кеш и занимают процессы PHP.

Уровни кеширования WordPress

Кеширование — это не одна функция.

УровеньЧто кешируетсяОсновной эффект

Кеш страницотрисованный HTMLпозволяет обслуживать многие просмотры неавторизованных пользователей без запуска WordPress/PHP
Постоянный объектный кешповторно используемые объекты и результаты запросовсокращает повторную работу с базами данных/приложениями

В собственной документации по оптимизации WordPress рекомендует кеширование как важный инструмент производительности. Однако разные уровни кеша решают разные задачи.

Не называйте Redis кешем страниц. Redis часто используется как хранилище постоянного объектного кеша; полностраничное кеширование — отдельный уровень.

Постоянный кеш объектов и Redis

WordPress включает API объектного кеша, но по умолчанию этот кеш не сохраняется между запросами.

Для постоянного объектного кеширования нужны внешнее хранилище, например Redis или Memcached, и соответствующая интеграция с WordPress через drop-in.

Это помогает, когда сайт регулярно выполняет ресурсоёмкую работу с БД и объектами, но не обеспечивает автоматического ускорения.

Перед добавлением Redis:

  • убедитесь, что нагрузка сайта и БД выиграет от него;
  • проверьте, что для PHP и БД остаётся достаточно ОЗУ;
  • отслеживайте долю попаданий в кеш и потребление памяти;
  • принимайте решение о кеше страниц отдельно.

Сайт с эффективным полностраничным кешем и небольшой нагрузкой БД может получить меньше пользы от Redis, чем динамический сайт с подписками или большим числом запросов.

Потребности базы данных

Производительность WordPress может упереться в базу данных раньше, чем CPU окажется явно загружен до предела.

Проверьте:

  • медленные запросы;
  • большой объём options и автоматически загружаемых данных;
  • метаданные плагинов;
  • поиск/фильтрация/отчетные запросы;
  • нагрузки с интенсивным использованием postmeta;
  • набор данных базы данных, хранящийся в памяти;
  • одновременные операции записи;
  • импорт/экспорт;
  • задержки хранилища.

Дополнительные CPU не исправляют крайне неэффективный запрос. Больше ОЗУ может помочь, если базе данных действительно нужен больший рабочий набор в памяти, но не заменяет работу с индексами, запросами и плагинами.

Сначала измерения, затем масштабирование.

Плагины, темы и фоновые задачи

Плагин — это не только дисковое пространство.

Плагины/темы могут добавлять:

  • нагрузку PHP;
  • запросы к базе данных;
  • внешние вызовы API;
  • плановые задания;
  • инвалидацию кеша;
  • AJAX-запросы админки;
  • обработка изображений;
  • проверки безопасности;
  • резервные копии;
  • импорт/экспорт;
  • аналитика и журналирование.

Тяжёлые задачи могут совпасть с реальным пользовательским трафиком.

По возможности планируйте резервное копирование, сканирование, импорт и обработку изображений вне пиковых периодов. Если всплеск ресурсов вызывает один плагин или задача, исправьте или перенесите её по времени, прежде чем считать VPS слишком слабым.

WP-Cron и фоновые задачи

WP-Cron запускается по запросам WordPress, а не работает непрерывно, как системный планировщик.

Для обычных сайтов это может быть приемлемо. Для нагруженных сайтов или задач с точными сроками документация WordPress для разработчиков описывает вызов WordPress cron системным планировщиком с заданным интервалом.

При переходе на системный планировщик:

  • сначала настройте альтернативный запуск;
  • проверить, работает ли он;
  • только затем отключайте обычный запуск WP-Cron при посещениях, если это предусмотрено планом;
  • записывайте и отслеживайте сбои задач.

Не отключайте WP-Cron без другого планировщика.

Хранилище, медиафайлы, тестовая среда и резервные копии

При расчёте диска нужно учитывать не только ядро WordPress.

Заложите место для:

  • загрузок и медиафайлов;
  • база данных;
  • плагины/темы;
  • журналы;
  • кеш-файлы;
  • временные файлы обновления;
  • временных файлов обработки изображений;
  • копия тестовой среды;
  • архивы резервного копирования перед их перемещением с сервера;
  • ожидаемый рост.

Сайту, который сегодня занимает 20 ГБ, может потребоваться значительно больше временного места при клонировании, восстановлении, обновлении плагинов или сжатии резервной копии.

Не храните единственную резервную копию на VPS.

Ручная настройка, панель управления или FASTPANEL?

WordPress может отлично работать без cPanel или другой панели.

Ручное администрирование Linux

Хорошо подходит, когда вы хотите:

  • минимальный стек;
  • Администрирование SSH;
  • особая конфигурация Nginx/Apache/PHP/БД;
  • автоматизация или развертывание на основе Git.

Для ручного развёртывания используйте руководство «Как разместить сайт на VPS».

Универсальная панель управления

Полезна, если управление доменами, SSL, PHP, БД, пользователями, почтой или резервными копиями через браузер устраняет достаточно повторяющейся работы.

Используйте VPS с панелью управления.

FASTPANEL

Официальный процесс настройки FASTPANEL поддерживает создание сайта WordPress. Сейчас VDSina предлагает FASTPANEL на Ubuntu 22 как вариант с предустановленной панелью.

Для настройки и расчёта ресурсов именно под эту панель используйте руководство «VPS-хостинг с FASTPANEL».

Панель управления упрощает администрирование, но не превращает VPS в управляемую услугу.

Управляемый и самостоятельно администрируемый VPS для WordPress

На самостоятельно управляемом VPS кто-то должен отвечать за:

  • Обновления ОС/пакета;
  • SSH / файрвол;
  • Обновление PHP/веб-сервера;
  • администрирование базы данных;
  • обновления WordPress, плагинов и тем;
  • резервные копии и тесты восстановления;
  • мониторинг;
  • инциденты.

Если за эти задачи никто не отвечает, выбирайте услугу администрирования. Не рассчитывайте, что WordPress или панель управления будут обслуживать сервер.

См. «Управляемый и неуправляемый VPS».

WooCommerce — другой тип нагрузки WordPress

WooCommerce использует стек WordPress, но под реальным трафиком магазина ведёт себя иначе.

Корзина, оформление заказов, личный кабинет, заказы, остатки и многие задачи по расписанию динамичны. Их нельзя считать анонимными кешируемыми страницами блога.

Если транзакции магазина важны, используйте руководство по VPS для WooCommerce с отдельной моделью расчёта ресурсов и эксплуатации.

Несколько сайтов WordPress

Несколько сайтов WordPress совместно используют:

  • ЦП;
  • ОЗУ;
  • сервис баз данных;
  • PHP-процессы/пулы;
  • хранилище;
  • временные окна cron и фоновых задач;
  • время резервного копирования;
  • общую область отказа.

Десять малопосещаемых кешируемых сайтов могут создавать меньшую нагрузку, чем один активный динамический сайт с подписками.

При необходимости используйте отдельных пользователей и учётные данные БД, а ресурсы рассчитывайте по суммарному пику, а не по числу доменов.

См. VPS для нескольких сайтов.

Когда увеличивать ресурсы VPS для WordPress

Увеличивайте ресурсы только после измерения реального ограничения.

Веские основания:

  • устойчивая нехватка ОЗУ, использование swap или события OOM;
  • регулярные очереди к процессам PHP или полная занятость процессов;
  • устойчивая полная загрузка CPU после оптимизации кеша, запросов и плагинов;
  • задержки БД из-за реальной нехватки памяти для рабочего набора;
  • рост данных за пределы безопасного запаса хранилища;
  • регулярное совпадение фоновых задач с пользовательским трафиком;
  • несколько активных сайтов, истощающих общие ресурсы.

Если сайт медленный, а эти показатели в норме, более мощный VPS может не решить проблему.

Частые вопросы

Сколько оперативной памяти нужно WordPress на VPS?

Ядро WordPress не определяет требования к ОЗУ рабочего VPS. Памяти должно хватать на Linux, веб-сервер, процессы PHP, БД, кеши, панель, почту, фоновые задачи и запас. Лёгкому сайту может хватить 2 ГБ; 4 ГБ — более надёжная практическая база для коммерческого сайта.

Достаточно ли 1 ГБ оперативной памяти для WordPress VPS?

Такой объём позволяет запустить очень лёгкую или тестовую установку WordPress, но оставляет мало запаса для БД, процессов PHP и фоновых задач. Не считайте его обычной рекомендацией для рабочего сайта.

Достаточно ли 2 ГБ оперативной памяти для WordPress?

Этого может хватить для небольшого сайта с хорошим кешированием и лёгким стеком. Следите за памятью процессов PHP, ОЗУ базы данных, плагинами и фоновыми задачами.

Достаточно ли 4 ГБ оперативной памяти для WordPress?

Для многих коммерческих сайтов WordPress 4 ГБ — практичная отправная точка. Тяжёлые плагины, посещения авторизованных подписчиков, WooCommerce, крупные БД, импорт или несколько активных сайтов могут потребовать больше.

Сколько посетителей может обрабатывать WordPress VPS?

Надёжного универсального числа посетителей нет. Возможности определяют доля попаданий в кеш, параллельные некешируемые запросы, длительность PHP-запросов, ресурсоёмкость плагинов, работа БД и фоновые задачи.

Нужен ли Redis для WordPress на VPS?

Нет. Redis может обеспечивать постоянный объектный кеш, если нагрузка выигрывает от повторного использования объектов и результатов запросов БД. Но он нужен не каждому сайту WordPress и не заменяет полностраничный кеш.

Должен ли я использовать Nginx или Apache для WordPress VPS?

Оба варианта подходят. WordPress.org рекомендует Apache и Nginx как надёжные решения. Используйте стек, с которым приложение и администратор смогут надёжно работать.

Должен ли я заменить WP-Cron системным cron?

Только если нагрузке полезен управляемый планировщик и вы настроите работающую замену. Не отключайте WP-Cron без другого способа запуска.

Нужна ли WordPress VPS панель управления?

Нет. WordPress может работать на Linux VPS с ручным администрированием. Панель необязательна: выбирайте её ради удобства управления, а не как условие производительности.

Включает ли VDSina предустановленный WordPress?

На текущей странице Standard VPS WordPress не указан как отдельное предустановленное приложение в видимых группах шаблонов и приложений. Проверьте актуальный экран заказа, прежде чем рассчитывать на наличие шаблона.
