VPS para vários sites: dimensione um servidor com base na carga de pico combinada, isole usuários e bancos de dados, entenda o alcance de uma falha em um servidor único e saiba quando separar sites ou serviços.

Um VPS para vários sites funciona bem quando eles podem compartilhar com segurança os mesmos recursos, um modelo de administração e um domínio de falha. O limite importante não é o número de domínios. É o pico combinado de CPU, RAM, processos PHP/da aplicação, operações de banco de dados, armazenamento, tarefas em segundo plano e backups de todos os sites no servidor.

Avaliação de arquitetura VPS multi-site

Use isso para decidir se um VPS ainda é o domínio de falha certo.

Escolha as características do portfólio que realmente se aplicam.

Considere a carga de trabalho, não os domínios

A pergunta “quantos sites um VPS pode hospedar?” não tem uma resposta fixa confiável.

Um modelo de capacidade útil é:

carga de vários sites = tráfego normal combinado + picos dinâmicos sobrepostos + bancos de dados + cron/processos + backups/importações + painel/e-mail/monitoramento + margem de capacidade

Exemplos:

  • dez sites estáticos ou agressivamente em cache podem usar muito pouca capacidade PHP/DB;
  • três sites de negócios do WordPress podem precisar materialmente de mais RAM porque cada um tem processos PHP e uma carga de trabalho de banco de dados;
  • uma loja WooCommerce pode dominar todo o servidor durante o checkout ou um evento de venda;
  • uma importação de imagem, backup ou varredura de segurança pode consumir temporariamente mais CPU / I / O do que vários sites silenciosos combinados.

Considere a carga de trabalho simultânea mais pesada, não o número de domínios no painel de controle.

Quantos sites um VPS pode hospedar?

Use a quantidade de sites apenas como dado de inventário.

A capacidade depende de:

  • taxa de acerto de cache;
  • concorrência de requisições sem cache;
  • Memória do processo PHP/aplicativo;
  • duração das requisições;
  • conjunto de dados de banco de dados mantidos na memória;
  • intensidade das gravações;
  • tarefas agendadas/em segundo plano;
  • tráfego de bots;
  • armazenamento/crescimento de mídia;
  • Janelas de backup;
  • painel/email consumo adicional de recursos;
  • Quanta margem de capacidade você deixa.

Se você não consegue identificar os consumidores de recursos dominantes, a confiança de qualquer estimativa de “sites N” é baixa.

Para o comportamento específico do WordPress, use VPS para WordPress. Uma loja transacional deve ser tratada separadamente; veja VPS para WooCommerce.

Um IP pode hospedar muitos sites

Os sites modernos normais não precisam de um IP público por domínio.

Com hospedagem virtual baseada em nome:

  1. DNS aponta vários domínios para o mesmo IP VPS;
  2. o navegador envia o nome de host solicitado;
  3. Nginx/Apache corresponde esse nome de host ao bloco de servidor correto / host virtual;
  4. O TLS usa o SNI para que o servidor possa apresentar o certificado apropriado para cada nome de host.

É por isso que muitos sites HTTPS não relacionados podem compartilhar portas 80/443 em um IP.

Um IP separado ainda pode ser importante para políticas de rede especiais, requisitos legados, reputação de e-mail ou serviços não-web, mas não é um requisito normal para cada site.

Isole cada site de forma planejada

Colocar sites em pastas diferentes é organização, não isolamento forte.

Para sites não relacionados/clientes, prefira limites separados onde for prático:

Uma prática inadequada comum é executar todos os sites PHP com o mesmo usuário Unix e arquivos de configuração acessíveis entre eles. Um plugin comprometido pode permitir a invasão de outros sites.

A própria orientação de segurança do FASTPANEL recomenda usuários FASTPANEL separados para sites diferentes. Se você quer uma interface de hospedagem, compare VPS com painel de controle; o fluxo específico da ferramenta está em Hospedagem VPS com FASTPANEL.

Separe pools PHP, serviços de aplicativos e credenciais de banco de dados

Para sites PHP, pools separados de PHP-FPM podem ajudar a isolar:

  • usuário/grupo Unix;
  • limites de processo;
  • Configuração do PHP;
  • logs;
  • soquetes;
  • comportamento dos recursos.

Para aplicações Node.js/Python/personalizadas, use usuários/serviços separados e portas/sockets locais.

Para bancos de dados:

  • usar bancos de dados separados;
  • usar credenciais separadas;
  • conceder apenas os privilégios que cada aplicativo precisa;
  • não forneça a todos os sites uma única conta root/admin compartilhada do banco de dados.

Isso não cria uma multilocação perfeita, mas melhora materialmente a contenção e a solução de problemas.

Cargas de trabalho mistas precisam de orçamentos diferentes

Não dimensione um portfólio misto como se cada site fosse o mesmo.

Sites estáticos / em cache

Geralmente consomem pouca CPU da aplicação e poucos recursos do banco de dados.

WordPress

Precisam de recursos para processos PHP, banco de dados, cache e cron.

WooCommerce / áreas de membros / sites transacionais

Precisa de margem de capacidade PHP/DB mais dinâmica e planejamento cuidadoso de tarefas em segundo plano.

Aplicativos personalizados

Pode precisar de processos persistentes, filas, contêineres, diferentes tempos de execução ou portas separadas.

O site mais pesado geralmente determina se todo o VPS precisa de mais recursos ou se esse site deve ser transferido para outro servidor.

Seus próprios sites podem se tornar vizinhos barulhentos.

Um VPS reduz parte da dependência de outros clientes da hospedagem compartilhada, mas a consolidação cria “vizinhos barulhentos” internos.

Um site pode consumir recursos desproporcionais através de:

  • pico de tráfego;
  • plugin/consulta com problemas;
  • ataque de bot;
  • processamento de imagem;
  • importação/exportação;
  • varredura de segurança;
  • compressão de backup;
  • tarefa cron fora de controle;
  • grande crescimento dos logs;
  • bloqueios no banco de dados / pressão de I/O.

Observe o uso de recursos durante esses eventos, não apenas quando o servidor está ocioso.

Quando a stack permitir, limites de processos por site ou de contêineres/cgroups podem reduzir o risco de uma carga consumir todos os recursos. Porém, não presuma que o painel de controle impõe automaticamente cotas rígidas de CPU/RAM, a menos que a documentação confirme isso.

Picos combinados importam mais do que o uso médio

Servidores multi-site falham quando picos independentes se sobrepõem.

Por exemplo:

  • Site A recebe um pico de campanha;
  • O site B executa uma importação de banco de dados;
  • O site C inicia um backup completo;
  • Site D executa uma verificação de malware;
  • o painel de controle faz a rotação dos logs;
  • O buffer de banco de dados já é grande.

Individualmente, cada site pode parecer pequeno. Juntos eles podem esgotar CPU, RAM ou E/S.

Planeje a manutenção e as tarefas em segundo plano para todo o portfólio, não para cada site isoladamente.

Manual, painel de controle ou containers?

Blocos de servidor manuais / hosts virtuais

Bom quando:

  • um operador competente gerencia o servidor;
  • a contagem do site é modesta;
  • pilhas são semelhantes;
  • automação/scripts mantêm a configuração consistente.

O caminho de implantação geral é coberto em Como hospedar um site no VPS.

Painel de controle de hospedagem

Útil quando:

  • muitos domínios/usuários precisam de administração de rotina;
  • o acesso de clientes/delegado é importante;
  • você quer uma IU para SSL, PHP, bancos de dados, backups e correio.

O modelo usuário/conta do painel é mais importante do que quantos domínios ele afirma suportar.

Contêineres

Útil quando:

  • o isolamento do ambiente de dependência/execução é importante;
  • aplicações têm pilhas diferentes;
  • As implantações são nativas de contêineres;
  • A equipe já conhece as operações de contêineres.

Contêineres não são automaticamente mais simples. Eles acrescentam responsabilidades com o ciclo de vida das imagens, rede, volumes persistentes, backups e monitoramento.

Agência e sites de clientes

Agências são um caso natural de hospedagem de vários sites, mas o fato de os sites pertencerem a clientes aumenta a necessidade de isolamento.

Defina:

  • quem é o dono do domínio/DNS;
  • contas de painel/sistema separadas;
  • Separe credenciais de banco de dados;
  • acesso delegado;
  • responsabilidade pelos backups de cada cliente;
  • granularidade da restauração;
  • caminho de migração/exportação quando um cliente sai;
  • quem é responsável pelas atualizações de aplicativos;
  • Se o incidente de um site do cliente pode afetar outros.

Não prometa a um cliente "hospedagem isolada" se todos os sites de clientes compartilharem o mesmo usuário Unix e domínio de falha.

O antigo candidato VPS para sites da agência permanece mesclado nesta página a menos que uma futura verificação SERP/volume prove um proprietário separado e limpo.

Se ninguém da equipe assume as atualizações do sistema operacional, a segurança, a verificação dos backups, o monitoramento e os incidentes do servidor compartilhado, resolva isso antes de reunir os sites dos clientes: veja VPS gerenciado ou não gerenciado.

Para transferir um portfólio existente para um VPS, não copie todos os sites e altere todo o DNS de uma só vez. Prepare, teste e faça a virada com um plano de reversão; use Migração de site para VPS para o processo de migração.

Backups e granularidade da restauração

Um único VPS significa que vários sites podem falhar ao mesmo tempo.

Um projeto de backup útil deve deixar você responder:

  • Posso restaurar apenas o Site A?
  • Posso restaurar apenas o banco de dados?
  • Posso recuperar o VPS completo após a perda de disco/servidor?
  • Há uma cópia fora do servidor?
  • Quantos dados podem ser perdidos entre backups?
  • Posso verificar restaurações sem substituir os outros sites?

Uma imagem de servidor completo é útil para recuperação de desastres, mas não deve ser o único método de recuperação se a restauração de um site comprometido forçar todos os outros sites de volta a um ponto mais antigo. Para retenção, cópias externas, RPO / RTO e restaurar testes, use Estratégia de backup VPS.

Um VPS é um domínio de falha

A consolidação reduz o custo e a duplicação de administração, mas aumenta o alcance do impacto.

Um único evento pode afetar todos os sites:

  • Queda de VPS;
  • sistema de arquivos sem espaço;
  • atualização ruim do sistema operacional/web-stack;
  • falha do banco de dados;
  • erro de firewall;
  • conta de administrador comprometida;
  • malware/comprometimento do acesso root;
  • deleção acidental;
  • tarefa de backup esgotando disco/I/O.

A questão não é se esse risco existe — ele existe. A questão é se a empresa o aceita.

Quando dividir sites ou cargas de trabalho

Dividir quando a razão é operacionalmente mensurável.

Gatilhos fortes:

  • um site domina repetidamente CPU/RAM/I/O;
  • um site crítico não pode compartilhar o risco de interrupção com sites de baixa prioridade;
  • uma carga WooCommerce/de loja prejudica sites de menor atividade;
  • há requisitos incompatíveis de sistema operacional, ambiente de execução ou segurança;
  • um banco de dados precisa de RAM/I/O/scaling independente;
  • processos/tarefas em segundo plano dominam os recursos;
  • janelas de manutenção diferem;
  • um limite cliente/conformidade requer uma separação mais forte;
  • A contenção de recursos permanece após otimização e agendamento.

Possíveis padrões de divisão:

  • site crítico -> seu próprio VPS;
  • web -> VPS separado para banco de dados;
  • web -> VPS separado para processos em segundo plano;
  • agências -> grupos de clientes separados;
  • produção -> ambiente de teste separado;
  • loja/carga com muitas gravações -> servidor separado.

Não se divida automaticamente: cada VPS extra adiciona monitoramento, backups, patches, rede e superfície de incidentes.

Monitorando um VPS multi-site

Monitore em dois níveis.

Nível do servidor

  • CPU;
  • RAM/swap/OOM;
  • uso do disco;
  • espera de I/O;
  • Saúde DB;
  • rede;
  • saúde do processo/serviço.

Nível do site

  • Verificações HTTP(S) externas por hostname importante;
  • tempo de resposta;
  • Erros de 5xx;
  • Registros PHP/app;
  • tráfego/pressão sobre processos por site, quando disponível;
  • Falhas de cron/fila;
  • crescimento do banco de dados/logs/armazenamento.

Um servidor pode estar disponível enquanto um host virtual, certificado ou aplicação apresenta falhas. O modelo completo de alertas do servidor e por hostname está em Monitoramento de VPS.

FAQ

Quantos sites posso hospedar em um VPS?

Não há um número fixo confiável. Capacidade depende do pico combinado CPU, RAM, processos PHP/aplicativo, trabalho de banco de dados, armazenamento e tarefas em segundo plano de todos os sites.

Vários sites precisam de endereços IP separados?

Normalmente não. A hospedagem virtual baseada em nomes e o TLS SNI permitem que vários domínios HTTPS compartilhem um IP público. IPs separados ainda podem ser úteis para requisitos especiais de rede / email / legado.

Vários sites do WordPress podem compartilhar um VPS?

Sim. Use usuários/credenciais separados e dimensione o servidor para a carga combinada de PHP, banco de dados e tarefas em segundo plano. Vários sites WordPress leves podem funcionar bem juntos; um site dinâmico pesado pode dominar o servidor.

Cada site deve ter um pool PHP-FPM separado?

Para sites PHP não relacionados ou clientes, pools separados podem melhorar o isolamento do processo/usuário e tornar o ajuste/logging por site mais claro. O design exato depende do modelo de painel/pilha da Web.

Uma loja WooCommerce pode compartilhar um VPS com outros sites?

Pode, mas os picos de checkout, banco de dados e tarefas em segundo plano da loja podem se tornar a carga dominante. Se a loja for essencial para o negócio ou deixar os outros sites sem recursos repetidamente, separe-a.

Um painel de controle é melhor para hospedar vários sites?

Muitas vezes para administração. Um painel pode simplificar domínios, usuários, SSL, PHP, DBs e backups, mas verificar seu modelo de isolamento de usuário / conta e consumo adicional de recursos.

Os contêineres são necessários para vários sites?

Não. Os hosts virtuais Nginx/Apache mais usuários/processos separados podem hospedar muitos sites. Os contêineres são úteis quando o isolamento de dependência/processo justifica a complexidade operacional extra.

Qual é o principal risco de hospedar muitos sites em um VPS?

Uma interrupção, atualização problemática, falta de espaço em disco ou invasão no nível do servidor pode afetar todos os sites desse VPS.

As agências devem colocar todos os clientes em um VPS?

Somente quando a agência aceita o domínio de falha compartilhada e implementa forte isolamento de conta/arquivo/DB, backups, monitoramento e procedimentos de saída do cliente. Clientes críticos ou incompatíveis podem merecer servidores separados.

Quando devo dividir em vários servidores VPS?

Dividir quando uma carga de trabalho domina os recursos, um site crítico precisa de isolamento de falha independente, as pilhas/limites de segurança são incompatíveis ou DB/processos precisam de escala independente.
