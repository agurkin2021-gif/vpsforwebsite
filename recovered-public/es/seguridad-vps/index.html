Lista de comprobación de seguridad de un VPS

Protege el acceso administrativo, configura el cortafuegos, actualiza el software, protege las credenciales, verifica las copias de seguridad y prepara la respuesta a incidentes sin perder el acceso.

Esta lista prioriza las medidas de seguridad de un VPS no administrado expuesto a Internet. No pretende hacer que un servidor sea «100% seguro», sino reducir la superficie de ataque evitable, proteger el acceso privilegiado, mantener el software actualizado, permitir la recuperación y comprobar que alguien asume las tareas de seguridad.

El orden importa: conserva una vía de recuperación, comprueba un segundo acceso administrativo, inventaría los servicios expuestos y después restringe SSH y el cortafuegos.

Si nadie se encarga de las actualizaciones, el cortafuegos, las copias, la monitorización y los incidentes, resuelve primero la administración. Consulta VPS administrado o no administrado.

Para la decisión más amplia del servidor, véase VPS para el sitio web.

Controles básicos de seguridad, en orden

Para un típico VPS público de Linux:

  1. Mantener disponible el acceso a la consola/recuperación del proveedor.
  2. Crea un usuario administrativo individual distinto de root y prueba su acceso.
  3. Agregar autenticación con clave SSH y verificar una segunda sesión de inicio de sesión.
  4. Inventaría todos los servicios que escuchan conexiones y los puertos públicos.
  5. Restringe la política de SSH/root/contraseña solo después de que funcione el acceso por clave.
  6. Aplica una política de firewall de denegación predeterminada y abre solo los puertos necesarios.
  7. Mantener bases de datos, Redis y puertos de aplicación internos privados por defecto.
  8. Aplica las actualizaciones de seguridad del sistema y sus paquetes, y asigna responsables de reiniciar servicios y servidor.
  9. Actualiza también paneles, CMS, plugins, entornos de ejecución y dependencias.
  10. Protege las credenciales y limita los privilegios de usuarios y bases de datos.
  11. Agregue controles de fuerza bruta/límite de velocidad como defensa en profundidad.
  12. Utilice HTTPS para sitios web públicos y proteja las interfaces de administración.
  13. Conserva copias independientes y prueba su restauración.
  14. Habilitar registros/alertas que pueden revelar fallas de seguridad y recuperación.
  15. Define cómo actuar ante una posible intrusión.
  16. Repite la auditoría regularmente.

No restrinjas el acceso remoto pegando comandos sin entenderlos. Un cambio que impide entrar al administrador legítimo también provoca una interrupción.

Evaluador de seguridad básica del VPS

Esta herramienta ayuda a identificar controles pendientes. No certifica que el servidor sea seguro.

Marque solo los controles que realmente se implementan y prueban.

Mantenga una ruta de recuperación antes de cambiar el acceso

Antes de restringir SSH o habilitar un firewall estricto, confirme que puede recuperarse de una mala regla.

Mantenga al menos una opción fuera de banda disponible, como la consola del navegador del proveedor / VNC / interfaz de recuperación.

Entonces:

  1. crear el usuario administrativo individual;
  2. añadir la clave pública SSH;
  3. abrir una segunda sesión de terminal;
  4. verificar los derechos de inicio de sesión y sudo/admin;
  5. mantener abierta la sesión de trabajo mientras se prueba la nueva política;
  6. Solo entonces se restringen los métodos de acceso antiguos.

Lo importante no es desactivar root lo antes posible, sino sustituir un acceso arriesgado por una vía más segura y probada, sin perder el acceso.

El primer flujo de implementación está cubierto en Cómo alojar un sitio web en VPS.

Inventaría los servicios expuestos antes de restringir el acceso

No adivine qué puertos están abiertos.

En Linux, inspeccione los sockets de escucha con herramientas como:

sudo ss -lntup

Para cada servicio que escuche conexiones, decide:

  • ¿Es necesario que el servicio exista?
  • ¿Es necesario escuchar en todas las interfaces?
  • ¿Es necesario que sea público?
  • puede enlazar solo a localhost o una red privada?
  • ¿Qué redes de origen deberían llegar a él?
  • ¿quién se encarga de sus actualizaciones y registros?

Los puertos típicos de sitios web públicos pueden incluir:

  • Acceso SSH/admin;
  • HTTP 80;
  • HTTPS 443.

Eso no significa que todos los servidores deban exponer los tres servicios a todo Internet.

Elimine los servicios no utilizados en lugar de confiar solo en el firewall para ocultarlos.

Refuerza el acceso administrativo

La documentación OpenSSH de Ubuntu admite la autenticación de clave pública y recomienda algoritmos de clave modernos como Ed25519.

Un modelo administrativo básico es:

  • cuenta administrativa individual;
  • Autenticación de clave SSH;
  • clave privada protegida con contraseña cuando sea práctico;
  • sudo solo para usuarios que lo necesitan;
  • ninguna aplicación ejecutándose como root;
  • acceso SSH directo como root o mediante contraseña restringido después de verificar una alternativa más segura.

Para entornos con requisitos de garantía más altos, OpenSSH también admite modelos de autenticación más sólidos, incluida la autenticación de dos factores basada en FIDO / U2F o TOTP.

Acceso como root y autenticación por contraseña

No establezca ciegamente estas opciones antes de verificar el acceso a la clave y la recuperación de la consola.

Después de que el camino más seguro funcione, revise:

  • PermitRootLogin;
  • PasswordAuthentication;
  • AllowUsers / AllowGroups;
  • política de inactividad/sesión cuando sea necesario.

La política concreta depende del entorno.

Cambiar SSH del puerto 22 puede reducir el ruido de los escaneos, pero no sustituye a las claves, los privilegios mínimos, una política de cortafuegos y el software actualizado.

Firewall: solo los servicios que necesitas

UFW es la interfaz predeterminada para gestionar el cortafuegos de Ubuntu.

Una línea de base segura es conceptualmente:

  • por defecto denegar el tráfico entrante no solicitado;
  • permitir la ruta administrativa que realmente utiliza;
  • permitir HTTP/HTTPS para un servidor web público;
  • mantener bases de datos/servicios internos privados;
  • Revisión del comportamiento de IPv4 e IPv6.

Antes de habilitar reglas restrictivas, conserve el acceso SSH.

Ejemplo de inspección:

sudo ufw status verbose

No copie una lista genérica de “permitir 22/80/443” si su arquitectura difiere.

Firewall de proveedor y firewall de host

Un firewall de red/proveedor puede bloquear el tráfico antes de que llegue a la máquina virtual.

El cortafuegos del servidor controla las conexiones que acepta el sistema operativo del VPS.

El uso de ambos puede proporcionar una defensa útil en profundidad, pero solo cuando las reglas están documentadas y no se contradicen entre sí.

Mantenga las bases de datos y los servicios internos privados de forma predeterminada

No exponga MySQL/MariaDB/PostgreSQL, Redis, puertos internos de aplicaciones Node/Python o sockets de control a la Internet pública simplemente porque el servicio está escuchando.

Prioriza:

  • localhost para servicios del mismo servidor;
  • interfaces de red privadas para arquitectura multiservidor;
  • restricciones de IP de origen cuando sea necesaria la administración remota;
  • Acceso SSH/VPN/bastion para flujos de trabajo administrativos.

Abra un puerto de base de datos públicamente solo cuando la arquitectura lo requiera específicamente y el acceso esté fuertemente restringido.

Parches y actualizaciones de seguridad automáticas

Incluso un sistema operativo con soporte acaba desactualizado si nadie se encarga de aplicar los parches.

Ubuntu Server utiliza unattended-upgrades para las actualizaciones de seguridad automáticas de forma predeterminada en las instalaciones compatibles.

Eso es útil, pero el proceso de seguridad también debe responder:

  • ¿Qué repositorios están cubiertos?
  • ¿Se actualizan los paquetes/aplicaciones de terceros?
  • ¿Un servicio necesita reiniciarse?
  • ¿Hace falta reiniciar el servidor?
  • ¿Quién verifica las actualizaciones fallidas?
  • ¿Cuándo se pueden reiniciar de forma segura los servicios de producción?

La documentación de Ubuntu indica que, para activar el código actualizado, puede ser necesario reiniciar servicios y, en ocasiones, el servidor completo.

No trate las “actualizaciones automáticas habilitadas” como todo el proceso de administración de parches.

Fail2ban, CrowdSec y limitación de velocidad

Las herramientas de protección contra la fuerza bruta pueden reducir los intentos abusivos repetidos.

Son una medida de defensa en profundidad, no el mecanismo principal de autenticación.

Utilícelos después de:

  • El acceso privilegiado está protegido.
  • fuerte autenticación está en su lugar;
  • Los servicios expuestos son intencionalmente públicos.
  • Los registros están disponibles.

Una herramienta de bloqueo no convierte en seguros una contraseña débil, un panel sin actualizar o una base de datos expuesta.

El mínimo privilegio para aplicaciones y bases de datos

El mínimo privilegio se aplica a toda la pila.

Prioriza:

  • usuarios independientes de despliegue/administración;
  • usuarios de aplicaciones separados;
  • usuarios de bases de datos separados por aplicación;
  • únicamente los privilegios de base de datos necesarios;
  • usuarios separados para sitios de clientes no relacionados;
  • directorios escribibles limitados a lo que la aplicación necesita.

Evite:

  • ejecutar aplicaciones web como root;
  • compartir la cuenta root/admin de DB con las aplicaciones;
  • chmod 777 como una corrección de permiso;
  • un usuario de Unix para sitios de clientes no relacionados cuando es práctica una separación más fuerte.

Para el aislamiento de múltiples sitios, consulte VPS para varios sitios web.

Proteger secretos y credenciales

Mantenga las credenciales de producción fuera de:

  • repositorios públicos de Git;
  • directorios raíz del sitio accesibles desde la web;
  • páginas de depuración;
  • capturas, tickets de soporte o conversaciones;
  • historial de la consola, siempre que sea posible evitarlo;
  • archivos de entorno que puedan leer usuarios no autorizados.

Proteger:

  • contraseñas de base de datos;
  • Claves de API;
  • Credenciales SMTP;
  • secretos de pago/webhook;
  • credenciales del almacenamiento de copias;
  • credenciales de panel/admin;
  • Claves privadas SSH.

Cambia las credenciales cuando una persona o contratista deje de tener acceso, o después de sospechar una intrusión.

Paneles de control e interfaces de administración

Un panel de control es una aplicación de gestión privilegiada.

Auditoría:

  • versión actual del panel;
  • cuentas de administrador del panel;
  • 2FA donde el panel lo soporta;
  • puertos/nombres de host de administración expuestos;
  • restricciones por IP de origen cuando sean viables;
  • Inventario de plugin/extensión;
  • comportamiento de copia de seguridad/restauración;
  • registros del panel y actividad de inicio de sesión fallido.

No asuma que la instalación de un panel hace que el VPS sea seguro o administrado.

Para elegir un panel, consulta VPS con panel de control. Para el procedimiento específico de FASTPANEL, consulta alojamiento VPS con FASTPANEL.

Actualizaciones de aplicaciones, CMS y entornos de ejecución

Un sistema operativo completamente parcheado todavía puede alojar una aplicación vulnerable.

La responsabilidad de seguridad debe abarcar:

  • PHP, Node, Python u otro entorno de ejecución;
  • framework;
  • núcleo de WordPress;
  • plugins/temas;
  • WooCommerce/extensiones;
  • servidor web;
  • panel de control;
  • bibliotecas/dependencias.

Elimine los componentes abandonados que ya no reciben actualizaciones de seguridad.

Para operaciones específicas de WordPress, véase VPS para WordPress. Para tiendas transaccionales, véase VPS para WooCommerce.

HTTPS protege el transporte, no todo el servidor

HTTPS es necesario para los sitios web de producción que manejan inicios de sesión o datos confidenciales y es una línea base normal para los sitios públicos.

Protege los datos en tránsito entre cliente y servidor.

No soluciona:

  • plugins vulnerables;
  • SSH débil;
  • bases de datos públicas;
  • claves de API filtradas;
  • paquetes obsoletos;
  • permisos de archivo inseguros;
  • Faltan copias de seguridad.

Verifique la renovación del certificado y esté atento a la caducidad / falla.

La protección DDoS no es seguridad de aplicaciones

VDSina actualmente anuncia protección DDoS gratuita en VPS estándar.

Sus preguntas y respuestas indican que la protección gratuita cubre ataques al canal o a las capas de red L3-L4 y no está sujeta a un SLA.

Esa protección es útil en la capa de infraestructura/red, pero no reemplaza:

  • endurecimiento SSH;
  • Política de firewall;
  • seguridad de aplicaciones web;
  • limitación de velocidad de la capa de aplicación;
  • Controles WAF/bot cuando sea apropiado;
  • parcheo;
  • respuesta de incidente.

No describa la mitigación de DDoS en la capa de red como un servicio completo de seguridad del sitio web.

Las copias de seguridad son un control de seguridad

La seguridad incluye la capacidad de recuperarse después de un compromiso, ransomware, actualizaciones incorrectas y eliminación accidental.

Como mínimo:

  • mantener una copia fuera del VPS en ejecución;
  • no depender únicamente de una instantánea o imagen;
  • proteger las credenciales de copia de seguridad;
  • mantener las copias de seguridad no disponibles para la aplicación cuando sea práctico;
  • supervisar los trabajos de copia de seguridad fallidos;
  • probar la restauración;
  • saber cuántos datos se pueden perder entre los puntos de restauración.

CISA recomienda mantener copias de seguridad fuera de línea / cifradas de datos críticos y probar regularmente la restauración en un escenario de recuperación de desastres.

El diseño más profundo de RPO / RTO, retención y topología de copia de seguridad está cubierto en Estrategia de copia de seguridad VPS .

Registros, alertas y seguimiento de auditoría

Una configuración segura que nunca se observa puede fallar silenciosamente.

Como mínimo, vigila:

  • Fallos SSH/auth repetidos;
  • nuevos usuarios inesperados de sudo/admin;
  • fallos de inicio de sesión en el panel;
  • cambios de firewall;
  • nuevos puertos de escucha;
  • fallos o reinicios de los servicios;
  • situaciones de disco lleno;
  • picos de errores 5xx de la aplicación o el servidor web;
  • Fallos de copia de seguridad;
  • fallos de renovación del certificado;
  • alertas de malware/herramientas de seguridad donde se utilicen.

Mantenga registros el tiempo suficiente para investigar incidentes.

El diseño de umbral/alerta más profundo está cubierto en monitorización de un VPS.

Ante una posible intrusión

Si sospechas que un atacante ha obtenido acceso privilegiado o root, no tomes una limpieza improvisada como prueba de que el servidor vuelve a ser seguro.

Una respuesta más segura es:

  1. contener la ruta VPS/red afectada;
  2. conservar los registros/evidencias pertinentes cuando sea posible;
  3. identificar qué credenciales/secretos pueden haber sido expuestos;
  4. rotar esas credenciales desde un sistema de confianza limpio;
  5. identificar un punto de restauración de datos y aplicación cuyo buen estado esté comprobado;
  6. reconstruir el servidor desde un sistema operativo y una configuración de origen fiable cuando corresponda;
  7. restaurar datos verificados sin recuperar a ciegas ejecutables o configuraciones comprometidos;
  8. revisar la causa de acceso inicial antes de volver a conectar el tráfico de producción.

La guía de respuesta a incidentes de CISA enfatiza el aislamiento, la revisión de evidencia / registro y la recuperación de copias de seguridad validadas.

Para un sistema crítico para el negocio, involucre a un profesional calificado en respuesta a incidentes / seguridad.

Repita la lista de verificación

La seguridad no se resuelve una sola vez al crear el servidor.

Establece una periodicidad para revisar:

  • usuarios de administración y claves SSH;
  • privilegios sudo;
  • abrir/escuchar puertos;
  • reglas del cortafuegos;
  • paquetes no compatibles/versiones de SO;
  • actualizaciones de seguridad pendientes;
  • versiones de panel de control/CMS/plugin;
  • éxito de copia de seguridad y pruebas de restauración;
  • la expiración/renovación del certificado;
  • registros y alertas;
  • cuentas/servicios no utilizados;
  • Secretos expuestos;
  • personas de contacto para incidentes.

Vuelva a ejecutar la lista de verificación después de migraciones importantes, cambios de panel, nuevos servicios o cambios de arquitectura.

Preguntas frecuentes

¿Qué debo asegurar primero en un nuevo VPS?

Conserva el acceso a la consola o a la recuperación, crea un administrador distinto de root y prueba su acceso por clave SSH. Inventaría los servicios que escuchan conexiones y después restringe SSH y el cortafuegos. Evita acumular cambios que puedan bloquearte antes de comprobar el acceso.

¿Debo deshabilitar el inicio de sesión con contraseña SSH?

Para la administración habitual de un VPS, las claves ofrecen una autenticación más sólida. Primero comprueba el acceso con la clave y la consola de recuperación. No desactives la única vía de acceso que funciona.

¿Debo cambiar el puerto SSH?

Puede reducir el ruido del escáner/registro, pero no es un control de seguridad principal. La autenticación sólida, el privilegio mínimo, la política de firewall y los parches son más importantes.

¿Necesito Fail2ban?

No siempre, pero puede ser una defensa útil en profundidad contra el abuso repetido de inicio de sesión. No reemplaza las claves SSH, los parches o la exposición correcta al servicio.

¿Qué puertos deben estar abiertos en un VPS?

Solo puertos requeridos por la arquitectura. Un servidor web público normalmente necesita HTTP/HTTPS además de una ruta de administración controlada. Las bases de datos y los servicios internos de aplicaciones normalmente deben permanecer privados.

¿Protege un firewall una aplicación vulnerable?

No. Un firewall limita la exposición a la red. Una aplicación web accesible al público todavía necesita código seguro, dependencias compatibles, actualizaciones y controles a nivel de aplicación.

¿Son suficientes las actualizaciones de seguridad automáticas?

No. Ayudan a actualizar los paquetes compatibles del sistema, pero las aplicaciones y dependencias externas pueden necesitar procesos separados. También hay que gestionar los reinicios de servicios y del servidor.

¿Es HTTPS suficiente para asegurar un VPS?

No. HTTPS protege el transporte. No corrige SSH débil, bases de datos expuestas, plugins vulnerables, paquetes obsoletos, secretos filtrados o copias de seguridad faltantes.

¿Es suficiente la protección DDoS de VDSina para proteger el sitio web?

No. VDSina anuncia protección DDoS gratuita y sus preguntas y respuestas la describen como protección L3-L4 sin SLA. Sigues necesitando seguridad del sistema operativo, los accesos, la aplicación y la recuperación.

¿Qué debo hacer si sospecho que el VPS se vio comprometido?

Conténgalo, conserve la evidencia/registros relevantes, rote las credenciales expuestas de un sistema limpio y prefiera la reconstrucción a partir de fuentes conocidas más copias de seguridad validadas cuando se sospeche un compromiso privilegiado. Para sistemas críticos, involucre a un profesional de respuesta a incidentes.
