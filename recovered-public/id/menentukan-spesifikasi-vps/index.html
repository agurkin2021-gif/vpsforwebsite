Menentukan Spesifikasi VPS

Hitung kebutuhan RAM, CPU, dan penyimpanan VPS dari beban website. Gunakan kalkulator dan data hosting untuk memilih paket dengan kapasitas yang sesuai.

Penentuan spesifikasi VPS untuk website harus dimulai dari beban yang mencapai server origin, bukan jumlah pengunjung bulanan. Kemampuan caching, permintaan dinamis bersamaan, worker PHP/aplikasi, aktivitas database, tugas latar belakang, konsumsi sumber daya panel kontrol, dan pertumbuhan penyimpanan menentukan kebutuhan CPU, RAM, dan disk sebenarnya.

Hitung kebutuhan setiap layanan sebelum memperkirakan kapasitas trafik

Perhitungan kebutuhan VPS yang berguna memisahkan setiap komponen pemakai sumber daya.

Alokasi RAM

Total RAM harus mencakup:

  1. sistem operasi dan layanan sistem;
  2. server web atau reverse proxy;
  3. PHP-FPM, Node.js, Python, atau runtime aplikasi lainnya;
  4. database;
  5. layanan cache seperti Redis jika digunakan;
  6. panel kontrol dan layanannya;
  7. proses pemantauan, keamanan dan pencadangan;
  8. worker aplikasi yang berjalan bersamaan;
  9. cadangan kapasitas aman untuk lonjakan, deployment, dan pemeliharaan.

Jangan menganggap batas memori CMS sebagai persyaratan RAM server. Batas memori PHP 256 MB tidak berarti bahwa VPS 1 GB dapat dengan aman menjalankan empat proses PHP 256 MB secara bersamaan ditambah Linux, database, dan setiap layanan lainnya.

Model praktisnya adalah:

RAM yang diperlukan = layanan dasar + memori kerja database + memori seluruh worker aktif + memori tugas latar belakang + cadangan kapasitas

Ukur proses nyata bila memungkinkan. Perkiraan berguna untuk memilih tingkat awal; pengukuran memutuskan apakah tingkat tersebut benar-benar memadai.

Kalkulator Kebutuhan RAM

Kalkulator ini membantu memeriksa asumsi kebutuhan RAM. CPU, penyimpanan, dan I/O tetap perlu diuji secara terpisah. Masukkan hasil pengukuran Anda; angka contoh pada kolom mengikuti perhitungan di bawah, bukan nilai yang berlaku untuk semua website.

Masukkan hasil pengukuran untuk menghitung alokasi RAM.

Contoh perhitungan: 450 MB layanan dasar + 500 MB database + 6 worker × 120 MB + 300 MB untuk panel/cache/tugas latar belakang = 1.970 MB sebelum cadangan kapasitas. Dengan cadangan 25%, kebutuhannya sekitar 2,4 GB. VPS 2 GB terlalu terbatas untuk asumsi tersebut; 4 GB adalah konfigurasi awal yang lebih aman.

Saat mengukur memori PHP-FPM atau worker sejenis, ingat bahwa RSS mentah dapat menghitung halaman memori dan pustaka bersama lebih dari sekali di berbagai proses. Gunakan pengukuran sebagai data pendukung, bukan angka yang dapat dijumlahkan secara mutlak.

Alokasi CPU

Kebutuhan CPU bergantung pada jumlah pemrosesan yang berjalan bersamaan. File statis dari cache memerlukan sedikit pemrosesan. Permintaan dinamis yang menjalankan kode aplikasi, kueri database, pembuatan halaman, pengubahan ukuran gambar, impor, atau API dapat memakai jauh lebih banyak CPU.

Cari:

  • CPU terus penuh saat melayani trafik yang memang diperlukan;
  • waktu permintaan aplikasi yang lama saat CPU sibuk;
  • beberapa permintaan dinamis berat datang bersamaan;
  • cron, backup, atau impor berjalan bersamaan dengan trafik pengguna;
  • kueri database memakan CPU karena indeks yang tidak efisien atau tugas yang berlebihan.

Lonjakan CPU yang singkat tidak secara otomatis menjadi alasan untuk melakukan upgrade. Kejenuhan yang terus-menerus sehingga menunda tugas yang sah adalah bukti yang lebih kuat.

Perkiraan konkurensi praktis adalah:

permintaan dinamis aktif ≈ permintaan dinamis per detik × durasi permintaan

Contoh: 6 permintaan dinamis tanpa cache per detik dengan durasi p95 sebesar 0,8 detik berarti sekitar 4,8 permintaan aktif saat itu. Jika aplikasi memerlukan satu worker per permintaan aktif, siapkan sekitar lima worker sibuk ditambah kapasitas antrean/cadangan. Jika tiap permintaan memakai 0,12 detik CPU, 6 permintaan per detik menghasilkan sekitar 0,72 detik kerja CPU per detik sebelum cadangan kapasitas. Ini perkiraan beban, bukan jaminan vCPU universal: generasi CPU, perebutan sumber daya, dan penjadwalan penyedia berbeda-beda.

Gunakan batas shared hosting untuk menghitung kebutuhan VPS

Jika website sudah berjalan di shared hosting, bukti penentuan spesifikasi yang paling berguna mungkin sudah ada di dashboard hosting.

Kumpulkan:

  • Penggunaan CPU dan kejadian batas CPU;
  • penggunaan memori fisik;
  • batas entry processes atau permintaan bersamaan;
  • jumlah proses;
  • I/O disk dan tekanan IOPS;
  • ukuran dan pertumbuhan database;
  • penggunaan penyimpanan;
  • pola puncak trafik per jam, bukan hanya kunjungan bulanan;
  • proses PHP atau perilaku proses aplikasi jika terlihat.

Diagnosis sebelum pindah dari shared hosting ke VPS

Gunakan pola pelanggaran batas sumber daya untuk menentukan apa yang perlu diperiksa. Alat ini tidak mengubah batas CloudLinux langsung menjadi jumlah vCPU atau RAM.

Pada cPanel dengan CloudLinux, periksa riwayat Resource Usage (Penggunaan Sumber Daya). Catat kapan batas sumber daya berulang kali tercapai, lalu cocokkan waktunya dengan trafik, cron, backup, impor, dan aktivitas admin.

Pilih sinyal yang benar-benar Anda amati.

Jangan menyalin batas hosting bersama langsung ke spesifikasi VPS. Persentase CPU CloudLinux, batas proses masuk, atau batas memori menjelaskan lingkungan hosting saat ini; ini adalah bukti mengenai kemacetan, bukan konversi VPS satu-ke-satu.

Gunakan pola sebagai gantinya:

Peristiwa batas memori berulang dengan CPU normal: selidiki memori worker, memori database, dan tugas latar belakang sebelum menambahkan vCPU.

Peristiwa batas CPU yang berulang selama tugas dinamis yang sah: analisis penggunaan CPU oleh aplikasi dan database, lalu pertimbangkan tambahan CPU jika pemrosesan tersebut memang diperlukan.

Batas entry processes tercapai atau worker penuh: ukur permintaan dinamis bersamaan dan durasinya. Mempercepat pemrosesan dapat mengurangi antrean tanpa menambah kapasitas server.

Tekanan I/O: periksa backup, log, aktivitas database, impor, atau plugin dengan I/O tinggi sebelum berasumsi RAM tambahan akan menyelesaikannya.

Ini memisahkan masalah kapasitas sebenarnya dari batas paket hosting yang mungkin dipicu oleh satu komponen yang tidak efisien.

VPS atau optimasi website?

VPS yang lebih besar dibenarkan ketika beban kerja yang sah berulang kali menghabiskan sumber daya setelah masalah aplikasi yang jelas telah diatasi.

Optimalkan terlebih dahulu ketika tekanan berasal dari:

  • satu plugin atau ekstensi lambat;
  • kueri database tanpa indeks yang sesuai atau kueri yang tidak efisien;
  • cache halaman atau objek yang tidak berfungsi;
  • bot yang membebani server secara berlebihan;
  • tugas cron yang tidak terkendali;
  • pemrosesan gambar berukuran besar;
  • pencadangan atau pemindaian malware yang dijadwalkan selama lalu lintas puncak;
  • kebocoran memori;
  • pencatatan log berlebihan.

Tingkatkan sumber daya server ketika pengukuran menunjukkan bahwa beban kerja yang dioptimalkan masih memerlukan kapasitas lebih besar.

Perbedaan itu penting secara ekonomi. Memindahkan kode yang tidak efisien dari shared hosting ke VPS yang lebih besar dapat menyembunyikan kemacetan untuk sementara tanpa menghilangkannya.

Tentukan kapasitas worker PHP dan aplikasi dari konkurensi

Kunjungan bulanan adalah data penentuan spesifikasi yang lemah karena server mengalami permintaan secara bersamaan.

Untuk beban kerja PHP dinamis, setiap proses PHP yang aktif menggunakan memori dan CPU saat memproses permintaan. Oleh karena itu, kapasitas worker bergantung pada memori rata-rata per worker dan berapa lama permintaan tetap sibuk.

Pemeriksaan RAM yang disederhanakan adalah:

Alokasi RAM worker = RAM tersisa setelah layanan dasar × proporsi yang aman untuk worker

Kemudian bandingkan anggaran tersebut dengan memori worker yang diukur. Jangan mengonfigurasi jumlah maksimum teoritis worker jika hal itu tidak menyisakan memori untuk database, cache, atau sistem operasi.

Caching mengubah perhitungan ini. Halaman anonim yang di-cache dapat melewati PHP sepenuhnya, sementara checkout, sesi login, wp-admin, API, dan halaman yang dipersonalisasi masih menjangkau aplikasi.

Untuk perilaku spesifik WordPress, lihat VPS untuk WordPress. Untuk beban kerja transaksional, lihat VPS untuk WooCommerce.

Beban database dapat menentukan spesifikasi server

Sebuah website dapat tampak terbatas CPU ketika masalah mendasarnya adalah tugas database.

Periksa:

  • pola kueri lambat;
  • ukuran data aktif database yang perlu ditampung di memori;
  • konkurensi kueri;
  • indeks yang belum tersedia;
  • data besar yang dimuat secara otomatis atau metadata aplikasi yang setara;
  • operasi pencarian, pemfilteran, atau pelaporan yang mahal;
  • tugas impor dan pemeliharaan;
  • latensi penyimpanan.

Lebih banyak RAM dapat membantu ketika database secara sah membutuhkan set data aktif yang lebih besar, namun hal ini tidak memperbaiki kueri yang tidak efisien. Lebih banyak CPU dapat meningkatkan throughput, namun juga memungkinkan kueri yang lebih mahal untuk bersaing sekaligus.

Rencanakan untuk lalu lintas puncak, bukan lalu lintas rata-rata

Perhitungan berdasarkan trafik rata-rata dapat melewatkan periode ketika pengguna mengalami gangguan.

Tentukan periode tersibuk yang realistis: peluncuran kampanye, promosi, pengiriman newsletter, peluncuran produk, impor, backup, atau lonjakan cron. Perkirakan permintaan yang tetap dinamis dan yang dapat dilayani oleh cache halaman atau CDN.

Pertahankan cadangan kapasitas untuk kombinasi:

  • lalu lintas pengguna normal;
  • lalu lintas puncak dinamis;
  • kegiatan administratif;
  • tugas terjadwal;
  • deployment dan pengisian awal cache;
  • proses pemantauan dan pencadangan.

CDN dapat mengurangi pengiriman statis dan beberapa permintaan origin. Itu tidak menghapus tugas aplikasi atau database dinamis yang masih mencapai VPS.

Contoh beban puncak: jika website menerima 20 permintaan/detik dan 90% dilayani dari cache/CDN, server origin menerima sekitar 2 permintaan dinamis/detik. Kampanye yang menggandakan trafik total menjadi 40 permintaan/detik dengan rasio cache yang sama mengirim sekitar 4 permintaan dinamis/detik ke aplikasi. Dengan durasi p95 sebesar 0,8 detik, sekitar 3,2 permintaan dinamis aktif bersamaan sebelum ditambah tugas administrasi atau lonjakan checkout/API.

Menentukan kapasitas penyimpanan

Kapasitas disk bukan hanya direktori website saat ini.

Sertakan:

  • file website;
  • database;
  • media yang diunggah;
  • log;
  • file sementara;
  • cache paket dan aplikasi;
  • salinan lingkungan staging jika disimpan secara lokal;
  • file cadangan jika cadangan dibuat sementara di VPS;
  • pertumbuhan yang diharapkan.

Jangan mengisi sistem file mendekati batasnya. Database, pembaruan, log, dan operasi pencadangan memerlukan ruang kerja.

Anggaran kapasitas praktis adalah:

disk yang diperlukan = file saat ini + database + ruang operasi sementara + ruang sementara backup lokal + perkiraan pertumbuhan + ruang kerja kosong sebagai cadangan

Contoh: penggunaan saat ini 18 GB + ruang sementara migrasi/pembaruan 8 GB + ruang sementara backup lokal 18 GB + pertumbuhan yang diperkirakan 6 GB sudah melampaui disk 40 GB sebelum cadangan kapasitas aman. Dalam skenario ini, 80 GB adalah konfigurasi awal yang lebih aman. Kapasitas berbeda dari IOPS dan latensi penyimpanan: disk lebih besar tidak otomatis mempercepat database yang lambat.

Menghitung bandwidth dan transfer bulanan

Transfer data bulanan berbeda dari CPU, RAM, dan kecepatan port. Server yang masih memiliki kapasitas pemrosesan longgar tetap dapat melewati kuota transfer jika mengirim file besar atau media tanpa cache secara langsung.

Perkiraan kasarnya adalah:

transfer origin bulanan ≈ rata-rata byte yang dikirim dari VPS per permintaan × permintaan origin per bulan + cadangan/ekspor/lalu lintas keluar lainnya

Untuk perkiraan yang lebih berguna, pisahkan lalu lintas yang dapat disimpan dalam cache dan dinamis:

transfer origin ≈ total byte yang diminta × (1 - proporsi yang dilayani CDN/cache) + respons dinamis tanpa cache + trafik keluar non-web

Contoh: jika pengguna meminta aset/halaman sebesar 2 TB per bulan dan CDN melayani 80% byte tersebut tanpa menghubungi origin, VPS mungkin mengirim sekitar 400 GB trafik yang dapat di-cache, ditambah halaman dinamis, respons API, backup, ekspor, dan semua permintaan yang tidak ditemukan dalam cache.

Jangan berasumsi CDN membuat transfer origin menjadi nol. Halaman pengguna login, checkout, API, cache miss, pembersihan cache, unduhan besar, serta pengisian konten dari origin ke CDN tetap memakai trafik. Bedakan juga kuota transfer bulanan dari kecepatan port jaringan: port cepat menunjukkan potensi throughput, sedangkan kuota menunjukkan banyaknya data yang dapat dikirim selama periode penagihan.

Beberapa website mengubah perhitungannya

Beberapa website pada satu VPS berbagi CPU, RAM, penyimpanan, dan kapasitas proses. Lonjakan bebannya dapat terjadi bersamaan meskipun masing-masing situs kecil.

Tentukan spesifikasi server dari gabungan beban kerja dan sisakan cadangan kapasitas agar tugas latar belakang satu situs tidak menghabiskan sumber daya situs lainnya. Jika isolasi, dampak kegagalan, atau perebutan sumber daya menjadi penting, pemisahan beban bisa lebih berguna daripada terus memperbesar satu server.

Lihat VPS untuk Banyak Website untuk keputusan multi-situs.

Masukkan kebutuhan tambahan panel kontrol dan email ke dalam perhitungan

Panel kontrol memudahkan pengelolaan domain, SSL, database, versi PHP, dan akun. Layanan panel juga memakai sumber daya, sehingga kebutuhan memori dan penyimpanannya harus dihitung bersama kebutuhan website.

Layanan email dapat menambahkan lapisan sumber daya persisten lainnya: SMTP, IMAP/POP, pemfilteran spam, pemindaian antivirus, antrean, log, dan penyimpanan kotak surat. Jika VPS akan menghosting website + email, masukkan penggunaan sumber daya tambahan tersebut ke dalam RAM, CPU, penyimpanan, dan anggaran cadangan alih-alih berasumsi bahwa email gratis.

Untuk website kecil, memindahkan email ke penyedia email terkelola dapat mengurangi beban server dan risiko operasional. Jika email tetap ada di VPS, verifikasi persyaratan keterkiriman seperti catatan DNS dan batasan penyedia/IP secara terpisah; VPS yang lebih besar tidak menentukan reputasi pengirim.

Jika ingin menggunakan panel, bandingkan pilihan dan konsekuensinya di VPS dengan panel kontrol.

Alur kerja penentuan spesifikasi VPS yang dapat diulang

  1. Ukur beban kerja saat ini. Catat CPU, memori, konkurensi dinamis, perilaku database, penyimpanan, dan periode puncak.
  2. Identifikasi hambatannya. Pisahkan masalah CPU, RAM, worker, database, I/O, dan batasan perangkat lunak.
  3. Atasi inefisiensi yang jelas. Perbaiki caching, tugas yang tidak terkendali, kueri bermasalah, dan trafik abusif sebelum membeli kapasitas.
  4. Susun alokasi sumber daya. Sisihkan RAM untuk layanan dasar, database, worker aplikasi, panel, dan tugas latar belakang.
  5. Pilih konfigurasi awal dengan cadangan kapasitas. Hindari alokasi berlebihan berdasarkan dugaan maupun konfigurasi tanpa cadangan.
  6. Uji beban puncak yang realistis. Uji konfigurasi dengan permintaan dinamis yang mewakili penggunaan nyata, bukan hanya membuka beranda saat trafik sepi.
  7. Pantau setelah migrasi. Sesuaikan kapasitas berdasarkan pengukuran setelah migrasi; gunakan panduan Monitoring VPS untuk menetapkan pemantauan server produksi.

Setelah spesifikasi server tujuan ditentukan, gunakan Migrasi Website ke VPS untuk merencanakan inventarisasi, pengujian privat, sinkronisasi data terakhir, pengalihan DNS, dan rollback.

Rekomendasi berbasis bukti

Rekomendasi VPS yang berguna harus menyatakan konfigurasi dan alasannya.

Misalnya:

2 vCPU / 4 GB RAM / 80 GB mungkin merupakan titik awal yang masuk akal ketika website bisnis menjalankan CMS yang didukung database, memiliki aktivitas PHP tanpa cache yang berarti, memerlukan panel kontrol, dan memerlukan cadangan kapasitas operasional. Ini bukan jaminan bahwa server mendukung jumlah pengunjung bulanan tertentu.

Keyakinan akan lebih rendah ketika satu-satunya masukan adalah jumlah pengunjung. Keyakinan menjadi lebih tinggi ketika riwayat CPU, tekanan memori, permintaan dinamis bersamaan, memori worker, perilaku database, dan pertumbuhan penyimpanan diketahui.

Gunakan tingkat keyakinan berdasarkan kelengkapan data:

  • Keyakinan rendah: jumlah pengunjung, nama CMS, dan penyimpanan kasar saja.
  • Keyakinan sedang: beberapa riwayat CPU/RAM nyata ditambah jenis beban kerja dan pola puncak.
  • Keyakinan tinggi: riwayat CPU, RAM, dan I/O dari waktu ke waktu, permintaan tanpa cache bersamaan, memori worker, durasi permintaan, beban database, dan pertumbuhan penyimpanan.

Label kepercayaan yang lebih tinggi berarti asumsinya lebih baik, bukan jaminan lalu lintas di masa depan.

Pertanyaan Umum

Berapa banyak RAM yang dibutuhkan VPS website?

Tidak ada angka yang berlaku untuk semua website. Situs ringan dengan cache dapat memakai sedikit memori, sedangkan CMS dinamis dengan database, panel, dan worker aktif bersamaan memerlukan lebih banyak. Hitung kebutuhan seluruh proses yang berjalan bersama, lalu sisakan cadangan kapasitas.

Apakah RAM 2 GB cukup untuk VPS website?

Bisa cukup untuk beban kerja kecil dengan stack ringan. Kapasitasnya menjadi terbatas ketika panel kontrol, database, beberapa proses PHP, tugas latar belakang, atau banyak website harus berjalan bersamaan. Ukur tekanan memori, jangan hanya mengandalkan angka RAM.

VPS RAM 4 GB cocok untuk apa?

VPS 4 GB adalah titik awal praktis untuk banyak beban kerja CMS bisnis karena memberikan lebih banyak ruang untuk Linux, database, aplikasi/proses PHP, dan caching. Kesesuaian persisnya bergantung pada konkurensi dinamis, permintaan database, tugas latar belakang, dan penggunaan sumber daya tambahan oleh panel. Untuk keputusan spesifik WordPress, gunakan VPS untuk WordPress.

Berapa banyak pengunjung yang dapat ditangani oleh VPS?

Jumlah pengunjung saja tidak cukup. Rasio cache hit, permintaan bersamaan, waktu eksekusi aplikasi, pemrosesan database, dan tugas latar belakang dapat membuat kebutuhan kapasitas dua situs dengan trafik serupa berbeda hingga beberapa orde besaran.

Haruskah saya menambahkan RAM atau CPU terlebih dahulu?

Tambah sumber daya yang terbukti menjadi batas berdasarkan pengukuran. Tekanan memori, aktivitas swap, atau OOM mengarah pada kebutuhan RAM atau optimasi memori. CPU yang terus penuh saat menjalankan beban nyata yang sudah dioptimalkan mengarah pada kebutuhan CPU. Hambatan database dan I/O perlu diagnosis terpisah.

Apakah CDN mengurangi persyaratan VPS?

Ini dapat mengurangi pengiriman file statis dan permintaan origin yang dapat di-cache. Permintaan aplikasi dinamis dan tugas database yang mencapai origin masih menggunakan sumber daya VPS.

Haruskah saya mengukur lalu lintas rata-rata atau puncak?

Tentukan spesifikasi untuk puncak realistis dengan cadangan kapasitas operasional. Trafik rata-rata dapat menyembunyikan periode singkat ketika permintaan bersamaan, tugas terjadwal, dan beban dinamis terjadi sekaligus.
